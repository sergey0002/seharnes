## Суть

Документ содержит полный аудит агентского харнеса проекта CopyTrust, сравнительный анализ с базовой конфигурацией Claude Code и пошаговый план перехода на процесс разработки Test-First. Новый процесс ставит подготовку исполняемых тестов на основе извлеченной бизнес-логики перед формированием плана и кодированием, а также вводит непрерывную проверку каждого изменяемого фрагмента кода. Внедрение изменений устраняет риск регрессий в смежных модулях монолита и сокращает цикл обратной связи при решении задач.

## 1. Сравнение текущего харнеса с базовой конфигурацией Claude Code

### 1.1 Архитектурный профиль базового Claude Code

Базовый (vanilla) Claude Code работает через минималистичный агентский цикл:
- Контекст формируется через единый файл инструкций (`CLAUDE.md`), системный промпт и динамическое чтение файлов через Bash/Grep.
- Навигация по коду опирается на стандартные консольные утилиты (`find`, `grep`, `ripgrep`, `cat`).
- Запуск тестов выполняется через передачу команд в терминал с последующим чтением текстового stdout/stderr.
- Память сессии ограничена текущим контекстным окном; долгосрочные связи между сущностями и прошлыми решениями отсутствуют.

### 1.2 Матрица возможностей

| Параметр | Базовый Claude Code | Текущий харнес CopyTrust | Целевой Test-First харнес |
|---|---|---|---|
| Поиск по коду и связям | Grep / Glob (линейный поиск по тексту) | Граф знаний (CBM, CodeGraph, CodePrism, Serena LSP) | Граф знаний + мгновенная фильтрация callers/callees для фрагмента |
| Управление бизнес-правилами | Память модели из текста задачи | Реестр `business-analyst` (в режиме shadow) | Активный реестр `business-analyst` + генератор контрактов |
| Планирование | Свободный текст в чате | Двухслойный гейт P0-P7 (JSONdoc, anchor uniqueness) | План с жесткой привязкой фрагментов к исполняемым тестам |
| Момент создания тестов | После написания кода (по запросу) | Фаза B скила `prepare-task-test` (после появления diff) | Фаза 0: до составления детального патча кода |
| Проверка правок | Ручной запуск команды разработчиком | Запуск `test-task` на всю задачу или стейдж | Автономный прогон микро-теста фрагмента (< 1 сек) |
| Защита от регрессий | Надежда на внимание модели | 9 уровней blast radius Tier 0-8 | Автоматический выбор тестов смежных флоу по графу связей |
| Накладные расходы среды | Минимальные (быстрый старт) | Высокие (19 MCP серверов, 6 зеркал сред, синхронизация) | Оптимизированные (фокус на ключевых MCP, очистка дублей) |

### 1.3 Сильные стороны и точки трения текущего харнеса

Сильные стороны текущего харнеса:
- Детерминированные шлюзы качества. Валидатор `jsondoc plan verify` механически пресекает галлюцинации моделей (плейсхолдеры, неуникальные якоря, устаревшие хеши файлов).
- Глубокий граф зависимостей. Связка CBM + CodePrism + Serena позволяет точно вычислять blast radius даже в нетипизированном legacy PHP коде.
- Контроль контракта с трекером. Жесткая связь артефактов `task.md` -> `task.json` -> `plan.md` -> `verdict.json` предотвращает самовольное изменение требований.

Точки трения (friction points), требующие устранения:
- Поздний цикл тестирования. Скил `prepare-task-test` опирается на `diff.files.md`. Пока код не написан и диффа нет, скил не может определить затронутые флоу, что блокирует TDD подход.
- Пассивность бизнес-аналитика. Скрипт `business_analyst.py` по умолчанию запускается в режиме `--shadow` и не передает проверенные постулаты напрямую в генератор тестовых сценариев.
- Отсутствие инструмента проверки единичного фрагмента. Раннер `task-test.sh` ориентирован на прогон группы `@group task-{N}` или всего файла Cest, что занимает от десятков секунд до минут и делает проверку каждой строчки слишком медленной.
- Платформенный барьер WSL/Windows. Скрипты на bash требуют среды WSL, в то время как часть инструментов запускается из Windows PowerShell. Это вызывает задержки на трансляцию путей и блокировки файлов.
- Избыточность неподдерживаемых MCP серверов. Наличие отключенных конфигураций (Sourcegraph, Xdebug, Deepwiki, Bitbucket-task) усложняет аудит и создает паразитный шум в схемах инструментов.

## 2. Архитектура целевого процесса: Test-First и проверка фрагментов

### 2.1 Принцип сквозного процесса

Разработка строится по схеме Red-Green-Refactor на уровне каждого логического блока:
1. До первой правки продуктового кода определяются правила поведения системы.
2. Создается исполняемый тест, фиксирующий ожидаемое поведение и подтверждающий текущую ошибку или отсутствие функциональности (Red).
3. Формируется план реализации, где каждая причина изменения (R) жестко связана с тестовым методом (T).
4. Разработчик или агент применяет патч ровно к одному фрагменту.
5. Запускается микро-тест только этого фрагмента.
6. Выполняется локальный статический анализ затронутого файла.
7. При успешном прохождении шаг фиксируется, и процесс переходит к следующему фрагменту.

```
Jira / Task -> business-analyst (verified rules) 
            -> prepare-task-test (pre-implementation Cest / Unit)
            -> prepare-plan (binding: Patch_K -> Test_K)
            -> Loop:
                 [Apply Patch_K] 
                 -> [Fast Test_K (<1s)] 
                 -> [CodePrism / PHPStan diff gate]
                 -> [Green: Next / Red: Instant Fix]
            -> test-task (Full Task Group + Neighbor Flows Regression)
            -> task-diff -> reports -> send-to-git
```

### 2.2 Семь этапов целевого цикла

#### Этап 1. Захват задачи и извлечение бизнес-логики
- `gototask` экспортирует данные задачи и создает ветку.
- `business-analyst` в обязательном активном режиме (флаг `--promote`) извлекает требования, связывает их с `registry.json` и строит матрицу влияния `test-matrix.json`.
- На выходе формируется список инвариантов системы: что должно работать и что запрещено ломать.

#### Этап 2. Проектирование тестов до реализации (Pre-Implementation Test Design)
- `prepare-task-test` запускается в режиме предварительной генерации `--pre-flight`.
- На основе `test-matrix.json` и карты флоу `qa/index.md` создается заготовка `Task{N}Cest.php` и юнит-тесты.
- Заполняется файл `ac-matrix.json`, связывающий критерии приемки с конкретными методами `Class::testMethod`.
- Выполняется первичный запуск: тесты на новую функциональность обязаны завершиться ошибкой (Red), подтверждая корректность формулировки теста.

#### Этап 3. План с привязкой к тестам (Test-Driven Plan)
- `prepare-plan` строит декомпозицию R1..Rn.
- Каждый блок декомпозиции `R_k` обязан содержать ссылку на исполняемый метод теста `Test_k` и команду его мгновенной проверки.
- Гейт P7.0 отклоняет любой план, где для изменения кода нет исполняемого теста.

#### Этап 4. Пошаговая реализация и мгновенная верификация фрагментов
- Внедряется строго один блок `Patch_k`.
- Выполняется команда изолированного прогона: `task-test.sh {N} --single-method {MethodName}`.
- Проверяется синтаксис и типы через `phpstan-task.sh` только по измененному файлу.
- Если микро-прогон упал, правка исправляется на месте без перехода к другим файлам.

#### Этап 5. Регрессионный шлюз смежных доменов (Neighbor Regression Gate)
- На основе графа CodePrism (`get_impact`) и истории `git-task-blame` вычисляется точный список смежных модулей.
- Запускаются тесты смежных флоу (`--skip-neighbors=0`).
- Запускается `gates.py` для валидации 13 системных шлюзов (G0-G13).

#### Этап 6. Фиксация артефактов и отчетность
- `task-diff` фиксирует изменения.
- `task-change-report` генерирует отчет с сопоставлением изменений и бизнес-постулатов.
- `send-to-git` согласовывает коммит.

#### Этап 7. Актуализация документации
- `task-doc` синхронизирует состояние архитектуры (`B3`) и обновляет индекс задач (`B4.5`).

## 3. Детальный аудит и доработка всех скилов (Skills)

### 3.1 Группа жизненного цикла задачи (Task Lifecycle)

#### 1. gototask
- Текущее состояние: Переключает ветку, экспортирует задачу через `server.php`, вызывает `comment-triage.md`. Запуск `business-analyst` идет в фоновом/теневом режиме.
- Проблема: Разработчик приступает к планированию без загруженных правил предметной области.
- Решение: Встроить шаг обязательного вызова `python3 .agents/skills/business-analyst/scripts/auto_run.py --promote --task {N}`. Завершать переход к задаче генерацией первичного контекста бизнес-логики `task.json`.

#### 2. task-intake
- Текущее состояние: Первичный разбор входящих требований, вопросов и комментариев.
- Проблема: Формирует неструктурированные текстовые списки, которые теряются при составлении тестов.
- Решение: Добавить генерацию артефакта `requirements.draft.json` с четким разделением: Preconditions, Action, Expected Results, Invariants.

#### 3. prepare-plan
- Текущее состояние: Пайплайн P0-P7. Генерирует декомпозицию R1..Rn и описательные сценарии S1..Sn.
- Проблема: Сценарии S часто остаются текстовым описанием ("проверить в браузере"), а не вызовом кода теста.
- Решение:
  - Ввести в модель плана обязательное поле `test_anchor`: каждый `R_k` обязан ссылаться на метод из `ac-matrix.json`.
  - В каждый блок патча добавить директиву `Verification Command`: точную команду запуска теста одного метода.
  - В валидатор `jsondoc.py plan verify` добавить проверку: если для блока патча метод теста не объявлен в тестовом классе задачи, возвращать код 2 (ошибка валидации).

#### 4. prepare-task-test
- Текущее состояние: Скил работает только после появления `diff.files.md`. Читает diff и подбирает Page/Step объекты.
- Проблема: Блокирует подход Test-First. Не может создать тест до начала реализации.
- Решение:
  - Разделить работу скила на два режима: `--mode pre-flight` (до кодирования) и `--mode audit` (после кодирования).
  - В режиме `--mode pre-flight` входными данными служат `task.md`, извлеченные правила `business-analyst` и затронутые страницы из `qa/index.md`.
  - Скил генерирует каркас `Task{N}Cest.php` с тестовыми методами, проверяющими новые требования на падение (Red State), и формирует `ac-matrix.json`.

#### 5. test-task
- Текущее состояние: Оркестратор тестирования. Имеет фазы preflight, unit, browser, all, finalize.
- Проблема: Нет режима сверхбыстрого запуска одного метода для проверки единичного патча. Прогон всей задачи занимает слишком много времени.
- Решение:
  - Добавить флаг `--method {MethodName}` и `--quick`: запуск Codeception с параметром `-o "reporters: report: null"` и запуском конкретного теста без сбора скриншотов соседних шагов.
  - Сократить время обратной связи микро-прогона до 1-2 секунд.

#### 6. browser-verify
- Текущее состояние: Запуск Codeception и Playwright, снятие скриншотов, формирование `verdict.json`.
- Проблема: Избыточный сбор логов и скриншотов на промежуточных итерациях.
- Решение: Ввести разделение на режимы `interactive` (промежуточный без скриншотов) и `checkpoint` (финальный со скриншотами и сохранением артефактов в `test-runs/`).

#### 7. task-code-review
- Текущее состояние: Проверка чистоты кода, применения паттернов и правила Ponytail.
- Проблема: Проводит ревью в отрыве от бизнес-правил, проверяет только стилистику и переусложнение.
- Решение: Добавить проверку соответствия кода инвариантам из `task.json business_logic`.

#### 8. task-diff
- Текущее состояние: Генерация `diff.md` и `diff.files.md`.
- Оценка: Работает стабильно, изменений логики не требуется. Обеспечить корректность путей в WSL.

#### 9. send-to-git
- Текущее состояние: Запрос подтверждения, формирование сообщения, коммит и пуш в origin GitVerse.
- Проблема: Может отправить код, если тесты не запускались вовсе.
- Решение: Добавить жесткий гейт: проверка наличия зеленого `verdict.json` за последние 30 минут перед выводом запроса на коммит.

#### 10. task-report и task-change-report
- Текущее состояние: Генерация комментария для Jira и HTML отчета.
- Решение: Добавить в HTML отчет блок "Business Invariants Checked": таблицу подтвержденных правил с ссылками на методы тестов.

#### 11. login-as-user
- Текущее состояние: Вход под конкретным пользователем через админский имперсонейт.
- Оценка: Полезный локальный инструмент. Сохранить без изменений.

#### 12. git-task-blame
- Текущее состояние: Анализ `git log -L` для выявления риска конфликтов и активных веток.
- Решение: Интегрировать вывод скрипта в фазу выбора тестов регрессии: если строка менялась в задаче M, автоматически подключать тесты задачи M.

#### 13. task-core
- Текущее состояние: Маршрутизатор задач.
- Решение: Обновить документацию маршрутов с учетом шага Pre-Implementation Test.

### 3.2 Группа бизнес-анализа, кода и документации

#### 1. business-analyst
- Текущее состояние: Извлекает цитаты и кандидаты правил из комментариев Jira, фильтрует дубликаты, строит `registry.json`. Работает в shadow режиме.
- Проблема: Изолирован от процесса кодирования, разработчики не видят извлеченные правила.
- Решение:
  - Перевести режим по умолчанию в активный (`BUSINESS_ANALYST_AUTO=1`, `BUSINESS_ANALYST_PROMOTE=1`).
  - При каждом открытии задачи генерировать `business-contract.md` в папке `.doc/tasks/{N}/` со списком обязательных ограничений.
  - Интегрировать скрипт `build_test_impact.py` напрямую в `prepare-task-test`.

#### 2. code и bug-cause
- Текущее состояние: Исследование первопричины багов по диффам, истории и коду.
- Решение: Завершать работу скила `bug-cause` генерацией минимального воспроизводящего юнит- или интеграционного теста, демонстрирующего баг.

#### 3. codegraph и codeprism
- Текущее состояние: Локальные графы кода. `codegraph` дает карту вызовов, `codeprism` выполняет AST анализ, поиск потоков данных и проверку секретов.
- Решение:
  - Использовать `codeprism.get_impact` для динамического формирования списка тестов регрессии: метод находит все зависимые классы, а тестовый раннер выбирает для них Cest методы.
  - Встроить `codeprism.scan_diff` в микро-гейт проверки фрагмента кода.

#### 4. project-doc, doc-verify, task-doc
- Текущее состояние: Управление документацией, сверка фактов и рендеринг представлений.
- Решение: Сохранить текущие механизмы `doc_rules.md`. Добавить в `task-doc` автогенерацию секции обратной связи с тестовыми сценариями.

### 3.3 Группа мета-харнеса

#### 1. harness-router, harness-core, improvement
- Текущее состояние: Управление средой, регистрация компонентов в `component_registry.json`, синхронизация зеркал сред.
- Решение: Обновить реестр компонентов, зафиксировав новые связи между `business-analyst`, `prepare-task-test` и `prepare-plan`.

#### 2. mirror и index
- Текущее состояние: Индексация файлов харнеса в `graph.json`, статический просмотрщик графа.
- Проблема: Запуск `harness_mirror.py scan` по сети WSL занимает много времени из-за синхронного обхода файлов.
- Решение: Оптимизировать обход файловой системы, исключив каталоги кэша и виртуальных окружений. Заменить unix-специфичные вызовы на кроссплатформенные аналоги.

#### 3. ponytail
- Текущее состояние: Принцип минимально достаточных изменений (YAGNI).
- Решение: Распространить принцип Ponytail на тесты: тест задачи должен содержать минимальное количество проверок, строго подтверждающих бизнес-инвариант, без избыточного тестирования системных библиотек.

#### 4. migration-review, skill-authoring, add-skill, remove-skill
- Текущее состояние: Создание, очистка и сопровождение скилов.
- Оценка: Архитектура зрелая, изменений не требуется.

## 4. Детальный аудит и доработка правил (Rules)

### 4.1 Системные и поведенческие правила

#### 1. context-router (`context-router.mdc`)
- Изменение: В Сцене 5 ("Задачи") изменить стартовую цепочку. Вместо прямого перехода `gototask -> plan -> diff -> test` закрепить маршрут:
  `gototask -> business-analyst -> prepare-task-test (pre-flight) -> prepare-plan -> fragment-loop -> regression-test`.

#### 2. prepare-plan (`prepare-plan.mdc`)

## Известные проблемы и ограничения

### П-1: Скорость старта браузерного стенда
- Симптом: Первый запуск Codeception может занимать до 15-20 секунд из-за инициализации веб-сервера и сессии браузера.
- Причина: Использование полных браузерных сценариев AcceptanceTester для простых условий логики.
- Решение: Для изолированной проверки фрагментов логики использовать быстрые Unit/Integration тесты PHPUnit, а браузерные тесты запускать на уровне интеграции задачи.

### П-2: Рассинхронизация путей между WSL и Windows
- Симптом: Ошибки доступа к файлам скриптов или неверная интерпретация абсолютных путей при запуске из Windows PowerShell.
- Причина: Различие форматов путей `\\wsl.localhost\Ubuntu\...` и `/home/newuser/...`.
- Решение: Использовать относительные пути от корня репозитория и единую точку входа через `bash` внутри WSL.
