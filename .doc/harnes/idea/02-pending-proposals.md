## P4. Машинная связка ready-artifact для JSON-планов

Факт: в plan_verify.py уже есть гейты ledger_missing, test_stub_patch (против
`assertTrue(true)`), `_simulate_balance` (против `</div>>`), SOURCE_STALE,
before_not_unique. Но связка status ready к evidence artifact существует и свежее
plan_sha256 проверяется внутри verify-прогона, а не на уровне план лежит ready
без свежего прогона.

Предложение: в validate_plan.py validate_json_view вместо строки-подсказки
run jsondoc plan verify manually (когда root и task не распознаны) возвращать ошибку
unverifiable plan location, а при успешной делегации требовать в ответе plan_sha256,
совпадающий с моделью из `_jsondoc/artifacts/`, и свежесть
`_jsondoc/plan-verifications/{RUN}/` не старше модели. Сейчас делегация печатает
stdout и доверяет exit-коду, этого достаточно для green-path, но тихий пропуск
при нестандартном пути остается.

Проверка: фикстуры ready без ledger, ready со stale verification, plan вне tasks,
три негативных кейса в test_validate_plan.py. Не делать: дублирование семантики
plan_verify.py в legacy-валидаторе, только проверка наличия и свежести артефакта.

Статус: отложено (покрыто существующими гейтами, нужна запись в jsondoc-движок,
отдельный контур, до живых кейсов).

## P5. T3-сверка в механический дифф формулировок

Факт: в SKILL добавлено требование цитировать brief против decision. Машиной
не проверяется, валидатор не читает T-таблицу.

Предложение: в validate_plan.py мягкий гейт: если в `## Sources of truth` есть
строка T3 и в плане есть `status: ready` или passed, требовать секцию
`User decisions vs brief` (или подстроку T3 в Acceptance criteria строках out-of-scope
excluded). Отсутствие warning-ошибка unverified user decision. Полный семантический
дифф цитат машине не поручать, только наличие сверки.

Проверка: позитивная фикстура с секцией проходит, без секции падает. Уровень: error
для ready, silent для draft (не мешать черновикам).

Статус: отложено (ложные positives на планах без T3, нужна выборка реальных планов с T3).

## P7. Разделить validate_plan на legacy и json требованием

Факт: `JSON_VIEW_MARKER = "generated from plan model by jsondoc plan"` эвристика
по подстроке. План, сгенерированный вручную с такой строкой, уйдет не в тот гейт;
JSON-view без маркера (старый рендер) пойдет в legacy и даст ложные ошибки.

Предложение: маркер заменить структурным признаком, наличие `_jsondoc/artifacts/*.json`
модели для этого task и scope рядом с планом. validate_json_view уже резолвит task
через tasks предков, дополнить проверкой существования модели до выбора ветки:
модель есть json-гейт, нет legacy-гейт с явной пометкой. Проверка: оба направления
на фикстурах (маркер без модели, модель без маркера).

Статус: отложено (маркер работает на текущих планах, смена без фикстур рискованна).

## P9. Метрики дрейфа зеркал в отчет синка

Факт: синк молча копирует, parity в конце бинарный. Нет ответа что именно разъехалось
и когда.

Предложение: перед копированием снимать sha256 манифесты канона и каждого вью
(та же функция manifest из verify_parity.py), после diff-список changed, added,
removed в parity-report.json рядом с errors. Поле changed после успешного синка
обязано быть пустым для skills и rules (для kilo.jsonc и mcp.json expected, форматы
разные). Проверка: повторный синк без изменений канона дает changed пусто везде.
Польза: F1-диагностика что дрейфовало без ручного diff.

Статус: частично (parity errors уже содержат пути missing, mismatch, extra,
отдельный манифест-дифф не добавлялся, P2 freshness закрывает главную боль).

## P13. Frozen-артефакты для внешних зависимостей

Факт: page-content, xmlriver, serp-study работают через внешние API
(`.doc/skil_data/page-content/`, `.doc/skil_data/xmlriver/`, `.doc/skil_data/serpanalise-report/`). При падении
или смене API скил сломается без возможности откатить к рабочей версии артефакта.

Предложение: для скилов с внешними зависимостями ввести необязательный
frozen-artifacts в каталоге скила, снапшоты API-ответов по каноническим кейсам
(один URL, один SERP-запрос, одна задача) с timestamp и API version. При падении
внешнего API скил может переключиться в `--use-frozen` режим для демонстрации
или регресс-теста. Детали: frozen-артефакты НЕ заменяют живые вызовы (только fallback
при explicit flag), НЕ коммитятся в git (`.gitignore`), обновляются вручную
разработчиком через `skill-name freeze-sample --url ...`. Формат: JSON с полем
captured_at, api_version, request, response. Проверка: отключить сеть,
`page-content --use-frozen` отдает снапшот, без флага ошибка сети как обычно.
Польза: регресс-тест не зависит от доступности API, при смене формата видно diff.
Не делать: автоматическое переключение на frozen при ошибке (скроет реальную
проблему), только explicit flag.

Статус: не внедрено (инфра без срочности, внешних падений API в сессии не было).

## P14. Контрольная сумма базы кода для P0.1 preflight

Факт: P0.1 требует убедиться в фактическом доступе к коду, но проверка формальная
(наличие путей). Если база проиндексирована на старом коде, а план строится на новом
(после merge без reindex), CBM-tier даст устаревшую информацию без предупреждения.

Предложение: в preflight добавить запрос `codebase-memory-mcp index_status`, сравнить
last_index_time с mtime исходников из ledger. Если хотя бы один файл свежее индекса
более чем на 5 минут, warning stale_index в ledger-отчет. Не блокировать план
(может быть холодный старт без индекса), но явно отметить. Детали: проверка только
для файлов с role patch, entry, caller в ledger (внешние схемы не требуют
переиндексации). Для проектов без CBM проверка возвращает `n/a: no index server`.
Проверка: правка файла, прогон plan preflight без reindex дает warning, после reindex
чисто. Польза: явное указание на риск устаревших данных вместо молчаливого графа.

Статус: не внедрено (CBM недоступен в среде проверки, контроль остался ручным по P0.1).
