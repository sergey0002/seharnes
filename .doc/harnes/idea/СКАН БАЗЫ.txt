Если вы заставите агента просто читать файлы подряд в алфавитном порядке, он потеряет нить бизнес-логики (прочитает UserService, забыв, как устроен AuthController), а контекстное окно быстро переполнится мусором. Поскольку у вас уже стоят графовый и мемори-MCP, вы можете построить идеальный агентский конвейер с очередью задач.

1. В каком формате хранить бизнес-процессы (вместо гигантского AGENTS.md)

Чтобы агент не грузил всё сразу, а брал только нужный раздел через MCP, используйте модульную архитектуру знаний:
1. Машиночитаемые диаграммы (Mermaid StateDiagrams и SequenceDiagrams): ИИ-модели идеально понимают синтаксис Mermaid. Один блок stateDiagram-v2 на 15 строк заменяет 3 страницы текста о том, как заказ переходит из статуса PENDING в PAID и где возможен откат.
2. Доменные контракты (YAML Frontmatter + Markdown): Разбейте документацию на папки по доменам (docs/domains/billing.md, docs/domains/auth.md). В начале каждого файла — четкая шапка в YAML (точки входа, связанные таблицы, главные инварианты).

2. Архитектура «Очереди» (Как просканить все 2000 файлов и не упасть)

Ни один агент не осилит 2000 файлов за один промпт (сработает лимит шагов или размоется внимание). Вам нужен файл-диспетчер очереди (audit_queue.json) или таблица состояний в вашем Memory MCP, плюс цикл запуска.

Шаг 1. Генерация очереди по точкам входа (Entrypoints) через codegraph MCP

Не сканируйте утилиты и модели отдельно. Бизнес-логика всегда начинается с точек входа: API-роуты, консольные команды (CLI), крон-джобы (Workers/Cron) и обработчики очередей (Kafka/RabbitMQ consumers).
Дайте агенту задачу №1 (Инициализация):
«Используя codegraph MCP, найди все точки входа в приложение (контроллеры, роуты, воркеры). Сгруппируй их по бизнес-доменам. Создай файл audit_queue.json, где каждый элемент — это один бизнес-сценарий (entrypoint), его статус "status": "pending" и список прямых зависимостей 1-2 уровня по графу вызовов».
Вместо 2000 разрозненных файлов вы получите очередь из ~80–150 бизнес-потоков (Flows), которые покрывают все важные файлы проекта (остальные 1000+ файлов — это DTO, конфиги, интерфейсы и хелперы, которые подтянутся сами по графу, только если они реально участвуют в логике).

Шаг 2. Воркер-аудитор (Цикл обработки по батчам)

Теперь вы запускаете Codex в режиме итераций (по 1–3 бизнес-потока за сессию, чтобы контекст оставался кристально чистым и модель думала на максимум).
Алгоритм одного шага очереди для агента:
1. Взять задачу: Прочитать audit_queue.json, взять первый поток со статусом pending.
2. Собрать контекст по графу (codegraph MCP): Не читать файлы целиком! Запросить у codegraph цепочку вызовов (Call Graph) от выбранного контроллера вглубь до слоя базы данных. Прочитать код только тех методов, которые участвуют в цепочке.
3. Задокументировать процесс (codebase-memory MCP):
	• Составить схему процесса (Mermaid Sequence/State) и список бизнес-инвариантов (что обязано быть правдой).
	• Записать это в codebase-memory MCP (и/или сохранить в docs/flows/<flow_name>.md).
4. Найти логические баги: Сопоставить код цепочки с только что выведенными инвариантами. Проверить:
	• Есть ли изменение нескольких таблиц без транзакции?
	• Возможен ли Race Condition при параллельном вызове этого роута?
	• Пропущена ли проверка статуса (например, отмена уже доставленного заказа)?
	• Что будет, если внешний сервис посередине функции отвалится по таймауту?
5. Сохранить отчет и сдвинуть очередь: Записать найденные баги в bugs_report.md (или в память MCP), пометить поток в audit_queue.json как "status": "completed" и завершить шаг.

3. Как автоматизировать прогон всей очереди (без ручного кликанья)

Если у вас Codex CLI или агент в терминале, вы не обязаны нажимать Enter 100 раз. Заверните вызов агента в простейший bash/python цикл на вашем компьютере:
bash
# Псевдокод цикла запуска воркера до опустошения очереди
while grep -q '"status": "pending"' audit_queue.json; do
  echo "Запуск новой итерации аудита с чистым контекстом..."
  codex exec "Прочитай audit_queue.json. Возьми ровно 2 задачи со статусом pending. 
  Через codegraph MCP раскрути их граф вызовов. 
  Запиши описание бизнес-процесса в codebase-memory MCP. 
  Найди логические баги в этой цепочке и допиши их в bugs_report.md. 
  Обнови статус этих 2 задач в audit_queue.json на completed и заверши работу."
  sleep 5
done
Используйте код с осторожностью.

Почему эта схема — лучшая для 2000 файлов:

• Никакого переполнения контекста: Каждые 2 бизнес-процесса сессия сбрасывается. Умная модель всегда работает со свежей головой и держит в памяти только 5–10 связанных файлов конкретного процесса.
• Стопроцентная связность: За счет codegraph MCP агент идет ровно по нитке выполнения кода (Controller → Service → Repository → Event), как это происходит в реальной жизни.
• Готовая навигация: По окончании цикла у вас в codebase-memory MCP лежит полная, разбитая по полочкам база знаний о бизнес-процессах, а в bugs_report.md — список логических дыр с точными путями воспроизведения.

Чтобы превратить codebase-memory MCP в идеальный навигатор по бизнес-логике, нужно задать для агента строгую схему записи данных (Schema): какие типы узлов (Entities) создавать, какие факты (Observations) туда класть и какими связями (Relations) их сшивать.

1. Схема узлов (Entities) в codebase-memory MCP

Заставьте агента при сканировании создавать ровно 4 типа сущностей:
1. BusinessFlow (Бизнес-процесс) — главный узел сценария (например, Flow:OrderCheckout, Flow:SubscriptionRenewal).
2. DomainEntity (Доменная сущность / Таблица) — вокруг чего крутится логика и какие у нее статусы (например, Entity:Order, Entity:Wallet).
3. CodeComponent (Ключевой узел кода) — точка входа или главное ядро логики из codegraph (например, Component:PaymentService.process).
4. LogicBug (Найденный баг / Риск) — конкретная логическая дыра, найденная при аудите (например, Bug:DoubleRefundRaceCondition).

2. Что писать внутрь узла (Шаблон Observations)

В стандартных Memory MCP у каждой сущности есть массив observations (короткие атомарные факты). Чтобы агент легко искал их векторным или теговым поиском, каждый факт должен начинаться с префикса-ключа:
Пример идеального узла Flow:OrderCheckout в памяти MCP:
json
{
  "name": "Flow:OrderCheckout",
  "entityType": "BusinessFlow",
  "observations": [
    "[TAGS] domain:billing, flow:checkout, critical:high",
    "[ENTRYPOINT] POST /api/v1/orders/checkout -> OrderController.create()",
    "[CALL_CHAIN] OrderController.create -> CartService.validate -> PaymentService.charge -> OrderRepo.save",
    "[STATE_TRANSITION] Order: DRAFT -> PENDING_PAYMENT -> PAID (or FAILED)",
    "[INVARIANT_1] Сумма списания обязана строго равняться сумме позиций минус активный промокод",
    "[INVARIANT_2] Списание баланса и смена статуса заказа должны идти в одной БД-транзакции",
    "[MERMAID_FLOW] graph TD; A[Checkout] -->|Validate| B(Hold Funds); B -->|Success| C[Create Order]; B -->|Fail| D[Rollback];"
  ]
}
Используйте код с осторожностью.
Пример узла найденного бага Bug:PromoCodeReuse:
json
{
  "name": "Bug:PromoCodeReuse",
  "entityType": "LogicBug",
  "observations": [
    "[TAGS] severity:high, type:race-condition, domain:billing",
    "[LOCATION] src/services/PromoService.ts:142 (метод applyPromo)",
    "[BROKEN_INVARIANT] Промокод с лимитом 1 раз может быть применен к 2 заказам параллельно",
    "[PROOF_OF_CONCEPT] Между проверкой promo.isUsed (строка 120) и записью в БД (строка 155) нет SELECT FOR UPDATE или атомарного лок-ключа в Redis",
    "[FIX_IDEA] Обернуть проверку и инкремент счетчика использования в единый атомарный запрос UPDATE ... WHERE used_count < max_uses"
  ]
}
Используйте код с осторожностью.

3. Схема связей (Relations) между узлами

Именно связи позволяют агенту «гулять» по бизнес-логике, не читая все 2000 файлов. Агент должен связывать узлы активными глаголами:
• Flow:OrderCheckout STARTS_AT \(\rightarrow \) Component:OrderController.create
• Flow:OrderCheckout MODIFIES_STATE_OF \(\rightarrow \) Entity:Order
• Flow:OrderCheckout DEPENDS_ON \(\rightarrow \) Flow:WalletCharge
• Bug:PromoCodeReuse BREAKS_LOGIC_IN \(\rightarrow \) Flow:OrderCheckout
• Bug:PromoCodeReuse LOCATED_IN \(\rightarrow \) Component:PromoService.applyPromo

4. Готовый системный промпт для вашего Агента-Аудитора

Скопируйте эту инструкцию и дайте ее вашему агенту в Codex при запуске цикла по очереди:
Инструкция по работе с codebase-memory MCP и codegraph MCP:
Ты — агент-аудитор бизнес-логики. Твоя задача — перевести кодовую базу в граф бизнес-процессов и найти логические баги.
Для каждой точки входа из очереди выполняй строго по шагам:
1. Сбор графа (codegraph): Получи дерево вызовов (callees) от точки входа на глубину до слоя БД/внешних API. Прочитай код только тех функций, где есть ветвления (if/else/switch), циклы, транзакции и мутации данных.
2. Проверка памяти (codebase-memory): Сделай поиск в памяти по названию сущностей, которые трогает этот код. Если узел DomainEntity уже есть в памяти — прочитай его инварианты и статусы.
3. Запись процесса в MCP: Создай сущность типа BusinessFlow. В её observations запиши строго по шаблону: [TAGS], [ENTRYPOINT], [CALL_CHAIN], [STATE_TRANSITION], [INVARIANT] (правила бизнеса, которые код пытается соблюсти).
4. Поиск логических багов: Проанализируй код цепочки на:
	• Нарушение записанных [INVARIANT].
	• Отсутствие транзакций при записи в 2+ таблицы.
	• Состояния гонки (Time-of-check to time-of-use / TOCTOU).
	• Невалидные переходы между статусами из [STATE_TRANSITION].
	• «Зависшие» состояния при падении внешнего API в середине функции.
5. Фиксация багов: Если найден баг, создай узел типа LogicBug в codebase-memory, опиши [LOCATION], [BROKEN_INVARIANT] и [PROOF_OF_CONCEPT], и привяжи его связью BREAKS_LOGIC_IN к текущему BusinessFlow.

🛠️ Как работает Codex Security под капотом

Вместо построения банального отчета по ключевым словам, плагин использует пятиэтапный конвейер (pipeline) на базе рассуждающих моделей (семейства GPT-5/Soul с высоким уровнем Test-Time Compute):
1. Создание модели угроз (Threat Modeling): Агент сканирует архитектуру проекта, определяет точки входа данных, границы доверия (trust boundaries), логику авторизации и то, как модули общаются между собой.
2. Поиск уязвимостей (Discovery): На основе модели угроз ИИ целенаправленно ищет сложные логические ошибки, проблемы с правами доступа (Broken Access Control) и уязвимости в API.
3. Валидация в песочнице (Sandbox Validation): Главное отличие от обычных линтеров — Codex пытается воспроизвести атаку в изолированной среде. Если уязвимость подтверждается (exploit proven), она получает высокий приоритет, что сводит ложные срабатывания (false positives) почти к нулю.
4. Анализ путей атаки (Attack Path Analysis): Система трассирует полный путь, который может пройти злоумышленник от внешнего запроса до уязвимого куска кода.
5. Генерация патчей (Remediation): Плагин не просто говорит «тут ошибка», а автоматически создает код исправления (Pull Request) для вашей команды.

⚠️ Проблема «Огромной кодовой базы»: Ограничения и Подводные камни

Если вы запустите полный аудит (Full Repository Scan) на гигантском монолите, вы неизбежно столкнетесь со следующими барьерами:
• Огромный расход токенов и лимитов: Глубокий аудит требует миллионов токенов контекста. Пользователи отмечают, что один запуск на крупном проекте может «съесть» до 35-50% недельного лимита ИИ-агента всего за пару часов префлайт-подготовки.
• Время выполнения: Из-за стадии валидации и симуляции атак аудит большой базы данных идет медленно (может занимать часы).
• Лимиты подписок: Для работы требуется подписка ChatGPT Enterprise, Business, Edu или использование официального CLI/SDK с оплатой по API (на обычных тарифах лимиты закончатся мгновенно).

Semgrep ? че такое
10:53 PM
Semgrep — это один из самых популярных в мире современных инструментов для быстрого сканирования кода на уязвимости и ошибки (SAST). Название расшифровывается как Semantic Grep (семантический grep).
Если обычная консольная команда grep ищет совпадения просто по тексту или регулярным выражениям, то Semgrep понимает структуру вашего кода и его логику, как настоящий компилятор.

🔥 В чем его главная фишка?

Представьте, что вы хотите найти в коде небезопасное использование функции exec().
Если вы будете искать словом exec, обычный поиск найдет вам и комментарии // TODO: exec this later, и безопасные названия переменных let exec = true.
Semgrep работает умнее. Вы пишете правило на простом псевдокоде:
yaml
pattern: exec(...)
Используйте код с осторожностью.
И Semgrep поймет, что нужно искать именно вызов функции с любыми аргументами, проигнорировав комментарии и строки. При этом он поймет это одинаково хорошо и в JavaScript, и в Python, и в Go, и еще в 30+ языках.

🚀 Почему он стал стандартом в индустрии (вместо старых сканеров)?

1. Невероятная скорость: В отличие от тяжеловесных классических сканеров (вроде SonarQube или Checkmarx), которые строят огромные абстрактные деревья и могут сканировать проект часами, Semgrep проверяет миллионы строк кода за секунды или минуты.
2. Простота написания правил: Любой программист может написать кастомное правило безопасности для своего проекта буквально за 5 минут. Не нужно учить сложные языки запросов (как CodeQL).
3. Запуск где угодно: Его можно запустить одной командой на своем компьютере через терминал (semgrep scan) или бесплатно встроить в GitHub Actions / GitLab CI. Код при этом никуда не отправляется — все работает локально.
4. Огромная база готовых правил: Из коробки доступен бесплатный репозиторий правил (Semgrep Registry), созданный комьюнити и экспертами по безопасности, который закрывает 90% стандартных уязвимостей (OWASP Top 10).

🤖 Как Semgrep работает в связке с ИИ?

Возвращаясь к теме ИИ-агентов (вроде Codex или Claude): Semgrep часто используют как «первую линию обороны» в ИИ-конвейерах.
Вместо того чтобы сканировать огромную базу кода дорогой нейросетью, разработчики делают так:
1. Semgrep за пару секунд пролетает по миллиону строк кода и находит 100 потенциально подозрительных мест.
2. ИИ (LLM) подключается только к этим 100 найденным точкам. Нейросеть внимательно изучает контекст вокруг них, отсеивает ложные срабатывания (False Positives) и сама пишет Pull Request с исправлением.
Это позволяет объединить феноменальную скорость и дешевизну Semgrep с глубоким «разумом» искусственного интеллекта.

Да, такие инструменты существуют, но они делятся на две разные категории: AI-ревьюеры для поиска багов логики и генераторы графов знаний (Codebase Knowledge Graphs), создающие документацию для агентов.
Обычные линтеры и сканеры безопасности (SAST) ищут только известные паттерны уязвимостей, но не понимают, почему скидка применилась дважды или почему состояние корзины рассинхронизировалось. Для этого сейчас применяют специализированные связки.

1. Сканеры багов бизнес-логики (AI Code Reviewers)

Эти инструменты встраиваются в CI/CD или репозиторий и анализируют логические связи, расхождения в бизнес-правилах, гонки данных (race conditions) и утечки состояний.
• CodeRabbit: Популярный агент автоматического код-ревью. Он читает контекст всего репозитория и PR, понимает доменную область и находит не просто опечатки, а именно сбои бизнес-логики (например, пропущенные проверки статусов заказов, неконсистентные транзакции).
• Qodo (ранее CodiumAI): Специализируется на проверке логики через поведение кода. Анализирует кодовую базу, находит пограничные случаи (edge cases) и автоматически генерирует сложные сценарии тестирования, проверяющие корректность именно бизнес-требований.
• SonarQube / DeepCode AI: Традиционные платформы, которые добавили ИИ-анализ потоков данных (data flow analysis) для отслеживания логических багов между разными модулями.

2. Индексаторы бизнес-логики и генераторы документации для агентов

Чтобы ИИ-агенты (Codex, Claude Code, Cursor) понимали сложную логику монолита и не тратили миллионы токенов на перечитывание файлов, используют специализированные инструменты индексации:
• Swimm: Платформа, создающая «живую» документацию бизнес-логики. Она анализирует пути исполнения кода, объясняет, как устроены флоу данных, и автоматически обновляет документацию при изменении кода.
• Codebase Knowledge Graphs (например, codegraph / Tree-sitter + AST): Парсят репозиторий не как текст, а как граф вызовов (Call Graph) и связей. Агенту не нужно перебирать проект поиском — он делает один вызов к графу и сразу видит цепочку: «Какой контроллер вызывает этот сервис, какие таблицы он трогает и какие права проверяет».
• Augment Code: Инструмент корпоративного уровня (Context Engine), который умеет индексировать репозитории на сотни тысяч файлов, строит карту взаимосвязей модулей и держит актуальный контекст архитектуры.

3. Инструменты генерации спецификаций для агентов (AGENTS.md / CLAUDE.md)

Сейчас стандартом управления агентами в больших репозиториях стали файлы контекста в корне проекта (концепция Architecture as Context):
• Файлы инструкций (AGENTS.md / CLAUDE.md): Инструменты вроде repo-to-text или утилиты упаковки контекста (repomix) сканируют скелет архитектуры и генерируют сжатую карту системы.
• В этот файл выносятся:
	• Основные сущности и границы доменов (Domain Boundaries).
	• Инварианты бизнес-логики (например: «Пользователь не может оформить заказ без списания баланса»).
	• Правила вызова сервисов и типичные ошибки архитектуры.

Резюме: как это работает на практике

Если перед вами стоит задача отдать большой проект на аудит и разработку агентам:
1. Индексатор строит Knowledge Graph / AST-дерево проекта.
2. Генератор документации оформляет это в AGENTS.md (структура, правила, флоу данных).
3. Агентный сканер (вроде CodeRabbit или Qodo) использует эту карту, чтобы сопоставлять код с бизнес-логикой и указывать на несоответствия.

Да, в сфере поиска логических багов и индексации кода для ИИ-агентов есть мощные Open-Source (бесплатные) альтернативы, которые можно развернуть локально на своем сервере или ПК.
Их использование полностью решает проблему приватности данных и экономит бюджет на токены, так как тяжелую работу по структурированию кода они берут на себя.
Вот лучшие open-source инструменты, разделенные по задачам:

1. Сборка контекста и создание карт кода для агентов (Repo to Context)

Эти утилиты «упаковывают» ваш огромный репозиторий в структурированный вид, строят дерево зависимостей и генерируют идеальный файл контекста, который затем скармливается любому ИИ-агенту.
• Repomix (ранее Packmule): Один из самых популярных инструментов в этом классе. Он берет весь ваш репозиторий и собирает его в один структурированный текстовый или Markdown-файл. При этом он автоматически генерирует схему архитектуры, считает токены и удаляет «мусор» (тесты, логи, сборки). Полученный файл идеально подходит для того, чтобы агент сразу понял всю логику проекта.
• Aider: Это open-source ИИ-ассистент для терминала, но у него внутри потрясающий собственный движок индексации репозиториев (Repository Map). Он использует Tree-sitter для анализа AST-дерева кода и строит компактную карту проекта: выписывает все классы, методы и их связи, не перегружая контекст агента лишними строками кода.
• Grepflow / Tree-sitter утилиты: Набор open-source парсеров, которые преобразуют код в графы вызовов (Call Graphs) локально, помогая понять, как функции бизнес-логики связаны между собой.

2. Локальный поиск багов и логических ошибок (AI-ревьюеры)

• Mentat: Мощный open-source AI-кодинг-агент с открытым исходным кодом. В отличие от коммерческого CodeRabbit, Mentat можно запустить полностью локально (например, связав с локальной моделью через Ollama или Llama.cpp). Он индексирует файлы, понимает логику изменений и ищет несоответствия в бизнес-логике прямо в процессе написания кода.
• Sweep (Open-Source версия): Известный ИИ-агент для работы с бэклогом. Он умеет читать тикеты (описания багов бизнес-логики), сканировать репозиторий, находить место ошибки в кодовой базе и самостоятельно предлагать исправление. Код проекта открыт, его можно кастомизировать под свои правила.

3. Традиционный поиск логических багов (Deep Анализ без ИИ)

Если нужно найти сложные баги в логике (например, утечки памяти, состояния гонки, взаимные блокировки) на миллионах строк кода без единого токена:
• Infer (от Meta/Facebook): Легендарный open-source инструмент статического анализа. Meta использует его для проверки кода Facebook, Instagram и WhatsApp. Infer не просто ищет уязвимости безопасности, он специализируется на поиске сложнейших логических багов: падения из-за Null Pointer, утечки ресурсов и нарушения логики многопоточности.
• Semgrep OSS: Базовая (опенсорсная) версия Semgrep, о которой мы говорили ранее. Написав логические правила (например, «если статус заказа изменился на Отменен, но функция ВернутьДеньги() не вызвалась»), вы можете бесплатно ловить сбои в бизнес-логике на огромной скорости.

Оптимальный бесплатный стек (DIY)

Чтобы выстроить этот процесс бесплатно, инженеры обычно собирают следующий конвейер:
1. Infer / Semgrep OSS — крутятся в CI/CD, мгновенно ловят критические баги и утечки в логике кода при каждом коммите.
2. Repomix / Aider — раз в неделю сканируют проект и обновляют локальную карту архитектуры (файл ARCHITECTURE.md или AGENTS.md).
3. Mentat / Ollama — локальный ИИ-агент читает эту карту и точечно помогает разработчикам фиксить логику, не отправляя код в облако.

1. Qodo (бывший CodiumAI) — 🟢 Есть отличный бесплатный тариф

Платформа для ИИ-анализа логики, генерации тестов и код-ревью в PR.
• Бесплатная версия (Developer): Есть. Дает возможность бесплатно делать до 75 пулл-реквестов в месяц и начисляет базовые лимиты на ИИ-токены (250 кредитов в месяц). Для личного использования или небольших пет-проектов этого более чем достаточно.
• Платная версия (Teams / Enterprise): Стоит от $30 до $45 за пользователя в месяц. Снимает лимиты на количество ревью, подключает продвинутых ИИ-агентов (мультиагентную архитектуру), позволяет подключать свои ключи LLM (BYOK) и использовать кастомные правила.

2. SonarQube — 🟨 Бесплатен для локального запуска (Open-Source Core)

Классический гигант статического анализа кода. У него уникальная модель:
• Бесплатная версия (Community Edition): Полностью бесплатна. Вы можете скачать SonarQube Server, развернуть его на своем железе (в Docker-контейнере) и сканировать сколько угодно миллионов строк кода. Если вы заставите агента просто читать файлы подряд в алфавитном порядке, он потеряет нить бизнес-логики (прочитает UserService, забыв, как устроен AuthController), а контекстное окно быстро переполнится мусором. Поскольку у вас уже стоят графовый и мемори-MCP, вы можете построить идеальный агентский конвейер с очередью задач.

1. В каком формате хранить бизнес-процессы (вместо гигантского AGENTS.md)

Чтобы агент не грузил всё сразу, а брал только нужный раздел через MCP, используйте модульную архитектуру знаний:
1. Машиночитаемые диаграммы (Mermaid StateDiagrams и SequenceDiagrams): ИИ-модели идеально понимают синтаксис Mermaid. Один блок stateDiagram-v2 на 15 строк заменяет 3 страницы текста о том, как заказ переходит из статуса PENDING в PAID и где возможен откат.
2. Доменные контракты (YAML Frontmatter + Markdown): Разбейте документацию на папки по доменам (docs/domains/billing.md, docs/domains/auth.md). В начале каждого файла — четкая шапка в YAML (точки входа, связанные таблицы, главные инварианты).
3. Узлы в codebase-memory MCP: Сохраняйте каждый бизнес-процесс как отдельную сущность (Entity) в памяти MCP с тегами (domain:billing, flow:checkout, bug:high-risk). Агент сможет делать векторный или теговый запрос к MCP и подтягивать только нужный бизнес-процесс.

2. Архитектура «Очереди» (Как просканить все 2000 файлов и не упасть)

Ни один агент не осилит 2000 файлов за один промпт (сработает лимит шагов или размоется внимание). Вам нужен файл-диспетчер очереди (audit_queue.json) или таблица состояний в вашем Memory MCP, плюс цикл запуска.

Шаг 1. Генерация очереди по точкам входа (Entrypoints) через codegraph MCP

Не сканируйте утилиты и модели отдельно. Бизнес-логика всегда начинается с точек входа: API-роуты, консольные команды (CLI), крон-джобы (Workers/Cron) и обработчики очередей (Kafka/RabbitMQ consumers).
Дайте агенту задачу №1 (Инициализация):
«Используя codegraph MCP, найди все точки входа в приложение (контроллеры, роуты, воркеры). Сгруппируй их по бизнес-доменам. Создай файл audit_queue.json, где каждый элемент — это один бизнес-сценарий (entrypoint), его статус "status": "pending" и список прямых зависимостей 1-2 уровня по графу вызовов».
Вместо 2000 разрозненных файлов вы получите очередь из ~80–150 бизнес-потоков (Flows), которые покрывают все важные файлы проекта (остальные 1000+ файлов — это DTO, конфиги, интерфейсы и хелперы, которые подтянутся сами по графу, только если они реально участвуют в логике).

Шаг 2. Воркер-аудитор (Цикл обработки по батчам)

Теперь вы запускаете Codex в режиме итераций (по 1–3 бизнес-потока за сессию, чтобы контекст оставался кристально чистым и модель думала на максимум).
Алгоритм одного шага очереди для агента:
1. Взять задачу: Прочитать audit_queue.json, взять первый поток со статусом pending.
2. Собрать контекст по графу (codegraph MCP): Не читать файлы целиком! Запросить у codegraph цепочку вызовов (Call Graph) от выбранного контроллера вглубь до слоя базы данных. Прочитать код только тех методов, которые участвуют в цепочке.
3. Задокументировать процесс (codebase-memory MCP):
	• Составить схему процесса (Mermaid Sequence/State) и список бизнес-инвариантов (что обязано быть правдой).
	• Записать это в codebase-memory MCP (и/или сохранить в docs/flows/<flow_name>.md).
4. Найти логические баги: Сопоставить код цепочки с только что выведенными инвариантами. Проверить:
	• Есть ли изменение нескольких таблиц без транзакции?
	• Возможен ли Race Condition при параллельном вызове этого роута?
	• Пропущена ли проверка статуса (например, отмена уже доставленного заказа)?
	• Что будет, если внешний сервис посередине функции отвалится по таймауту?
5. Сохранить отчет и сдвинуть очередь: Записать найденные баги в bugs_report.md (или в память MCP), пометить поток в audit_queue.json как "status": "completed" и завершить шаг.

3. Как автоматизировать прогон всей очереди (без ручного кликанья)

Если у вас Codex CLI или агент в терминале, вы не обязаны нажимать Enter 100 раз. Заверните вызов агента в простейший bash/python цикл на вашем компьютере:
bash
# Псевдокод цикла запуска воркера до опустошения очереди
while grep -q '"status": "pending"' audit_queue.json; do
  echo "Запуск новой итерации аудита с чистым контекстом..."
  codex exec "Прочитай audit_queue.json. Возьми ровно 2 задачи со статусом pending. 
  Через codegraph MCP раскрути их граф вызовов. 
  Запиши описание бизнес-процесса в codebase-memory MCP. 
  Найди логические баги в этой цепочке и допиши их в bugs_report.md. 
  Обнови статус этих 2 задач в audit_queue.json на completed и заверши работу."
  sleep 5
done
Используйте код с осторожностью.

Почему эта схема — лучшая для 2000 файлов:

• Никакого переполнения контекста: Каждые 2 бизнес-процесса сессия сбрасывается. Умная модель всегда работает со свежей головой и держит в памяти только 5–10 связанных файлов конкретного процесса.
• Стопроцентная связность: За счет codegraph MCP агент идет ровно по нитке выполнения кода (Controller → Service → Repository → Event), как это происходит в реальной жизни.
• Готовая навигация: По окончании цикла у вас в codebase-memory MCP лежит полная, разбитая по полочкам база знаний о бизнес-процессах, а в bugs_report.md — список логических дыр с точными путями воспроизведения.

1. Узлы в codebase-memory MCP: Сохраняйте каждый бизнес-процесс как отдельную сущность (Entity) в памяти MCP с тегами (domain:billing, flow:checkout, bug:high-risk). Агент сможет делать векторный или теговый запрос к MCP и подтягивать только нужный бизнес-процесс.

Чтобы превратить codebase-memory MCP в идеальный навигатор по бизнес-логике, нужно задать для агента строгую схему записи данных (Schema): какие типы узлов (Entities) создавать, какие факты (Observations) туда класть и какими связями (Relations) их сшивать.
Если не задать жесткий шаблон, агент начнет сваливать в память «простыни» текста, и смысл MCP потеряется. Ниже — готовая архитектура графа знаний специально для поиска логических багов.

1. Схема узлов (Entities) в codebase-memory MCP

Заставьте агента при сканировании создавать ровно 4 типа сущностей:
1. BusinessFlow (Бизнес-процесс) — главный узел сценария (например, Flow:OrderCheckout, Flow:SubscriptionRenewal).
2. DomainEntity (Доменная сущность / Таблица) — вокруг чего крутится логика и какие у нее статусы (например, Entity:Order, Entity:Wallet).
3. CodeComponent (Ключевой узел кода) — точка входа или главное ядро логики из codegraph (например, Component:PaymentService.process).
4. LogicBug (Найденный баг / Риск) — конкретная логическая дыра, найденная при аудите (например, Bug:DoubleRefundRaceCondition).

2. Что писать внутрь узла (Шаблон Observations)

В стандартных Memory MCP у каждой сущности есть массив observations (короткие атомарные факты). Чтобы агент легко искал их векторным или теговым поиском, каждый факт должен начинаться с префикса-ключа:
Пример идеального узла Flow:OrderCheckout в памяти MCP:
json
{
  "name": "Flow:OrderCheckout",
  "entityType": "BusinessFlow",
  "observations": [
    "[TAGS] domain:billing, flow:checkout, critical:high",
    "[ENTRYPOINT] POST /api/v1/orders/checkout -> OrderController.create()",
    "[CALL_CHAIN] OrderController.create -> CartService.validate -> PaymentService.charge -> OrderRepo.save",
    "[STATE_TRANSITION] Order: DRAFT -> PENDING_PAYMENT -> PAID (or FAILED)",
    "[INVARIANT_1] Сумма списания обязана строго равняться сумме позиций минус активный промокод",
    "[INVARIANT_2] Списание баланса и смена статуса заказа должны идти в одной БД-транзакции",
    "[MERMAID_FLOW] graph TD; A[Checkout] -->|Validate| B(Hold Funds); B -->|Success| C[Create Order]; B -->|Fail| D[Rollback];"
  ]
}
Используйте код с осторожностью.
Пример узла найденного бага Bug:PromoCodeReuse:
json
{
  "name": "Bug:PromoCodeReuse",
  "entityType": "LogicBug",
  "observations": [
    "[TAGS] severity:high, type:race-condition, domain:billing",
    "[LOCATION] src/services/PromoService.ts:142 (метод applyPromo)",
    "[BROKEN_INVARIANT] Промокод с лимитом 1 раз может быть применен к 2 заказам параллельно",
    "[PROOF_OF_CONCEPT] Между проверкой promo.isUsed (строка 120) и записью в БД (строка 155) нет SELECT FOR UPDATE или атомарного лок-ключа в Redis",
    "[FIX_IDEA] Обернуть проверку и инкремент счетчика использования в единый атомарный запрос UPDATE ... WHERE used_count < max_uses"
  ]
}
Используйте код с осторожностью.

3. Схема связей (Relations) между узлами

Именно связи позволяют агенту «гулять» по бизнес-логике, не читая все 2000 файлов. Агент должен связывать узлы активными глаголами:
• Flow:OrderCheckout STARTS_AT \(\rightarrow \) Component:OrderController.create
• Flow:OrderCheckout MODIFIES_STATE_OF \(\rightarrow \) Entity:Order
• Flow:OrderCheckout DEPENDS_ON \(\rightarrow \) Flow:WalletCharge
• Bug:PromoCodeReuse BREAKS_LOGIC_IN \(\rightarrow \) Flow:OrderCheckout
• Bug:PromoCodeReuse LOCATED_IN \(\rightarrow \) Component:PromoService.applyPromo

4. Готовый системный промпт для вашего Агента-Аудитора

Скопируйте эту инструкцию и дайте ее вашему агенту в Codex при запуске цикла по очереди:
Инструкция по работе с codebase-memory MCP и codegraph MCP:
Ты — агент-аудитор бизнес-логики. Твоя задача — перевести кодовую базу в граф бизнес-процессов и найти логические баги.
Для каждой точки входа из очереди выполняй строго по шагам:
1. Сбор графа (codegraph): Получи дерево вызовов (callees) от точки входа на глубину до слоя БД/внешних API. Прочитай код только тех функций, где есть ветвления (if/else/switch), циклы, транзакции и мутации данных.
2. Проверка памяти (codebase-memory): Сделай поиск в памяти по названию сущностей, которые трогает этот код. Если узел DomainEntity уже есть в памяти — прочитай его инварианты и статусы.
3. Запись процесса в MCP: Создай сущность типа BusinessFlow. В её observations запиши строго по шаблону: [TAGS], [ENTRYPOINT], [CALL_CHAIN], [STATE_TRANSITION], [INVARIANT] (правила бизнеса, которые код пытается соблюсти).
4. Поиск логических багов: Проанализируй код цепочки на:
	• Нарушение записанных [INVARIANT].
	• Отсутствие транзакций при записи в 2+ таблицы.
	• Состояния гонки (Time-of-check to time-of-use / TOCTOU).
	• Невалидные переходы между статусами из [STATE_TRANSITION].
	• «Зависшие» состояния при падении внешнего API в середине функции.
5. Фиксация багов: Если найден баг, создай узел типа LogicBug в codebase-memory, опиши [LOCATION], [BROKEN_INVARIANT] и [PROOF_OF_CONCEPT], и привяжи его связью BREAKS_LOGIC_IN к текущему BusinessFlow.

Как вы потом будете этим пользоваться?

Когда скрипт пройдет всю очередь, вам больше никогда не придется скармливать агенту весь проект:
• Вы пишете агенту: «Покажи все найденные баги в домене биллинга» \(\rightarrow \) Агент делает один запрос к codebase-memory MCP по тегу domain:billing + LogicBug и за секунду выдает выжимку.
• Вы пишете: «Хочу поменять статусы заказа, ничего ли я не сломаю?» \(\rightarrow \) Агент смотрит узел Entity:Order, видит все привязанные связями MODIFIES_STATE_OF бизнес-процессы и сразу проверяет их инварианты.

Вы уловили самую суть агентной архитектуры, но с одним важным дополнением: для поиска настоящих бизнес-багов нужно 3 разных роли (скилла), а не 2.
Почему? Потому что самые жесткие логические баги (рассинхрон балансов, покупка удаленного товара, зависшие статусы) происходят на стыке двух разных процессов, а не внутри одного файла. Если воркер смотрит только на один процесс в вакууме, он найдет только мелкие локальные косяки.
Вот как строится идеальный трехэтапный конвейер с динамической очередью:

🔄 Архитектура из 3 Скиллов (Пайплайн)


Скилл 1: «Разведчик» (Queue Seeder) — Запускается 1 раз в начале

Его задача — не читать код, а через codegraph MCP найти все «входы» в систему и создать стартовую очередь в audit_queue.json.
• Что он ищет: Все роуты (@Post, @Get), консольные команды, крон-джобы и слушатели очередей (Kafka/RabbitMQ/EventListeners).
• Результат: В audit_queue.json появляется ~100 корневых задач типа FLOW_TRACE.

Скилл 2: «Трассировщик + Пополнятель» (Flow Tracer) — Крутится в цикле

Этот скилл берет одну задачу из очереди, проходит по ней вглубь и делает две вещи: ищет локальные баги и динамически докидывает новые задачи в очередь, если видит скрытые ветвления.
Как именно он пополняет очередь во время работы:
Представьте, что агент идет по процессу Оплата заказа. В конце функции он видит строку: eventBus.emit('order.paid', orderId) или queue.push('send_invoice').
Граф прямых вызовов тут обрывается! И агент такой:
1. Проверяет, есть ли обработчик события order.paid в audit_queue.json.
2. Если нет — дописывает в конец очереди новую задачу (динамическое пополнение!).
Как именно он ищет локальные баги внутри одного потока (Чек-лист для промпта):
Идя по цепочке Controller -> Service -> Repository, он проверяет код по 4 жестким критериям:
1. Разорванная транзакция (Partial Update): В коде есть два вызова записи в БД (walletRepo.deduct() и orderRepo.setPaid()), но вокруг них нет @Transactional / db.transaction(). Если сервер упадет между строками — деньги спишутся, а заказ не оплатится.
2. Внешний API внутри транзакции: Агент видит db.beginTransaction(), затем вызов внешнего API (stripe.charge()), затем db.commit(). Если внешний сервис ответит со второй попытки или зависнет на 30 секунд — база данных встанет в дедлок, либо деньги спишутся дважды при откате транзакции.
3. TOCTOU (Гонка проверки и действия): Агент видит if (user.balance >= price) на строке 20, а списание user.balance -= price на строке 50 без блокировки строки (SELECT FOR UPDATE или атомарного декремента). Два параллельных запроса купят товар за 100р при балансе в 100р.
4. Проглоченные ошибки (Silent Failures): В блоке catch (e) просто пишется logger.error(e), но выполнение функции идет дальше, как будто всё успешно.
После проверки он записывает правила этого процесса и какие таблицы он меняет в codebase-memory MCP.

Скилл 3: «Судья Конфликтов» (Cross-Flow Bug Hunter) — Финальный босс

Вот где находятся 80% самых дорогих багов бизнес-логики. Когда очередь FLOW_TRACE опустела и вся память codebase-memory MCP заполнена описаниями процессов, запускается Скилл №3. Он вообще почти не читает файлы проекта — он работает по графу памяти!
Как он работает:
1. Он берет из codebase-memory MCP по очереди каждую сущность (например, Entity:Order или Entity:Balance).
2. Запрашивает все процессы (BusinessFlow), которые имеют связь MODIFIES_STATE_OF с этой сущностью (допустим, заказ меняют 5 разных процессов: Создание, Оплата, Отмена клиентом, Возврат админом, Авто-отмена по крону через 15 минут).
3. Сталкивает их лбами: Сравнивает их правила ([INVARIANT] и [STATE_TRANSITION]) между собой:
	• Вопрос агента самому себе: «В потоке Авто-отмена по крону заказ переводится в CANCELED, если прошло 15 минут. А в потоке Оплата через вебхук банка статус меняется на PAID без проверки текущего статуса заказа! Что будет, если вебхук от банка придет на 16-й минуте после крона? Заказ станет PAID, хотя товары уже вернулись на склад!»
4. Если находит несостыковку в бизнес-логике двух потоков — открывает через codegraph ровно эти 2 функции в коде, перепроверяет и пишет критический LogicBug в память и отчет.

📋 Формат файла очереди (audit_queue.json), чтобы всё работало как часы

Чтобы скиллы понимали друг друга и могли докидывать задачи, сделайте такой JSON:
json
{
  "tasks": [
    {
      "id": "flow_01",
      "type": "FLOW_TRACE",
      "entrypoint": "src/controllers/OrderController.ts#checkout",
      "status": "completed",
      "discovered_entities": ["Entity:Order", "Entity:Wallet"]
    },
    {
      "id": "flow_02",
      "type": "FLOW_TRACE",
      "entrypoint": "src/workers/ExpireOrdersCron.ts#run",
      "status": "pending",
      "discovered_by": "seed"
    },
    {
      "id": "flow_03",
      "type": "FLOW_TRACE",
      "entrypoint": "src/listeners/OrderPaidListener.ts#handle",
      "status": "pending",
      "discovered_by": "flow_01 (async event order.paid)"
    },
    {
      "id": "conflict_01",
      "type": "ENTITY_CONFLICT_CHECK",
      "target_entity": "Entity:Order",
      "status": "pending",
      "discovered_by": "flow_01"
    }
  ]
}
Используйте код с осторожностью.

Итог: как выглядит работа воркера

У вас может быть даже один универсальный воркер в цикле, который просто читает поле "type" у первой задачи со статусом "pending":
• Если "type": "FLOW_TRACE" → включает логику Скилла 2 (идет по codegraph, ищет локальные баги, сохраняет поток в codebase-memory, а если встретил новую сущность или ивент — дописывает в конец audit_queue.json новые задачи).
• Если "type": "ENTITY_CONFLICT_CHECK" → включает логику Скилла 3 (достает из codebase-memory все потоки вокруг этой сущности и ищет конфликты состояний между ними).
Такая схема из Трассировщика потоков + Судьи конфликтов сущностей закроет и документацию, и глубокие баги за один проход очереди.
