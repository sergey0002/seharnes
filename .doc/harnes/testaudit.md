## Суть

Этот документ задаёт обязательный маршрут от актуальных требований задачи до воспроизводимого результата. Тест задачи считается достаточным только тогда, когда проверены требования из Jira, последние комментарии, явно переданные дополнительные условия и затронутая общая логика проекта.

Цель не в том, чтобы запустить больше тестов. Цель в том, чтобы одна и та же команда повторно запускала определённый набор задач, сохраняла отдельные результаты и не позволяла объявить задачу готовой при пропущенном требовании, старом результате или непроверенной регрессии.

> **AI:** читать при подготовке, аудите или групповом прогоне тестов задач.
> **Сначала:** требования задачи и план, затем матрица покрытия, затем скрипты прогона.
> **Не считать доказательством:** одну зелёную UI-проверку, отметку в test.md или ручную проверку только в чате.

---

## 1. Источники требований

Перед подготовкой теста скил обязан собрать и явно различить:

1. `task.md`, включая описание и критерии приёмки.
2. Последние комментарии и вложения из трекера. Если свежесть выгрузки не подтверждена, это фиксируется как ограничение.
3. `plan.md`, включая Verification, Coverage matrix, OUT-регрессии и историю аудита.
4. `diff.files.md` и фактический diff.
5. Последние сообщения пользователя в текущем диалоге.
6. Дополнительные условия пользователя, переданные со слов тимлида или QA. Условие записывается с источником `user-extra`, а не считается частью Jira.
7. Архитектурный контракт, flow-документ и связанные задачи.

Если источники противоречат друг другу, скил не выбирает молча более поздний текст. Он помечает конфликт и блокирует готовность до уточнения. Условие из разговора сохраняется при обновлении task.md, даже если его нет в трекере.

## 2. Матрица покрытия задачи

В `.doc/tasks/{N}/test.md` обязательна таблица требований:

| ID | Требование | Источник | Сценарий/тест | Проверяемый результат | Статус |
|---|---|---|---|---|---|
| AC-01 | точная формулировка | task/comment/user-extra/plan | `Class::method` | UI/API/БД/внешний эффект | covered/partial/N-A/blocked |

Правила:

- Каждое обязательное требование имеет уникальный ID.
- Для `covered` указан исполняемый тест и конкретный ожидаемый результат.
- `partial` означает, что оставшаяся часть явно перечислена.
- `N-A` разрешён только с причиной и ссылкой на ограничение среды.
- `blocked` всегда запрещает ready-for-qa.
- Для каждого негативного требования указывается, чего быть не должно.
- Для каждого важного действия проверяются состояние после reload, повтор действия и побочные эффекты, если они применимы.
- Для shared UI перечисляются все затронутые маршруты, OUT callers и соседние flow.

Чек-лист из 13 категорий дополняет эту таблицу, но не заменяет её.

## 3. Требования к тесту задачи

`prepare-task-test` обязан:

1. Не создавать тест до построения матрицы требований.
2. Использовать точные литералы из task.md, комментариев и user-extra.
3. Создать строки `## Ветки логики` по [§9](#9-когда-проверять-и-что-считать-веткой): каждый S и каждая развилка диффа без S. Happy path один на все исходы не подходит.
4. Выбрать слой для каждого требования: `phpunit`, `cest`, `playwright-hole` или `manual-N/A`.
5. Для `cest` указать имя метода и группу `task-{N}`.
6. Для `phpunit` указать запускаемый класс или набор классов.
7. Для стабильного Playwright-hole создать Cest до передачи задачи.
8. Для багов сначала воспроизвести ошибку на версии до исправления, затем подтвердить исправление.
9. Не считать фикстуру или чтение из БД проверкой. Должно быть сравнение с ожидаемым результатом.
10. Не считать checkpoint доказательством бизнес-результата. Checkpoint только собирает диагностику.

## 4. Полный маршрут одной задачи

```text
актуальные требования + user-extra
  -> plan.md и impact mapping
  -> матрица AC/OUT/рисков
  -> prepare-task-test: таблица веток §9
  -> по мере реализации: сразу S только что закрытого R (один метод, без соседей и без Playwright)
  -> в конце: task-test.sh {N}
  -> task-test.sh {N} --group соседний-flow
  -> Playwright только для строк без метода
  -> test-runs/{stamp}/verdict.json и report.md
  -> gates.py {N} (G13: нет open/partial, каждый R есть в таблице)
  -> ready-for-qa только при полном наборе зелёных результатов
```

Падение теста, ошибка консоли, error-modal, отсутствие результата, невозможность проверить окружение или неполная матрица означают `not ready`.

---

## 5. Групповой воспроизводимый прогон

Для последовательного прогона нескольких задач релиза:

```bash
bash .agents/skills/task-router/children/testing-router/children/test-task/scripts/test-batch.sh 15 16 17
bash .agents/skills/task-router/children/testing-router/children/test-task/scripts/test-batch.sh --file .doc/tasks/release.tasks
```

Скрипт запускает задачи последовательно, перед каждой выполняет check, прогон и gates, сохраняет отдельный результат и общий `summary.json`, не останавливается после первой ошибки и возвращает ненулевой код, если хотя бы одна задача не готова.

Batch не запускает полный Acceptance suite. Полный suite разрешён только отдельной явной командой пользователя.

---

## 6. Защита от старых результатов

Каждый verdict должен быть привязан к номеру задачи, группе, ветке, commit, состоянию рабочей копии, хешам task.md, plan.md, diff.files.md, test.md и тестов, адресу стенда, WebDriver и закрытым AC-ID.

`gates.py` не должен использовать результат, если после него изменились код, тест, требования, план, diff или тестовая инфраструктура.

---

## 7. Definition of Done

Задача готова только если нет конфликтов требований, все AC-ID имеют `covered` или обоснованный `N-A`, выполнены PHPUnit и Cest по матрице, проверены соседние flow, нет неожиданных ошибок консоли, error-modal и 5xx, проверены БД, reload, повтор действия и роли когда применимо, стенд жив после прогона, а `gates.py` показывает готовность по актуальному результату.

Зелёный Cest без матрицы требований не является готовностью задачи.
Готовность также требует таблицу веток из [§9](#9-когда-проверять-и-что-считать-веткой): нет строк `open` и `partial`.

---

## 8. Ограничения

- Acceptance работает с dev-БД, поэтому задачи запускаются последовательно и с известными фикстурами.
- Стенд и chromedriver поднимаются человеком или по его явной команде.
- Playwright не заменяет повторяемый Cest.
- Голосовая договорённость считается требованием после того, как пользователь передал её содержание в чат или зафиксировал в доступном документе.

## 9. Когда проверять и что считать веткой

Декомпозиция плана (`## Decomposition`: причина R и сценарий S) уже задаёт этапы с проверяемым результатом. Её и нужно исполнять. Чек-лист из 13 категорий и зелёный Cest этот список не заменяют.

### Что такое ветка

Ветка задачи это одно из двух:

1. Сценарий S из `## Decomposition`. Один R даёт минимум одну строку. Если в S названы разные наблюдаемые исходы (успех и отказ, другая роль, другая запись), это разные строки, даже если план склеил их в один S.
2. Наблюдаемая развилка в диффе задачи, которой нет ни в одном S: другой редирект, другая запись в БД, другой текст, отказ, другая роль, второй вход (OUT caller из плана).

Не ветка: `php -l`, линтер, переименование без смены результата, код вне диффа, повтор того же исхода другим инструментом.

Строка покрыта, только если в тесте есть assert на её ожидаемый результат. `recordAcceptanceCriterion(...)`, `checkpoint()` и галочка §7 строку не закрывают.

Таблица живёт в `.doc/tasks/{N}/test.md`, секция `## Ветки логики`:

| ID | Ветка | Источник | Слой | Тест | Ожидание | Статус |
|---|---|---|---|---|---|---|
| B1 | короткий исход | R1 / S1 или `file:line` | phpunit или cest | `Class::method` | литерал, код, значение БД | covered |

Статусы: `covered`, `open`, `partial`, `N-A`. У `N-A` в колонке "Ожидание" написана причина. `open` и `partial` запрещают готовность. Гейт G13 сверяет каждый `R` из `plan.md` с этой таблицей.

### Два момента

По мере реализации. Сразу после патча одного R прогнать только его S, на слое из сценария (один метод PHPUnit или один метод Cest). Соседние флоу, весь Cest задачи и Playwright в этот момент не гонять. Гейты целиком не признак конца этапа: отмечается строка этой ветки.

В конце, команда "тестируй задачу". Сначала дописать таблицу: все R/S и все развилки диффа без S. Потом прогон `@group task-{N}` и `gates.py`. Пока есть `open` или `partial`, либо в плане есть R без строки, ответ "не готово" и список дыр. Зелёный Cest это не отменяет.

### Слои не повторяют одну строку

- PHPUnit в `tests/lib/...Test.php` (файл в git, рядом с классом), если результат в браузере не виден: формула, флаги заголовка, env, второй вход без экрана.
- Codeception, если это экран или эффект в БД на стенде. Один вход на сценарий, checkpoint один раз на исход ветки.
- Cest не делает `file_get_contents` по `lib/`: контейнер Codeception монтирует только `.doc`.
- Playwright только для строки, у которой ещё нет метода PHPUnit или Cest.
- Флак: один `--filter` упавшего метода. Весь suite повторно не гонять. Второй раз тот же assert красный: баг или тест.
