## Суть

Документ задает проактивный аудит кодовой базы: библиотеку проходов, контракт
дефекта, правила воспроизведения и порядок превращения находок в план
модернизации. Аудит отвечает на конкретные вопросы про состояние, деньги,
права, ввод, транзакции, конкурентность, данные, производительность,
безопасность, эксплуатацию, API и архитектуру.

Главный принцип: finding без доказательства не считается дефектом. Найденный
дефект не закрывается без regression test или воспроизведения. Модернизация не
начинается без characterization tests и измеримой цели.

---

## 1. Что считается дефектом

| Тип | Пример | Доказательство |
|---|---|---|
| Логическая ошибка | Ветка возвращает неверный статус | Code path и ожидаемое правило |
| Нарушение инварианта | Баланс меняется дважды | Reproduction и состояние до/после |
| Потеря данных | Частичная запись без транзакции | Сбой шага и наблюдаемое состояние |
| Нарушение прав | Клиент видит чужой заказ | Запрос под ролью и ответ |
| Небезопасный ввод | SQL-инъекция, XSS, path traversal | Payload и наблюдаемый эффект |
| Конкурентный дефект | Двойное списание | Два параллельных запроса |
| Ошибка retry | Повторная операция создает дубль | Два вызова и состояние |
| Проблема данных | Orphan rows, nullable в критичном поле | Схема и запрос |
| Производительность | N+1, полный скан, unbounded query | Query count, время, план |
| Контракт API | Несовместимый ответ, неверный код | Запрос и ответ |
| Архитектурный риск | Циклы, God class, дублирование | Метрика и blast radius |
| Эксплуатационный риск | PII в логах, нет таймаута | Лог и конфиг |

Не дефект: стилистическое предпочтение, отсутствие комментария, "мне не
нравится имя", гипотетический сценарий без пути выполнения, найденная строка
без влияния на поведение.

---

## 2. Границы аудита

| Что аудит делает | Что аудит не делает |
|---|---|
| Находит статические и воспроизводимые дефекты в объявленной области | Не доказывает отсутствие дефектов |
| Проверяет инварианты и контрпримеры | Не заменяет нагрузочное тестирование |
| Проверяет authz и trust boundaries | Не заменяет пенетрационное тестирование |
| Проверяет транзакции и retry | Не воспроизводит все сбои внешних систем |
| Дает приоритет и рекомендации | Не принимает бизнес-решение за владельца |
| Связывает finding с тестом | Не гарантирует, что тест покрывает все входы |

Отрицательный вывод формулируется только для проверенной области: "в
проверенных 12 entrypoints не найдено нарушений правила X". Фраза "дефектов
нет" запрещена.

## 3. Библиотека проходов

| ID | Вопрос | Сигналы | Инструменты | Evidence |
|---|---|---|---|---|
| P01 | Состояния и переходы | Enum статусов, terminal states, недопустимые переходы | CBM, codegraph, DB, tests | Таблица переходов и контрпример |
| P02 | Деньги и количества | Двойное списание, округление, возврат, баланс | Trace path, DB, tests | До/после и reproduction |
| P03 | Права и tenant isolation | Проверка роли, ownership, IDOR, имперсонейт | Routes, middleware, DB, tests | Запрос под ролью и ответ |
| P04 | Ввод и trust boundary | SQLi, XSS, path traversal, upload, deserialize, SSRF | Semgrep, source, runtime | Payload и эффект |
| P05 | Транзакции и атомарность | Несколько записей, partial failure, rollback | Graph, source, DB | Сбой шага и состояние |
| P06 | Конкурентность и идемпотентность | Гонки, double spend, locks, unique constraints | Source, DB, concurrency test | Два параллельных запроса |
| P07 | Retry, timeout, compensation | Повтор неидемпотентной операции, отсутствие таймаута | Source, config, logs | Два вызова и дубль |
| P08 | Целостность данных | Nullable, unique, FK, orphan, soft delete | Schema, SQL, data checks | Схема и запрос |
| P09 | Производительность | N+1, unbounded query, missing index, full scan | Query log, EXPLAIN, profiler | Query count и план |
| P10 | Безопасность | Секреты, authn, CSRF, session, crypto, зависимости | Semgrep, dependency scan, config | Находка и путь эксплуатации |
| P11 | Эксплуатация | PII в логах, нет наблюдаемости, config drift | Logs, config, source | Лог и конфиг |
| P12 | API и контракты | Совместимость, коды ошибок, пагинация, валидация | Source, tests, client code | Запрос и ответ |
| P13 | Архитектура и дублирование | Циклы, God class, copy-paste, связанность | CBM, query_graph, codegraph | Метрика и blast radius |
| P14 | UI-логика | Рассинхронизация состояния, неверная валидация | Codeception, Playwright | Шаг и наблюдаемый результат |

Проход выбирается по риску области, а не запускается весь на каждый файл.
Для денег, прав и данных обязательны P01-P08. Для остальных достаточно
целевых проходов.

## 4. Техники

### 4.1. Adversarial review

Вопрос формулируется как поиск контрпримера: "при каких входах инвариант
нарушится", а не "правильно ли написан код". Модель обязана вернуть либо
конкретный сценарий, либо `no_finding` с проверенной областью.

### 4.2. Static checks

1. Semgrep-правила проекта и общие security-правила.
2. PHPStan на повышенном уровне для затронутых файлов.
3. Cypher-запросы по graph: записи без транзакции, вызовы внешних эффектов,
   чтение чужих сущностей, unbounded выборки.
4. Проверка схемы БД: nullable, unique, FK, индексы.

### 4.3. Differential checks

1. Код против утверждения.
2. Документация против кода.
3. Тест против утверждения.
4. Поведение двух похожих веток.
5. Старая и новая реализация на одном входе.

### 4.4. Runtime checks

1. Логи и трейсы для подтверждения пути.
2. DB snapshot до и после.
3. Повтор запроса и сравнение состояния.
4. Конкурентный запуск двух запросов.
5. Симуляция ошибки внешней системы.

### 4.5. Test-based proof

1. Characterization test фиксирует текущее поведение.
2. Property-based test проверяет инвариант на диапазоне входов.
3. Regression test воспроизводит дефект и падает до исправления.
4. Mutation testing применяется точечно к критичной логике.

## 5. Контракт finding

Схема: [Finding](./04-knowledge-store-and-queue.md#43-finding).

### 5.1. Severity

| Уровень | Критерий | Пример |
|---|---|---|
| S0 | Потеря денег, данных, полный обход прав, разрушение системы | Двойное списание, доступ к чужому кабинету |
| S1 | Существенный дефект с ограниченным воздействием | Неверный возврат в одном сценарии |
| S2 | Локальная ошибка или риск при определенных условиях | Неверный статус при редком сбое |
| S3 | Слабый риск, деградация, отсутствие защиты в глубину | Нет таймаута у внешнего вызова |
| S4 | Гигиена, поддерживаемость, дублирование | God class, мертвый код |

### 5.2. Confidence

| Значение | Условие |
|---|---|
| `confirmed` | Есть воспроизведение или формальное доказательство |
| `high` | Статический путь полный, все ветки проверены |
| `medium` | Путь вероятен, но есть динамика или неизвестный конфиг |
| `low` | Гипотеза без полного пути |

S0 и S1 не могут быть `confirmed` без воспроизведения или доказательства.
`low` findings не попадают в автоматический backlog исправлений.

### 5.3. Fingerprint

```text
sha256(pass + normalized_symbol + normalized_evidence_locator + rule_version)
```

Fingerprint защищает от дублей при повторном сканировании и позволяет
отслеживать судьбу дефекта после исправления.

## 6. Triage и ложные срабатывания

1. Дедупликация по fingerprint.
2. Проверка, что путь достижим из entrypoint.
3. Проверка, что входные данные возможны в объявленной конфигурации.
4. Проверка, что защита отсутствует во всех ветках.
5. Проверка, что поведение не компенсируется на другом слое.
6. Для S0/S1 обязательна независимая проверка вторым проходом.
7. `false_positive` сохраняется с причиной, чтобы правило не срабатывало снова.
8. Правило или pass обновляется, если ложное срабатывание системное.

Типовые ложные срабатывания:

| Симптом | Причина | Решение |
|---|---|---|
| "Нет проверки прав" | Проверка в middleware или декораторе | Проверить весь путь, а не один метод |
| "SQL-инъекция" | Параметризованный запрос через билдер | Проверить фактический вызов |
| "Нет транзакции" | Транзакция в обертке | Проверить вызывающий слой |
| "N+1" | Данные уже в кеше | Проверить query log |
| "Двойной возврат" | Idempotency key на входе | Проверить ключ и хранилище |

## 7. Воспроизведение

Минимальный набор для finding:

1. Commit и generation.
2. Роль и предусловия.
3. Точная команда или шаги.
4. Входные данные без секретов.
5. Ожидаемый результат.
6. Фактический результат.
7. Состояние до и после.
8. Артефакт: тест, лог, DB snapshot или трасса.

Если воспроизведение невозможно, finding остается `suspected` или `high`, но
не становится `confirmed`. Исключение: формальное доказательство по полному
статическому пути с проверкой всех веток.

## 8. Модернизация

### 8.1. Принципы

1. Сначала characterization tests, потом изменение.
2. Маленькие обратимые шаги вместо big-bang rewrite.
3. Strangler fig для legacy: новая реализация рядом, переключение по
   возможности.
4. Измерять до и после: latency, query count, memory, error rate, complexity.
5. Не менять поведение без утверждения и теста.
6. Не рефакторить все сразу: приоритет по риску и влиянию.
7. Сохранять публичные контракты, пока не доказана безопасная миграция.

### 8.2. Критерии SOLID и ООП

| Критерий | Проверка | Антипаттерн |
|---|---|---|
| Single responsibility | У класса одна причина изменения | God class, смешение controller и domain |
| Open/closed | Новый вариант добавляется без правки всех веток | Большой switch по типу |
| Liskov | Подтип не ломает контракт | Наследник бросает неподдерживаемое исключение |
| Interface segregation | Узкие интерфейсы по роли клиента | Толстый интерфейс с пустыми методами |
| Dependency inversion | Домен не зависит от инфраструктуры | Domain знает про SQL и HTTP |
| Композиция | Поведение собирается из частей | Глубокая иерархия наследования |
| Связность и связанность | Высокая внутри модуля, низкая между | Циклы, общие глобальные состояния |

SOLID не является целью сам по себе. Механическое выделение классов может
ухудшить читаемость. Решение принимается по измеряемому эффекту и риску.

### 8.3. Производительность

1. Зафиксировать baseline: время, query count, память, размер ответа.
2. Найти доминирующие затраты: EXPLAIN, query log, profiler.
3. Устранить N+1, unbounded выборки, лишние сериализации.
4. Добавить индексы по фактическим запросам, а не по догадке.
5. Кешировать только с правилом инвалидации.
6. Проверить поведение под конкурентной нагрузкой.
7. Измерить после изменения и сравнить с baseline.

### 8.4. Приоритет

```text
priority = severity_weight * exposure * confidence / effort
```

| Параметр | Значение |
|---|---|
| `severity_weight` | S0 100, S1 40, S2 15, S3 5, S4 1 |
| `exposure` | 1-5, насколько часто путь используется |
| `confidence` | confirmed 1.0, high 0.8, medium 0.5, low 0.2 |
| `effort` | 1-13, оценка в условных единицах |

S0 и S1 не откладываются из-за низкого приоритета. Приоритет управляет
порядком, а не отменой критичного исправления.

### 8.5. Backlog item

```json
{
  "schema": "harness.modernization/1",
  "id": "mod_01J...",
  "title": "Вынести списание и создание заказа в транзакцию",
  "finding_ids": ["fnd_01J..."],
  "scope": {"symbols": ["PaymentService.charge"], "tables": ["client_balance", "order"]},
  "risk": "high",
  "effort": 5,
  "priority": 80,
  "expected_metric": {
    "name": "partial_writes",
    "before": 1,
    "target": 0
  },
  "characterization_tests": ["scn_01J..."],
  "steps": [
    "Зафиксировать текущее поведение тестом",
    "Ввести транзакцию",
    "Добавить compensation",
    "Проверить повтор и сбой"
  ],
  "rollback": "Отключить feature flag и вернуть прежний путь",
  "status": "proposed"
}
```

Backlog не является планом задачи. `prepare-plan` превращает выбранный item в
план с Patches, тестами и acceptance criteria.

## 9. Definition of Done

### 9.1. Для finding

1. Есть fingerprint и evidence.
2. Указан severity, confidence и impact.
3. Есть воспроизведение или формальное доказательство.
4. Есть regression test или characterization test.
5. После исправления тест проходит, а finding получает `verified`.
6. Повторный проход не находит дефект в той же области.
7. Документация и claim обновлены, если поведение изменилось.

### 9.2. Для modernization item

1. Есть characterization tests.
2. Есть baseline и целевая метрика.
3. Изменение разбито на обратимые шаги.
4. Публичный контракт сохранен или миграция описана.
5. После изменения метрика улучшена и измерена.
6. Нет новых S0/S1.
7. Rollback проверен.

## 10. Приемочные фикстуры

| Фикстура | Что должна найти система |
|---|---|
| Race condition | Двойное списание при двух запросах |
| Missing transaction | Частичная запись при ошибке |
| IDOR | Доступ к чужому объекту по ID |
| SQL injection | Payload в параметре запроса |
| Retry duplicate | Повтор создает второй эффект |
| N+1 | Число запросов растет с размером списка |
| Missing index | Full scan на большом фильтре |
| State violation | Недопустимый переход статуса |
| Secret in log | Токен в логе |
| Weak authz | Роль не проверяется на одном entrypoint |

Для каждой фикстуры известен ожидаемый результат: минимум один finding с
правильным severity и воспроизведением. Ложные срабатывания на чистом
контрольном проекте измеряются отдельно.

## 11. Метрики

| Метрика | Формула |
|---|---|
| Recall на seeded bugs | найденные / все заложенные |
| Precision | confirmed / все triaged |
| Reproduction rate | воспроизведенные S0/S1 / все S0/S1 |
| Regression coverage | findings с regression test / все fixed |
| Escape rate | дефекты после релиза / все дефекты |
| Modernization delta | метрика после / метрика до |
| Cycle time | время от finding до verified |
| Cost per finding | токены и время / confirmed finding |

Метрики считаются на одинаковых фикстурах и генерациях. Сравнение разных
версий pass library без калибровки запрещено.

## Известные проблемы и ограничения

Pass library является проектом; правила и пороги требуют калибровки на
фикстурах и реальном проекте. Статический аудит не находит все динамические и
смысловые дефекты. Security-проверки не заменяют pentest, performance-проверки
не заменяют load test. Модернизация legacy без characterization tests
запрещена, но сами tests могут быть неполными. Приоритет и severity остаются
предметом независимой проверки для S0 и S1.
