## Суть

Скил не может закрепить модель: frontmatter `SKILL.md` не содержит `model` и `mode`. Модель закрепляется на уровне агента-исполнителя, команды или native-конфигурации клиента. План вводит переносимый слой из трех частей: нейтральный манифест ролей, скил `delegation-router` с контрактом входа и выхода, адаптеры в Kilo, Qoder, OpenCode и Qwen Code. Главный агент декомпозирует большую задачу, отдает узкие подзадачи дешевым исполнителям и получает короткий проверяемый отчет вместо сырых файлов и логов. Экономия идет от изоляции контекста и сжатого отчета, а не от самого факта дешевой модели. Вложенные субагенты технически возможны, но по умолчанию запрещены: глубина 1, исключение только для read-only исследования с жесткими лимитами.

## 1. Цель, границы и критерии успеха

### 1.1. Цель

1. Снизить расход токенов дорогой модели на больших задачах без потери качества приемки.
2. Закрепить дешевую модель за ролью один раз, а не напоминать о ней в каждом промпте.
3. Сделать схему переносимой: один манифест ролей, разные native-адаптеры.
4. Запретить дешевому исполнителю принимать решения, менять продуктовый код и выходить за бюджет.
5. Измерить эффект на пилоте и откатиться, если экономия получена ценой переделок.

### 1.2. Что план не делает

- Не выбирает модели по цене автоматически. Привязка задается ролью и квалификацией.
- Не отменяет тесты, PHPStan, security-проверки и приемку задачи.
- Не разрешает дешевому исполнителю писать в исходники в первой фазе.
- Не отправляет закрытый код и секреты дешевому провайдеру без data policy.
- Не заменяет `prepare-plan` и `test-task`, а подключается к ним как исполнительный слой.

### 1.3. Критерии успеха

| ID | Критерий | Проверка |
|---|---|---|
| G1 | Экономия на пилоте не меньше 25 процентов на принятую задачу | receipts и сравнение с baseline |
| G2 | Доля принятых подзадач с первого прохода не падает больше чем на 5 процентных пунктов | журнал приемки |
| G3 | Каждая среда с заявленной поддержкой проходит runtime contract test | `tests/contract/` |
| G4 | Все native-файлы агентов собраны из одного манифеста, parity зеленый | `verify_parity.py` |
| G5 | Вложенность выключена по умолчанию, включение только по политике | конфиг и тест глубины |
| G6 | Нет секретов и лишних данных в пакетах и отчетах | `validate_report.py`, ревью |

## 2. Исходные факты и текущее состояние

### 2.1. Почему модель нельзя закрепить за скилом

Официальная документация Agent Skills и клиентов сходится в одном: `SKILL.md` описывает инструкцию и условия применения, но не запускает отдельный процесс и не переключает модель.

| Клиент | Что содержит скил | Где живет модель |
|---|---|---|
| Kilo Code | `name`, `description`, `license`, `compatibility`, `metadata` | профиль агента `.kilo/agents/*.md` или `agent` в `kilo.jsonc`, либо разовый override в `task` |
| OpenCode | те же поля Agent Skills | профиль агента `.opencode/agents/*.md` или `agent` в `opencode.json` |
| Qoder | скил как инструкция | `.qoder/agents/*.md`, поля `model` и `skills` |
| Qwen Code | скил как инструкция | `.qwen/agents/*.md`, поле `model`, плюс `agents.modelGrades` |

Отсюда разделение ответственности:

- скил хранит протокол: как декомпозировать, что передать, что принять обратно;
- агент хранит модель, инструменты, права и лимиты;
- команда хранит разовый запуск с моделью, если нужен ручной триггер;
- конфиг хранит глубину вложенности и общие лимиты.

### 2.2. Что уже описано в plan/01

Документ [01-subagent-planning-and-audit.md](./01-subagent-planning-and-audit.md) задает роли, независимые аудиты, frozen input, выбор моделей по ролям, минимальный eval и `max_spawn_depth`. Этот план не пересказывает его и не дублирует таблицы. Здесь описана недостающая операционная часть: конкретный скил, формат пакета и отчета, адаптеры по клиентам, генерация файлов и пилот.

Связь ролей:

- `research` из plan/01 соответствует `cheap-research` этого плана;
- `executor` из plan/01 соответствует `cheap-executor`, но в первой фазе только с готовым патчем;
- `integrator` и `*_reviewer` остаются на сильной модели;
- qualification и eval берутся из plan/01, раздел 8.2.

### 2.3. Текущее состояние харнеса

| Факт | Где видно | Следствие |
|---|---|---|
| Канон скилов это `.agents/skills` | `AGENTS.md`, `sync-agent-views.sh` | новый скил кладется туда |
| Канон правил и MCP это `.cursor` | `AGENTS.md` | общие правила не дублируются в скиле |
| `.kilo/kilo.jsonc` генерируется | `generate-agent-configs.py` | блок `agent` и `subagent_depth` должен генерироваться, а не правиться руками |
| `.qoder`, `.qwen`, `.codex` генерируются | `sync-agent-views.sh` | адаптеры агентов добавляются в тот же синк |
| `.opencode` отсутствует | корень репозитория | нужен новый адаптер |
| Файлов агентов нет | `.kilo/agents`, `.qoder/agents`, `.qwen/agents`, `.opencode/agents` | создаются генератором из манифеста |
| Mirror индексирует канон | `state/19-harness-mirror.md` | сгенерированные агенты получают ребро `generated_from`, а не второй канон |

## 3. Матрица сред

Статусы проверены по официальной документации 2026-11-06. Перед внедрением обязателен runtime contract test на установленной версии клиента: документация и фактическое поведение могут расходиться.

| Среда | Субагенты | Модель на роль | Предзагрузка скила | Вложенность | Конфиг | Статус |
|---|---|---|---|---|---|---|
| Kilo Code | да, `task` | да, `model` в профиле агента и per-task override | промпт агента загружает скил | да, при `subagent_depth > 1` и `permission.task` | `.kilo/agents/*.md`, `kilo.jsonc` | поддержано, проверить глубину |
| Qoder CLI и IDE | да, Agent tool | да, `model` в `.qoder/agents/*.md` | да, поле `skills` | да, через Agent tool, лимит `maxTurns` | `.qoder/agents/*.md` | поддержано, проверить вложенность |
| OpenCode | да, `task` | да, `model` в `.opencode/agents/*.md` | да, `.agents/skills` читается нативно | заявлена через `permission.task`, глубина не описана | `.opencode/agents/*.md`, `opencode.json` | поддержано, глубину проверить |
| Qwen Code | да, Agent tool | да, `model` и `agents.modelGrades` | да, `.agents/skills` читается | да, `model.maxSubagentDepth`, по умолчанию 5 | `.qwen/agents/*.md`, `.qwen/settings.json` | поддержано |
| Codex | по plan/01 официально описаны | заявлена | промпт агента | наследуется от parent | проверить установленную версию | проверить, не угадывать TOML |
| Cursor | да | да, с ограничениями аккаунта | промпт агента | проверить | `.cursor/agents` по версии | проверить |
| Claude Code | да | да | промпт агента | проверить | `.claude/agents` | вне синка проекта |
| Antigravity | не подтверждено | не подтверждено | скилы читает | не подтверждено | нет | fallback без субагентов |
| DSH | не подтверждено | не подтверждено | не подтверждено | не подтверждено | `.dsh/project.patch.yml` | fallback, sequential session |

### 3.1. Kilo Code

Подтверждено:

- профиль агента задает `mode: subagent`, `model`, `steps`, `hidden`, `permission`;
- `task` принимает `subagent_type`, а также разовые `model`, `provider`, `variant`;
- `permission.task` ограничивает список вызываемых субагентов;
- `agent.explore.model` переопределяет встроенный read-only исследователь;
- `subagent_depth` задает максимальную глубину, по умолчанию 1;
- дочерний агент может вызывать `task` только при разрешении и достаточной глубине;
- известна проблема: в части версий сессия субагента получает deny на `task` даже при явном allow. Нужен contract test.

### 3.2. Qoder

Подтверждено:

- проектный агент лежит в `.qoder/agents/*.md`, пользовательский в `~/.qoder/agents/*.md`;
- поля: `name`, `description`, `prompt`, `tools`, `disallowedTools`, `mcpServers`, `model`, `effort`, `maxTurns`, `skills`, `permissionMode`, `temperature`, `timeoutMins`, `isolation`;
- `model` принимает `inherit`, `auto`, `lite`, `efficient`, `performance`, `ultimate` или полный ID;
- `skills` предзагружает указанные скилы в контекст именно этого субагента;
- файл не задает имя агента: имя берется из frontmatter `name`;
- вложенность идет через Agent tool, ограничивается `maxTurns` и правами.

Qoder ближе всех к исходной идее: один агент, одна модель, один предзагруженный скил.

### 3.3. OpenCode

Подтверждено:

- агент лежит в `.opencode/agents/*.md` или `~/.config/opencode/agents/*.md`;
- поля: `description`, `mode`, `model`, `prompt`, `temperature`, `steps`, `permission`, `hidden`, `color`, `top_p`;
- `permission.task` задает, каких субагентов агент может вызывать;
- `.agents/skills` читается нативно, скилы грузятся инструментом `skill`;
- у субагента отдельная сессия, навигация по дочерним сессиям есть в TUI.

Глубина вложенности в документации не зафиксирована. Безопасное значение по умолчанию: плоская схема, `task: deny` у исполнителя.

### 3.4. Qwen Code

Подтверждено:

- агент лежит в `.qwen/agents/*.md`;
- поля: `name`, `description`, `model`, `tools`, `disallowedTools`, `approvalMode`, `maxTurns`;
- `model` принимает `inherit`, `fast`, ID модели, `authType:modelId`;
- `agents.modelGrades` задает семантические имена (`small`, `high`), `agents.allowedGrades` ограничивает выбор;
- `model.maxSubagentDepth` задает глубину, по умолчанию 5;
- `agents.builtin.exploreModel` переопределяет встроенный Explore;
- Agent tool может запускать несколько субагентов параллельно в одном сообщении.

### 3.5. Codex

Plan/01 фиксирует, что официальная документация Codex описывает custom subagents с настройкой роли и модели, а permissions наследуются от parent. Это не подтверждает синтаксис установленной версии. До contract test адаптер не генерирует файлы Codex и не выдумывает TOML. Fallback: последовательная fresh-session с явной моделью, если клиент это поддерживает.

### 3.6. Cursor и Claude Code

Оба поддерживают отдельный контекст и настройку модели по документации, но факт выбора модели зависит от аккаунта, администратора и версии. Адаптер включается только после проверки фактического файла конфигурации на машине. Запрошенный ID не равен доказанному фактически использованному.

### 3.7. Antigravity и DSH

Antigravity: нативные субагенты и привязка модели не подтверждены. DSH: сведений о нативных субагентах нет. Для этих сред скил работает в режиме `unsupported`: декомпозицию и контракт пакета можно использовать, но исполнение идет в основной сессии или в последовательной fresh-session. Молчаливая подмена модели запрещена.

## 4. Архитектура переносимого слоя

### 4.1. Три слоя

| Слой | Что хранит | Кто читает | Переносимость |
|---|---|---|---|
| Policy | роли, тиры, лимиты, схемы пакета и отчета | скил и генератор | полная |
| Router skill | шаги декомпозиции, выбора роли, приемки и эскалации | главный агент | полная |
| Native adapter | файл агента, модель, инструменты, глубина | конкретный клиент | зависит от клиента |

### 4.2. Поток

```text
Пользователь
  -> главный агент (сильная модель)
     -> D1 декомпозиция по AC и риску
     -> D2 выбор роли и тира
     -> D3 пакет подзадачи (JSON + краткий бриф)
     -> native task / Agent
        -> дешевый субагент (своя модель, свой контекст)
        -> отчет по схеме
     -> D4 проверка схемы и доказательств
     -> D5 принятие, переделка или эскалация
     -> D6 receipt и метрики
```

### 4.3. Канонические файлы

| Файл | Роль |
|---|---|
| `.agents/skills/delegation-router/SKILL.md` | протокол и маршрутизация детей |
| `.agents/skills/delegation-router/assets/roles.yaml` | нейтральный манифест ролей, тиров и лимитов |
| `.agents/skills/delegation-router/assets/packet.schema.json` | схема входа субагента |
| `.agents/skills/delegation-router/assets/report.schema.json` | схема выхода субагента |
| `.agents/skills/delegation-router/references/environments.md` | точные поля и ограничения клиентов |
| `.agents/skills/delegation-router/references/nested.md` | политика вложенности и топологии |
| `.agents/skills/delegation-router/scripts/preflight.py` | проверка пакета и оценка окупаемости |
| `.agents/skills/delegation-router/scripts/validate_report.py` | машинная проверка отчета |
| `.agents/skills/delegation-router/scripts/receipt.py` | запись расхода и статуса |

Модели и пути native-файлов живут в `roles.yaml` и в генераторе, а не в `SKILL.md`.

## 5. Скил delegation-router

### 5.1. Назначение и триггеры

`delegation-router` это родительский скил. Он не выполняет подзадачу сам, а решает, стоит ли делегировать, какой профиль вызвать, что передать и как принять результат.

Триггеры родителя:

- разбей задачу на подзадачи;
- делегируй субагентам;
- запусти параллельно;
- используй дешевую модель для подзадачи;
- сэкономь токены на большой задаче;
- собери результаты субагентов;
- субагент застрял, эскалируй;
- оцени дешевую модель на роли;
- subagents, delegation, cheap model, nested subagents.

Отрицательные триггеры:

- задача меньше порога окупаемости;
- нужен один grep или чтение одного файла;
- требуется архитектурное решение;
- требуется финальная приемка diff;
- среда не поддерживает субагентов и fallback не согласован.

### 5.2. Маршрутизация детей

Родитель обязан сам собрать все триггеры детей и выбрать ребенка по тексту запроса.

| Ребенок | Триггеры | Вход | Выход |
|---|---|---|---|
| `decompose` | разбей, декомпозиция, план подзадач, какие части независимы | задача, AC, границы | `DelegationPlan` |
| `dispatch` | делегируй, запусти субагентов, параллельно, вызови | `DelegationPlan`, роли | `WorkerPacket[]` и native-вызовы |
| `collect` | собери, сведи, проверь отчеты, объедини | отчеты | принятые факты, конфликты |
| `escalate` | субагент застрял, эскалируй, нужна сильная модель | статус `blocked` или `escalate` | решение и новый исполнитель |
| `eval` | оцени модель, квалификация, пилот стоимости | роль, fixtures | `qualification.json` и метрики |

### 5.3. Инварианты

1. Модель не задается в скиле. Она задается в native-профиле или разовым override.
2. Дешевый исполнитель по умолчанию read-only.
3. Ни одна подзадача не передает право решения по AC, архитектуре, security и финальному diff.
4. Пакет без acceptance checks, output schema и бюджета не отправляется.
5. Отчет без доказательств не принимается.
6. Глубина вложенности по умолчанию 1.
7. Каждый запуск пишет receipt: роль, запрошенная модель, наблюдаемая модель, токены, время, статус.
8. Секреты, `.env`, токены и персональные данные в пакет не попадают.
9. Неподдерживаемая среда объявляется явно, без тихой замены модели.
10. Экономия не может быть достигнута удалением обязательных проверок.

### 5.4. Шаги

| Шаг | Действие | Результат | Стоп-условие |
|---|---|---|---|
| D0 | Проверить, что задача выше порога окупаемости | решение делегировать или нет | подзадача меньше порога |
| D1 | Разложить задачу по независимым причинам и AC | `DelegationPlan` | есть общий write-set без владельца |
| D2 | Выбрать роль и тир по неопределенности, а не по цене | роль, tier, модель | нужной квалификации нет |
| D3 | Собрать пакет и проверить его `preflight.py` | `WorkerPacket` | пакет неполный или превышает бюджет |
| D4 | Вызвать native-субагента | отчет или ошибка | среда не поддерживает запуск |
| D5 | Проверить отчет `validate_report.py` | статус `accepted`, `rework`, `escalate` | схема невалидна |
| D6 | Выборочно проверить 1-2 claims по `file:line` | подтверждение фактов | evidence не совпал |
| D7 | Свести результаты и обновить общий план | обновленный план | конфликт фактов |
| D8 | Записать receipt и метрики | запись в `work/{run}/receipts/` | нет данных о модели |


### 6.2. Поля

| Поле | Обязательно | Смысл |
|---|---|---|
| `schema_version` | да | версия контракта |
| `packet_id` | да | уникальный ID подзадачи |
| `run_id` | да | ID общего запуска, связывает receipts |
| `task_ref` | да | задача или рабочий элемент |
| `role` | да | роль из `roles.yaml` |
| `tier` | да | `cheap`, `mid`, `strong` |
| `goal` | да | одно предложение, проверяемый результат |
| `scope.read` | да | разрешенные пути и символы |
| `scope.write` | да | пустой список для read-only роли |
| `scope.forbidden` | да | явные запреты |
| `facts` | да | только подтвержденные факты, не догадки |
| `anchors` | да | стартовые `file:line` |
| `acceptance` | да | проверяемые условия с ID |
| `output_schema` | да | имя схемы отчета |
| `budget` | да | лимиты инструментов, токенов, строк и времени |
| `escalate_if` | да | условия остановки и передачи наверх |
| `data_policy` | да | классификация и разрешенные провайдеры |
| `model_requested` | да | тир или alias, не конкретный секрет |
| `depth` | да | текущая глубина, для политики вложенности |

### 6.3. Бриф для модели

Пакет передается двумя частями: JSON и короткий текст. JSON машиночитаем, текст задает рамку поведения.

```text
Ты исполнитель роли {role}. Работай только в scope.read.
Ничего не выдумывай. Каждый факт подкрепляй file:line.
Не меняй файлы, если scope.write пуст.
Остановись и верни status=escalate, если сработало escalate_if.
Ответ верни строго по схеме {output_schema}.
Сводка не длиннее {max_output_lines} строк. Код и логи не копируй.
```

### 6.4. Гейт пакета

`preflight.py` проверяет:

1. все обязательные поля заполнены;
2. acceptance содержит ID и проверяемое ожидание;
3. пути из scope существуют или явно помечены как отсутствующие;
4. бюджет задан и не превышает лимит роли;
5. `scope.write` пуст для read-only роли;
6. `data_policy` не разрешает секреты;
7. оценка окупаемости положительна.

Пакет с ошибкой не отправляется. Исполнитель не может увеличить бюджет самостоятельно.

## 7. Контракт выхода: Worker Report

### 7.1. Пример

```json
{
  "schema_version": 1,
  "packet_id": "DP-CT2606-01",
  "status": "done",
  "summary": "Найдены две серверные проверки владельца и один путь без проверки. Подробности в claims.",
  "claims": [
    {
      "claim": "Проверка владельца есть в AdminItemController",
      "evidence": "admin/lib/Objects/Item/AdminItemController.php:120",
      "confidence": "high"
    },
    {
      "claim": "В методе сохранения проверка отсутствует",
      "evidence": "admin/lib/Objects/Item/AdminItemController.php:240",
      "confidence": "medium"
    }
  ],
  "checks": [
    {
      "id": "A1",
      "result": "pass",
      "observed": "две разные строки"
    },
    {
      "id": "A2",
      "result": "pass",
      "observed": "указан путь без проверки"
    }
  ],
  "files_touched": [],
  "open_questions": [],
  "escalate_reason": null,
  "usage": {
    "tool_calls": 9,
    "approx_tokens": 8200,
    "wall_seconds": 74
  },
  "model_observed": "unknown"
}
```

### 7.2. Поля

| Поле | Обязательно | Смысл |
|---|---|---|
| `packet_id` | да | связь с входом |
| `status` | да | `done`, `partial`, `blocked`, `escalate` |
| `summary` | да | не более 12 строк, без дампов |
| `claims` | да | факты с evidence |
| `checks` | да | результат по каждому acceptance ID |
| `files_touched` | да | пустой список для read-only |
| `open_questions` | да | что осталось неясным |
| `escalate_reason` | да при `escalate` | причина передачи наверх |
| `usage` | да | инструменты, токены, время |
| `model_observed` | да | фактическая модель или `unknown` |

### 7.3. Гейт отчета

`validate_report.py` проверяет:

1. JSON соответствует схеме;
2. `packet_id` совпадает;
3. `summary` не длиннее лимита;
4. каждый `claim` имеет evidence формата `file:line` или явный `evidence: "not_found"` с причиной;
5. каждый acceptance ID закрыт строкой в `checks`;
6. `status=done` несовместим с `result=fail` без `escalate_reason`;
7. `files_touched` пуст для read-only роли;
8. нет секретов и подозрительных строк;
9. нет фрагментов кода длиннее 20 строк.

### 7.4. Приемка родителем

Схема и гейт не доказывают истинность. Главный агент выборочно проверяет 1-2 claims по указанным `file:line`. Если evidence не совпал, отчет получает `rework`, а не `accepted`. Повторный запуск допускается один раз. После второго провала подзадача уходит на сильную модель или выполняется родителем.

## 8. Декомпозиция и выбор подзадач

### 8.1. Классы подзадач

| Класс | Роль | Что делает | Что запрещено |
|---|---|---|---|
| Locate | `cheap-research` | найти файлы, символы, вызовы | менять код, делать вывод о поведении без evidence |
| Summarize | `cheap-summarize` | сжать файл или модуль до фактов | пересказывать весь файл, терять ссылки |
| Extract | `cheap-extract` | вытащить поля, маршруты, конфиги | додумывать отсутствующие значения |
| Test run | `cheap-test-runner` | запустить разрешенную команду и разобрать падение | менять тесты и исходники |
| Draft patch | `mid-executor` | подготовить точный патч по утвержденному плану | менять scope, выбирать архитектуру |
| Verify claims | `mid-verifier` | независимо проверить факты и тесты | принимать решение за интегратора |

Первая фаза пилота использует только `cheap-research`, `cheap-summarize`, `cheap-extract` и `cheap-test-runner`. Роли с записью включаются после квалификации.

### 8.2. Порог делегирования

Делегировать имеет смысл, когда ожидаемое исследование или чтение внутри родителя заметно больше накладных расходов на субагента. Накладные расходы: системный промпт, схемы инструментов, пакет, отчет.

Практическое правило:

- не делегировать один поиск, одно чтение или одну правку;
- делегировать, если ожидается серия из 5 и более инструментальных шагов;
- делегировать, если результат нужен в сжатом виде, а сырые данные родителю не нужны;
- не делегировать, если пакет получается больше самого исследования.

Точный порог задает `preflight.py` по оценке `expected_inline_tokens` и `overhead_tokens`. Значения калибруются на пилоте.

### 8.3. Что нельзя делегировать дешевой модели

- выбор архитектурного решения;
- толкование требований и AC;
- security-подпись и оценку риска;
- финальное утверждение diff;
- изменение общего контракта или схемы данных;
- работу с секретами и персональными данными вне разрешенной политики;
- подзадачу с неясным критерием приемки.

### 8.4. Конфликт записи

Две подзадачи не могут писать в один файл параллельно. Read-only подзадачи можно запускать параллельно. Если подзадачи читают состояние, которое меняет сосед, они выполняются последовательно. Разные файлы не доказывают независимость, если общее состояние меняется через базу, события или кеш.

## 9. Топологии: поток, параллель и вложенность

### 9.1. Fan-out

Несколько read-only подзадач по разным вопросам запускаются параллельно. Родитель сводит отчеты и разрешает конфликты. Это основной режим экономии.

```text
main
  -> research A (cheap)
  -> research B (cheap)
  -> research C (cheap)
  -> collect -> main
```

### 9.2. Pipeline

Результат одной подзадачи становится входом следующей. Каждый шаг имеет свой контракт и не смешивает роли.

```text
research (cheap) -> summarize (cheap) -> verify (mid) -> main
```

Поток данных идет через файлы в `work/{run}/` или через явный packet, а не через общий чат.

### 9.3. Вложенные субагенты

Да, технически субагент может иметь своих субагентов. Это называется глубиной больше 1. Политика проекта:

| Глубина | Разрешено | Условия |
|---|---|---|
| 1 | обычная подзадача | по умолчанию, исполнитель не имеет `task` |
| 2 | только `cheap-research` | родитель read-only, дочерний тоже read-only, не более 2 детей, общий бюджет |
| 3 и больше | запрещено | нет доказанной окупаемости и контроля |

Причины ограничения:

- вложенный отчет теряет прозрачность для главного агента;
- каждый уровень добавляет свой системный промпт и схемы;
- ошибка суммирования на нижнем уровне трудно обнаруживается сверху;
- растет риск бесконечной рекурсии и гонки за файлы.

Как включить по средам:

| Среда | Механизм | Проверка |
|---|---|---|
| Kilo | `subagent_depth: 2`, `permission.task` у роли, дочерний агент с `task: allow` | тест: глубина 2 разрешает research, глубина 3 отклоняется |
| Qwen Code | `model.maxSubagentDepth: 2` | тест: вложенный research работает, запись запрещена |
| Qoder | Agent tool и `maxTurns` | тест: дочерний агент видит только разрешенные tools |
| OpenCode | `permission.task` | тест: при `task: deny` инструмент скрыт |
| Codex, Cursor | проверить установленную версию | без теста глубина 1 |
| Antigravity, DSH | нет | глубина 1, только fallback |

### 9.4. Tournament

Два дешевых исполнителя решают одну подзадачу независимо, сильный агент сравнивает и выбирает. Применять только для задач с дешевой проверкой результата. Это дороже fan-out и не является режимом по умолчанию.

### 9.5. Лимиты

| Лимит | Значение по умолчанию | Где задается |
|---|---|---|
| Максимум параллельных детей | 3 | `roles.yaml`, `limits.max_fanout` |
| Максимум глубины | 1 | `roles.yaml`, native-конфиг |
| Максимум повторов подзадачи | 1 | `roles.yaml` |
| Максимум инструментальных вызовов | по роли, 10-20 | packet budget |
| Максимум вывода | 40 строк | packet budget |
| Общий дедлайн запуска | 180 секунд на подзадачу | packet budget |

### 9.6. Поток и фоновый режим

Субагент возвращает финальный отчет, а не поток токенов. Межинструментальный поток возможен так:

- Kilo: `task` с `background: true`, результат приходит в родительскую сессию позже; для координации вложенных агентов есть Kilo Swarm board;
- Qwen Code: background agent и продолжение после завершения;
- Qoder: отдельная сессия и `maxTurns`;
- OpenCode: дочерние сессии и навигация между ними.

Переносимый контракт не зависит от board: промежуточные файлы лежат в `work/{run}/status.json` и `work/{run}/outbox/`. Board используется только как ускоритель в Kilo и не является обязательным.

## 10. Модельные тиры и квалификация

### 10.1. Тиры

| Тир | Для чего | Пример роли | Ограничение |
|---|---|---|---|
| cheap | поиск, сжатие, извлечение, прогон теста | `cheap-research` | read-only, малый бюджет |
| mid | проверка фактов, черновик патча | `mid-verifier` | не принимает финальное решение |
| strong | декомпозиция, интеграция, финальная приемка | главный агент | не делегируется дешевому |

### 10.2. Квалификация

Модель не становится пригодной по названию, цене или самооценке. Квалификация привязана к версии модели, роли, набору инструментов, бюджету контекста и классу риска. Минимальный eval и правила допуска берутся из [plan/01, раздел 8.2](./01-subagent-planning-and-audit.md#82-минимальный-eval).

Для пилота достаточно трех фикстур на роль:

1. корректный поиск с точным `file:line`;
2. ложный пакет, где нужного файла нет;
3. конфликт фактов, где нужно вернуть `escalate`, а не догадку.

### 10.3. Профиль или разовый override

| Способ | Когда | Плюс | Минус |
|---|---|---|---|
| Профиль агента | постоянная роль | модель применяется детерминированно | нужен файл и синк |
| Разовый `model` в `task` | эксперимент или нетипичная подзадача | не требует файла | модель может не вспомнить override |
| Команда с `subtask: true` | ручной запуск | явный триггер | не подходит для автоматической декомпозиции |

Основной способ: профиль агента. Override используется для пилота и сравнительных прогонов.

### 10.4. Наблюдаемая модель

`model_requested` фиксируется всегда. `model_observed` заполняется, только если runtime отдает модель или есть подтверждение провайдера. Если модель неизвестна, ставится `unknown`, и подзадача не считается доказанно дешевой. Нельзя выдавать запрошенный alias за фактически использованную модель.

### 10.5. Политика данных

Пакет содержит `data_policy`. Если классификация данных не разрешает выбранного провайдера, запуск блокируется до отправки. Это касается и дешевого fallback. Секреты, ключи, `.env`, персональные данные и закрытые фрагменты в пакет не попадают.

## 11. Адаптеры по средам

### 11.1. Нейтральный манифест

```yaml
schema_version: 1

limits:
  max_fanout: 3
  max_depth: 1
  max_retries: 1
  max_wall_seconds: 180
  max_packet_bytes: 12000

roles:
  cheap-research:
    tier: cheap
    description: Ищет файлы, символы и вызовы, возвращает только факты с file:line.
    input_schema: packet-v1
    output_schema: report-v1
    tools: [read, grep, glob]
    deny: [edit, write, bash, task]
    budget: {max_tool_calls: 15, max_tokens: 12000, max_output_lines: 40}
    escalate_if: [ambiguity, missing_file, conflicting_sources, decision_required]

  cheap-summarize:
    tier: cheap
    description: Сжимает файл или модуль до фактов и ссылок.
    input_schema: packet-v1
    output_schema: report-v1
    tools: [read, grep]
    deny: [edit, write, bash, task]
    budget: {max_tool_calls: 8, max_tokens: 8000, max_output_lines: 30}

  cheap-test-runner:
    tier: cheap
    description: Запускает разрешенную команду и разбирает падение.
    input_schema: packet-v1
    output_schema: report-v1
    tools: [read, bash]
    deny: [edit, write, task]
    bash_allow: ["php -l *", "vendor/bin/codecept *", "git diff *", "git status *"]
    budget: {max_tool_calls: 10, max_tokens: 8000, max_output_lines: 40}

  mid-verifier:
    tier: mid
    description: Независимо проверяет claims и результаты тестов.
    input_schema: packet-v1
    output_schema: report-v1
    tools: [read, grep, glob, bash]
    deny: [edit, write]
    budget: {max_tool_calls: 20, max_tokens: 16000, max_output_lines: 50}

model_aliases:
  cheap:
    description: Дешевая модель с приемлемым tool calling, выбирается после discovery.
    per_environment:
      kilo: "<provider>/<cheap-model>"
      qoder: "efficient"
      opencode: "<provider>/<cheap-model>"
      qwen: "fast"
    qualification: "qualification://cheap-research/v1"

  mid:
    description: Средняя модель для проверки.
    per_environment:
      kilo: "<provider>/<mid-model>"
      qoder: "performance"
      opencode: "<provider>/<mid-model>"
      qwen: "<model-id>"
    qualification: "qualification://mid-verify/v1"

environment_bindings:
  kilo:
    status: supported
    agent_dir: ".kilo/agents"
    config: ".kilo/kilo.jsonc"
    depth_key: "subagent_depth"
  qoder:
    status: supported
    agent_dir: ".qoder/agents"
    skill_preload: true
  opencode:
    status: supported
    agent_dir: ".opencode/agents"
    config: "opencode.json"
    depth_key: "permission.task"
  qwen:
    status: supported
    agent_dir: ".qwen/agents"
    config: ".qwen/settings.json"
    depth_key: "model.maxSubagentDepth"
  codex:
    status: verify
  cursor:
    status: verify
  antigravity:
    status: unsupported
  dsh:
    status: unsupported
```

Конкретные ID моделей не выдумываются. Их заполняют после discovery командой клиента (`kilo models`, `opencode models`, `qwen models`, Qoder model picker) и проверяют на квалификации.

### 11.2. Kilo

Файл `.kilo/agents/cheap-research.md`:

```yaml
---
description: Ищет файлы, символы и вызовы. Возвращает факты с file:line, не меняет код.
mode: subagent
model: <provider>/<cheap-model>
steps: 20
hidden: false
permission:
  edit: deny
  write: deny
  task: deny
  bash:
    "*": deny
    "git diff *": allow
    "git status *": allow
---
Ты исполнитель роли cheap-research. Следуй скилу delegation-router.
Работай только в scope.read из пакета. Каждый факт подкрепляй file:line.
Не меняй файлы. При неоднозначности верни status=escalate.
```

Фрагмент генерируемого `.kilo/kilo.jsonc`:

```jsonc
{
  "subagent_depth": 1,
  "agent": {
    "explore": {
      "model": "<provider>/<cheap-model>"
    }
  }
}
```

Если включена глубина 2 для research:

```jsonc
{
  "subagent_depth": 2,
  "agent": {
    "cheap-research": {
      "mode": "subagent",
      "model": "<provider>/<cheap-model>",
      "permission": {
        "task": {
          "*": "deny",
          "cheap-research": "allow"
        }
      }
    }
  }
}
```

Проверка обязательна: на некоторых версиях сессия субагента получает deny на `task` независимо от конфигурации. Если тест не проходит, глубина остается 1.

### 11.3. Qoder

Файл `.qoder/agents/cheap-research.md`:

```yaml
---
name: cheap-research
description: Ищет файлы, символы и вызовы. Возвращает факты с file:line.
model: efficient
tools: Read, Grep, Glob
disallowedTools: Edit, Write, Bash, Agent
maxTurns: 15
skills:
  - delegation-worker
permissionMode: default
---
Ты исполнитель роли cheap-research. Работай только в scope.read.
Каждый факт подкрепляй file:line. При неоднозначности верни status=escalate.
```

`skills` предзагружает только контракт исполнителя, а не весь родительский скил. Для этого в `delegation-router/children/worker` создается отдельный дочерний скил `delegation-worker` с брифом и схемами отчета.

### 11.4. OpenCode

Файл `.opencode/agents/cheap-research.md`:

```yaml
---
description: Ищет файлы, символы и вызовы. Возвращает факты с file:line.
mode: subagent
model: <provider>/<cheap-model>
hidden: true
steps: 20
permission:
  edit: deny
  write: deny
  task: deny
  bash:
    "*": ask
    "git diff *": allow
    "git status *": allow
```

Если нужен запрет на вызов конкретных субагентов, он задается в `opencode.json` через `permission.task`. Корневой конфиг не перезаписывается генератором без явного флага: генератор создает отдельный файл агента и печатает предлагаемый фрагмент конфигурации.

### 11.5. Qwen Code

Файл `.qwen/agents/cheap-research.md`:

```yaml
---
name: cheap-research
description: Ищет файлы, символы и вызовы. Возвращает факты с file:line.
model: fast
tools:
  - read_file
  - grep_search
  - glob
disallowedTools:
  - write_file
  - edit_file
  - run_shell_command
maxTurns: 15
---
Ты исполнитель роли cheap-research. Работай только в scope.read.
Каждый факт подкрепляй file:line. При неоднозначности верни status=escalate.
```

Фрагмент `.qwen/settings.json`:

```json
{
  "model": {
    "maxSubagentDepth": 1
  },
  "agents": {
    "builtin": {
      "exploreModel": "fast"
    },
    "modelGrades": {
      "small": "fast",
      "high": "<model-id>"
    },
    "allowedGrades": ["small"]
  }
}
```

`model: fast` использует `fastModel`. Если `fastModel` не настроен, субагент наследует модель родителя, и это фиксируется в receipt как `model_observed=inherit`.

### 11.6. Codex, Cursor, Antigravity, DSH

| Среда | Действие | Условие включения |
|---|---|---|
| Codex | не генерировать файлы до contract test | официальная документация подтверждает subagents, синтаксис установленной версии неизвестен |
| Cursor | проверить формат агентов и precedence модели | аккаунт и версия могут менять выбор |
| Antigravity | статус `unsupported` | нет подтвержденного native-механизма |
| DSH | статус `unsupported` | fallback в основной сессии |

Fallback для неподдерживаемых сред: последовательная fresh-session с явно выбранной моделью, если клиент это позволяет. Если и это не подтверждено, скил работает только как протокол декомпозиции, без экономии на модели.

### 11.7. Что генерирует синк

| Среда | Файлы | Источник |
|---|---|---|
| Kilo | `.kilo/agents/{role}.md`, блок `agent` и `subagent_depth` в `.kilo/kilo.jsonc` | `roles.yaml` |
| Qoder | `.qoder/agents/{role}.md` | `roles.yaml` |
| OpenCode | `.opencode/agents/{role}.md` | `roles.yaml` |
| Qwen Code | `.qwen/agents/{role}.md`, блок `agents` и `model.maxSubagentDepth` в `.qwen/settings.json` | `roles.yaml` |
| Codex | ничего до contract test | `roles.yaml` статус `verify` |
| Antigravity, DSH | ничего | статус `unsupported` |

Каждый сгенерированный файл получает первую строку `generated from delegation-router/assets/roles.yaml ... do not edit`.

## 12. Синхронизация, зеркало и реестр

### 12.1. Генератор

Добавить в `generate-agent-configs.py` функцию `generate_agent_roles(root)`:

1. читает `.agents/skills/delegation-router/assets/roles.yaml`;
2. проверяет схему и обязательные поля;
3. удаляет только ранее сгенерированные файлы с маркером;
4. пишет native-файлы для сред со статусом `supported`;
5. сливает блоки `agent`, `subagent_depth`, `agents`, `model.maxSubagentDepth` в существующие конфиги;
6. не трогает локальные ключи пользователя;
7. печатает отчет: какие среды обновлены, какие пропущены и почему.

Генератор идемпотентен. Повторный запуск не меняет содержимое, если манифест не менялся.

### 12.2. Parity

`verify_parity.py` расширяется проверкой:

- каждый поддерживаемый агент существует в ожидаемой среде;
- содержимое совпадает с рендером из манифеста;
- конфиг содержит ожидаемую глубину и модель;
- среда со статусом `unsupported` не получает сгенерированных файлов;
- нет ручных правок в сгенерированных файлах.

### 12.3. Mirror

Harness mirror индексирует канон: `SKILL.md`, `roles.yaml`, схемы и скрипты. Сгенерированные файлы агентов не становятся вторым каноном. Они получают ребро `generated_from` к узлу `skill:delegation-router` и статус view. При расхождении mirror показывает `drift`, а не отдельный узел.

### 12.4. Реестр и документация

- README.md в `.agents/skills/task-router/children/delegation-router/`;
- запись в `component_registry.json`;
- строка в `.doc/harnes/index.md`, раздел `plan/`;
- строка в `.doc/harnes/state/02-skills.md`, если там перечисляются корневые скилы;
- ссылка в `AGENTS.md` на каталоги агентов, если они появляются в проекте.

## 16. Метрики пилота и откат

### 16.1. Метрики

| Метрика | Как считать | Цель |
|---|---|---|
| Токены на принятую задачу | сумма usage по receipt | минус 25 процентов |
| Стоимость на принятую задачу | токены на цену модели | минус 25 процентов |
| Первый проход | accepted без rework | не хуже baseline на 5 пунктов |
| Эскалации | доля `escalate` | не выше 20 процентов |
| Переделки | доля `rework` | не выше 15 процентов |
| Время | wall time | не хуже baseline на 20 процентов |
| Наблюдаемая модель | доля `unknown` | стремится к нулю |

### 16.2. Откат

Откат выполняется, если:

- экономии нет;
- первый проход упал больше чем на 5 пунктов;
- переделки выросли больше чем на 15 процентов;
- дешевая модель регулярно выдумывает факты;
- вложенность дает неконтролируемый расход.

Порядок отката:

1. выключить delegation-router в триггерах;
2. вернуть `subagent_depth: 1`;
3. удалить сгенерированные файлы агентов;
4. оставить скил как документацию протокола, но не использовать;
5. зафиксировать причину в истории изменений.

## 17. Риски

| Риск | Причина | Снижение |
|---|---|---|
| Дешевая модель выдумывает факты | слабое следование инструкции | evidence, spot-check, эскалация |
| Делегирование дороже | большой пакет и накладные расходы | `preflight.py`, порог, пилот |
| Неконтролируемая вложенность | глубина и рекурсия | `max_depth`, `permission.task`, тесты |
| Рассинхрон адаптеров | ручные правки и разные версии | единый манифест, parity, contract test |
| Секреты уходят дешевому провайдеру | широкий scope | `data_policy`, запрет секретов |
| Модель не та, что заявлена | runtime не отдает модель | `model_observed`, статус `unknown` |
| Потеря качества приемки | дешевый исполнитель решает смысл | запрет на решения, сильная приемка |
| Скил не срабатывает | слабое описание | явные триггеры в description |

## Известные проблемы и ограничения

### П-1: Имя файла не по правилу латиницы

- Симптом: файл называется `субагенты.md`, хотя `doc_rules.md` требует строчные латинские буквы, цифры и дефис.
- Причина: имя задано явным требованием пользователя.
- Ограничение: при переносе в другой проект имя следует заменить на `06-cheap-subagents.md`.
- Файлы: `.doc/harnes/plan/субагенты.md`

### П-2: Модель нельзя закрепить в SKILL.md

- Симптом: попытка добавить `model:` в frontmatter скила игнорируется клиентом.
- Причина: Agent Skills не содержит полей модели, а Kilo и OpenCode явно перечисляют допустимые поля.
- Решение: модель живет в профиле агента или команды.
- Файлы: `.agents/skills/delegation-router/SKILL.md`, `.kilo/agents/*.md`

### П-3: Вложенность в Kilo зависит от версии

- Симптом: субагент с разрешенным `task` не видит инструмент.
- Причина: известная проблема сессионного deny на `task` в части версий.
- Ограничение: глубина 1 по умолчанию; глубина 2 только после contract test.
- Файлы: `.kilo/kilo.jsonc`, `.kilo/agents/*.md`

### П-4: Antigravity и DSH без native-субагентов

- Симптом: нет файла агента и нет привязки модели.
- Причина: механизм не подтвержден официальной документацией.
- Решение: статус `unsupported` и fallback, без имитации поддержки.
- Файлы: `.agents/skills/delegation-router/assets/roles.yaml`

### П-5: Накладные расходы съедают экономию

- Симптом: маленькая подзадача стоит дороже, чем выполнить ее сразу.
- Причина: каждый субагент заново получает системный промпт, схемы и пакет.
- Решение: порог окупаемости и `preflight.py`.
- Файлы: `.agents/skills/delegation-router/scripts/preflight.py`

### П-6: Сгенерированные агенты расходятся с манифестом

- Симптом: после правки `roles.yaml` часть сред остается старой.
- Причина: синк не покрывает каталоги агентов.
- Решение: генератор, маркер `do not edit`, parity.
- Файлы: `generate-agent-configs.py`, `verify_parity.py`
