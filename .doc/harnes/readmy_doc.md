## 2. Как работает система (Цикл жизни)

### 2.1. Генерация карты (map-project.ps1)

Это **первый шаг** при начале работы с документацией.

```
powershell -ExecutionPolicy Bypass -File .agents/skills/documentation-router/children/project-doc/scripts/map-project.ps1
```

**Что делает:**
1. Через `git ls-files` получает список ВСЕХ файлов проекта (уважая `.gitignore`).
2. Подсчитывает файлы по типам (PHP, Vue, JS, CSS, SQL, TPL).
3. Через `git log --since=90d` находит самые активные файлы → `hot-files.txt`.
4. Вызывает `generate-doc-index.ps1` → сканирует `architecture/*.md` → `doc-index.tsv`.
5. Вызывает `generate-file-registry.ps1` → строит/обновляет Реестр-Очередь → `file-registry.tsv`.

**Ключевой момент:** При обновлении карты все существующие пометки (`status`, `first_indexed`, `doc_refs`) **сохраняются**. Новые файлы добавляются как `not_indexed`. Удалённые файлы получают статус `deleted`.

### 2.2. Реестр-Очередь (file-registry.tsv)

Это **сердце** всей системы. TSV-файл с колонками:

| Колонка | Назначение |
|---------|-----------|
| `path` | Относительный путь к файлу |
| `kind` | Тип: php, js, vue, css, sql, tpl, config, other |
| `status` | **not_indexed** (в очереди), **indexed** (задокументирован), **noise** (игнор), **deleted** (удалён из проекта), **manual** |
| `domain` | К какому бизнес-домену относится (payments, orders...) |
| `doc_refs` | В каких architecture/*.md файл упоминается |
| `first_indexed` | Дата первого покрытия документацией |
| `last_checked` | Дата последней проверки скриптом |
| `source` | Откуда появилась запись: map, merged |

**Как файл попадает в статус `indexed`:**
Если в каком-то документе `architecture/*.md` есть ссылка на файл в бектиках (например, `` `lib/Objects/Order/OrderService.php` ``), скрипт `generate-file-registry.ps1` автоматически поставит этому файлу `status = indexed` и запишет имя документа в `doc_refs`.

### 2.3. Пакетная индексация (Batching)

Главный процесс документирования. Работает порциями по 10 файлов:

```
Шаг 1: powershell .agents/skills/documentation-router/children/project-doc/scripts/get-indexing-batch.ps1 -Count 10
        → Выдаёт 10 файлов с status=not_indexed → current-batch.txt

Шаг 2: Агент читает код этих 10 файлов.

Шаг 3: Агент определяет бизнес-процесс (payments? orders? admin?).

Шаг 4: Агент дописывает architecture/[процесс].md, вставляя
        ссылки на файлы в бектиках: `admin/ident.php`

Шаг 5: powershell .agents/skills/documentation-router/children/project-doc/scripts/map-project.ps1
        → Карта видит бектики → status меняется на "indexed"

Шаг 6: Агент говорит: «Напишите "продолжи" для следующих 10.»
```

**Фильтрация шума:** Если агент видит плагин/библиотеку:
```
powershell .agents/skills/documentation-router/children/project-doc/scripts/mark-noise.ps1 -Paths "scripts/plugins/tinymce.js"
```
Файл навсегда исключается из очереди.

### 2.4. Index Gate

Перед созданием/дополнением `architecture/*.md` агент **обязан** проверить:

1. Прочитать `index.md` целиком.
2. Найти подходящий существующий документ (по имени, тегам, meta).
3. Если есть — **дописать**, НЕ создавать новый.
4. Если нет — спросить пользователя перед созданием.
5. После записи — **обновить index.md** в том же проходе.

**Пример ошибки:** Создать `order.md`, когда уже есть `orders.md`.

## 3. Справочник скриптов

### 3.1. _lib.ps1 — Общая библиотека

Зависимость **всех** скриптов. Ключевые функции:

| Функция | Что делает |
|---------|-----------|
| `Get-ProjectFiles` | Возвращает список файлов через `git ls-files`, фильтруя `.doc`, `vendor`, `node_modules` |
| `Get-DocMeta` | Парсит блок `<!-- meta -->` из markdown-файла |
| `Get-DocCodeRefs` | Извлекает все пути из бектиков в документе |
| `Get-ArchitectureDocs` | Возвращает список `architecture/*.md` (без `_map/`, без `_*.md`) |
| `Write-Utf8File` | Записывает файл в UTF-8 без BOM |
| `Test-StrictExcluded` | Проверяет, входит ли путь в список исключений |
| `Get-FileKind` | Определяет тип файла по расширению |
| `Test-GitAvailable` | Проверяет доступность git |

**Список исключённых директорий:**
`vendor`, `node_modules`, `cache`, `templates_c`, `dist`, `backups`, `uploads`, `img`, `imgp`, `pageImages`, `mailing`, `tests/cache`, `bin`, `obj`, `build`, `.doc`, `.agents`, `.cursor`

### 3.2. validate-docs.ps1 — Валидатор

Проверяет каждый `architecture/*.md` на:
- Наличие `<!-- meta -->` блока
- Обязательные поля: `type`, `status`, `updated`
- Обязательные секции: `## Суть`, `## Связи`, `## Известные проблемы и ограничения`, `## История изменений`
- Корректность ссылок (существует ли целевой файл)
- Формат дат (YYYY-MM-DD)

### 3.3. audit-docs.ps1 — Аудитор

Генерирует отчёт из 6 блоков:
1. Активные файлы без упоминания в документации (90 дней)
2. Документы не обновлявшиеся более 60 дней
3. Сломанные ссылки
4. Документы без meta-блока
5. Изолированные документы (никто не ссылается)
6. Топ-20 активных файлов за 30 дней

### 3.4. sync-docs.ps1 — Синхронизатор

Для каждого `architecture/*.md`:
1. Извлекает дату `updated` из meta.
2. Находит все файлы кода в бектиках.
3. Проверяет `git log`: менялись ли эти файлы после `updated`.
4. Выводит: какие документы устарели и какие файлы изменились.

Полный состав docscripts (включая build-tasks-index.ps1, find-related-tasks.ps1,
get-verify-batch.ps1, mark-verify-done.ps1, export-rebase-project.ps1,
_batch-ai-links.py и recovery-утилиты): см. [state/05-scripts.md](state/05-scripts.md).

## 4. Навыки AI-агентов (Skills)

### 4.1. project-doc — Документирование проекта

**Файл:** `.agents/skills/documentation-router/children/project-doc/SKILL.md`  
**Триггеры:** «задокументируй проект», «продолжи индексацию», «проанализируй карту»

**Режимы работы:**

| Команда | Режим |
|---------|-------|
| «задокументируй проект» | INIT — создание структуры с нуля |
| «проанализируй карту» | MAP — анализ вывода map-project.ps1 |

- Сортировка по директориям **снижает** вероятность конфликта.
- Полное решение (lock-файл) пока не реализовано.

**К-4: ✅ ИСПРАВЛЕНО — Поддержка -Skip**
- `get-indexing-batch.ps1` принимает `-Skip N` для параллельных агентов.

**К-5: ✅ ИСПРАВЛЕНО (2026-06-01) — Safety Gate против обнуления реестра**
- `generate-file-registry.ps1` abort'ится, если в директории найдено меньше 50% файлов от существующего реестра.
- Защищает от запуска вне корня git-репозитория.

### 12.2. Архитектурные проблемы 🟠

**А-1: Фрагментация вместо консолидации (историческая оценка аудита: 87 документов)**
- Актуально на 2026-09-26: 50 документов; консолидация mikro-docs выполнена (см. П-1).
- Но многие домены — это псевдодомены одного контроллера (например, `tariff-controller`, `tariff-parameters`, `tariff-subscription-fee` — это всё `tariffs`).
- **Решение:** Определить 15-20 каноничных бизнес-доменов и влить мелкие документы.

**А-2: Отсутствует стратегия группировки новых файлов**
- Когда агент берёт батч из 10 файлов, он может получить файлы из 5 разных доменов.
- Это заставляет его открывать и дописывать 5 разных документов за 1 батч — неоптимально.
- **Решение:** Сортировать Очередь по директориям (файлы из одной папки попадают в один батч). Тогда батч из `admin/lib/Objects/Item/` целиком попадёт в `item.md`.

**А-3: _lib.ps1 монолит на 303 строки (мёртвый код удалён, см. П-3)**
- Функции `Get-CleanupQueueFilePath`, `Get-SectionCatalogPath`, `Read-SectionCatalog`, `Get-SectionCatalogEntry`, `Get-SectionFiles` — мёртвый код от удалённых скриптов.
- **Решение:** Удалить 6 мёртвых функций (строки ~162-347), сэкономив ~180 строк.

### 12.3. Рекомендации по оптимизации 🟢

**Р-5: Группировка батча по директориям (КРИТИЧНО для качества)**
```
Сейчас (алфавитный порядок):
  admin/ident.php
  admin/lib/Objects/CallbackRequest/AdminCallbackRequestController.php
  admin/lib/Objects/Certifications/AdminCertificationsController.php
  ...
  → 10 файлов из 10 разных модулей → агент пишет в 10 документов

Предлагается (группировка по директории):
  lib/Objects/Order/OrderController.php
  lib/Objects/Order/OrderService.php
  lib/Objects/Order/OrderHelper.php
  lib/Objects/Order/Traits/OrderViewController.php
  ...
  → 10 файлов из 1 модуля → агент пишет в 1 документ (orders.md)
```
Это в 3-5 раз снижает количество переключений контекста агента.

**Р-6: Двухфазная индексация**
- **Фаза 1 (быстрая, ~1 час):** Агент просматривает ВСЕ файлы только по именам и путям, без чтения кода. Расставляет `domain` в реестре и помечает `noise`. Стоимость: ~500K токенов.
- **Фаза 2 (глубокая, ~8 часов):** Агент берёт батчи, отсортированные по домену, читает код и дописывает документы. Стоимость: ~7M токенов.

**Р-7: Увеличение размера батча до 20-30 для простых файлов**
- Файлы CSS, TPL, SQL, config — обычно тривиальны (средний LOC ~100).
- Для них можно выдавать батчи по 30 файлов вместо 10, ускорив процесс в 3 раза для ~790 файлов (CSS+TPL+SQL+config).

**Р-8: Кеширование doc_rules.md и SKILL.md**
- При каждой новой сессии агент перечитывает `doc_rules.md` (667 строк, ~8K токенов) и `SKILL.md` (632 строки, ~9K токенов).
- **Решение:** Создать компактную версию `doc_rules_compact.md` (~100 строк) только с правилами записи, без примеров. Экономия ~12K токенов × 264 батча = **~3.2M токенов**.
