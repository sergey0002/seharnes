Строгая проверка документов скриптов добавляет разделы из политики к встроенному обязательному набору, проверка README добавляет запрещённые шаблоны, а аудит MCP проверяет указанный в layout путь внутри скила. Встроенное расположение MCP-документа и проверка дублей остаются обязательными. Полная проверка согласованности ещё не подключена.

Каждый скил, каждый скрипт и каждый MCP-сервер имеет отдельный файл документации.
Скилы документируются кратко, скрипты подробно по аргументам, MCP подробно по
вызову, конфигурации, параметрам и работе с несколькими проектами. Документ задает
места, имена, обязательные разделы и проверки. Формат самого скила описан отдельно
в [skill-format.md](./skill-format.md), мета и общие правила записи в
[doc_rules.md](./doc_rules.md).

Установка нового компонента с проверкой всех сред и переноса:
[component-install.md](./component-install.md).

## 1. Три уровня документации

| Уровень | Где | Для кого | Объем |
|---|---|---|---|
| README скила | `.agents/skills/{name}/README.md` | человек и агент, выбирающий скил | без ссылок |
| Документ скрипта | `{skill}/docs/scripts/{файл скрипта}.md` | человек и агент, запускающий скрипт | без ограничения, все аргументы |
| Документ MCP | `{mcp-skill}/docs/mcp/{server}.md` | человек и агент, настраивающий сервер | без ограничения, все параметры |

Правила:

| ID | Правило | Уровень |
|---|---|---|
| D01 | У каждого скила есть README внутри папки | ОБЯЗАТЕЛЬНО |
| D02 | У каждого запускаемого скрипта есть документ в `docs/scripts/` скила-владельца | ОБЯЗАТЕЛЬНО |
| D03 | У каждого MCP-сервера есть отдельный файл в `.doc/harnes/mcp/` | ОБЯЗАТЕЛЬНО |
| D04 | Один компонент равен одному файлу | ОБЯЗАТЕЛЬНО |
| D05 | Файл документации не описывает два компонента | ЗАПРЕЩЕНО |
| D06 | Дублирование текста между файлами запрещено, только ссылки | ЗАПРЕЩЕНО |
| D07 | Документация компонента обновляется в том же проходе, что и компонент | ОБЯЗАТЕЛЬНО |
| D08 | Новый компонент добавляется в индекс своего раздела в том же проходе | ОБЯЗАТЕЛЬНО |
| D09 | Адаптерный скил DSH документируется в DSH-документации, README лежит в `.dsh/skills/{name}/` | ОБЯЗАТЕЛЬНО |
| D10 | Данные и состояние скила лежат в `.doc/skil_data/{skill}/`, не в папке скила | ОБЯЗАТЕЛЬНО |
| D11 | Родительский скил документирует всех детей и маршрутизацию в README | ОБЯЗАТЕЛЬНО |

## 2. Какие скрипты документируются

Область: первый исполняемый файл, который запускает агент, скил, синхронизация или
перенос. Расширения: `.py`, `.ps1`, `.sh`, `.js`, `.mjs`, `.php`, `.cmd`.

| Скрипт лежит | Владелец | Документ |
|---|---|---|
| `.agents/skills/{...}/scripts/{rel}` | ближайший скил с `SKILL.md` | `{skill}/docs/scripts/{rel}.md` |
| `.tools/scripts/{rel}` | `harness-core` | `harness-core/docs/scripts/tools/{rel}.md` |
| `.dsh/scripts/{rel}` | `environment-sync` | `environment-sync/docs/scripts/{rel}.md` |

Имя документа повторяет имя файла скрипта вместе с расширением:

```
{rel}.md
```

Примеры:

| Скрипт | Документ |
|---|---|
| `.agents/skills/task-router/children/testing-router/children/test-task/scripts/task-test.sh` | `.agents/skills/task-router/children/testing-router/children/test-task/docs/scripts/task-test.sh.md` |
| `.tools/scripts/multi-search.sh` | `.agents/skills/harness-router/children/harness-core/docs/scripts/tools/multi-search.sh.md` |
| `.tools/scripts/multi-search.ps1` | `.agents/skills/harness-router/children/harness-core/docs/scripts/tools/multi-search.ps1.md` |
| `.agents/skills/task-router/children/gototask/scripts/gototask.ps1` | `.agents/skills/task-router/children/gototask/docs/scripts/gototask.ps1.md` |

Коллизий нет: имя файла с расширением уникально внутри `scripts/`.

Не документируются: библиотеки без точки входа (`__init__.py`, `lib/`, `common/`),
сторонние библиотеки, `vendor/`, `node_modules/`, `__pycache__`, сгенерированные
файлы, минифицированный код, файлы данных без исполняемой логики.

Решение D2: документы нужны на все запускаемые скрипты, включая тесты скилов.
Скрипт считается запускаемым, если у него есть расширение `.sh`, `.ps1`, `.cmd`,
shebang, `__main__` или `argparse` для Python, `process.argv` для JS, `$argv` или
Symfony Console для PHP.

## 3. Документ скрипта

Обязательные разделы в этом порядке:

```markdown
# Скрипт: {путь от корня проекта}

<!-- meta
type: script
status: actual | draft | outdated | frozen
argv: passthrough | manual
updated: YYYY-MM-DD
related: [./README.md, ...]
tags: [harness, script, {тема}]
-->

## Суть
Что делает скрипт и зачем он нужен, 2-4 предложения.

## Когда запускать
Кто и в какой ситуации вызывает. Что будет, если запустить не вовремя.

## Аргументы
Таблица всех аргументов, включая устаревшие и скрытые.

## Коды выхода
Таблица: код, значение, что делает вызывающий.

## Что читает и что пишет
Входные файлы, каталоги, база, сеть. Выходные файлы и формат.

## Побочные эффекты
Что меняется вне выходных файлов: git, процессы, порты, кеш, блокировки.

## Окружение и зависимости
Переменные окружения, версии, внешние команды, права.

## Примеры
Минимум один рабочий вызов и один вызов с необязательными аргументами.

## Ограничения
Чего скрипт не делает, где ломается, что не проверяет.

## Связи
Кто вызывает, кто зависит, какие документы описывают результат.

## История изменений
- YYYY-MM-DD: что изменилось и почему
```

Поле `argv` необязательное. Оно говорит `doc_script.py --audit`, что аргументы
разбираются вручную или пробрасываются как есть: `passthrough` для обёрток
`exec "$@"`, `manual` для `sys.argv`, `$argv` и позиционных параметров. Без этого
поля аудит требует автоматического разбора и помечает обёртки как
`UNRELIABLE_PARSE`.

### 3.1 Аргументы

Таблица обязательна всегда. Если аргументов нет, пишется строка `Аргументов нет`
и отдельно перечисляются переменные окружения.

| Колонка | Что писать |
|---|---|
| Аргумент | точное имя, включая префикс `-` или `--` |
| Алиас | короткая форма или пусто |
| Тип | строка, число, путь, флаг, список |
| Обязателен | да или нет |
| По умолчанию | фактическое значение из кода |
| Что делает | одно предложение без догадок |

Правила:

1. Перечисляются все аргументы, включая устаревшие. Устаревший помечается
   `legacy` и указывает замену.
2. Значения по умолчанию берутся из кода, а не из памяти автора.
3. Если аргумент принимает перечисление, перечисляются все допустимые значения.
4. Если у скрипта есть подкоманды, для каждой подкоманды дается своя таблица.
5. Секреты не печатаются. Указываются только имена переменных окружения.

Пример:

| Аргумент | Алиас | Тип | Обязателен | По умолчанию | Что делает |
|---|---|---|---|---|---|
| `-TaskNumber` | нет | число | да | нет | номер задачи Jira |
| `-Action` | нет | строка | нет | `switch` | `switch`, `export-task`, `inspect` |
| `-ConfirmCreateBranch` | нет | флаг | нет | выключен | разрешает создать ветку |
| `-ConfirmMerge` | нет | флаг | нет | выключен | разрешает влить релиз |
| `-ConfirmDiscard` | нет | флаг | нет | выключен | разрешает отбросить локальные правки |

### 3.2 Коды выхода

Коды обязательны. Если скрипт всегда возвращает `0`, так и пишется. Для каждого
кода указывается действие вызывающей стороны: повторить, остановиться, спросить
пользователя.

### 3.3 Побочные эффекты

Отдельно фиксируются:

- запись в git, ветки, коммиты, push;
- запуск или остановка процессов и контейнеров;
- занятые порты;
- запись в базу;
- сетевые запросы и внешние API;
- кеш и блокировки;
- удаление или перезапись файлов.

## 4. README скила

Документация скила это его `README.md` в папке скила. README нужен для выбора и
понимания скила, а не для исполнения. Пошаговые инструкции в нем запрещены.

```markdown
# {name}

Назначение скила в 2-4 предложениях: что делает и когда нужен.

Короткое описание работы без флагов и команд, 3-6 предложений.
```

| ID | Правило | Уровень |
|---|---|---|
| K02 | README не пересказывает шаги `SKILL.md` | ЗАПРЕЩЕНО |
| K03 | README не содержит ссылок и раздела `Связи` | ЗАПРЕЩЕНО |
| K04 | README есть у корневого и у дочернего скила | ОБЯЗАТЕЛЬНО |
| K05 | Отдельная карточка скила в `.doc/harnes/skills/` не создается | ЗАПРЕЩЕНО |

Шаги, флаги и ограничения остаются в `SKILL.md`. README отвечает только на вопрос
"зачем этот скил".

## 5. Документ MCP

Правила ведения, шаблон и состав уже заданы в [mcp/README.md](./archive/mcp/README.md).
Документ активного сервера лежит в скиле этого сервера:
`{mcp-skill}/docs/mcp/{server}.md`. Если скила еще нет, документ временно
остается в `.doc/harnes/mcp/{server}.md`, а сервер считается незакрытым.
Здесь фиксируются обязательные требования, которых шаблон требует явно:

| ID | Правило | Уровень |
|---|---|---|
| C01 | Путь `{mcp-skill}/docs/mcp/{server}.md`, имя файла совпадает с ключом сервера в `.cursor/mcp.json` | ОБЯЗАТЕЛЬНО |
| C02 | Отключенный сервер тоже имеет файл с причиной отключения и заменой | ОБЯЗАТЕЛЬНО |
| C03 | Есть раздел `## Когда вызывать` с порядком относительно других MCP | ОБЯЗАТЕЛЬНО |
| C04 | Есть раздел `## Конфигурация` со всеми параметрами запуска | ОБЯЗАТЕЛЬНО |
| C05 | Есть раздел `## Текущие значения` с фактическими значениями из канона | ОБЯЗАТЕЛЬНО |
| C06 | Есть раздел `## Инструменты и аргументы` со всеми инструментами сервера | ОБЯЗАТЕЛЬНО |
| C07 | Есть раздел `## Несколько проектов` с моделью изоляции | ОБЯЗАТЕЛЬНО |
| C08 | Есть раздел `## Установка и перенос` | ОБЯЗАТЕЛЬНО |
| C09 | Есть раздел `## Проверка` с командами проверки сервера | ОБЯЗАТЕЛЬНО |
| C10 | Секреты не печатаются, только имена переменных окружения | ЗАПРЕЩЕНО |
| C11 | Устаревшее значение помечается и не удаляется без замены | СЛЕДУЕТ |

`## Текущие значения` это таблица фактических параметров: транспорт, URL или
команда, порт, служба, таймауты, лимиты, каталог данных, область индексации,
переменные окружения, статус. Значения сверяются с `.cursor/mcp.json`,
`.cursor/mcp.env` и системными юнитами.

`## Несколько проектов` отвечает на вопросы:

1. Один процесс на все проекты или отдельный на каждый.
2. Чем выбирается проект: параметр вызова, порт, каталог, переменная.
3. Какие данные общие, а какие принадлежат проекту.
4. Что происходит при ошибке выбора проекта.
5. Какие ограничения у параллельной работы.

`## Инструменты и аргументы` перечисляет все инструменты, которые дает сервер, с
аргументами и возвращаемым результатом. Список сверяется с исходником сервера, а
не с памятью.

## 6. Индексы и имена

| Индекс | Что содержит |
|---|---|
| `harness-core/docs/scripts/` | документы скриптов `.tools/scripts` и собственных скриптов `harness-core` |
| `{skill}/docs/scripts/` | документы скриптов этого скила |
| `{mcp-skill}/docs/mcp/` | документы MCP-серверов этого скила |
| `.doc/harnes/mcp/README.md` | состав серверов, статусы, шаблон, проверки |
| `harness_mirror.py` | узлы и связи компонентов, карта харнеса |

Центральных индексов `.doc/harnes/scripts/README.md` и `.doc/harnes/skills/README.md`
больше нет. Список документов вычисляется по путям скриптов и скилов.

Правила имен файлов:

- имя документа повторяет имя файла скрипта вместе с расширением;
- расширение `.md` добавляется в конец;
- имя отражает компонент, а не автора и не дату;
- переименование скрипта требует переименования документа и обновления ссылок.

## 7. Когда обновлять

| Событие | Что обновить |
|---|---|
| новый скил | README, `state/02-skills.md`, роутер родителя |
| новый скрипт | документ в `docs/scripts/` скила-владельца |
| новый MCP | документ сервера, `mcp/README.md`, `state/04-mcp.md`, правило `mcp-*` |
| новый аргумент скрипта | таблица аргументов и примеры |
| изменение конфигурации MCP | `## Конфигурация`, `## Текущие значения`, `state/04-mcp.md` |
| изменение правил или скилов | DSH-документация через JSONdoc, `DSH-RULES.md`, `mcp-names.md` при смене серверов |
| удаление компонента | статус `frozen`, причина, замена; файл не удаляется |
| изменение поведения скила | `SKILL.md`, README |

### 7.1. Данные скилов

Рабочие данные, результаты, кеши, индексы и venv скила не лежат в папке скила и не документируются как файлы компонента. Они хранятся в `.doc/skil_data/{skill}/`.

Статические шаблоны, схемы и примеры, которые нужны скилу для работы, остаются в `assets/` и описываются в `skill.json`. Правило структуры: `skill-format.md` S11.

## 8. Проверка

Проверки документации:

```bash
python3 .agents/skills/harness-router/children/improvement/scripts/validate_skills.py
python3 .agents/skills/harness-router/children/doc-script/scripts/doc_script.py --audit
python3 .agents/skills/harness-router/children/doc-skill/scripts/doc_skill.py --audit
python3 .agents/skills/harness-router/children/doc-mcp/scripts/doc_mcp.py --audit
```

`validate_skills.py` проверяет структуру скилов по [skill-format.md](./skill-format.md).
`doc_script.py --audit` проверяет:

1. у каждого запускаемого скрипта есть документ в `docs/scripts/` владельца;
2. документ не в статусе `draft`;
3. есть все обязательные разделы;
4. аргументы из кода перечислены в таблице;
5. нет шаблонных заглушек `Заполнить:` и `Определить при ревью`.

`doc_skill.py --audit` проверяет README каждого скила:

1. README существует;
2. не содержит ссылок и раздела `Связи`;
3. не пустой.

`doc_mcp.py --audit` проверяет размещение документов, наличие файлов скила,
дубли документов и локальные ссылки, включая `meta.related`.
В `harness_cli.py doctor` включены гейты `docs-scripts`, `docs-skills` и `docs-mcp`.
Код выхода: `0` нет ошибок, `1` есть ошибки, `2` неверные аргументы.

## Известные проблемы и ограничения

### П-1: Миграция документов скриптов не завершена

- Симптом: часть запускаемых скриптов не имеет документа в `docs/scripts/`;
  актуальный список и число вычисляет `doc_script.py --audit`.
- Причина: новый порядок введен 2026-11-07, старые 839 файлов созданы по другой схеме.
- Ограничение: гейт `docs-scripts` в `doctor` падает, пока документы не заполнены.
- Файлы: `.doc/harnes/scripts/`, `{skill}/docs/scripts/`

### П-2: Старые карточки скилов удалены

Каталоги `.doc/harnes/skills/` и `.doc/harnes/scripts/` удалены по решению
пользователя. Документация скила находится в его README, документы существующих
скриптов создаются внутри скила-владельца.

### П-3: Правила не имеют отдельного слоя документов

- Симптом: правила описаны одной таблицей в `state/03-rules.md`; состав меняется вместе с каноном.
- Причина: `component-docs.md` задает формат только для скилов, скриптов и MCP.
- Ограничение: подробное описание правила живет в самом `.mdc` и в state-документе.
- Файлы: `.cursor/rules/`, `.doc/harnes/state/03-rules.md`

### П-4: Все включенные MCP имеют скил

Документы всех 17 включенных серверов размещены в `{skill}/docs/mcp/{server}.md`.
У каждого владельца есть README и манифест. Четыре отключенных сервера сохраняют
документы в `.doc/harnes/mcp/`. Смысловая проверка эксплуатационных утверждений
выполняется отдельно от структурного аудита.
