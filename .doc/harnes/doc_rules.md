## Суть

Единый стандарт для всех, кто пишет и читает документацию проекта -
люди, AI-агенты, скилы Cursor, Claude, Codex и другие инструменты.

Документация живёт в `.doc/architecture/` (общая архитектура) и `.doc/tasks/{N}/` (документация задач).
Точка входа в архитектуру - `.doc/architecture/index.md`.
**Этот файл (`.doc/harnes/doc_rules.md`) читается первым при любой работе с документацией.**

Документация не входит в харнес. Карта харнеса индексирует только `.cursor/` и зеркала,
связи на `.doc/` из скилов и правил отбрасываются, скилы и правила работают без
документации. Границы: [state/01-canon-envs.md](./state/01-canon-envs.md), раздел
"Границы харнеса".

## Принципы

### 1. Простота важнее полноты
Документ, который читают, лучше идеального, которого избегают.
- Один документ - одна тема
- Минимум необходимый для понимания
- Вырос больше двух экранов - выноси часть в отдельный файл и ставь ссылку

### 2. Единственный источник правды
Каждый факт живёт в одном месте.
Все остальные места ссылаются на него.
Дублирование запрещено - только ссылки.

### 3. Ссылки вместо копирования
Если нужно сослаться - ставь ссылку на конкретную секцию.
Если ссылка неудобна - значит, структура документов неверная.

### 4. Близость к коду
Документация описывает реальный код, не желаемый.
Код изменился - документация устарела.
Устаревшее помечай явно, не удаляй.

### 5. Контекст для агента = контекст для человека
Пиши так, чтобы AI-агент, получив только этот файл,
понял, что делать, без дополнительных вопросов.
Конкретные пути, конкретные имена, конкретные примеры.
Никаких "файл контроллера" - только `app/Controllers/PaymentController.php:145`.

### 6. Самодостаточный тезис
Каждый тезис понятен без перечитывания соседних секций.
Называй объект, место и результат прямо в тезисе.
Заменяй "это", "он", "там", "данный" на конкретное имя.
Сжимай смысл, а не выбрасывай факты.
Формула и проверки: [text-style](../../.cursor/rules/text-style.mdc).

### MCP-серверы: один сервер, один файл

Подробности по MCP-серверам лежат в `.doc/harnes/mcp/`, один файл на сервер.
Имя файла совпадает с ключом сервера в `.cursor/mcp.json`. Общая картина,
порядок в задачах и адаптации сред остаются в `state/04-mcp.md`; там таблица
состава и ссылки, без дублирования деталей. Новый сервер добавляется в канон,
в таблицы `index.md` и `state/04-mcp.md`, и отдельным файлом по шаблону
`mcp/README.md`. Отключенный сервер тоже получает файл: причина отключения и
замена должны быть зафиксированы.

### JSONdoc: `doc.md` - представление, а не источник

`doc.md` генерируется из `task.json` (`jsondoc.py render`). Первая строка содержит
маркер `generated from task:N ... do not edit`. Правило простое:

- знания задачи меняются через `task.json` (`jsondoc.py apply`), не руками в `doc.md`;
- после правки модели выполняется `jsondoc.py render`, он пересобирает `doc.md`;
- ручная правка `doc.md` даст `VIEW_CONFLICT` при следующем рендере и будет потеряна;
- если `task.json` у задачи нет, `doc.md` остается живым файлом и правится по общим
  правилам ниже.

Порядок чтения задачи: `task.md` -> `task.json --keys` (или `doc.md`, если JSON нет)
-> diff-артефакты. Не читать `_jsondoc/` руками, только через `jsondoc.py get/batch`.

Исключение из "не править": секция обратных ссылок и `## Известные проблемы`
допустимы в модели и попадают в `doc.md` через рендер, а не прямой записью.

Имена файлов:
- только строчные буквы
- слова через дефис
- без пробелов и спецсимволов
- отражают содержание: `payment-flow.md`, `auth-service.md`

### Фактический формат CopyTrust

Текущий `.doc/architecture/index.md` в проекте Target использует **тематические блоки с таблицами**
(`| Документ | Описание |`), а не шаблон "## Навигация + ## Статус документации" выше.
При обновлении оглавления **сохраняй существующую структуру файла** - не переписывай index под шаблон без команды.

`index.md` - **единственный реестр** architecture-документов. Любой новый или дополненный `.md`
должен быть отражён в index в том же проходе (см. "Index Gate" ниже).

## Index Gate - перед созданием architecture/*.md

**Обязательно** перед созданием нового файла в `.doc/architecture/` (индексация, MAP, SECTION):

```
1. Прочитать .doc/architecture/index.md целиком
2. Просмотреть список существующих *.md в .doc/architecture/ (кроме _*.md и _map/)
3. Найти наиболее подходящий существующий документ по:
   - совпадению имени (order ↔ orders, payment ↔ payments)
   - теме в таблицах index.md
   - tags: и related: в meta существующих docs
   - заголовку H1 и секции ## Суть
4. Если подходящий документ найден → ДОПИСАТЬ в него, НЕ создавать новый файл
5. Если не найден → предложить имя нового файла и AskQuestion: создать?
6. После создания или существенного дополнения → ОБЯЗАТЕЛЬНО обновить index.md
```

Пример: паттерн `order` → сначала проверить `orders.md` в index; не создавать `order.md` параллельно.

**Куда добавлять строку в index.md CopyTrust:**

| Тема | Блок index.md |
|------|----------------|
| architecture, auth, data_model, SQL | `## 1. Архитектура и основы` |
| routes, admin, controllers | `## 2. Маршруты и контроллеры` |
| frontend, vue, page_types | `## 3. Фронтенд` |
| orders, payments, tariffs, deposition | `## 4. Бизнес-процессы` |
| s3, cron, email, cicd | `## 5. Инфраструктура и интеграции` |

Если блок неочевиден - спроси пользователя через AskQuestion.

## Правила ссылок

### Форматы ссылок

```markdown
# Между файлами внутри .doc/architecture/
[Название секции](./другой-файл.md)
[Конкретная секция](./другой-файл.md#якорь-секции)

# Из tasks/{N}/doc.md на архитектуру
[Название секции](../../architecture/файл.md#якорь)

# Из tasks/{N}/doc.md на правила
[Правила документации](./doc_rules.md)

# Из архитектуры на файлы проекта - только код-блок, не ссылка
`app/Services/PaymentService.php`
`app/Services/PaymentService.php:145`
```

### Запрещено

```
[[wikilinks]]              ← только Obsidian, ломает AI-агентов
/абсолютные/пути/          ← не работают при переносе
../../../../три и больше   ← слишком глубоко, пересмотри структуру
```

### Как строить якоря

Якорь = заголовок в нижнем регистре, пробелы → дефис, спецсимволы убираются.

```
## Как устроено          → #как-устроено
## API / Интерфейс       → #api--интерфейс
## Проблемы и решения    → #проблемы-и-решения
## TODO                  → #todo
```

Проверяй якорь перед вставкой - сломанная ссылка хуже отсутствующей.

### Правило обратных ссылок

Если документ A ссылается на документ B -
в секции `## Связи` документа B должна быть ссылка на A.

Это позволяет:
- Obsidian строить граф связей
- AI-агентам находить полный контекст
- Людям понимать, что зависит от этого документа

### Правило ссылок из задач

Когда `doc.md` задачи ссылается на архитектурный документ или агент правит
архитектуру в рамках **task-doc** (Режим B) - в секции `## Известные проблемы и ограничения`
архитектурного документа **обязательно** добавь обратную ссылку на задачу:

- `[#{N} - task.md](../tasks/{N}/task.md)`
- `[doc.md](../tasks/{N}/doc.md)` - если файл существует

Формат пункта "П-N" - см. `.agents/skills/documentation-router/children/task-doc/SKILL.md`, шаг B3.3.
Подтверждение пользователя **не требуется** для обновления архитектуры и обратных ссылок
в workflow task-doc.

### Doc-verify: сверка architecture ↔ код ↔ задачи

Пакетный цикл (1 шаг = 1 `architecture/*.md`): скил
[`.agents/skills/documentation-router/children/doc-verify/SKILL.md`](../../.agents/skills/documentation-router/children/doc-verify/SKILL.md)
(отдельного reference.md в скиле нет).

Индекс задач для поиска: `.doc/tasks/index.md` в проекте Target.  
Пересборка: скрипт [`.agents/skills/documentation-router/children/project-doc/scripts/build-tasks-index.ps1`](../../.agents/skills/documentation-router/children/project-doc/scripts/build-tasks-index.ps1)

```powershell
powershell -ExecutionPolicy Bypass -File .agents/skills/documentation-router/children/project-doc/scripts/build-tasks-index.ps1 -AlsoTsv
```

В рамках **doc-verify** агент:

1. **MCP Gate:** codebase-memory-mcp → codegraph → serena (см. скил), затем точечно правит секции по расхождениям с кодом
2. Чинит `## Связи` / `related:` и **обратные** ссылки arch↔arch (в т.ч. из `trace_path`)
3. Ищет связанные задачи (`find-related-tasks.ps1`) и проставляет:
   - arch → task: П-N + ссылки `../tasks/{N}/task.md` (+ `doc.md` если есть)
   - task → arch: зеркало в **существующем** `tasks/{N}/doc.md` (не создавать doc.md)
4. Доводит Obsidian-совместимость: md-ссылки (не `[[wikilinks]]`), tags в meta и хвост `#tags`

Опционально в arch: секция `## Связанные задачи` (только список ссылок, без копипаста П-N).

### Obsidian и граф

- В тексте документов - **только** markdown-ссылки `[текст](./file.md#якорь)`.
  `[[wikilinks]]` запрещены (ломают агентов и скрипты).
- Теги: meta `tags:` для агентов + хвост файла `#tag` для Obsidian.
- Сейчас `.obsidian` лежит в `.doc/architecture/` - папка `tasks/` **вне vault**,
  поэтому ссылки `../tasks/{N}/` работают как файлы, но слабо видны в графе.
  **Рекомендация:** открывать vault от корня `.doc/`, чтобы `architecture/` и `tasks/`
  были одним графом. Миграцию vault делать отдельной командой, не в каждом батче сверки.

### Блок "AI: когда читать" (обязателен в hub-доках)

В начале `index.md`, `architecture.md`, `data_model.md` и **каждого** тематического
`architecture/*.md` после `## Суть` добавляй блок:

```markdown
> **AI:** читай этот doc если …  
> **Сначала:** …  
> **Не читай целиком:** … (для монолитов frontend/architecture)  
> **См. также:** [файл.md](./файл.md)
```

`index.md` дополнительно содержит **§ Дерево решений** - маршрут по типу задачи.

### Factual audit (сверка с кодом, не только git-даты)

`sync-docs.ps1` ловит изменения **после** `updated:` в meta. Отдельно проверяй:

| Проверка | Источник истины |
|----------|-----------------|
| Имена таблиц `ct_*` | `base_structure.sql`, `mysql describe_table` |
| Пути JS/Vue/PHP | glob / `file-registry.tsv` |
| "Отдельная таблица" vs флаг | код repository/DataManager |
| Дубли doc-ов | `partner.md` канон для referral; `base-framework.md` для ORM |

При правке по factual audit: `<!-- updated: YYYY-MM-DD, factual-audit -->`, запись в `## История изменений`.

**task-doc B3** и **doc-verify** выполняют factual audit **автоматически**, без AskQuestion:
это сверка уже написанного.

**project-doc SYNC/SECTION** спрашивает иначе: подтверждение нужно не на факт сверки, а на
**область** работы (какие файлы перезаписываем). Проверка идет сама, а список файлов
согласуется. Правило `project-doc` описывает тот же порядок, расхождения нет.

**Пакет AI-блоков:** `.agents/skills/documentation-router/children/project-doc/scripts/_batch-ai-links.py` - словарь `AI_HINTS`, запуск из корня репо.

## Codebase-memory-mcp при индексации

При документировании разделов (`project-doc` SECTION/MAP) агент **обязан** использовать
MCP `codebase-memory-mcp`, если сервер доступен в Cursor.

CBM строит **граф кода** (классы, routes, вызовы). Он **не заменяет** Index Gate по `index.md`
и **не пишет** в markdown сам - результаты переносятся в `.doc/architecture/*.md`.

### Обязательный минимум на раздел

```
1. list_projects → index_status (index_repository при отсутствии индекса)
2. search_graph по паттерну раздела
3. trace_path (calls + cross_service для UI-модулей) - до 3 ключевых символов
4. Заполнить ## Связи ссылками на смежные architecture/*.md
5. related: в meta - имена связанных arch-файлов
```

### Что переносить из CBM в документ

| CBM | Секция doc |
|-----|------------|
| Route → Controller → Service | `## Как устроено` |
| cross_service / semantic пересечения | `## Связи` |
| high inbound / shared component | `## Известные проблемы` |
| qualified names, file paths | backticks в тексте |

### Запрещено

```
✗ manage_adr CBM вместо .doc/architecture/
✗ Пропускать CBM при зелёном MCP без записи в отчёте
✗ Mass Read репозитория там, где достаточно search_graph / get_code_snippet
```

Подробный workflow: [`.agents/skills/documentation-router/children/project-doc/SKILL.md`](../../.agents/skills/documentation-router/children/project-doc/SKILL.md) → S4.6, раздел "CBM при индексации".  
Инструкция MCP: [правило mcp-codebase-memory](../../.cursor/rules/mcp/codebase-memory-mcp.mdc) и [документация сервера](../../.agents/skills/codebase-memory-mcp/docs/mcp/codebase-memory-mcp.md).  
Связи после CBM: [правило codegraph](../../.cursor/rules/mcp/codegraph.mdc) и [документация сервера](../../.agents/skills/codegraph/SKILL.md).
Документацию искать через jdocmunch ([jdocmunch.md](../../.agents/skills/jdocmunch/docs/mcp/jdocmunch.md));
`multi-search.sh` / `rg` только для литералов и не-Markdown.

## MCP-маршрут для документации и задач

Чтобы агент использовал MCP последовательно и экономно, придерживайся маршрута ниже.

| MCP | Когда использовать | Что даёт для `.doc/` |
|-----|---------------------|----------------------|
| `jdocmunch` | Поиск и чтение документации, навигация по секциям | Готовый индекс `.doc/architecture`, `.doc/harnes`, `.doc/tasks`, `.doc/web`; секции, оглавление, связи |
| `codebase-memory-mcp` | Индексация разделов, Reuse/Impact проверка в задачах | Граф кода: routes, классы, вызовы, cross-service связи |
| `codegraph` | Сразу после CBM: исходник, связи и blast radius | `codegraph_explore`, `codegraph_callers`, `codegraph_impact` |
| `serena` | Точечная проверка символов и references | Подтверждение переиспользования и blast radius перед фиксацией решения |
| `mysql` | Документация домена данных (`data_model`, `payments`, `tariffs`) | Фактическая схема таблиц и поля (не выдумывать) |
| `context7` | Только внешние библиотеки и framework API | Актуальная внешняя документация без подмены внутренней архитектуры |
| `phpstan-mcp` / `semgrep` | После существенных PHP/security правок | Риски и регрессии, которые стоит отразить в "Известных проблемах" |
| `playwright` | Когда задача меняет UI/flow | Быстрая проверка пользовательского сценария, о котором пишется в doc |
| `git` | Анализ изменений и актуальности | Какие файлы/модули реально затронуты и должны попасть в doc |
| `xdebug` | Только если баг подтверждается лишь в runtime | Причина расхождения docs vs runtime-поведения |

### Минимальный MCP-checklist

```
Индексация (project-doc SECTION):
  1) CBM (обязательно при доступном MCP)
  2) codegraph - explore / callers / impact по паттерну раздела (после CBM)
  3) Serena при неочевидных references
  4) mysql для DB-секций

Документирование задачи (task-doc):
  1) документация: jdocmunch search_sections → get_section_context
  2) код: CBM → codegraph (если зелёный) → Serena для Reuse/Impact Gate
  3) multi-search.sh только для точных литералов и не-Markdown
  2) mysql если задача меняет данные/таблицы
  3) при риске регрессий: phpstan/semgrep, по необходимости playwright
  4) после записи doc.md / diff.files - B4.5:
     [build-tasks-index.ps1](../../.agents/skills/documentation-router/children/project-doc/scripts/build-tasks-index.ps1) `-AlsoTsv`
     → `.doc/tasks/index.md` + `_map/file-to-tasks.tsv`
```

Ограничения:
- Не вызывать все MCP "на всякий случай" - только по типу задачи.
- Не использовать `manage_adr` CBM как второй источник правды - решения живут в `.doc/`.
- Не вызывать MCP `jira-task` вручную в task-flow: использовать `gototask`/`task-diff` (экспорт через `.agents/skills/task-router/children/jira/scripts/server.php`).

## Правила для AI-агентов

### Поиск и чтение документации

Любое упоминание документации, панели, задачи, architecture, harnes, отчёта
или просьба "подтяни контекст" начинается с MCP `jdocmunch`, индекс
`local/testdeploy-arch`, вызов `search_sections`. Это гейт, а не рекомендация.
Правило: [`.cursor/rules/mcp/jdocmunch.mdc`](../../.cursor/rules/mcp/jdocmunch.mdc).
Полное описание сервера и корпуса: [jdocmunch.md](../../.agents/skills/jdocmunch/docs/mcp/jdocmunch.md).

Read, Grep и `multi-search.sh` применяются только после пустого результата MCP
или для известного пути, точного литерала, regex и файлов вне индекса
(не-Markdown и сгенерированные каталоги). URL, порт и номер задачи не отменяют
semantic-поиск: сначала `search_sections`, затем точный литерал в найденном
файле. Начинать поиск по документации с обхода `.doc` запрещено.

### Порядок чтения (обязательный)

```
1. .doc/harnes/doc_rules.md             ← этот файл, всегда первым
2. jdocmunch search_sections или .doc/architecture/index.md  ← навигация
3. Только релевантные задаче файлы по ссылкам из index.md
4. Конкретные секции, не файл целиком, если не нужен весь
```

**Запрещено сканировать все файлы подряд без навигации через `index.md` или jdocmunch.**

### Порядок записи (обязательный)

```
1. Прочитай файл целиком перед правкой
2. Правь только конкретную секцию
3. Пометь изменённую секцию:
   <!-- updated: YYYY-MM-DD, task: {TASK_ID} -->
4. Обнови поле updated: в блоке meta
5. Добавь запись в ## История изменений
6. Проверь, нужно ли обновить обратные ссылки
7. Запись в architecture/*:
   - **task-doc (Режим B):** обновляй сразу при расхождении с кодом, без AskQuestion
   - **doc-verify:** точечные правки при расхождениях в очереди сверки, без AskQuestion
   - **создание нового architecture/*.md:** Index Gate + AskQuestion (см. ниже)
   - **прочие правки вне task-doc / doc-verify:** спроси перед записью, если нет явной команды пользователя
```

Служебные комментарии `<!-- meta ... -->`, `<!-- generated ... -->`, `<!-- updated: ... -->`,
`<!-- task-dir ... -->` и `<!-- project-root ... -->` разрешены. Другие HTML-комментарии
в тексте секций запрещены: `check-doc-text.py` считает их ошибкой.

### Что запрещено агентам

```
✗ Перезаписывать файл целиком
✗ Удалять секции без явной команды пользователя
✗ Менять структуру файла без явной команды
✗ Писать в index.md без явной команды пользователя
  ИСКЛЮЧЕНИЯ - index.md обновлять ОБЯЗАТЕЛЬНО:
  • режим индексации project-doc (INIT, MAP, SECTION)
  • создание или merge architecture/*.md в рамках индексации
  • команда "обнови оглавление" / "добавь в index"
✗ Создавать новый architecture/*.md без Index Gate (см. выше)
✗ Завершать SECTION индексации без записи документа в index.md
✗ Копировать текст из одного документа в другой - только ссылки
✗ Использовать [[wikilinks]] формат
✗ Использовать абсолютные пути
✗ Обновлять архитектурные файлы без явной команды пользователя
  ИСКЛЮЧЕНИЯ - architecture/* обновлять ОБЯЗАТЕЛЬНО без AskQuestion:
  • **task-doc** (Режим B): аудит B3 + обратные ссылки на task.md и doc.md
  • **index.md при индексации project-doc** - см. выше
  • **doc-verify** (сверка docs↔код): точечные правки секций при расхождениях
    с кодом в рамках очереди `verify-registry.tsv` (команда "сверка документации"
    / "продолжи сверку"). Не перезаписывать файл целиком.
```

### Когда найдено расхождение с кодом

**В workflow task-doc (Режим B):** не спрашивай - обнови секцию, историю изменений
и обратную ссылку на задачу (шаг B3). В отчёте перечисли что изменил.

**В workflow doc-verify** (очередь сверки architecture↔код): не спрашивай -
обнови секцию, meta `updated`, `## История изменений` (`doc-verify`), отметь
в `mark-verify-done.ps1`. В отчёте батча перечисли что изменил.

**Вне task-doc и вне doc-verify** зафиксируй и спроси:

```
⚠️ Найдено расхождение в [файл.md#секция]:
   Документация: "лимит 1000 записей"
   В коде:       "лимит 500" (app/Services/PaymentService.php:234)

   Обновить документацию? (да / нет / пропустить)
```

### Когда нужно создать новый файл архитектуры

**Сначала Index Gate** - проверь index.md и существующие docs (см. раздел "Index Gate").

Если подходящий документ уже есть - допиши секцию, обнови `index.md` (описание строки при необходимости).

Если нового файла действительно нет - спроси перед созданием:

```
📄 Index Gate: подходящих документов не найдено.

Предлагаю создать:
   .doc/architecture/[имя-файла].md
   Тема: [описание]
   Блок index.md: [например "4. Бизнес-процессы"]
   Связи с существующими: [список]

   Создать? (да / нет)
```

После подтверждения - **в том же проходе** добавь строку в `index.md` (в нужный тематический блок).
Не завершай индексацию раздела, пока документ не отражён в index.

## Чеклист перед коммитом изменений в документацию

```
□ Все ссылки ведут на существующие файлы и якоря
□ Обратные ссылки проставлены в связанных документах
□ Блок meta обновлён (updated, status)
□ Запись в "История изменений" добавлена
□ Index Gate пройден: не создан дубль рядом с существующим doc (order vs orders)
□ index.md отражает новый или дополненный файл (обязательно при индексации)
□ Строка добавлена в правильный тематический блок index.md
□ Теги добавлены в конец файла
□ Новый тег добавлен в таблицу тегов index.md
□ Нет скопированного текста - только ссылки
□ Нет абсолютных путей
□ Нет [[wikilinks]]
```
