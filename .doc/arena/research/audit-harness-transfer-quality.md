## Суть

Аудит того, **как качественно выполнен перенос харнеса из проекта CopyTrust в
эталон `seharnes`** с помощью движка `export_kit.py` / `harness_transfer.py`. Перенос
по сути выполнен: харнес перенесён, но в repo осталось «хвостов» CopyTrust (512
упоминаний в 155 файлах), и незавершена настройка Target. Документ разбирает
качество **по каждому режиму** (`install`/`update`/`mirror`) и **по каждой команде**
движка, оценивает фактическое состояние, причины остатков и даёт вердикт. Код не
менялся — это纯 аудит.

> **AI:** читай этот файл, чтобы понять качество выполненного переноса и оставшиеся
> риски. Планы по фиксам и повторному переносу требуют отдельного согласования.

## 3. Аудит по каждому режиму

Режимы определены в `lib/transfer_modes.py`. Все три используют **один** план/
аппров/аплай pipeline и отличаются только разрешением предложений.

### 3.1 Режим `install` — первый перенос в пустой проект

**Семантика (код):**
- Копирует kit в проект без харнеса.
- Существующий файл **никогда не перезаписывается**: если в Target есть файл и он
  отличается от incoming → `KEEP` (остаётся локальным), пишется предупреждение
  «existing file kept as local».
- То, что в Target, но не в Source и не защищено/не generated → сохраняется
  (`preserved`).

**Качество реализации:**
- ✅ Корректно удерживает локальные файлы Target (не ломает существующий контекст).
- ✅ Отчётно сигнализирует о каждом «kept as local».
- ⚠️ Не перезапись может оставить устаревшие kit-файлы в Target (install не
  обновляет). Для первого переноса в пустой Target это адекватно.

**Применимость к данному переносу:** не использовался (это был `update`). Для
первого входа в чистую папку режим корректен и безопасен.

**Оценка:** **хорошо** для своей задачи; не умеет обновлять, что и не требуется.

### 3.2 Режим `update` — обновление kit поверх установленного харнеса

**Семантика (код):**
- `target is not None and incoming is None` → `KEEP` (файл остаётся, он не в Source).
- Файлы с `requires_review` (существуют и отличаются) → `TAKE_INCOMING` (берётся
  Source — приоритет Source).
- Файлы, которых нет в Target → добавляются.
- **Не удаляет** файлы kit, которых нет в Source (это ключевое отличие от mirror).

**Качество реализации:**
- ✅ Приоритет Source соблюдён: отличающиеся kit-файлы заменяются на Source.
- ✅ Файлы, отсутствующие в Source, сохраняются (не ждёт до mirror).
- ✅ Имептентность подтверждена в опорном прогоне (`added 0, overwritten 0`).
- ⚠️ **Не удаляет мусор**: устаревшие kit-файлы (например, удалённый в Source
  PS1-движок, скил `login-as-user`) остаются в Target и требуют **ручного удаления**
  (в опорном прогоне удалили 11 файлов вручную). Это естественный ограничение
  `update`.
- ⚠️ Де-брендинг **не входит** в режим: engine копирует содержимое как есть.

**Применимость к данному переносу:** **этот режим использовался**. Опорный прогон
дал `added 62, overwritten 132, same 1373, preserved 31` — цифры согласуются с
семантикой (132 перезаписано = отличившиеся kit-файлы; 31 preserved = вне kit).

**Оценка:** **удовлетворительно для своего назначения**, но требует последующей
чистки ручных удалений и отдельного де-брендинга (см. §6).

### 3.3 Режим `mirror` — точная копия (clean install)

**Семантика (код):**
- `absence(plan)` → все Target-файлы без Source-counterpart становятся `DELETE`.
- После backup удаляет kit-файлы, которых нет в Source.
- Защищённые и `--keep`-пути не удаляются.

**Качество реализации:**
- ✅ Отрицает kit до точного состояния Source.
- ✅ `--keep` и защищённые пути соблюдаются.
- ✅ Backup перед удалением.

**Применимость к данному переносу:** **не использовался**. Канон предупреждает:
mirror применять только после ревью списка удалений, так как он затрагивает локальные
файлы эталона. Для опорного переноса chosen `update` — правильный выбор, потому что
mirror могла бы удалить локальные эталонные файлы (например, панель `web2`, локальные
адаптеры), которые не входят в kit.

**Оценка:** технически корректен, но **опасен** для эталона без строгой ревью
удалений; его неиспользование в данном переносе — правильное решение.

### Сводка по режимам

| Режим | Использован | Качество | Примечание |
|---|---|---|---|
| `install` | нет | хорошо | безопасен для чистого Target |
| `update` | **да** | удовлетворительно | приоритет Source + иммептентность; не чистит мусор, не де-брендит |
| `mirror` | нет | корректен, но рискован | правильно не применён к эталоне |

## 4. Аудит по каждой команде движка

### 4.1 `inventory` — инвентарь
- **Роль в переносе:** снимок Source/Target (SHA-256, режим, защищённые пути).
- **Качество:** корректно работает (runtime-прогон: 1142 файла, `secret_scan` passed).
- **Оценка:** **хорошо**.

### 4.2 `fetch` — получение ref
- **Роль:** получение одной ref в локальное bare-хранилище.
- **Качество:** guard по схемам, `--allow-local`, отклонение пароля в URL. В данном
  переносе не использовался (Source — локальная папка).
- **Оценка:** **хорошо** (но в `plan`/`inventory` есть ложный check «fetch not
  implemented» — см. приложение [audit-harness-transfer-cli.md], Н-2).

### 4.3 `plan` — read-only предпросмотр
- **Роль:** построение предпросмотра с решениями по конфликтам.
- **Качество:** fail-closed: без baseline (receipt/base-commit) каждый файл →
  `needs_decision` (runtime-прогон: 334/334). Guard «source and target roots must not
  overlap» срабатывает корректно.
- **Оценка:** **хорошо**, но для больших kit требует baseline, иначе много решений.

### 4.4 `verify` — сверка с receipt
- **Роль:** сравнение Target с receipt.
- **Качество:** без `.doc/web/state/transfer/receipt.json` → корректный preflight.
  Receipt gitignored → в эталоне его нет, поэтому verify в чистом clone невозможен
  до повторного применения.
- **Оценка:** **корректно**, ограничение — receipt локальное.

### 4.5 `approve` — утверждение плана
- **Роль:** проверка решений, фикс плана в `.approved.json` (0600).
- **Качество:** контроль plan_sha256 + source_tree_digest + срок. Не использовался в
  export-pipeline (export_kit идёт напрямую).
- **Оценка:** **хорошо**.

### 4.6 `apply` — применение
- **Роль:** apply с backup, journal, receipt.
- **Качество:** pipeline защищён (journal + backup + verify + receipt последним). Не
  использовался в данном переносе (перенос шёл через export_kit, не через
  plan/approve/apply).
- **Оценка:** **хорошо**.

### 4.7 `rollback` — откат
- **Роль:** восстановление активного journaled прогона.
- **Качество:** корректен; не использовался.
- **Оценка:** **хорошо**.

### 4.8 `render` / `compact` — генерация views
- **Роль:** пересборка/удаление generated views.
- **Качество:** вызывает доверенные генераторы с таймаутом. В export-pipeline
  `_render(target)` вызывает `sync-agent-views.sh --local-only`.
- **Оценка:** **хорошо**.

### 4.9 `export` — сам перенос
- **Роль:** вызывает `export_kit.export()` — основной pipeline переноса.
- **Качество:** pipeline содержит: подбор состава kit (`kit_selection`), path-rewrite,
  MCP-адаптацию (`kit_adapt`: scrub/prune/disable/serena-name/registry/manifests/
  doc-links), `_render`, `_must_check`, отчёт, receipt (`.rebase-kit.json`).
- **Оценка:** **хорошо по механизму**; ограничение — не делает де-брендинг (см. §6).

### 4.10 `adopt` — legacy adoption
- **Роль:** предпросмотр/принятие существующих файлов Target.
- **Качество:** корректен; не использовался в данном переносе.
- **Оценка:** **хорошо**.

## 5. Pipeline `export()` — что проверено и что пропущено

Из кода `export_kit.export()` (строки ~395-600):

**Сделано (качественно):**
- ✅ **Подбор состава kit** по профилю из `kit.json` (один walker для предпросмотра и
  переноса — невозможность расхождения состава).
- ✅ **Path-rewrite**: абсолютные пути Source переписываются на Target
  (`kit_adapt.rewrite_source_paths`).
- ✅ **MCP-адаптация**: scrub/prune/disable/set-serena-project-name/registry/
  skill-manifests — серверы Target сохраняются, лишние выключаются.
- ✅ **Нормализация doc-ссылок** и отчёт о внешних ссылках.
- ✅ **`_must_check`**: проверка обязательных файлов (BASE_MUST/CORE_MUST/ENV_MUST)
  и запрещённых (FORBIDDEN, включая `.doc/tasks/*`, секретные файлы, файлы с
  source-path в конфигах).
- ✅ **Receipt** `.rebase-kit.json` (Маркер) + отчёт `.rebase-report.{md,json}` +
  `.rebase-conflicts.json` + `.rebase-preserved.txt`.
- ✅ **Иммептентность**: повторный прогон = `added 0, overwritten 0`.
- ✅ **Core-policy preflight** (для профиля core) — отказ при POLICY_MISSING /
  TRUSTED_GATE_WEAKENING.

**Пропущено / ограничено:**
- ❌ **Де-брендинг не входит в pipeline.** `kit_adapt` меняет пути, MCP, имена
  Serena/registry — но **не трогає** текстовое название `CopyTrust`, имена
  Docker-контейнеров/образов, URL-стенды, скил `copytrust`. Это прямой источник
  «хвостов» (см. §6).
- ❌ **`update` не удаляет** файлы, отсутствующие в Source (мусор остаётся, требует
  ручной чистки).
- ⚠️ **Generated views** (`.kilo/kilo.jsonc`, `.omp/mcp.json`, `opencode.json`,
  `.codex/config.toml`, `.codex/rules`) — не committed (gitignored), должны быть
  собраны sync. В текущем clone их нет.

## 6. «Хвосты» CopyTrust — фактическое остаток

**Всего: 512 строк в 155 файлах.** По каталогам:

| Каталог | Строки | Что |
|---|---:|---|
| `.doc` (документация/панель) | 308 | документы, панель, changelog |
| `.agents/skills` (канон скилов) | 148 | скил `copytrust` + упоминания |
| `.cursor` (канон правил/mcp) | 22 | правила, mcp.json, mcp-stack |
| Сгенерированные зеркала сред | 17 | `.codex`, `.kilo` и т.п. |
| `.tools` (инструменты) | 11 | codeception, docker, php-docker |
| `.agents` (остальное) | 4 | `mcp.env.example` и т.п. |
| Корневые файлы | 2 | `AGENTS.md`, `.gitignore` |

**По типу:**
- Runtime-имена (контейнеры/образы/URL/пути/schema): **251** строк
  (`copytrust-dev-*`, `copytrust-codecept`, `copytrust-tools`, `*.copytrust.ru`,
  `C:\projects\copytrust`, `copytrust.local`).
- Текст/описание/комментарии: **261** строк.

**По формату файлов:** `.md` — 96, `.json` — 11, `.sh` — 11, `.py` — 7, `.ps1` — 6,
`.yml` — 5, `.js`/`.toml`/`.yaml` — по 1.

### Почему остались (причина)

1. **Движок не делает де-брендинг.** `kit_adapt` меняет пути, MCP, имена Serena —
   но не название проекта, не имена контейнеров, не URL. Перенос копирует
   содержимое Source дословно.
2. **Режим `update` не удаляет** файлы/имена, отсутствующие в Source — следовательно,
   легаси copytrust-имена не убираются.
3. **Скил `copytrust`** (платформенный скил для работы с copytrust.ru) и его дети
   `platform-logs`/`platform-browser-test` — это по сути проектный скил; он
   переносится как есть.
4. **Runtime-имена** (`copytrust-dev-*`) — это окружение на машине; engine их
   не переименовывает и не может переименовать без пересоздания окружения.

### Где это критично

- **`.agents/skills/copytrust/**`** и ссылки на него — это канон скилов; остаётся
  как проектный скил.
- **`.cursor/mcp.json`** — контейнеры `copytrust-dev-php-apache-1` в jira-task/
  bitbucket-task; runtime-имена.
- **`.tools/**`** — docker-стенды с copytrust-образами; runtime.
- **`.doc/web/**`** — сервис `copytrust-tools`; runtime-имя.

**Это не баг переноса, а следствие ограничения движка**: перенос — это копирование
+ path/MCP-адаптация, а не де-брендинг.

## 8. Оценка качества переноса (вердикт)

По осям:

| Ось | Оценка | Обоснование |
|---|---|---|
| **Функциональность движка** | ✅ Хорошо | 11 команд, pipeline, 117 тестов, иммептентность, receipt, must-check |
| **Следование канону (процедура)** | ✅ Хорошо | Соответствует `seharnes-transfer.md`: режим update, приоритет Source, исключения, проверки |
| **Адаптация пути/MCP** | ✅ Хорошо | Path-rewrite, MCP-merge/prune/disable, serena-name, registry |
| **Чистота Target (мусор)** | ⚠️ Удовл. | `update` оставляет мусор; в опорном прогоне 11 файлов удалили вручную |
| **Де-брендинг (хвосты)** | ❌ Не сделан | 512 упоминаний CopyTrust остались — не входит в задачу движка |
| **Завершённость настройки Target** | ❌ Не завершено | EXPORT_NEXT_STEPS присутствует, views/mirror/receipt не собраны в clone |
| **Документирование** | ✅ Хорошо | Опорный прогон, подводные камни, проверки задокументированы |

**Итог:** перенос выполнен **квалитативно как файловый движок** — корректно,
иммептентно, с адаптациями и проверками, соответствует канону. **Но** это перенос
**имен/файлов, а не де-брендинга**: «хвосты» CopyTrust остались по конструкции, а
настройка Target в текущем состоянии не завершена.

**Что нужно для доведения до готовности:**
1. **Де-брендинг** (отдельная задача, не входящая в export): заменить CopyTrust →
   seharnes в тексте, runtime-имена, скил — по согласованному плану.
2. **Завершить настройку Target**: secrets → sync-agent-views → rebuild mirror →
   onboard-project --check → doctor → удалить `EXPORT_NEXT_STEPS.md`.
3. **Повторный прогон** для подтверждения иммептентности и сверки receipt.

## 9. Рекомендации

- Для будущих переносов **не рассчитывать на де-брендинг из движка** — планировать
  его отдельной стадией (название, runtime-имена, скил).
- Использовать `update` для переноса правок, `mirror` — только после ревью удалений.
- Сохранять receipt/baseline **локально** (они gitignored): без него иммептентность
  и `verify` в новом clone невозможны.
- После переноса обязательно: `sync-agent-views.sh` → `harness_mirror.py rebuild` →
