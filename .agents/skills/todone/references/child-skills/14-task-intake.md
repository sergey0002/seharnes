# Постановка задачи через диалог

## Маршрут

Подключай эту процедуру, когда пользователь пишет **«постановка задачи»**,
**«собери требования»** или явно просит сформулировать новую работу.

Стартовый ответ:

> Готов собирать требования. Буду задавать уточняющие вопросы по одному и
> сформирую задачу после команды «сформулируй задачу» или «собери задачу».

Дальше веди bounded intake context в текущем диалоге и, если пользователь
подтвердил создание draft, сохраняй его в записи типа `intake`. Скилл не
подменяет reasoning модели фиксированной анкетой: выбирай следующий вопрос по
самому важному текущему gap, ограничениям и рискам.

## Источники и статусы

Разделяй в контексте:

```text
observed      факт из сообщения/файла/скриншота
requested     требование пользователя
proposed      вариант, который ещё не принят
accepted      явно подтверждённое решение
unknown       пробел, который нельзя додумывать
provenance    откуда взят факт
```

Обычное обсуждение не записывай как нормативный факт. Фразу «зафиксируй в
задаче» трактуй как явный write intent и записывай только подтверждённую часть.
Не меняй workspace policy ответом на вопрос или выбором в диалоге.

## Когда спрашивать

Задавай один вопрос или одну короткую группу связанных choices за ход, если
неясны:

- ожидаемый результат и пользовательская ценность;
- границы in/out of scope;
- acceptance и способ проверки;
- владельцы, зависимости, сроки и риски;
- затронутые файлы, API, flow или documentation modules;
- конфликт с существующей задачей/кодом/документом.

Если есть несколько разумных решений, покажи плюсы/минусы и спроси выбор.
Текст вопроса, choices и default бери из активного контекста, а не придумывай
от имени пользователя.

## Действия

- **«постановка задачи»** — открыть intake mode и сообщить, что сбор начат;
- **«зафиксируй в задаче»** — явным `tcheck intake fix` записать
  подтверждённый факт в активный persistent draft с provenance;
- **«сформулируй задачу» / «собери задачу»** — показать резюме, gaps и draft,
  затем explicit `tcheck intake finalize` создать typed task и связать её с
  intake; обычный разговор сам по себе ничего не финализирует;
- **«проведи аудит задачи»** — запустить `tcheck intake audit`, проверить
  refs/code/docs/tests и сохранить `TASK-AUDIT-1` verdict в read-only child;
- **«отмени постановку»** — `tcheck intake cancel`; ничего не финализировать,
  оставить только явно созданный пользователем draft/capture.

## Source-of-truth gates

Перед финализацией проверь:

```bash
tcheck types show <тип>
tcheck intake validate --session <session-id> --root <root>
tcheck validate <task-id> --strict --root <root> --queue <queue>
tcheck docs resolve --mode for-task --task-ref <queue>:<type>:<task-id> --root <root>
```

`intake start` сохраняет draft между сообщениями; `--persist` нужен только для
явной operational draft task. `capture --file` сохраняет file/screenshot bytes
с digest и stored provenance ref. Финальная запись создаётся только через
`tcheck intake finalize` после explicit intent. Не редактируй `task.json`
напрямую, не копируй body другой записи и не скрывай unresolved questions. Для
внешнего входа используй `mirror` → `intake` → typed task.

Подробная инструкция типа и практические команды: `types/intake/instruction.md`.
