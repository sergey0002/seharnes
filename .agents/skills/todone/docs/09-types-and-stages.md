# Типы, поля и внутренние этапы

## Что такое «вид задачи»

В интерфейсе это называется **видом задачи**, а в JSON хранится как `kind` или
`type`. Это не тип данных вроде `string` и не техническая категория сущности.
Это готовый профиль работы: например, исследование, планирование, новая
возможность, исправление, тестирование или документация. Профиль объясняет,
что заполнить, кто выполняет работу и что нужно проверить перед закрытием.

### Тип — это плагин, а не просто метка

Запись получает `kind` один раз. Тип определяет:

- человеческое имя и класс (`product`, `research`, `source`);
- значения по умолчанию и исполнителя (`role`, `tier`, `mode`);
- дополнительные поля `FIELD-1`;
- capabilities среды;
- редактор (`any` или `import_only`);
- гейты закрытия;
- необязательные `checks`, `profile`, agents и инструкцию.

Посмотреть фактическое разрешённое объявление:

```bash
tcheck types list
tcheck types show feature
tcheck types fields planning
```

Изменить `kind` после создания нельзя. Если запись стала другой работой, создай
новую запись с `--parent`, а связь оставь указателем.

## 14 типов поставки

| Тип | Для чего | Особые поля | Главные гейты/возможности |
|---|---|---|---|
| `mirror` | дословное зеркало внешнего входа | `mirror_note` необязательное | `editor: import_only`, закрытие не требуется |
| `default` | обычная работа без специальной формы | нет | минимум 2 AC, `change_kind_required` |
| `intake` | формализация сырого входа | `raw_gaps`, `assumptions`, `draft_child` | handoff, capabilities `code-graph`, `memory` |
| `planning` | план реализации | `approach`, `changes`, `outcome`, `check` | минимум 2 AC, знание как результат |
| `plan-audit` | независимый аудит плана | `verdict`, `findings` | handoff, refs, read-only reviewer |
| `research` | исследование без изменения продукта | нет | handoff, refs, `code-graph`, `memory` |
| `libs-research` | сравнение готовых библиотек | `candidates`, `comparison`, `verdict` | handoff, `web-search` |
| `feature` | новая возможность | нет | tests, evidence, docs, минимум 2 AC, change kind |
| `fix` | дефект | `reproduce` | tests, evidence, reproduce, минимум 2 AC, change kind |
| `small-fix` | малая правка без смены поведения | `why_no_test` | минимум 2 AC, change kind |
| `test-prep` | тексты тестов до реализации | нет | handoff, исполнитель tester |
| `testing` | фактический прогон и verdict | `verdict` | tests, evidence, verdict, test-runner |
| `code-review` | разбор изменения/диффа | `verdict` | evidence, git, code-graph |
| `doc` | документация продукта | нет | docs, docs-store |

Таблица отражает JSON-плагины `assets/types/*/type.json`, а не только встроенные
значения `typedefs.py`. `tcheck types show` — окончательный источник при
разногласии с этой справкой.

## Дополнительное поле FIELD-1

Форма поля:

```json
{
  "name": "reproduce",
  "type": "string",
  "required": true,
  "enum": null,
  "pattern": null,
  "message": "что нужно заполнить",
  "example": "пример хорошего значения"
}
```

Разрешённые типы: `string`, `int`, `number`, `bool`, `array`, `object`. Числовых
квот на длину текста нет: `int`/`number` относятся к типу значения, а не к числу
символов.

Заполнение:

```bash
ttask set T-001 --extra reproduce='python3 -m unittest tests.test_bug' --by dev
ttask set T-001 --extra verdict='AC-1 met, AC-2 blocked' --by tester
```

Строки `true`/`false`, JSON-массивы/объекты и целые числа коэрцируются CLI;
остальное остаётся строкой. Необъявленное имя поля даёт `TYPE_FIELD_UNKNOWN`.

## Гейты и инструкции

`instruction.md` — не декоративное описание: он задаёт цель, порядок, границы,
запасной путь при отсутствии capability и форму результата. `tcheck doctor`
проверяет, что для объявленной capability есть запасной путь.

`editor: import_only` используется зеркалом. Для него разрешён только importer;
обычная команда изменения выдаёт `MIRROR_READONLY`.

## Внутренние этапы записи

Этапы одной записи (`stages-default.md`) — это контур работы внутри одного
`task.json`: подготовить вход, выполнить изменение/исследование, проверить,
передать результат. Они **не создают записи очереди автоматически**.

Новая запись появляется только если:

- человек явно создаёт продолжение через `ttask new --parent`;
- `ttask flow start` создаёт черновик внешнего шага потока;
- importer печатает, а человек выполняет дочерную команду формализации.

Так сохраняется разница между «подэтапом работы» и «новым адресуемым домом».

## Процедурные проверки и профиль

Плагин может объявить `checks` и `profile`, но текущая базовая поставка типов
использует универсальный профиль и не содержит пользовательских `checks/*.py`.
Если добавляется процедурная проверка, она обязана быть потомком `CheckPlugin`,
вернуть `{ok, findings, summary}` и объявить все коды в `type.json`. Если нужен
исполняемый профиль, он наследует `TypeProfile`; путь не должен выходить из
папки типа.
