# Обзор: что такое `todone`

`todone` — локальный JSON-движок управления работой. Он хранит не только список
задач, но и проверяемую историю: цель, границы, критерии приёмки, указатели на
источники, артефакты, ленту решений, доказательства и отчёт закрытия.

Главная архитектурная мысль: **очередь отвечает за порядок, запись — за работу,
тип — за форму и гейты, поток — за маршрут**. Эти четыре ответственности не
смешиваются.

## Что входит в систему

| Сущность | Что это | Почему отдельна | Где находится |
|---|---|---|---|
| Проект | корень, где лежат реестр очередей, роли, tools и поставка | один проект может иметь несколько очередей | `<root>` |
| Очередь | именованный порядок записей | список и доска не должны владеть телом задачи | `<root>/.todone/queues.json` + `tasks/<alias>/` |
| Запись | одна работа и её полный контекст | это единственный дом фактов по работе | `data/T-NNN-тип/task.json` |
| Индекс | производный список ссылок и мета | быстро строит list/board и хранит состояние потока, но не дублирует текст | `.todone/index.json` очереди |
| Тип | форма записи, дополнительные поля, исполнитель и гейты | одинаковые данные проходят одинаковые проверки | `todone/assets/types/<тип>/` |
| Поток | граф/порядок шагов | маршрут можно менять независимо от конкретных записей | `todone/assets/flows/<поток>/` или `<root>/.todone/flows/<поток>/` |
| Зеркало | запись внешнего входа | raw должен остаться дословным и неизменяемым вручную | обычная запись с `kind: mirror` |
| Лента | последовательность реплик | решения и пересменка не должны теряться в свободном чате | `comments` в `task.json` |
| Указатель | адрес факта в другом доме | факт не копируется между записями | `refs` в `task.json` |
| Артефакт | файл результата или доказательства | большой результат читается по адресу, а не копируется в JSON | `artifacts` + файл в папке записи |
| Отчёт | формальный результат закрытия | закрытие должно быть воспроизводимым | `report.json` в папке записи и `report` в записи |
| Роль | назначение уровня, режима, инструментов и моделей | тип не должен содержать хрупкий model id | `<root>/.todone/roles.json` |
| Capability | возможность среды | тип объявляет потребность, проект даёт конкретную команду | `<root>/.todone/tools.json` |
| Documentation workspace | локальный каталог модулей, revisions, sidecars и claims | docs имеют собственный manifest/catalog, но не становятся второй очередью | `<root>/<docs_path>/` (default `docs`) + `<root>/.todone/catalog/docs.json` |
| Aggregate catalog | generated namespace/provenance view нескольких declared roots | не владеет child source of truth | `<root>/.todone/aggregate/` |

## Три точки входа

```text
tqueue  → очередь как порядок: найти, перечислить, отсортировать, показать доску
ttask   → запись как работа: создать, читать, править, связать, закрыть, вести поток
           и явно вызвать `document` / «задокументируй»
tcheck  → контроль: validate, doctor, схемы, типы, потоки, роли, tools, импорт,
           documentation workspace/catalog/resolver
```

Точки входа намеренно не смешивают области. Например, `tqueue next` выбирает
кандидата, но не берёт его в работу; `ttask claim` назначает владельца и меняет
статус; `tcheck doctor` не чинит данные молча, а печатает находку и готовое действие.

## Что происходит при обычной работе

1. Выбрать или создать очередь: `tqueue find`, затем `tqueue init site`.
2. Создать обычную запись: `ttask new «Заголовок» --type feature --queue site`.
3. Заполнить смысловые поля и критерии через `ttask set ... --by <имя>`.
4. Посмотреть, что брать: `tqueue next` или `tqueue board`.
5. Взять запись: `ttask claim T-001 --by <имя>`.
6. Читать нужным режимом: `ttask show T-001 --mode full` или собрать пакет
   `ttask pack T-001`.
7. Сохранить указатели, артефакты и evidence, а большие результаты оставить
   файлами в папке записи.
8. Создать и заполнить `report.json` через `ttask report-skeleton T-001`, затем
   закрыть `ttask close T-001 --report report.json --verdict met --by <имя>`.
9. Проверить: `tcheck validate T-001 --strict`, затем `tcheck doctor --all --strict`.
10. При необходимости явно зафиксировать durable product knowledge:
    `ttask document ... --by <имя>`, затем `tcheck docs check`.

Documentation workspace не записывает обычный разговор автоматически. Capture или
module появляется по явному intent, а `manual`/`disabled` policy ограничивает
автоматический и явный путь согласно effective policy.

## Что изменяемо, а что нет

- `id` и `kind` назначаются при создании и затем неизменны. Продолжение или
  смена формы — новая дочерняя запись с `--parent`.
- `status`, поля, комментарии, refs и artifacts изменяемы только CLI.
- `source.raw` зеркала меняется только импортом. Ручной `set`, `comment`, `ref`,
  `artifact` и другие операции над зеркалом получают `MIRROR_READONLY` или
  `COMMENT_SOURCE_LOCKED`.
- `digest.md` — производный кэш. Его можно пересоздать; править его как источник
  фактов нельзя.
- Все JSON-записи пишутся атомарно; прежний файл сохраняется как `.bak`.

## Контракт чтения

Чтение выбирает состав, но не режет выбранные тексты. Есть отдельные режимы тела,
полной записи, всей ленты, оглавления, handoff, одной реплики, одного элемента и
отчёта. Команда сообщает размеры тела и ленты в знаках и байтах. Если запись
большая, появляется предложение создать `digest.md` и читать его частями.

## Контракт отказа

Отказ — это не молчаливое `false`. Формат:

```text
[CODE] предмет: что не так → чем лечить → команда
```

Код возврата `0` означает успех, `1` — находки/ошибки контроля, `3` — нужно
решение или недостающий вход. `--json` оставляет один JSON-объект без обычного
текста.
