1. Архитектура и Структура Папок

Система создает служебную директорию (например, .harness-viz/), которая зеркалирует структуру проекта, но хранит данные в JSON.
Структура файловой системы:
text
/project-root
  ├── .harness-viz/
  │   ├── data/                 # Зеркало файловой системы с JSON-файлами
  │   │   ├── .agents/
  │   │   │   └── skills/
  │   │   │       └── triage/
  │   │   │           ├── SKILL.json         <-- Скомпилированный узел
  │   │   │           └── SKILL.v1.json      <-- История версий
  │   │   └── scripts/
  │   │       └── run.json
  │   ├── graph.json            # Единый агрегированный граф (Сборка)
  │   └── index.html            # Визуализатор (генерируемый)
  ├── scripts/
  │   ├── hvm-scan.py           # Скрипт сканирования и конвертации (Шаг 1, 2)
  │   ├── hvm-build.py          # Сборка графа и HTML (Шаг 3, 4)
  │   └── hvm-sync.py           # Инструмент редактирования (JSON <-> Source)
Используйте код с осторожностью.

2. Компоненты Системы


Компонент А: "Индексатор" (Scanner & Converter)

Скрипт: hvm-scan.py
Роль: Обход файловой системы и вызов AI-агента для конвертации.
1. 
Input: Список путей для сканирования (whitelist: .agents/, scripts/, docs/rules/).
2. 
Process:

	• 
Для каждого файла вычисляет хеш (чтобы не переделывать неизмененные файлы).
	• 
Если файл изменен: вызывает Parser Skill (ваш скилл конвертации в JSON).
	• 
Важно: Генерирует уникальный node_id на основе пути (например: skill:triage-bug или script:prod-logs).
3. 
Output: Сохраняет результат в .harness-viz/data/<original_path>.json.

Компонент Б: "Сборщик Графа" (Graph Builder)

Скрипт: hvm-build.py
Роль: Агрегация всех мелких JSON в единую сетевую структуру.
1. 
Process:

	• 
Читает все JSON файлы из .harness-viz/data/.
	• 
Link Resolution (Резолвинг связей): Проходит по массивам relations внутри каждого JSON.
	• 
Если Блок А ссылается на check.sh, скрипт ищет node_id, соответствующий check.sh, и создает ребро графа Edge(Source=Block_A, Target=Script_Check, Type=invokes).
2. 
Output: Генерирует graph.json и обновляет index.html.

Компонент В: "Визуализатор" (Frontend Viewer)

Файл: index.html (генерируется скриптом Б).
Технология: Vis.js Network или Cytoscape.js (подключаются через CDN, без сложной сборки).
Функционал UI:
• 
Canvas: Интерактивный граф. Узлы — это файлы/скиллы. Группы узлов (кластеры) — папки.
• 
Стрелки: Показывают связи (invokes, reads, governed_by). Стрелка идет от конкретного блока внутри узла (если возможно) или от узла к узлу.
• 
Инспектор: При клике на узел справа выезжает панель.

	• 
Показывает raw_text (исходник).
	• 
Кнопка "Copy ID for Agent" (копирует skill:triage-bug).
	• 
Кнопка "Edit Mode" (визуально показывает JSON форму, но сохранение идет через агента).

Компонент Г: "Редактор" (Bi-directional Syncer)

Скрипт: hvm-sync.py
Инструмент для Агента: manage_harness_node
Это критический компонент. Он позволяет Агенту редактировать JSON, а системе — обновлять исходный файл.
Логика работы:
1. 
Агент получает команду: "Отредактируй блок симптомов в скилле Triage".
2. 
Агент вызывает get_node(id="skill:triage-bug").
3. 
Агент получает JSON. Меняет текст в raw_content нужного блока.
4. 
Агент вызывает update_node(id="...", new_json=...).
5. 
Скрипт делает магию (Lossless Reconstruct):

	• 
Сохраняет старую версию в *.v{N}.json.
	• 
Берет новый JSON.
	• 
Запускает алгоритм сборки (конкатенация блоков по order), описанный в вашем Скилле парсинга.
	• 
Перезаписывает оригинальный .md или .sh файл.

# ЗАДАЧА: Реализация Harness Visual Manager (HVM)

## 1. Скрипт `hvm-build.py` (Агрегатор)
**Задача:** Собрать разрозненные JSON-ноды в единый граф для Cytoscape.js.
**Вход:** Рекурсивный обход папки `.harness-viz/data/`.
**Логика:**
1. Загрузить все JSON файлы.
2. Создать список `nodes`:
   - id: уникальный ID (путь к файлу или meta.name).
   - label: meta.name.
   - group: meta.type (skill, rule, script).
   - data: весь JSON объект.
3. Создать список `edges`:
   - Пройтись по всем `content_blocks` -> `relations`.
   - Для каждой связи найти целевой `target_id` (по fuzzy search имени файла или точному пути).
   - Создать ребро: { source: current_id, target: target_id, label: relation_type }.
4. Сгенерировать `index.html`, внедрив JSON внутрь шаблона с библиотекой Cytoscape.js.

## 2. Инструмент `hvm-sync.py` (CLI для Агента)
**Задача:** Обеспечить CRUD операции для AI-агента.
**Команды:**

### `get-node <node_id>`
- Ищет JSON файл по ID.
- Возвращает полный JSON + список входящих/исходящих связей (из graph.json).

### `update-node <node_id> <json_string>`
- **Валидация:** Проверяет JSON на соответствие схеме.
- **Бэкап:** Копирует текущий JSON в `.history/`.
- **Сохранение:** Перезаписывает JSON файл в `.harness-viz/data/`.
- **Компиляция (CRITICAL):**
  - Читает обновленный JSON.
  - Если это тип `declarative`: склеивает `content_blocks[].raw_content` в строку.
  - Если это тип `executable`: склеивает `code_blocks[].raw_code` в строку.
  - Перезаписывает ОРИГИНАЛЬНЫЙ файл исходного кода (`source_file_path`).

## 3. Требования к HTML (Визуализации)

5. Что нужно дать Агенту прямо сейчас

Дайте агенту задание "Реализовать Sub-Agent Loop" (шаг 2 вашей идеи), так как это самое сложное:
"Напиши Python-скрипт hvm-scan.py, который сканирует папку проекта. Для каждого найденного .md или .sh файла он должен формировать промпт к LLM, используя [ТЕКСТ ВАШЕГО СКИЛЛА ПАРСЕРА], получать JSON и сохранять его в зеркальную структуру папок в .harness-viz/data. Предусмотри кэширование по MD5 файла, чтобы не тратить токены на неизмененные файлы."




==========

Проблемы "Наивного" подхода:
1. 
Цена (Output Tokens): Вы платите за то, что LLM "печатает" вам ваш же код обратно в JSON. Это 80% стоимости запроса.
2. 
Риск потерь: LLM может случайно пропустить запятую, удалить комментарий или изменить отступ в raw_code.
3. 
Галлюцинации связей: Без знания о других файлах проекта, LLM будет выдумывать связи или не находить их.
Вот стратегия оптимизации "Гибридный Парсер", которая снизит затраты токенов в 5-10 раз и гарантирует 100% точность восстановления текста.

Стратегия 1: Разделение труда (Python = Тело, LLM = Мозг)

Вместо того чтобы просить агента "Сделай мне JSON из этого файла", мы используем Python для структуры и Агента для аналитики.

Новый Алгоритм (Hybrid Pipeline):

1. 
Python (Бесплатно & Точно):

	• 
Читает файл.
	• 
Разбивает на блоки:

		• 
Для .md: Использует Regex ^#{1,4}\s+(.*) для деления на секции.
		• 
Для .sh: Разбивает просто по строкам или оставляет как один блок (если скрипт небольшой).
	• 
Формирует "Скелет" JSON: Заполняет raw_content, header, order.
	• 
Вычисляет Hash: MD5 хеш текста блока.
2. 
LLM (Точечно & Умно):

	• 
Мы отправляем Агенту текст файла (Input tokens дешевые).
	• 
ЗАПРЕЩАЕМ возвращать raw_content.
	• 
Просим вернуть только метаданные и массив связей (Relations) с привязкой к номерам блоков.
3. 
Python (Сборка):

	• 
Берет "Скелет" (с реальным текстом).
	• 
Берет "Мозг" (ответ LLM с метаданными).
	• 
Сливает их в итоговый JSON.
Результат: 0% риска потери текста (так как текст никогда не покидал память Python-скрипта в плане записи), минимальные затраты на Output tokens.

Стратегия 2: "Телефонная Книга" (Project Index Injection)

Чтобы Агент не галлюцинировал связи (например, не ссылался на несуществующий deploy.sh), ему нужно знать контекст.
1. 
Этап 0 (Предварительный скан):

	• 
Скрипт быстро пробегает по всем папкам и составляет index.json:
json
{
  "files": ["scripts/deploy.sh", ".agents/skills/git-flow.md", ...],
  "aliases": {"deploy": "scripts/deploy.sh"}
}
Используйте код с осторожностью.
2. 
Промпт для Агента:

	• 
В системный промпт добавляется этот список.
	• 
Инструкция: "Когда находишь связь, сверяйся с этим списком. Если в тексте написано 'запусти деплой', ищи наиболее подходящий файл в списке (например, scripts/deploy.sh)."

Стратегия 3: Инкрементальный парсинг (Кеширование)

Не пересчитывать то, что не менялось.
1. 
Скрипт хранит файл .harness-viz/cache.map: { "file_path": "md5_hash" }.
2. 
При запуске hvm-scan.py сравнивает текущий хеш файла с кешем.
3. 
Если хеш совпадает — пропускаем обращение к LLM (экономия 100%).

# ТЗ: Создание Оптимизированного HVM-Парсера (Hybrid Parser)

Нужно реализовать скрипт `hvm-scan.py`, который работает по принципу "Python для структуры, LLM для смысла".

## 1. Шаг Pre-Scan (Индексация)
Функция `build_project_index()`:
- Проходит рекурсивно по `source_dirs` (['.agents', 'scripts', 'docs']).
- Создает словарь `context_map`: Ключ = имя файла (без расш), Значение = относительный путь.
- Сохраняет `context_map` в память.

## 2. Шаг Parse File (Гибридный метод)
Функция `process_file(file_path, context_map)`:

### А. Python-сторона (Structural Parsing):
1. Прочитать файл.
2. Если `.md`:
   - Разбить регуляркой на блоки по заголовкам (`^#+ `).
   - Создать список объектов `blocks`: `[{id: 0, text: "...", header: "..."}]`.
3. Если `.sh/.py`:
   - Считать файл целиком как один блок (или разбить по функциям, если сможешь).
4. **ВАЖНО:** Сохранить этот список в переменной `skeleton`. Не отправлять `text` в output запроса к LLM.

### Б. LLM-сторона (Semantic Enrichment):
1. Сформировать промпт:
   - Вход: Полный текст файла + `context_map` (список известных файлов).
   - Задача: "Проанализируй текст. Для каждого логического блока (разделенного заголовками) выдели:
     1. `summary` (краткое описание).
     2. `relations` (связи). Используй `context_map` для точного `target_path`.
     3. `lifecycle` (триггеры запуска)."
   - **Constraint:** Верни JSON строго определенной структуры (AnalysisSchema), БЕЗ полей `raw_content`. Используй `block_index` для привязки к частям текста.

### В. Merge (Слияние):
1. Получить JSON от LLM.
2. Объединить `skeleton` (где лежит верный `raw_content`) и ответ LLM (где лежат `relations` и `meta`) по индексу блока.
3. Сохранить итоговый `harness_declarative_node` (Схема А) или `executable` (Схема Б).

## 3. Схема ответа LLM (AnalysisSchema)
Агент должен возвращать ТОЛЬКО это (чтобы экономить токены):
```json
{
  "meta": { "name": "...", "type": "...", "description": "..." },
  "lifecycle": { ... },
  "blocks_analysis": [
    {
      "block_index": 0,
      "relations": [
        { "target_name": "...", "relation_type": "...", "anchor_text": "..." }
      ]
    }
  ]
}
Используйте код с осторожностью.
Обрати внимание: здесь НЕТ raw_content. Его подставит Python.

4. Кэширование

• 
Проверять MD5 файла перед обработкой. Если не изменился — пропускать.


Как это улучшит качество?

1. 
Валидация связей: Благодаря "Телефонной книге" (Context Map), агент не будет придумывать пути. Если он найдет в тексте "run check", он посмотрит в карту, увидит scripts/check.sh и создаст валидную ссылку.
2. 
Читабельность графа: Вы получите не просто "связь", а точный тип связи (потому что LLM сосредоточен только на анализе, а не на перепечатывании текста).
3. 
Визуализация: Поскольку Python гарантирует сохранение структуры заголовков, при нажатии на блок в HTML-схеме вы увидите идеально отформатированный Markdown.
