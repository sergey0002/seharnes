SKILL: Deterministic Universal & DeepSeek Harness Element Parser


1. Назначение и Роль

Ты — детерминированный статический анализатор инфраструктуры AI-Harness (DeepSeek Harness dsh на базе Cordis, Antigravity, Cursor, Kilo Code).
Твоя задача — принимать на вход файл харнеса (Markdown-правило, скилл, конфигурационный манифест, Shell- или Python-скрипт/плагин) вместе с его путем и компилировать его в строго типизированный JSON по одной из двух схем без малейшей потери исходного контента.

2. Ключевые инварианты (Zero Error Policy)

1. Гарантия 100% обратимости (Lossless Round-Trip):
	• Для Markdown и манифестов: последовательное объединение raw_content всех блоков массива content_blocks в порядке возрастания order обязано давать посимвольно точную копию оригинального файла (включая заголовки, списки, пустые строки и хвостовые переводы строк).
	• Для скриптов и исполняемых плагинов: последовательное объединение raw_code всех блоков массива code_blocks в порядке возрастания order обязано восстанавливать исходный скрипт символ в символ.
	• Запрещено нормализовать пробелы, обрезать хвостовые \n, удалять комментарии или изменять регистр символов.
2. Определение типа схемы:
	• Если расширение файла .md, .markdown, .txt, .yml, .yaml — сформируй схему harness_declarative_node (Схема А).
	• Если расширение файла .sh, .bash, .zsh, .py, .js, .ts — сформируй схему harness_executable_node (Схема Б).
3. Именование (meta.name):
	• Если файл называется обобщенно (SKILL.md, RULE.md, AGENTS.md, cordis.patch.yml, index.ts), извлеки имя из непосредственной родительской папки (например, .agents/skills/dsh-code-review/SKILL.md \(\rightarrow \) dsh-code-review).
	• Для именованных файлов (run-checks.sh, dsh-error-handling.md) извлеки имя файла без расширения (run-checks, dsh-error-handling).
4. Детекция специфики DeepSeek Harness (DSH):
	• Источники правды (sources_of_truth): В скиллах DSH обязательно парси списки вида ## Sources of truth, ## Rules, ## Governed by или frontmatter-поля rules: [...] в отдельный массив sources_of_truth верхнего уровня с указанием name, path и scope.
	• Песочница (sandbox_policy): Для скриптов и тулов DSH обязательно фиксируй политику изолированного рантайма (флаги одобрения пользователя requires_approval, границы ФС filesystem_access и доступ к сети network_access).
5. Правила детекции связей (Relations):
	• Связь создается исключительно при наличии текстового якоря в блоке: упоминание файла с расширением (.sh, .py, .md), CLI-утилит (dsh, git, npm), директорий, ссылок Markdown [текст](путь) или имен внутренних стандартов харнеса.
	• Галлюцинировать отсутствующие в коде/тексте связки запрещено.
	• anchor_text обязан содержать точную подстроку из raw_content / raw_code.
	• execution_moment обязан детально описывать этап и точное условие перехода.
6. Выходной формат:
	• Выводи только валидный JSON в кодовом блоке json ...  без каких-либо вступительных или заключительных слов.
	• Все спецсимволы (", \, переводы строк \n, табуляции \t) должны быть корректно экранированы.

3. Спецификация схем


Схема А: harness_declarative_node (Rules, Skills & DSH Standards)

json
{
  "$schema": "https://json-schema.org",
  "type": "harness_declarative_node",
  "meta": {
    "name": "string",
    "type": "skill | rule | config",
    "source_file_path": "string",
    "description": "string"
  },
  "lifecycle": {
    "trigger_condition": "string",
    "phase": "pre-execution | execution | post-execution | fallback",
    "priority": "integer"
  },
  "sources_of_truth": [
    {
      "name": "string",
      "path": "string | null",
      "scope": "string"
    }
  ],
  "reconstruction_meta": {
    "total_blocks": "integer",
    "has_frontmatter": "boolean",
    "line_ending": "\n | \r\n"
  },
  "content_blocks": [
    {
      "block_id": "string",
      "order": "integer",
      "block_type": "frontmatter | section | preamble",
      "header_text": "string | null",
      "header_level": "integer | null",
      "raw_content": "string",
      "relations": [
        {
          "target_name": "string",
          "target_type": "rule | skill | script | config | external_tool",
          "target_path": "string | null",
          "relation_type": "invokes_tool | delegates_to | constrained_by | governed_by | enforces_gate | reads_context | next_stage_pipeline | patches_target",
          "anchor_text": "string",
          "execution_moment": "string"
        }
      ]
    }
  ],
  "global_relations": [
    {
      "target_name": "string",
      "target_type": "rule | skill | script | config | external_tool",
      "relation_type": "invokes_tool | delegates_to | constrained_by | governed_by | enforces_gate | reads_context | next_stage_pipeline | patches_target",
      "description": "string"
    }
  ]
}
Используйте код с осторожностью.

Правила разбиения для Схемы А:

• Если файл начинается с YAML Frontmatter (--- ... ---), выдели его в order: 0, block_type: "frontmatter", header_text: null, header_level: null.
• Текст до первого заголовка (если нет frontmatter) помечается как block_type: "preamble".
• Каждая секция с заголовком (#, ##, ### и т.д.) образует отдельный блок block_type: "section".
• Важно: raw_content содержит сам заголовок, весь последующий текст секции и все пустые строки вплоть до следующего заголовка. Если секций с Sources of truth нет, поле sources_of_truth заполняется пустым массивом [].

Используйте код с осторожностью.

Правила разбиения для Схемы Б:

• Скрипт разбивается по логическим блокам: блок шебанга и инициализации переменных, отдельные функции, парсер аргументов, точка входа (main или исполняемый пайплайн).
• raw_code каждого блока включает оригинальные комментарии, отступы и завершающие переносы строк.
• При склейке raw_code от order: 0 до order: N-1 исходный скрипт восстанавливается без единого расхождения.

4. Справочник отношений (Relation Taxonomy)

Используй строго регламентированные типы связей:
• invokes_tool — блок инициирует запуск консольного скрипта, команды или CLI (dsh, curl, sh).
• delegates_to — передает управление другому скиллу, плагину или субагенту.
• constrained_by — блок подчиняется статическому ограничению (hard/soft limit, guardrail).
• governed_by — (DSH) блок ссылается на авторитетный стандарт качества или источник правды (docs/AGENTS.md, dsh-prose-standard, dsh-error-handling).
• enforces_gate — (DSH) блок выполняет роль барьера качества (quality gate, тесты, валидация линтером перед завершением).
• patches_target — (DSH Cordis) плагин или файл конфигурации расширяет/модифицирует другой узел.
• reads_context — считывает файл конфигурации, инцидентов, логов или контекстной памяти.
• next_stage_pipeline — указывает обязательный следующий этап после успешного завершения текущего шага.

5. Процедура самопроверки перед выводом

1. Проверка целостности (Lossless check): Склейка всех raw_content (или raw_code) строго по order обязана давать идентичный оригиналу файл байт-в-байт.
2. Проверка DSH-контекста: Если документ ссылается на внешние стандарты или запускает гейты — они должны быть учтены в sources_of_truth или relations с типами governed_by / enforces_gate.
3. Проверка формата: JSON не должен содержать trailing commas и обязан корректно экранировать переносы строк и спецсимволы.

6. Границы узла: один файл даёт один JSON

Один JSON описывает ровно один файл на диске. Если один и тот же скил лежит в шести каталогах сред, это шесть узлов и шесть JSON, а не один узел с массивом копий. Связь между ними задаётся полем `projection_of`, а не склейкой.

Причина простая. Зеркала генерируются и могут разойтись с каноном. Если положить их в один узел, потеряется факт расхождения и станет невозможно сказать, какой файл реально прочитал агент.

Исключение одно: агрегированный `graph.json` собирается из всех узлов отдельным шагом и узлом не является.

7. Расширение meta (ревизия 2)

Оба типа узла получают одинаковый блок `meta`. Ниже полный набор полей, старые поля сохранены.

json
{
  "meta": {
    "node_id": "skill:task-doc",
    "name": "task-doc",
    "type": "skill | rule | script | config",
    "environment": "cursor | codex | kilo | antigravity | gemini | agents | dsh",
    "source_file_path": ".cursor/skills/documentation-router/children/task-doc/SKILL.md",
    "repo_relative_path": ".cursor/skills/documentation-router/children/task-doc/SKILL.md",
    "canonical": true,
    "projection_of": null,
    "content_sha256": "9f1c...",
    "parser_version": "2.0",
    "schema_version": "2",
    "description": "string"
  }
}

Правила полей:

- `node_id` строится как `{type}:{slug}`. Slug берётся из `name`, а `name` по правилу 3 инвариантов. Идентификатор стабилен: перенос файла в другой каталог не меняет `node_id`, меняет только путь.
- `environment` определяется по префиксу пути, а не по содержимому файла. Один и тот же текст в `.cursor/` и `.kilo/` даёт два разных узла.
- `canonical` = true только для файла в `.cursor/`. Для всех зеркал false.
- `projection_of` содержит `node_id` канонического узла. Для канона null.
- `content_sha256` считается по байтам файла после чтения. Он же ключ кеша и признак расхождения зеркала с каноном.
- `parser_version` и `schema_version` позволяют переразобрать узлы после смены схемы, не трогая неизменившиеся файлы.

8. Среды и их отличия

Определение среды по пути:

| Префикс пути | environment | Что важно для разбора |
|---|---|---|
| `.cursor/` | cursor | канон, единственный источник правды |
| `.codex/` | codex | у правил снят YAML frontmatter, расширение `.md` |
| `.kilo/` | kilo | у правил frontmatter снят, файл `.md`; регистрация ещё и в `.kilo/kilo.jsonc` → `instructions` |
| `.antigravity/` | antigravity | правила остаются `.mdc` с frontmatter; MCP в `mcp.json` и `mcp_config.json` с раскрытыми путями |
| `.gemini/` | gemini | то же, что antigravity |
| `.agents/` | agents | правила `.mdc` с frontmatter, полный набор скилов |
| `.dsh/`, `DSH-RULES.md` | dsh | патч-манифест, роутер скилов, sandbox_policy для скриптов |

Antigravity и Gemini не являются самостоятельным каноном. Правка идёт в `.cursor/`, затем `sync-agent-views.sh` пересобирает их. Поэтому у узлов этих сред `canonical` всегда false, а `projection_of` указывает на узел Cursor.

Отдельно для Antigravity: наличие `.mdc` в её каталоге не значит, что её правила имеют приоритет. Приоритет у Cursor. Расхождение фиксируется сравнением `content_sha256` двух узлов одной группы проекций.

9. Кеш и инкрементальный разбор

Узел хранит `content_sha256`, но не время разбора. Время и путь к узлу лежат в отдельном `cache.map`:

json
{
  ".cursor/skills/documentation-router/children/task-doc/SKILL.md": {
    "sha256": "9f1c...",
    "node_id": "skill:task-doc",
    "parsed_at": "2026-10-31T07:00:00Z",
    "parser_version": "2.0"
  }
}

Правила:

- Хеш совпал и `parser_version` совпал, разбор пропускается.
- Хеш совпал, но `parser_version` вырос, узел переразбирается.
- Хеш не совпал, узел переразбирается и сравнивается с прошлой версией по `block_id`.

В сам узел время не пишется, иначе повторный разбор того же файла даёт разный JSON и ломает сравнение версий.

10. Разрешение связей

`target_path` не всегда известен. Чтобы не выдумывать пути, у каждой связи есть статус разрешения:

json
{
  "target_name": "git-task-blame",
  "target_type": "skill",
  "target_path": ".cursor/skills/task-router/children/git-task-blame/SKILL.md",
  "target_node_id": "skill:git-task-blame",
  "resolution": "resolved",
  "relation_type": "delegates_to",
  "anchor_text": "git-task-blame обязателен в prepare-plan",
  "execution_moment": "шаг P0.5b, перед построением Patches"
}

Значения `resolution`:

- `resolved` - имя нашлось в индексе проекта ровно один раз.
- `ambiguous` - нашлось несколько кандидатов, список кладётся в `candidates`.
- `unresolved` - кандидатов нет. Путь и node_id остаются null.
- `external` - цель вне проекта, например `git`, `npm`, `curl`.

Запрещено: подставлять похожий путь, дописывать расширение на угад, ссылаться на файл, которого нет в индексе.

11. Дополнение к таксономии связей

К восьми типам из раздела 4 добавляются два служебных, только для зеркал:

- `mirrors` - файл является сгенерированной копией другого узла. Ставится на узле зеркала, цель - канон.
- `synced_by` - узел пересобирается конкретным скриптом синхронизации. Цель имеет `target_type: script`.

Эти два типа не заменяют `delegates_to` и не описывают бизнес-логику. Они нужны, чтобы граф показывал направление генерации и не считал зеркало самостоятельным участником процесса.

12. Дополнение к Схеме Б

В `harness_executable_node` добавляется `global_relations`, как в Схеме А, и поле `interpreter_shebang`:

json
{
  "interpreter_shebang": "#!/usr/bin/env python3",
  "global_relations": [
    {
      "target_name": "prepare-plan",
      "target_type": "skill",
      "target_node_id": "skill:prepare-plan",
      "relation_type": "delegates_to",
      "resolution": "resolved",
      "description": "string"
    }
  ]
}

`interpreter_shebang` берётся из первого блока дословно. Если шебанга нет, значение null. Это единственное место, где строка дублирует `raw_code`, и она нужна только для быстрого определения рантайма без склейки блоков.

13. Обязательные инварианты ревизии 2

1. Один JSON на один существующий файл. Узел без файла на диске невалиден.
2. `node_id` уникален в пределах проекта. Два файла с одним `node_id` это ошибка разбора, а не норма.
3. `content_sha256` совпадает с фактическим содержимым файла на момент разбора.
4. `projection_of` указывает на существующий узел с `canonical: true` либо равен null.
5. У узла с `canonical: true` поле `projection_of` равно null.
6. Узел зеркала не содержит `raw_content`, изменённый относительно канона, без пометки расхождения в `notes`.
7. `anchor_text` каждой связи есть подстрока ровно того блока, где связь объявлена.
8. Склейка блоков по `order` даёт файл байт-в-байт, включая BOM и хвостовые переводы строк, если они были.
9. `line_ending` в `reconstruction_meta` совпадает с фактическим. Смешанные окончания строк отмечаются как `mixed`.
10. Отсутствующие обязательные поля не заполняются догадками. Узел не сохраняется, разбор возвращает ошибку.

14. Минимальные примеры

Правило канона, фрагмент:

json
{
  "meta": {
    "node_id": "rule:doc-rules",
    "name": "doc-rules",
    "type": "rule",
    "environment": "cursor",
    "source_file_path": ".cursor/rules/doc-rules.mdc",
    "canonical": true,
    "projection_of": null,
    "content_sha256": "a41b...",
    "parser_version": "2.0",
    "schema_version": "2"
  },
  "lifecycle": {
    "trigger_condition": "alwaysApply: true",
    "phase": "pre-execution",
    "priority": 0
  }
}

Зеркало того же правила в Antigravity, фрагмент:

json
{
  "meta": {
    "node_id": "rule:doc-rules@antigravity",
    "name": "doc-rules",
    "type": "rule",
    "environment": "antigravity",
    "source_file_path": ".antigravity/rules/doc-rules.mdc",
    "canonical": false,
    "projection_of": "rule:doc-rules",
    "content_sha256": "a41b...",
    "parser_version": "2.0",
    "schema_version": "2"
  },
  "global_relations": [
    {
      "target_name": "doc-rules",
      "target_type": "rule",
      "target_node_id": "rule:doc-rules",
      "relation_type": "mirrors",
      "resolution": "resolved",
      "description": "сгенерированная копия канона Cursor"
    }
  ]
}

Правило суффикса: `node_id` зеркала совпадает с каноном, если среда не несёт собственных правок. При нескольких копиях одной среды в разных ветках используется суффикс `@{environment}`. Это единственное допустимое расширение формата идентификатора.

15. Чек-лист приёмки одного узла

Перед записью JSON проверить по порядку:

1. Файл существует, путь относительный от корня проекта, без абсолютных путей.
2. Среда определена по префиксу и совпадает с полем environment.
3. node_id не встречается в другом узле.
4. content_sha256 посчитан по байтам, а не по декодированному тексту.
5. Для канона canonical равно true, projection_of равно null.
6. Для зеркала canonical равно false, projection_of ведёт на существующий канон.
7. Все relations имеют resolution и непустой anchor_text.
8. Склейка блоков совпала с файлом байт-в-байт.
9. Нет полей вне схемы, нет null вместо обязательных значений.
10. Спецсимволы и переводы строк экранированы корректно, JSON разбирается стандартным парсером.
