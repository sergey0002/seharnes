# Устройство harness-mirror

Подробное описание реализации: что делает каждая команда, как устроены данные, какие проверки стоят на каждом шаге и чем ограничен инструмент.

Нормативный формат узла: [node-format.md](./node-format.md). Полная спецификация: [mirror-format.md](./mirror-format.md). Порядок работы агента: [../SKILL.md](../SKILL.md). Быстрый старт и диагностика: [../README.md](../README.md).

---

## 1. Назначение и границы

Скил превращает файлы агентского харнеса в данные: один JSON на один файл, плюс граф связей и просмотрщик.

Разделение ответственности:

| Слой | Кто делает | Что получается |
|---|---|---|
| Структура | `scripts/harness_mirror.py` | блоки, хеши, обратимость, связи по литералам |
| Смысл | агент по заданию `prompt` | описание, жизненный цикл, источники правды, связи, которых нет в тексте |
| Перенос копий | `sync-agent-views.sh` проекта | зеркала сред |
| Паритет | `verify_parity.py` проекта | подтверждение, что копии равны канону |

Скил не заменяет синхронизацию и паритет, не пишет в зеркала, не вызывает модель, не ходит в сеть, не использует MCP, базу и сторонние библиотеки. Только Python 3 stdlib.

## 2. Состав файлов

```
SKILL.md                            порядок работы агента, 6 шагов
README.md                           быстрый старт, команды, маршруты, диагностика
ADAPTERS.local.md                   проектные значения, transferable: false
assets/harness-node.schema.json     машинная схема узла v2.1
assets/viewer.html                  просмотрщик, один файл, без CDN
references/mirror-plan.md            решения и этапы разработки
references/mirror-format.md          полная спецификация формата
references/node-format.md           краткий нормативный формат
references/panel-integration.md     как отдавать карту через панель
references/implementation.md        этот файл
scripts/harness_mirror.py           все команды, около 1500 строк
tests/test_harness_mirror.py        31 тест
.cursor/.state/harness-mirror/      состояние конкретного проекта, не переносится
```

Каталог `.cursor/.state/harness-mirror` начинается с точки, поэтому не попадает ни в зеркала, ни в паритет, ни в собственный скан.

## 3. Данные на диске

| Путь | Содержимое | Кто пишет |
|---|---|---|
| `<DATA_DIR>/nodes/<safe>.json` | по одному узлу на файл | `scan`, `apply`, `set` |
| `<DATA_DIR>/nodes/.history/<safe>.vN.json` | прошлые версии узла | `set`, `serve` |
| `<DATA_DIR>/cache.map` | хеши и версии разобранных файлов | `scan`, `set` |
| `<DATA_DIR>/graph.json` | узлы и ребра для просмотрщика | `build`, `set`, `serve` |
| `<DATA_DIR>/index.html` | копия `assets/viewer.html` | `build` |
| `<DATA_DIR>/.lock` | файл блокировки записи | любая изменяющая команда |

Имя файла узла: `node_id`, где каждый символ вне `[A-Za-z0-9._-]` заменён на `__`. Пример: `skill:task-doc@kilo` даёт `skill__task-doc__kilo.json`.

Все записи атомарные: временный файл в том же каталоге, `fsync`, затем `os.replace`. Прерванная запись не оставляет половину файла.

## 4. Модель узла

Узел описывает ровно один файл. Два вида: декларативный (`.md`, `.mdc`, `.txt`, `.yml`, `.yaml`) и исполняемый (`.sh`, `.bash`, `.zsh`, `.py`, `.js`, `.mjs`, `.ts`).

### 4.1 meta

| Поле | Тип | Смысл |
|---|---|---|
| `node_id` | строка | `{тип}:{slug}`, у зеркала суффикс `@{среда}` |
| `name` | строка | `slug`, отображается в карточке |
| `type` | `skill`, `rule`, `script`, `config`, `doc` | определяется по пути и расширению |
| `environment` | `cursor`, `codex`, `kilo`, `antigravity`, `gemini`, `agents`, `dsh`, `project` | по префиксу пути |
| `source_file_path` | строка | путь от корня, разделитель `/` |
| `canonical` | bool | true для `.cursor/`, `.agents/skills/` и файлов вне известных сред |
| `projection_of` | строка или null | `node_id` канона у зеркала |
| `transferable` | bool | false только у `ADAPTERS.local.md` |
| `content_sha256` | строка | хеш байтов исходного файла |
| `parser_version` | строка | версия разбора, сейчас `3.6` |
| `schema_version` | строка | версия схемы, сейчас `2.1` |
| `description` | строка | заполняет агент, при разборе переносится из прошлой версии узла |
| `symlink_target` | строка, необязательно | цель симлинка, файл читается по реальному пути |

Время разбора в узле не хранится: иначе одинаковый вход давал бы разный JSON и ломал сравнение версий. Время лежит в `cache.map`.

### 4.2 reconstruction_meta

`total_blocks`, `line_ending` (`\n`, `\r\n`, `mixed`), `bom` (bool), `final_newline` (bool), у декларативного узла ещё `has_frontmatter`.

### 4.3 Блоки

Общие поля: `block_id`, `order`, `relations`, плюс текст: `raw_content` у декларативного и `raw_code` у исполняемого.

Декларативный блок: `block_type` (`frontmatter`, `preamble`, `section`), `header_text`, `header_level`.
Исполняемый блок: `line_range` вида `start-end` (нумерация с 1), `name_or_purpose`.

`block_id` вида `b000`, `b001` по порядку `order`. Склейка всех блоков по `order` даёт исходные байты.

### 4.4 execution_profile

Только у исполняемого узла:

- `runtime`: `bash`, `zsh`, `python`, `node` по расширению;
- `interpreter_shebang`: первая строка, если начинается с `#!`, иначе null;
- `command_template`: `<расширение> <путь>`;
- `env_vars_required`: имена вида `${VAR}` из текста, кроме `PATH`, `HOME`, `PWD`, `IFS`, `SHELL`, `USER`;
- `arguments`: имена из `add_argument("...")`, тип string, необязательные.

### 4.5 lifecycle и sandbox_policy

У декларативного узла `lifecycle` по умолчанию: пустой `trigger_condition`, `phase: execution`, `priority: null`. Агент может уточнить через `apply`.

У исполняемого узла `lifecycle.security_level` вычисляется по тексту: `destructive_write` при `rm -rf`, `git push`, `DROP TABLE`, `DELETE FROM`, `truncate`; иначе `idempotent_write` при перечислении записи (`>`, `tee`, `mv`, `cp`, `mkdir`, открытие файла на запись); иначе `read_only`.

`sandbox_policy`: `requires_approval` равно признаку разрушительности, `filesystem_access: workspace_only`, `network_access` по наличию `curl`, `wget`, `npm install`, `pip install`, `fetch(`, `requests.`.

### 4.6 sources_of_truth, global_relations, analysis

`sources_of_truth`: массив `{name, path, scope}`, заполняет агент. `path` равно null, если стандарт упомянут без ссылки.

`global_relations`: связи уровня файла, без привязки к блоку. Проверка блока и якоря к ним не применяется.

`analysis`: `{status: pending|filled, model: null|agent|<имя модели>}`. Заполненный узел не перезаполняется наследованием.

## 5. Идентификаторы

### 5.1 Тип

Порядок проверок в `type_of`:

1. путь содержит `/skills/` и оканчивается на `SKILL.md`: `skill`;
2. путь содержит `/rules/`: `rule` (даже если расширение `.json`);
3. расширение исполняемое: `script`;
4. расширение `.json`, `.jsonc`, `.yml`, `.yaml`, `.toml`: `config`;
5. имя `mcp.json`, `config.toml`, `kilo.jsonc`: `config`;
6. иначе `doc`.

### 5.2 Slug

1. Берётся имя файла без расширения в нижнем регистре.
2. Если путь внутри `/skills/` и это не `SKILL.md`, slug получает префикс имени скила: `<скил>-<имя>`. Для имён из списка основных (`index`, `main`, `skill`, `rule`, `agents`, `claude`, `cordis.patch`) вместо имени берётся имя родительской папки, поэтому `references/index.md` в разных скилах даёт разные идентификаторы.
3. Иначе, если имя основное, slug равен имени родительской папки.
4. Иначе, если имя вспомогательное (`readme`, `guide`, `docs`, `notes`, `changelog`, `plan`), slug получает префикс папки, кроме корневых папок харнеса.
5. Недопустимые символы заменяются на `-`, крайние `-` и `.` срезаются. Пустой результат заменяется на `node`.

### 5.3 node_id

`{тип}:{slug}`. У скрипта к slug добавляется расширение: `script:harness_mirror-py`. У зеркала добавляется `@{среда}`: `skill:task-doc@kilo`. Для `cursor` и `project` суффикса нет.

Два узла одной среды с одинаковым `node_id` это ошибка проекта: `scan` завершается с кодом 1 и сообщением `node_id collision`. Идентификатор не правят вручную, переименовывают файл.

## 6. Корень и каталог данных

`--root`:

- если задан, каталог должен содержать `.git` или `.cursor`, иначе код 2;
- если не задан, поиск идёт от каталога скрипта, затем от текущего каталога вверх до `.git` или `.cursor`.

`--data` по умолчанию `.cursor/.state/harness-mirror`, считается от корня. Абсолютный путь в узлы не попадает.

Такой порядок позволяет запускать скрипт из копии в любой среде и из любого рабочего каталога.

## 7. Область сканирования

Канон по умолчанию:

```
.cursor/rules
.agents/skills
.cursor/scripts
.cursor/mcp-stack
```

Документация, задачи и продуктовый код в область не входят: пути вне префиксов харнеса не индексируются, а связи на них отбрасываются.

Флаги:

- `--include-mirrors`: добавляет `.codex`, `.kilo`, `.agents`; legacy `.antigravity` и `.gemini` не генерируются;
- `--include-dsh`: добавляет `.dsh`;
- `--paths a b c`: заменяет список канона целиком, флаги добавляются к нему;
- `--force`: игнорирует кеш.

Расширения: `.md`, `.markdown`, `.txt`, `.yml`, `.yaml`, `.mdc`, `.sh`, `.bash`, `.zsh`, `.py`, `.mjs`, `.js`, `.ts`, `.json`, `.jsonc`, `.toml`.

Не сканируются: `package-lock.json`, файлы, имя которых начинается с точки, `*.lock`, каталоги из списка исключений. В список входят `.git`, `node_modules`, `vendor`, `__pycache__`, виртуальные окружения, каталоги сборки и продуктовые каталоги, `tools`, `worktrees`, `.history`, `.playwright*`, `graphify-out` (legacy), `.codegraph`, `.data`.

Индекс проекта (`build_index`) обходит дерево шире, чтобы связи могли ссылаться на файлы вне области скана, но фильтрует результат теми же префиксами (`INDEX_PREFIXES`), глубиной до 8 частей пути и теми же правилами секретов. Благодаря этому ссылка на `.kilo/...` получает правильный `target_node_id`, даже когда зеркала не сканировались.

### 7.1 Секреты

Пропускаются по имени: `*.env`, `.env`, `*.key`, `*.pem`, `*.p12`, `*.pfx`, `mcp.env`, `id_rsa`, `id_ed25519`, а также имена, содержащие `secret`, `credential`, `token`, `password` (варианты с суффиксом `.example`, `.dist`, `.template`, `.sample` считаются безопасными).

Пропускается по содержимому: файл, где найдены шаблоны вида `sgp_...`, `ghp_...`, `sk-...`, `AKIA...`, `-----BEGIN ... PRIVATE KEY-----`, `Bearer <16+ символов>`. Причина печатается в stderr, файл в узлы не попадает.

Из конфигурации MCP читаются только имя сервера, транспорт, команда, число аргументов и имена переменных окружения. Значения не сохраняются.

## 8. Конвейер scan

Порядок операций в `cmd_scan`:

1. `build_index`: карта всех файлов проекта и карта имён для разрешения ссылок.
2. `load_mcp_servers`: список серверов из `.cursor/mcp.json` или `.cursor/mcp_config.json`.
3. Чтение `cache.map`.
4. Для каждого файла из `targets_for`:
   - фильтр имени и секретов;
   - чтение байтов, декодирование UTF-8; ошибка декодирования даёт код 2;
   - проверка на значения секретов;
   - вычисление `node_id` и проверка коллизии;
   - вычисление `sha256`;
   - пропуск, если узел существует, хеш совпал, `node_id` совпал, `parser_version` совпал и `schema_version` совпал;
   - иначе разбор с сохранением смысловых полей из прошлой версии узла;
   - запись узла и записи кеша.
5. Удаление из кеша записей, чьих файлов больше нет.
6. Удаление алиасов симлинкованного дерева: `.cursor/skills` и `.agents/skills` дают один реальный путь, в кеше остаётся `.agents/skills`.
7. Наследование зеркалами (раздел 11).
8. Нормализация связей и `projection_of`.
9. Удаление файлов узлов, которых нет в кеше.

Вывод: `{"status": "ok", "written": N, "skipped": N, "inherited": N, "removed": N, "downgraded": N, "nodes": N}`.

Счётчики означают: `written` разобрано заново, `skipped` пропущено по кешу, `inherited` зеркал получило смысл канона, `removed` файлов узлов удалено, `downgraded` связей сменило состояние из-за исчезнувшей цели.

Разбор идемпотентен: повторный запуск без изменений даёт `written: 0`.

## 9. Кеш

`cache.map` это объект, ключ это путь файла от корня:

```json
{
  ".cursor/rules/doc-rules.mdc": {
    "sha256": "<hex>",
    "node_id": "rule:doc-rules",
    "parser_version": "3.6",
    "schema_version": "2.1",
    "node_file": "nodes/rule__doc-rules.json"
  }
}
```

Инвалидация:

| Условие | Результат |
|---|---|
| хеш файла изменился | переразбор |
| узел отсутствует | переразбор |
| `parser_version` вырос | переразбор |
| `schema_version` вырос | переразбор |
| `--force` | переразбор |

Правило про несовпадение версии схемы проверяется наравне с версией разбора, поэтому смена формата не оставляет старых узлов.

`check` предупреждает в stderr, если запись кеша отстаёт по версии, но это не ошибка: лечится повторным `scan`.

## 10. Разбор файлов

### 10.1 Markdown

1. Если текст начинается с `---` и дальше есть `\n---`, первый блок это frontmatter. Конец блока включает перевод строки после закрывающего забора.
2. Заголовки ищутся по шаблону `^#{1,6}\s+`. Заголовок внутри блока кода не отличается от обычного: разбор не учитывает ограждения ```.
3. Текст до первого заголовка это `preamble`.
4. Каждый заголовок начинает `section` и включает весь текст до следующего заголовка.
5. Если заголовков нет, весь остаток становится `preamble`, а при наличии frontmatter `section`.

Ограничение: `---` как горизонтальная линия в начале файла может быть принята за frontmatter, если ниже есть `\n---`.

### 10.2 Скрипты

1. Текст режется на строки с сохранением окончаний.
2. Новая группа начинается на строке без отступа, которая совпадает с одним из маркеров: `def`, `async def`, `class`, `function`, `export function`, `const|let|var x = function|(`, `name() {`.
3. Вложенные функции остаются в блоке родителя.
4. Имена блоков берутся из определений, для шебанга `shebang`, иначе `block N`.
5. `line_range` считается в номерах строк с 1, конец включительно.

Дополнительно по всему тексту считаются `execution_profile.lifecycle.security_level`, `sandbox_policy` и `env_vars_required`.

## 11. Зеркала

Правила:

- `environment` определяется по префиксу пути; канон это `.cursor/`, `.agents/skills/` и файлы вне сред, остальные зеркала получают `canonical: false` и `projection_of` равен `node_id` канона, если файл канона существует;
- `node_id` канона не имеет суффикса среды, зеркало получает суффикс `@{среда}`;
- для зеркал скилов канон ищется сначала в `.agents/skills/`, затем в `.cursor/skills/`;
- сравнение содержимого идёт по хешу с нормализацией CRLF в LF, как в паритете проекта;
- если хеши совпали и у зеркала `analysis.status` не `filled`, зеркало получает `description`, `lifecycle`, `sources_of_truth`, `global_relations`, `analysis` канона;
- связи копируются поблочно, только когда совпадает вид блоков у канона и зеркала;
- если канон исчез, `projection_of` сбрасывается в null, узел остаётся самостоятельным файлом среды;
- legacy-копии `mcp-servers/` в зеркалах адаптированы под среду (пути `.codex/tools`, `.kilo/tools`), поэтому не считаются проекциями канона и не дают `state: drift`;
- правка зеркала запрещена: `set` и `PUT` возвращают отказ с указанием канона.

Расхождение содержимого даёт в графе ребро `mirrors` со `state: drift`. Совпадение даёт `state: equal`.

## 12. Связи

### 12.1 Источники автоматических связей

| Источник | Шаблон | Что даёт |
|---|---|---|
| Markdown-ссылка | `текст (цель)` | цель без якоря `#...`; внешние схемы, `mailto:` и `#` пропускаются |
| Код в бэктиках | `` `path/file.ext` `` | цель по расширению из белого списка |
| Упоминание скила | `скил X`, `skill X` | цель с подсказкой `skill` |
| Упоминание MCP | имя сервера из конфигурации | `target_type: mcp`, `relation_type: invokes_tool` |

### 12.2 Разрешение цели

1. Имя из списка внешних программ (`git`, `npm`, `php`, `python3`, `curl`, `docker`, ...) даёт `external`.
2. Обратные слэши заменяются на `/`, снимаются кавычки и бэктики.
3. Если цель начинается с `/`, `./` или `../`, путь нормализуется относительно каталога исходного файла.
4. Второй вариант: цель без ведущих `../`.
5. Проверка в индексе файлов. Совпадение даёт `resolved`.
6. Если слэша нет, имя ищется вверх по дереву до 4 уровней от каталога файла. Так `README.md` внутри скила находит README этого скила, а не первый попавшийся.
7. Иначе поиск по имени файла без расширения, затем по совпадению slug.
8. При подсказке `skill` кандидаты сужаются до путей с `/skills/`.
9. Если кандидатов несколько и среди них ровно один в `.cursor`, выбирается канон: зеркала не создают ложную неоднозначность.
10. Один кандидат даёт `resolved`, несколько дают `ambiguous` со списком до 8 путей, ноль даёт `unresolved`.

Путь никогда не выдумывается: похожее имя не повод подставить файл.

### 12.3 Тип связи

`relation_type_for`:

- внешняя программа или скрипт с глаголом запуска в строке-якоре: `invokes_tool`;
- цель это скил: `delegates_to`;
- цель это правило: `governed_by`;
- остальное: `reads_context`.

Остальные типы (`enforces_gate`, `constrained_by`, `reads_context`, `next_stage_pipeline`, `patches_target`, `mirrors`, `synced_by`) ставит агент через `apply` или сборка графа.

### 12.4 Слияние

Автоматические связи пересчитываются при каждом разборе: устаревшее обнаружение не живёт вечно. Связи агента (`origin: agent`) сохраняются, если блок с тем же порядком и тем же текстом остался на месте. Ключ дедупликации: цель (`target_node_id` или имя) плюс тип связи. При совпадении побеждает автоматическая свежая связь.

`anchor_text` это первая строка блока с этим текстом, обрезанная до 200 символов. Для связей агента якорь обязан быть точной подстрокой блока, это проверяет `apply`.

### 12.5 Состояния цели

| Состояние | Значение | Путь и идентификатор |
|---|---|---|
| `resolved` | цель одна и найдена | заполнены |
| `ambiguous` | кандидатов несколько | `candidates` со списком, путь пустой |
| `unresolved` | цели нет | пустые |
| `missing` | цель была, файл исчез | сохранены, чтобы потеря была видна |
| `external` | цель вне проекта | пустые |

При каждом `scan` состояния пересчитываются по наличию файла, а не по набору отсканированных узлов. Поэтому скан только канона не превращает ссылки на непросканированные зеркала в `missing`. Если файл вернулся, состояние возвращается в `resolved`.

## 13. Распознавание MCP

Серверы читаются из `.cursor/mcp.json` (или `.cursor/mcp_config.json`), ключи `mcpServers` или `servers`. Узел синтетический: файла нет, есть имя, транспорт (`type` или `url` даёт `http`, иначе `stdio`), команда, число аргументов и имена переменных.

Упоминание засчитывается, если выполнено одно из условий:

1. строка содержит отдельный токен `MCP`, но не как хвост имени файла (`mcp.json`, `mcp.env`, `mcp-stack`, `mcp-servers`, `mcp_config`);
2. имя сервера само содержит `mcp`;
3. запись вида `mcp__имя` или `mcp-server-имя`.

Для имён, совпадающих с обычными программами (`git`, `mysql`, `playwright`, `serena`, `codegraph`, `semgrep`, `context7`, `xdebug`, `sourcegraph`, `deepwiki`, `jira-task`, `bitbucket-task`), дополнительно нужно, чтобы токен `MCP` стоял в пределах 25 символов, а сразу после имени не шёл глагол командной строки (`status`, `push`, `-e`, `--flag`, ...).

Практика: `git status` и `mysql -e` связей не создают, а строка `MCP Gate: codebase-memory-mcp -> codegraph -> serena` создаёт три верные.

## 14. Команды

Общие ключи: `--root`, `--data`. Коды выхода: 0 успех, 1 проверяемое отрицание (нарушение, отказ, неверный якорь), 2 ошибка аргументов, окружения или кодировки.

В примерах ниже `HM` это `python3 .agents/skills/harness-router/children/mirror/scripts/harness_mirror.py`.

| Команда | Пишет | Код 1 когда |
|---|---|---|
| `scan` | узлы, кеш | коллизия `node_id` |
| `prompt` | ничего | узел не найден |
| `apply` | узел | ошибка валидации анализа |
| `get` | ничего | узел не найден |
| `set` | канон, узел, история, кеш, граф | зеркало, неверный блок, сбой обратимости |
| `build` | `graph.json`, `index.html` | нет каталога узлов |
| `check` | ничего | найдены нарушения |
| `serve` | по запросу | смотри раздел про API |

### 14.1 scan

Полный конвейер описан в разделе 8. Ключ `--force` игнорирует кеш целиком.

### 14.2 prompt

Печатает задание для одного узла: путь, `node_id`, тип, список блоков, правила ответа, список неразрешённых целей из литерального прохода. Текст блоков не печатается, агент читает исходный файл сам.

Правила задания: описание в одно-два предложения, `trigger_condition` из точных фраз, `sources_of_truth` с путями, связи только с `origin: agent` и точным якорем, тип связи из таксономии, запрет выдумывать путь, ответ строго в формате `description`, `lifecycle`, `sources_of_truth`, `relations`, `global_relations`.

### 14.3 apply

Принимает файл (`--json`) или stdin. Проверки:

- набор ключей верхнего уровня ограничен пятью полями;
- у каждой связи есть обязательные поля: `block_id`, `target_name`, `target_type`, `relation_type`, `origin`, `resolution`, `anchor_text`;
- `relation_type` из таксономии, `target_type` из списка типов, `origin` только `agent`;
- `resolution` из допустимых значений;
- блок существует;
- якорь непустой и является точной подстрокой блока;
- для `resolved` нужен `target_node_id`, и он должен быть в индексе (кроме `mcp`).

При ошибках узел не меняется, печатается список причин, код 1. При успехе поля сливаются, `analysis` получает `filled` и модель `agent`. Повторный вызов идемпотентен: связь с тем же ключом заменяется. Если один якорь используется несколькими связями блока, печатается предупреждение в stderr.

### 14.4 get

Печатает узел и его ребра из `graph.json`, раздельно входящие и исходящие. Если граф ещё не собран, ребёр нет.

### 14.5 set

Порядок операций:

1. загрузка узла, отказ для зеркала;
2. поиск блока, замена текста в копии узла;
3. сборка файла из всех блоков;
4. проверка, что новое содержимое декодируется обратно;
5. проверка, что исходный файл не изменился с момента чтения узла;
6. атомарная запись нового содержимого с BOM при необходимости;
7. побайтовая проверка после записи, при расхождении восстановление исходника;
8. сохранение прошлой версии узла в `nodes/.history/<safe>.vN.json`, номер версии увеличивается;
9. повторный разбор узла и запись кеша;
10. пересборка графа, статистика попадает в ответ.

Вывод: `{"status": "ok", "node": ID, "block": bNNN, "backup": N, "stats": {...}}`. Если собрать граф не удалось, статистика равна null, причина в stderr, файл уже записан.

### 14.6 build и check

`build` пишет `graph.json`, копирует просмотрщик в `index.html` и печатает путь, число узлов, логических карточек, рёбер и расхождений.

`check` ничего не пишет. Проверки перечислены в разделе 16.

### 14.7 serve

Статический сервер с API. Слушает `127.0.0.1` по умолчанию, `--port` по умолчанию 8090. При не-loopback адресе печатает предупреждение.

Маршруты:

| Метод и путь | Тело | Ответ |
|---|---|---|
| `GET /` и статика | нет | просмотрщик, `graph.json`, `nodes/*.json` |
| `GET /api/health` | нет | `{status, writable: true, stats}` |
| `GET /api/node?id=ID` | нет | `{status, node}` или 404 |
| `PUT /api/node?id=ID` | `{block_id, raw_content}` | результат `set` и статистика графа |
| `POST /api/rebuild` | нет | `{status, stats}` |
| `OPTIONS` | нет | 204 или 403 |

Коды ошибок API: 404 неизвестный маршрут, 400 битый JSON или отказ по правилам (`MirrorError` с кодом 1), 403 сторонний `Origin`, 500 внутренняя ошибка или отказ с кодом 2.

Политика доступа:

- заголовок `Access-Control-Allow-Origin` не бывает `*`, он возвращается только для loopback `Origin`;
- мутации требуют loopback `Origin` и loopback `Host`, иначе 403 и файл не меняется;
- запросы без `Origin` (curl, агент) разрешены, но запись всё равно ограничена каноном и loopback-адресом.

Одновременные изменения сериализуются блокировкой `flock` на файле `.lock`. Блокировка работает на Unix, на Windows вырождается в отсутствие защиты.

## 15. Граф

`graph.json`, схема `harness-graph/2.3`. Рёбра схлопнуты по тройке источник-цель-тип: одно ребро на пару и тип, поля `blocks` и `anchors` показывают, сколько блоков и какие фрагменты дали связь. `stats.relation_blocks` хранит исходное число упоминаний.

### 15.1 Узел графа

| Поле | Смысл |
|---|---|
| `id` | `node_id` |
| `logical_id` | `projection_of` или собственный `id`: одна карточка на все зеркала |
| `label` | имя файла у скрипта, иначе `name` |
| `heading` | первый заголовок файла для читаемого названия в панели |
| `type`, `environment`, `canonical`, `projection_of`, `transferable` | из `meta` |
| `path`, `dir`, `file` | путь, каталог, имя файла |
| `json` | относительный путь к узлу, null у синтетического MCP |
| `description` | из `meta` |
| `analysis` | `pending`, `filled` или `n/a` |
| `state` | у зеркала `equal` или `drift` |
| `summary`, `details` | короткая русская подпись и подробное описание из `analysis` |
| `synthetic`, `mcp` | только у сервера: признак и параметры |

### 15.2 Ребро

`source`, `target`, `type`, `origin`, `block_id` (null для связей уровня файла и зеркал), `anchor`, у зеркал ещё `state`.

Ребро попадает в граф только при `resolution: resolved` и непустом `target_node_id`, и только если обе стороны есть среди узлов. Остальные считаются в `stats.unlinked_relations`. Это нормально: цель может существовать в проекте, но быть вне текущего скана.

### 15.3 Счётчики

`nodes`, `canonical` (включая синтетические MCP), `mirrors` (nodes минус canonical), `logical`, `edges`, `drift`, `pending_analysis`, `mcp`, `unlinked_relations`.

`relation_types` считает все связи до фильтра по разрешению, поэтому сумма по типам может быть больше числа рёбер.

Сборка детерминирована: одинаковый вход даёт побайтово одинаковый файл. Дубли рёбер схлопываются по ключу из источника, цели, типа, блока и якоря, порядок сортируется.

## 16. Проверки check

1. Уникальность `node_id` среди файлов узлов.
2. Наличие исходного файла.
3. Совпадение `content_sha256` с файлом.
4. Обратимость: склейка блоков плюс BOM равна байтам файла.
5. У канона нет `projection_of`.
6. У зеркала с `projection_of` цель существует.
7. У каждой связи `origin` равен `auto` или `agent`.
8. Тип связи из таксономии.
9. У связи агента непустой якорь, который есть в блоке.
10. `resolution` из допустимых значений.
11. `unresolved` не хранит цель.
12. `missing` хранит путь.
13. `resolved` (кроме `mcp`) хранит путь.
14. У связи `mcp` есть `target_node_id`.
15. Разрешённая цель существует на диске.
16. `cache.map` и файлы узлов согласованы в обе стороны.

Отчёт: `status`, `nodes`, `nodes_without_projection`, `errors`. `nodes_without_projection` это файлы сред без пары в каноне, это норма, а не ошибка.

## 17. Просмотрщик

Один HTML-файл без внешних ресурсов. Данные читает относительными путями, поэтому работает и в панели проекта, и на любом статическом сервере.

Загрузка:

1. `fetch("api/health")`: успех означает доступную запись, ошибка оставляет режим чтения;
2. `fetch("graph.json")`: счётчики и граф;
3. по клику `fetch("nodes/<файл>.json")`: полная карточка.

Адрес хранит состояние: `#node=<id>`, `?mode=type`, `?linked=1`.

Элементы управления: поиск по имени и пути, фильтр типа, переключатели "показать зеркала", "связи", "только связанные", выбор режима, кнопки масштаба, "уместить" и "свернуть", масштаб колесом, перетаскивание полотна.

Режимы раскладки:

- `иерархия`: дерево папок по пути, папки сворачиваются кликом;
- `связи по типам`: колонки по типу в фиксированном порядке, порядок карточек внутри колонки считается по barycenter за шесть проходов, поэтому дуги пересекаются меньше.

Карточка файла показывает имя, путь без префикса среды, тип, среду, статус анализа, число зеркал и метку `drift`. Наведение подсвечивает соседей и гасит остальные линии.

Панель узла: идентификатор, тип, среда, путь, проекция и состояние, переносимость, блоки с окончаниями строк и BOM, описание, источники правды, список блоков, редактор, кнопки копирования `node_id` и команды `get`, входящие и исходящие связи с якорем.

Редактор: по умолчанию открыт первый блок, кроме frontmatter. Сохранение отправляет `PUT` с `block_id` и текстом. Перед отправкой проверяется режим: без API или у зеркала сохранение отклоняется с сообщением. После успеха граф перечитывается, карточка открывается заново.

Синтетический узел MCP показывает транспорт, команду, число аргументов, имена переменных, список использующих файлов и исходящих связей. Значений переменных в графе нет.

Безопасность: все поля экранируются, код из узлов не выполняется, внешние ссылки не открываются автоматически.

## 18. Безопасность и целостность

- Секреты отсеиваются по имени и по шаблонам значений до создания узла.
- Абсолютные пути не попадают в узлы, только относительные с прямым слэшем.
- Запись канона: проверка обратимости до записи, атомарная замена, побайтовая проверка после, откат при расхождении.
- Проверка, что файл не изменился между чтением узла и записью, защищает от гонки с редактором.
- API не принимает сторонний `Origin`, поэтому чужая вкладка не перепишет харнес.
- `set` и `PUT` пишут только в канон.
- История версий лежит в `.history` и не удаляется автоматически.

## 19. Переносимость и среды

Ядро не знает названий проекта и IDE. Среда определяется по префиксу пути, проектные значения живут в `ADAPTERS.local.md` и не переносятся.

Скил работает в Cursor, Kilo Code, Codex, Antigravity, Gemini, Agents и DeepSeek Harness. Запуск из копии и из любого каталога даёт тот же результат.

Перенос в другой проект:

1. скопировать каталог скила без `ADAPTERS.local.md` и `.cursor/.state`;
2. выполнить `scan --root <новый проект>`;
3. при другом имени канона передать `--paths`.

## 20. Типовые сценарии

### 20.1 Первая сборка

```bash
python3 .agents/skills/harness-router/children/mirror/scripts/harness_mirror.py scan
python3 .agents/skills/harness-router/children/mirror/scripts/harness_mirror.py build
python3 .agents/skills/harness-router/children/mirror/scripts/harness_mirror.py check
```

### 20.2 Файл изменили руками

`scan` читает файл заново, сравнивает хеш с кешем, разбирает при расхождении. Специальных действий не нужно. Повторный `scan` без изменений печатает `written: 0`.

### 20.3 Поменяли формат разбора

Поднять `PARSER_VERSION`, при изменении структуры ещё и `SCHEMA_VERSION`, затем `scan`. Кеш сам признает все записи устаревшими.

### 20.4 Добавили MCP-сервер

Дописать запись в `.cursor/mcp.json`, выполнить `scan`, затем `build`. Узел появится автоматически, связи `invokes_tool` пересчитаются по текстам.

### 20.5 Кнопка «Пересобрать граф харнеса» в панели

Кнопка запускает `rebuild`: `scan` освежает узлы по изменённым файлам, включая ранее проиндексированные зеркала, затем `build` пишет `graph.json`. Ручной `scan` перед кнопкой не нужен. После `rebuild` команда `check` проходит без ошибок `content_sha256 mismatch` и `lossless round trip failed`.

### 20.5 Правим блок через агента

```bash
HM get --node rule:doc-rules
HM set --node rule:doc-rules --block b003 --content new-section.md
```

`set` сам пересобирает граф и сохраняет прошлую версию узла.

### 20.6 Цель связи исчезла

После `scan` связь получает `missing` с сохранённым путём. В карточке видно, что цель потеряна. Если файл вернуть, следующий `scan` восстановит `resolved`.

### 20.7 Изменили канон, нужны зеркала

```bash
bash .agents/skills/harness-router/children/environment-sync/scripts/sync-agent-views.sh
HM scan --include-mirrors
HM build
python3 .cursor/scripts/harness/verify_parity.py --canonical .agents/skills --manifest .doc/skil_data/harness-core/parity-report.json --check
```

### 20.8 Смысловой анализ узла

```bash
HM prompt --node skill:task-doc
# агент читает файл и возвращает analysis.json
HM apply --node skill:task-doc --json analysis.json
```

## 21. Ограничения

- Связи описывают только явные упоминания в тексте.
- Заголовки Markdown внутри блоков кода не отличаются от обычных.
- `---` в начале файла может быть принято за frontmatter.
- Разбиение скриптов эвристическое, вложенные функции остаются в блоке родителя.
- Смысловой слой пуст, пока агент не выполнил `prompt` и `apply`.
- Правка идёт только в канон, зеркала пересобирает синхронизация проекта.
- Одновременная правка двумя редакторами упрётся в последнюю запись: обратимость поймает повреждение, но не конфликт.
- Блокировка записи полноценна только на Unix.
- Просмотрщик не хранит историю версий в интерфейсе, старые версии лежат в `.history`.
- Симлинки не раскрываются, читается реальный файл.

| Скан | запись, сборка, проверка, число узлов и зеркал, инкрементальность, пропуск секретов, переразбор при смене `schema_version` |
| Зеркала | наследование анализа, `logical_id`, ребро `mirrors`, обнаружение `drift`, отказ записи в зеркало |
| Связи | разрешение относительных путей от файла-источника, наличие рёбер канона, имя без пути внутри скила, переход в `missing` при удалении цели |
| MCP | синтетические узлы, отсутствие значений переменных, контекст для неоднозначных имён, имена файлов не считаются серверами |
| Анализ | отказ при неверном якоре, при `origin: auto` в анализе, при неизвестном блоке, при несуществующей разрешённой цели |
| Правка | отказ зеркалу, запись канона, история версий, BOM, пересборка графа |
| Устойчивость | детерминированность графа, определение корня от скрипта |
