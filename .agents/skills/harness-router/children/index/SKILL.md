# Harness Index

Индекс харнеса это карта правил, скилов, скриптов и MCP-конфигов. Скил описывает, как агенту читать эту карту, получать картину по одному элементу и проверять, что харнес устроен правильно.

## Когда применять

- нужно понять, что делает скил или правило, без чтения всего файла;
- нужно увидеть, с чем элемент связан и на какой фразе основана связь;
- после правок харнеса нужно проверить целостность индекса;
- нужно провести смысловой аудит харнеса по смыслу;
- нужно заполнить или исправить `summary`, `details`, триггер и связи.

Скил не заменяет правила проекта и не запускает продуктовые проверки. Он работает только с индексом харнеса.

## Что такое индекс

- Источник правды это один JSON на один файл харнеса в каталоге данных `nodes/`.
- `graph.json` это производная сборка: узлы, рёбра и подписи. Его не читают целиком, он весит около 1.6 МБ.
- `cache.map` хранит хеши и версии разбора, по нему скан пропускает неизменённые файлы.
- Область индекса это только харнес: `.cursor/`, `.codex/`, `.kilo/`, `.agents/`, `.dsh/`. Документация `.doc/`, задачи и продуктовый код не индексируются, связи на них отбрасываются.
- По умолчанию каталог данных `.agents/skills/harness-router/children/mirror/.data`, путь меняется ключом `--data`, корень проекта ключом `--root`.

Команды запускаются из корня проекта через скил mirror:

```text
вызови скил mirror, команда <команда> [аргументы]
```

## Картина по одному элементу

Порядок для скила:

1. `review --skill NAME` даёт дайджест: подпись, подробное описание, триггеры, источники, заголовки разделов с первой строкой, рёбра с якорями и вопросы для проверки.
2. `bundle --skill NAME` даёт все файлы скила и уникальные рёбра, если нужен обзор шире одного `SKILL.md`.
3. `get --node ID` даёт полный текст блоками, только когда дайджеста не хватило.
4. `review --node ID` делает то же для одного правила.

Порядок для всего харнеса:

1. `lint` находит кандидатов на смысловую проверку и делит их на уровни.
2. `review --all` показывает все скилы и правила одной таблицей.
3. Дальше `review --skill` или `review --node` по выбранным элементам.

## Команды

| Команда | Назначение | Размер ответа |
|---|---|---|
| `scan` | обновить узлы по исходным файлам | короткая сводка |
| `build` | пересобрать `graph.json` и просмотрщик | короткая сводка |
| `check` | проверить инварианты индекса | отчёт с ошибками |
| `get --node ID` | узел с блоками и рёбрами | 16 КБ в среднем |
| `get --node ID --slim` | узел без блоков: подписи, триггер, источники, рёбра | 15 КБ |
| `bundle --skill NAME` | скил целиком: файлы, триггеры, источники, уникальные рёбра | 20 КБ |
| `audit --node ID` или `--skill NAME` | покрытие, рёбра, неразрешённые связи, предупреждения, вердикт | 19 КБ |
| `lint` | проверки всего канона с уровнями важности | сводка и список находок |
| `review --all` | обзор всех скилов и правил | 15 КБ |
| `review --skill NAME` | пакет смыслового аудита по скилу | 10-30 КБ |
| `review --node ID` | пакет смыслового аудита по правилу или файлу | 10-30 КБ |
| `prompt --node ID` | задание агенту на смысловой разбор | текст задания |
| `apply --node ID --json FILE` | записать смысл в узел | короткий ответ |
| `set` | заменить блок или целый файл скила либо правила | короткий ответ |
| `serve` | просмотрщик и API правки на 127.0.0.1 | адрес |

### scan

```
scan [--paths PATH ...] [--include-mirrors] [--include-dsh] [--force]
```

Вход: исходные файлы харнеса. Выход:

```json
{"status":"ok","written":3,"skipped":118,"inherited":525,"removed":0,"downgraded":0,"nodes":729}
```

`written` сколько файлов разобрано заново, `skipped` сколько пропущено по совпадению хеша и версий, `inherited` сколько зеркал получило смысл канона, `removed` сколько узлов удалено, `downgraded` сколько связей потеряло цель.

- `--paths` разбирает только указанные пути, остальные узлы не трогает;
- `--include-mirrors` добавляет `.codex`, `.kilo`, `.agents`; legacy `.antigravity` и `.gemini` не генерируются;
- `--include-dsh` добавляет `.dsh`;
- `--force` игнорирует кеш.

Файлы харнеса вне текущего набора целей всё равно обновляются, если изменились их байты. Поэтому скан без флагов не держит старую версию зеркала.

### build

```
build
```

Читает все узлы, схлопывает рёбра по паре и типу, пишет `graph.json` и копию просмотрщика. Выход:

```json
{"status":"ok","graph":"...graph.json","nodes":748,"logical":221,"edges":2102,"drift":2}
```

`edges` это число уникальных рёбер, `drift` число зеркал, которые разошлись с каноном. `graph.json` всегда пересобирается из узлов, удалять его безопасно.

### check

```
check
```

Проверяет:

- обратимость: склейка блоков даёт исходные байты;
- `content_sha256` узла против файла;
- область харнеса: связи не выходят за префиксы;
- согласованность `cache.map` и файлов узлов;
- существование целей у разрешённых связей;
- корректность `resolution` и якорей.

Выход:

```json
{"status":"passed","nodes":729,"nodes_without_projection":84,"errors":[]}
```

Код выхода 0 при успехе, 1 при ошибках.

### get

```
get --node ID [--slim]
```

Вход: `node_id` вида `skill:gototask`, `rule:code-editing`, `script:gototask-gototask-ps1` или `config:gototask-config`.
Узлы `mcp:{server}` синтетические: они есть в графе и просмотрщике, файла в `nodes/` у них нет, поэтому `get`, `review` и `audit` по ним отвечают `node not found`. Смысл сервера читается в правиле `.cursor/rules/mcp/{server}.mdc` и в документе `.doc/harnes/mcp/{server}.md`.

Полный ответ: узел с `meta`, `reconstruction_meta`, блоками, связями и `analysis`, плюс `edges.incoming` и `edges.outgoing`.

Ответ с `--slim`: вместо блоков подпись, подробное описание, триггер, источники, число блоков и размер файла. Блоки не передаются, поэтому ответ дешевле.

Код выхода 1, если узел не найден.

### bundle

```
bundle --skill NAME
```

Вход: имя папки скила, например `gototask`. Выход:

- `main`: `node_id` главного файла;
- `files`: все файлы скила с подписью, статусом анализа и размером;
- `triggers`: триггеры по файлам;
- `sources_of_truth`: источники правды;
- `edges.outgoing` и `edges.incoming`: уникальные рёбра с `blocks` и `anchors`;
- `unresolved`: связи со статусом `ambiguous`, `unresolved`, `missing`.

Код выхода 1, если скил не найден.

### audit

```
audit --node ID
audit --skill NAME
```

Вход: ровно один из двух ключей. Выход:

```json
{
  "target": {"node":null,"skill":"gototask"},
  "files": [{"id":"skill:gototask","analysis":"filled","summary":"...","details":"..."}],
  "triggers": [{"node":"skill:gototask","text":"always"}],
  "edges": {"outgoing":[...],"incoming":[...]},
  "unresolved": {"count":0,"items":[]},
  "coverage": {"files":2,"filled":1,"pending":1,"with_summary":1,"with_details":1},
  "warnings": ["config:gototask-config: смысловой анализ не заполнен"],
  "notes": ["skill:gototask: не задан триггер"],
  "verdict": "review"
}
```

`warnings` влияют на `verdict`: незаполненный анализ, пустая подпись, неразрешённые связи. `notes` не влияют и показывают пробелы: нет триггера, нет источников правды, нет входящих или исходящих связей.

Код выхода 2 при неверных аргументах, 1 если цель не найдена.

### lint

```
lint
```

Проверяет весь канон без модели. Уровни:

| Уровень | Что значит |
|---|---|
| `error` | структурная поломка: нет `SKILL.md`, битая связь |
| `warn` | кандидат на смысловую проверку: цикл делегирования, ссылка на себя, одинаковые подписи |
| `info` | пробел покрытия: нет триггера, нет источников правды, изолированный узел, скрипт без упоминаний |

Выход: `issues` с полями `kind`, `node`, `detail`, `severity`, плюс сводки `by_kind` и `by_severity`. Всегда код 0, это обзор, а не гейт.

Проверки: циклы по `delegates_to` без зеркал и самоссылок, ссылка на себя, изолированные узлы, скрипты без упоминаний, одинаковые подписи, наличие `SKILL.md`, неразрешённые связи у скилов и правил, пустые `summary` и `details`, отсутствие триггера и источников правды.

### review

```
review --skill NAME
review --node ID
review --all
```

Пакет по одному элементу:

- `files`: подпись, подробное описание, триггер, источники и `outline` из пар «заголовок раздела» и «первая содержательная строка»;
- `edges`: уникальные рёбра с числом блоков и до трёх якорей;
- `issues`: находки `lint` только по этой цели;
- `questions`: что проверить по смыслу для этого типа элемента.

`review --all` отдаёт список всех скилов и правил: `node`, `type`, `path`, `summary`, статус анализа, наличие триггера, число источников и виды замечаний. Это карта для выбора, что смотреть глубже.

Код выхода 2 при неверной комбинации аргументов, 1 если цель не найдена.

### prompt и apply

```
prompt --node ID
apply --node ID --json FILE [--model NAME]
```

`prompt` печатает задание: путь, `node_id`, блоки, правила и список неразрешённых целей. Агент читает исходный файл и возвращает только смысл:

```json
{
  "summary": "одна строка до 90 символов",
  "details": "два-четыре предложения, только факты",
  "description": "одно-два предложения",
  "lifecycle": {"trigger_condition": "always"},
  "sources_of_truth": [],
  "relations": [],
  "global_relations": []
}
```

`apply` проверяет длины, якоря и типы связей, затем ставит `analysis.status = filled` и сохраняет узел. Ошибка не меняет узел и возвращает код 1.

### set

```
set --node ID --block bNNN --content FILE
set --node ID --file --content FILE
```

Первый вариант меняет один блок и пересобирает файл из блоков с проверкой обратимости. Второй заменяет файл целиком и разрешён только для канонических скилов и правил.

Перед записью проверяются канон, тип, переводы строк и BOM, затем файл пишется атомарно, читается обратно и заново делится на блоки. Прошлая версия узла уходит в `nodes/.history/`. Зеркала после правки пересобирает штатная синхронизация проекта.

### serve

```
serve [--host 127.0.0.1] [--port 8090]
```

Отдаёт просмотрщик, `graph.json` и API правки. `GET /api/health` показывает статистику и доступность записи, `PUT /api/node?id=ID` принимает `raw_file` или пару `block_id` и `raw_content`, `POST /api/rebuild` пересобирает граф. Запись принимается только с loopback-адреса.

## Поля, которые важно понимать

- `summary` короткая подпись для карточки, `details` подробное описание, оба заполняет агент, язык русский, только факты;
- `analysis.status` это `pending`, `filled` или `n/a`;
- связь содержит `type`, `origin`, `resolution`, `blocks` и `anchors`;
- `resolution`: `resolved` цель найдена, `ambiguous` несколько кандидатов, `unresolved` цели нет, `missing` файл цели исчез, `external` цель вне проекта;
- `blocks` сколько блоков дали связь, `anchors` фрагменты текста, на которых она основана;
- `drift` расхождение зеркала с каноном;
- `unlinked_relations` связи, чья цель есть в проекте, но вне текущего скана.

Типы связей: `delegates_to`, `governed_by`, `reads_context`, `invokes_tool`, `enforces_gate`, `synced_by`, `constrained_by`.

## Правила работы

- Не редактировать `.data` руками и не читать `graph.json` целиком.
- Порядок после правок файлов: `scan`, затем `build`, затем `check`.
- Если менялся канон, зеркала пересобирает штатная синхронизация проекта, затем `scan` и `build`.
- Писать смысл только через `apply`, файлы только через `set`.
- `set --file` и API записи разрешены только для скилов и правил.
- Если `check` сообщает `content_sha256 mismatch`, повторить `scan`.
- Если `check` сообщает `relation leaves harness scope`, убрать связь на путь вне харнеса.
- Если после `build` растёт `drift`, выполнить синхронизацию зеркал и повторить `scan`, `build`.

## Типовые ошибки

| Симптом | Причина | Действие |
|---|---|---|
| `graph.json не найден` | граф не собран | `build` |
| `node not found` | неверный `node_id` | `review --all` или `bundle --skill` |
| `editable types are rule, skill` | попытка правки скрипта или конфига | править исходник обычным способом |
| `unresolved relation keeps a target` | старый узел, состояние лечится сканом | `scan` |
| `mirror is generated` | попытка правки зеркала | править канон и синхронизировать |
| пустая карточка | у узла нет `summary` и описания | `prompt`, затем `apply` |
