## Суть

Запрос: после успешного push предложить обновление diff и документирование с HTML
и текстом Jira. Одно явное согласие запускает цепочку. В чат возвращается ссылка,
полные результаты остаются в документации и HTML.

## Аудит

- task-doc Post-step: сам формирует модель, дублируя ответственность HTML-skill;
  существующий HTML пропускается независимо от свежести.
- task-change-report: jira_reply поддержан схемой и renderer, но вызов jira-report
  не определён. Документированы отсутствующие CLI-флаги --no-copy-sources и
  --open-source-cdn. --open принят CLI, но открытия браузера код не выполняет.
- jira-report: запрет вывода вне чата мешает встраиванию текста в HTML.
- task-doc: вопросы об обновлении существующей архитектуры противоречат
  doc_rules.md и task-doc rule, которые требуют B3 без повторного согласования.
- Общая проблема: несколько финальных ответов и повторное чтение одних источников.

## План

1. send-to-git: после успешного push проверить diff по артефактам и git, предложить
   одну цепочку с фразой "Напишите да, если сделать". Отказ, ошибка, commit-only
   не запускают post-push цепочку. Согласие на push не равно согласию на отчёты.
2. task-doc: сохранить B0-B4.5 и шаблон, передать проверенный контекст HTML-skill;
   убрать самостоятельную сборку модели и многословный финальный ответ.
3. task-change-report: читать doc.md, сохранять все разделы; вызывать jira-report
   как вложенный skill. Не вызывать task-doc обратно. Проверять свежесть и права
   на пересборку; --force только при явном согласии. Исправить описание CLI.
4. jira-report: сохранить самостоятельный режим и все правила стиля; добавить
   встроенный режим без чата. Вернуть текст, скриншоты и ограничения в HTML-модель.
5. Проверить текстовые контракты, CLI --help, рендеринг готового fixture в temp,
   все представления и отсутствие правок продукта.

## Контракт передачи

В контексте вызова передаются task ID, scope/стадия, commit/ветка, пути и отпечатки
источников, доказательства поведения и тестов, решения пользователя, разрешение
на refresh и уже завершённые шаги. Это не новые CLI-флаги. Повторно используются
только неизменённые и проверенные источники. Новая сессия или новый scope требует
проверки заново. Не пропускаются MCP gates и анализ непокрытых фактов.

## Сохранение качества

Сохраняются архитектура и обратные ссылки, индекс задач, полный task, стадии,
логика before/after/delta/rationale, diff файлов и роли, Mermaid, скриншоты, тесты,
риски, evidence, вопросы тимлида, Jira-текст с релизом и отдельными вложениями.
Внешней публикации Jira, commit/push или новых тестовых прогонов не добавляется.
Стоимость: один набор источников, один Jira-текст, один render; сравнение hashes
дешевле повторного анализа. Fallback: краткая причина неполного результата, без
выдуманных версий, ссылок или успешных тестов.

## Откат

Отменить только изменения этой сессии в четырёх SKILL.md и синхронизировать views.
Продуктовые файлы, исторические аудиты и отчёты задач не затрагивать.

## Машинные проверки: второй этап

По отдельному согласию добавляются schema workflow-context, read-only preflight,
структурированный Jira-результат, безопасная запись renderer, scoped stage inputs,
проверка полноты/свежести и регрессионные тесты. Общие поля и алгоритмы находятся
в schema/scripts HTML-skill, другие skills ссылаются на них, не копируют реализацию.
Оценка стоимости ограничивается измеренными счётчиками и временем. Реальный
post-push workflow и токены не измеряются этим тестом.

### Приёмка второго этапа

1. Отказ/ограничение HTML или Jira сохраняется в контексте и не обходится renderer.
2. Изменённый источник, пропавший evidence или невалидная модель блокируют результат.
3. Документация обновляется, checkpoint принимает только подтверждённые артефакты
   шага, HTML получает свежую документацию, повторный запуск использует результат.
4. Старый HTML не перезаписывается без force; ошибка валидации его не повреждает.
5. Полный состав модели и Jira-текст сохраняется; scoped report не получает
   посторонние файлы и тесты из общей задачи.
6. Hash evidence проверяет неизменность, но не заменяет содержательную проверку
   фактов, scope и разрешения человеком/агентом.
7. Повторный успешный запуск даёт reuse без повторной записи; счётчики проверяются,
   заявлений об измеренных токенах без телеметрии нет.

Реализация второго этапа добавила `workflow_contract.py` с read-only `preflight()` и
`checkpoint()`. Checkpoint разрешает свежий `doc.md` только по artifact успешно
проверенного документационного шага и возвращает новый контекст без записи. Renderer
получает его через `--context`; модель и HTML валидируются до записи, существующий
HTML не переписывается без `--force`, stage scope проверяется по явным источникам.
