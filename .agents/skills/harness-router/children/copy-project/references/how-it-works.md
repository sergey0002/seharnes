# Как работает copy-project

Скил переносит приложение, а не харнес. Он создаёт копию Git-состояния в новой
папке и готовит отчёт о том, что нужно доделать для запуска.

## Что переносится

| Объект | Поведение |
|---|---|
| Отслеживаемые Git файлы | Копируются в Target с сохранением режима |
| Незакоммиченные tracked-изменения | Только с флагом `--include-tracked-changes` |
| `.git` | Копируется целиком: история, ветки, remotes, индекс. `worktrees/` и lock-файлы удаляются |
| Harness | Исключается по списку путей |
| Незатреканные и ignored файлы | Не копируются |
| Секреты в рабочих файлах | Не копируются и не печатаются; история `.git` сохраняется как есть |
| База данных и дампы | Не копируются и не импортируются |

Harness-пути исключения: `.agents/`, `.cursor/`, `.codex/`, `.kilo/`, `.qoder/`,
`.qwen/`, `.serena/`, `.dsh/`, `.codegraph/`, `.codeprism.toml`, `.cbmignore`,
`.doc/`, `AGENTS.md`. Список задан в массиве `HARNESS_PATTERNS` скрипта.

Секретные env-файлы исключаются отдельно: `.env`, `.env.*` кроме `.example`,
`.dist`, `.sample`, `.template`, и файлы `*.env`. Игнорируемые Git пути не
попадают в `git ls-files`; явные исключения также защищают от tracked harness и
секретных файлов. Например, `.dsh/` локально игнорируется в этом репозитории,
но `copy-project` не перенесёт его и в случае tracked-каталога.

## Порядок работы скрипта

1. Проверяет аргументы и существование Source.
2. Убеждается, что Source является Git-репозиторием.
3. Вычисляет абсолютные пути Source и Target.
4. Запрещает совпадение и перекрытие путей в любом направлении.
5. Отказывается работать при существующем Target без `--force`.
6. Отказывается работать при найденном `.gitmodules`, атрибуте `filter=lfs` или
   если `.git` не каталог (linked worktree, submodule, `.git`-файл).
7. Создаёт staging-каталог рядом с Target: `${TARGET}.partial.$$`.
8. Читает `git ls-files -z` и копирует каждый путь, кроме harness и секретных
   env-файлов, через `cp -p`.
9. Проверяет символические ссылки в копируемом наборе и завершает работу с кодом 3.
10. При включённых tracked-изменениях добавляет изменённые и staged файлы.
11. Копирует `.git`, удаляет в копии `worktrees/` и lock-файлы, добавляет
    `STARTUP-REQUIRED.md` в `.git/info/exclude`, проверяет читаемость репозитория
    и считает размер `.git` и число незакоммиченных изменений.
12. Собирает отчёт: шаблоны окружения, compose-файлы, lock-файлы, каталоги схемы,
    переменные окружения, найденные в коде.
13. Удаляет старый Target при `--force` и переименовывает staging в Target.
14. Печатает итог: коммит, число скопированных файлов, число исключённых
    harness-путей и секретных env-файлов, размер `.git` и состояние Git.

Staging защищает от частичной копии: Target появляется только после успешного
копирования. При ошибке staging удаляется через `trap`.

## Отчёт STARTUP-REQUIRED.md

Отчёт создаётся в корне Target. Разделы:

- источник, коммит, ветка;
- счётчики: скопировано, tracked-изменений, harness исключено, секретных env-файлов
  исключено, незатреканных не перенесено;
- Git: размер `.git`, число удалённых worktree-регистраций, число незакоммиченных
  изменений в Target, имена remotes;
- список намеренно неперенесённого;
- шаблоны окружения: `.env.example`, `.env.dist`, `.env.sample`;
- compose-файлы;
- lock-файлы;
- каталоги схемы: `migrations`, `migrate`, `sql`;
- переменные окружения, найденные по шаблонам `getenv('KEY')`, `$_ENV['KEY']`,
  `process.env.KEY`;
- порядок ручной проверки.

Значения переменных в отчёт не попадают: скрипт печатает только имена.

## Переменные окружения

Поиск идёт по скопированному дереву. Найденный список является кандидатом, а не
доказательством полного конфига. Агент сверяет его с шаблоном окружения и с кодом
чтения конфигурации. Конфиги в виде массивов и собственных загрузчиков могут не
попасть в список, поэтому ручная сверка обязательна.

## Ручная проверка

Чек-лист лежит в `assets/startup-checklist.md`. Он закрывает семь групп: Git-состояние,
окружение, зависимости, база, файлы вне Git, запуск, итог. Статус `ready` допустим
только после закрытия обязательных пунктов.

## Флаги и коды выхода

| Флаг | Назначение |
|---|---|
| `--source DIR` | Корень Git-репозитория |
| `--target DIR` | Новая папка |
| `--force` | Заменить существующий Target |
| `--include-tracked-changes` | Добавить незакоммиченные tracked-изменения |
| `--report FILE` | Скопировать отчёт в указанный путь |

Коды: 0 успех, 1 ошибка аргументов или существующий Target, 2 Source не Git,
3 запрещённое состояние: submodules, LFS, символическая ссылка, `.git`-файл.

## Чего скрипт не делает

- не устанавливает зависимости;
- не запускает приложение;
- не проверяет подключение к базе;
- не переносит ignored данные: загрузки, кэш, сгенерированные файлы;
- не вычищает секреты из истории `.git`;
- не меняет Source: индекс, `.gitignore`, `.git` и рабочие файлы остаются как были.

## Подводные камни

- `.git` копируется как есть: ветки, remotes, reflog и hooks сохраняются. URL с
  токенами в `.git/config` остаются в копии.
- `worktrees/` источника удаляется в копии. Иначе `git worktree remove` из копии
  мог удалить worktree исходного репозитория.
- Lock-файлы `index.lock`, `HEAD.lock`, `config.lock`, `shallow.lock` удаляются
  из копии.
- Если harness или секретные env были tracked, копия покажет их как удалённые:
  индекс перенесён, рабочие файлы исключены.
- `STARTUP-REQUIRED.md` добавляется в `.git/info/exclude` копии.
- Незапушенные коммиты остаются в копии, `git status` покажет `ahead N`.
- `.git` может быть большим; размер выводится в отчёте.
- `.git`-файл (linked worktree, submodule) не поддерживается и даёт код 3.

## Отличие от new-project

`new-project` переносит kit харнеса и режимы `migrate`, `clean`, `update`.
`copy-project` переносит приложение и не устанавливает harness в Target.
Смешивать эти задачи в одном запуске нельзя.
