# Send to Git (отправь в гит)

Скил **не** коммитит и **не** пушит до явного подтверждения.

## Триггеры

- «отправь в гит» / «отправь в git»
- «закоммить и запушь» / «предложи коммит» / «send to git»
- «запушь задачу»

**Не путать с:** gototask, task-diff.

## Формат коммита

Одна строка, русский, номер текущей задачи в начале:

```
{N} суть правки простыми словами
```

Примеры: `2392 коды гражданства NONE/NOT_EXIST`, `2410 переход в общественное достояние`.

Запрещено: English, `feat:`, Conventional Commits, body, «WIP».

`{N}` из текущей ветки (`features/#2410` → `2410`) или из сообщения пользователя.

## Workflow

### Шаг 1. Проверка (тихо)

```bash
git status
git branch --show-current   # пусто = detached HEAD, дальше не идти
git diff
git diff --staged
git status -sb
git log -5 --oneline
```

Определи `{N}` и текущую ветку. Секреты (`.env`, credentials, ключи) - **не** включать.

### Шаг 2. Файлы задачи

1. Собрать список изменённых и untracked.
2. **Не** предлагать слепой `git add .` как единственный шаг, пока не проверен список.
3. В список staging - только файлы, относящиеся к текущей задаче `{N}`.
4. Если в status есть файлы **не** по задаче - явно сообщить об этом и **не** включать их в предлагаемый add (или спросить отдельно).

### Шаг 3. Ответ пользователю (обязательный шаблон)

Структура ответа **строго** такая (можно чуть короче, но блоки сохранить):

```
Согласуйте отправку в гит.

Ветка: {currentBranch}
Задача: #{N}

git status:
{краткий вывод status -sb или список из status}

Файлы к отправке (только задача #{N}):
- path1
- path2

[Если есть лишние:]
Внимание: в рабочей копии есть файлы не по задаче #{N} - в коммит не войдут:
- other/path

Если вы подтверждаете отправку файлов:
- path1
- path2

я выполню команды:

git add -- "path1" "path2"
git commit -m "{N} суть правки"
git push origin "HEAD:refs/heads/{currentBranch}"
```

Никаких длинных пояснений сверх этого шаблона. Ждать ответа.

### Шаг 4. После подтверждения

Явные формулировки: «да», «ок», «согласовано», «подтверждаю», «выполняй».

Выполнить **только** согласованные команды (add перечисленных путей → commit → push на `origin`, текущая ветка в кавычках если есть `#`).

Не `git add .`, если в status были лишние файлы.  
Не `push --force`, не `--no-verify`, не amend без явной просьбы.

### Шаг 5. Отчёт

1. Коротко сообщить sha, subject и результат push.
3. После успешного push прочитать метаданные `diff.md` и `diff.files.md`, сравнить
   ветку, scope, состав task-коммитов, их SHA и файлы с git по правилам `task-diff`.
   Проверить, не остались ли в артефактах уже закоммиченные uncommitted changes.
   Наличие файлов, дата, один последний SHA или `inspect` сами по себе не доказывают
   актуальность. Отсутствие/расхождение означает `устарел`; недостаток данных -
   `актуальность не подтверждена`. В обоих случаях предложить обновление, не запускать
   генерацию до согласия. Актуальный diff повторно не собирать.
4. Предложить одну последовательную цепочку, а не три независимых запуска:
   `task-diff` при необходимости -> `task-doc` -> `task-change-report` -> `task-report`.
   Использовать skills текущей среды; `task-diff` запускать через project wrapper.
   В предложение явно включить обновление существующего HTML. Пример краткого вывода:

    ```text
    Отправлен {sha}: {subject}.
    Diff: {актуален / устарел / актуальность не подтверждена}.
    Предлагаю {обновить diff и }задокументировать задачу {N}, создать или обновить HTML-отчёт с текстом для Jira. Напишите да, если сделать.
    ```

5. Дождаться нового согласия именно на эту цепочку. Предыдущее согласие на push
   её не разрешает. После согласия выполнить обновление diff, если нужно, и вызвать
   `task-doc` с разрешением обновить HTML и с проверенным контекстом задачи.
   Остальные skills вызывает `task-doc`, не дублировать их здесь. Одно согласие
   покрывает названную цепочку, включая вложенный `task-report`, но не публикацию
   в Jira или новый commit/push. Частичный выбор пользователя ограничивает scope.
   После согласия создай `workflow-context.json` по общему контракту из раздела
   "Общий машинный контекст" skill `task-change-report`: зафиксируй разрешённые
   шаги, scope и разрешение обновления. Не приравнивай согласие на push к этим
   полям. После обновления diff зарегистрируй hashes артефактов и передай путь
   контекста task-doc; не пересказывай исходники дочерним skills.
6. После выполнения вывести один краткий результат по формату `task-change-report`:
   ссылку на HTML и URL для копирования; все подробности, включая Jira, внутри HTML.
   Существенную ошибку/неполноту сообщить одной строкой, не скрывать за ссылкой.
   Ошибка diff блокирует зависимые шаги; не строить новый отчёт на старом diff.
   Если task ID не подтверждён явным workflow или task artifact, не угадывать его
   по имени ветки и не запускать task-specific цепочку.

Предложение цепочки только после успешного push, включая push ранее созданных
коммитов. При отказе, ошибке push, отсутствии отправки или commit-only оно не
запускается.

## Особые случаи

| Ситуация | Действие |
|----------|----------|
| Нечего коммитить, есть unpushed | согласовать только `git push origin "{branch}"` |
| Чисто | «нечего отправлять» и стоп |
| Пользователь дал свой текст коммита | взять, если формат ок; иначе поправить и снова согласовать |
| Только commit без push | если явно сказал - убрать push из блока команд |

## Жёсткие правила

1. Нет подтверждения - нет add/commit/push.
2. Push по умолчанию в `origin` (GitVerse). Запасной `bitbucket` разрешен, если
   пользователь назвал его явно; вместо запрета назвать remote в блоке команд.
3. В коммит - только файлы задачи; лишние назвать явно.
4. Не коммитить секреты.
5. На согласование - шаблон из шага 3, не раздувать.
6. Пути в `git add` и имя ветки всегда в кавычках: пробелы и `#` в именах иначе
   разбираются шеллом неверно.
7. Перед commit проверить `git branch --show-current`. Пустой вывод означает
   detached HEAD: остановиться и спросить, на какую ветку ставить коммит.
