# Критерии аудита плана

Единый контракт для `audit-plan`. `prepare-plan` ссылается на этот файл и не
копирует его. Аудит не только проверяет, но и исправляет план.

## Два слоя

| Слой | Что доказывает | Источник истины |
|---|---|---|
| Корректность кода | After реален, радиус известен, двусмысленности нет | чтение исходников целиком |
| Закрытие задачи | план закрывает бриф трекера | свежий `task.md` и Coverage matrix |

`status: ready` требует оба слоя. Документация и бриф не заменяют чтение кода.

## Критерии C1-C6

| ID | Критерий | Что проверяется |
|---|---|---|
| C1 | Патчи реальны | каждый Before уникален в файле, каждый After полон и вставляется без догадок |
| C2 | Радиус и инварианты | все входы и вызывающие найдены, таблица IN/OUT есть для общего кода, инварианты сохранены |
| C3 | Полнота требований | каждый AC брифа связан с R и S, каждый R имеет S, closure 100 процентов для in-scope |
| C4 | Поведенческие сценарии | литеральный ожидаемый результат, слой, предусловие, действие, состояние после, `must not change` |
| C5 | Минимальность и границы | повторное использование вместо нового кода, нет изменения поведения OUT-вызывающих без согласия, есть откат |
| C6 | Свежие доказательства | версия плана не устарела, источники перечитаны, нет ссылок на удаленные артефакты |

Ни один критерий нельзя молча пропустить. Неприменимый критерий получает
`n/a` с причиной.

## Метод проверки по критериям

Порядок одного прохода: собрать доказательства, пройти критерии, исправить план,
записать метки и журнал. Править до сбора доказательств запрещено.

| Критерий | Метод | Инструменты | Доказательство | Fallback |
|---|---|---|---|---|
| C1 патчи | прочитать каждый файл патчей целиком; найти Before поиском и получить ровно одно совпадение; мысленно применить After до конца файла; проверить поздние чтения измененной переменной | чтение файла, `rg -F` для якоря, `serena get_diagnostics_for_file` только для синтаксиса | `file:line`, полный After, счетчик совпадений 1 | нет, без чтения целиком C1 fail |
| C2 радиус и инварианты | найти вызывающих и потребителей, прочитать каждого целиком, собрать таблицу IN/OUT | `codebase-memory-mcp` `search_graph`, `trace_path`; `codegraph_explore`; `codeprism` `get_context`, `get_callers`, `get_impact`; `php-deps-mcp`; `serena find_referencing_symbols`; `multi-search`; `mysql describe_table` | список вызывающих с указанием уровня, таблица IN/OUT, инварианты | `rg` по тем же расширениям и чтение целиком |
| C3 полнота требований | перечитать бриф, выписать все пункты, связать AC с R и S, сверить Coverage matrix | `gototask -Action export-task`; чтение `task.md`; `jdocmunch` для связанного раздела требований | строки Acceptance criteria, Coverage matrix, закрытие в процентах | вопрос пользователю, вердикт `blocked` |
| C4 сценарии | проверить слой, предусловие, действие, литеральный результат, состояние после, `must not change`; поведение не подменять синтаксисом | чтение `.doc/harnes/testaudit.md` раздел 9; чтение сценария | литеральная строка, число, код или значение в БД | ручной шаг с явной пометкой; без литерала C4 fail |
| C5 минимальность и границы | проверить повторное использование, отсутствие дублей, влияние на OUT-вызывающих, откат | `ponytail`; `jdocmunch` по архитектурному разделу; чтение соседнего файла с похожим решением; `codebase-memory-mcp` `get_impact` | Architecture check, список OUT и шагов регрессии | `rg` по похожему решению |
| C6 свежесть доказательств | проверить версию плана, актуальность индекса и источников, отсутствие ссылок на удаленные артефакты | `index_status` с `indexed_at`; `git-task-blame`; повторное чтение файлов; `mysql describe_table`; `context7` для версии SDK | таблица Research audit, `plan_rev`, даты прохода | `rg` и чтение целиком; недоступный инструмент дает `blocked` для этого утверждения |

## Набор инструментов по уровню риска

Глубина проверки зависит от риска, а не от ритуала. Уровень берется из P1.2.

| Риск | Обязательный минимум | Добавить |
|---|---|---|
| Low, один необщий файл | чтение файла целиком, `rg` по якорю, `git-task-blame` при истории | ничего, отсутствие вызывающих подтвердить поиском |
| Medium, два вызывающих в одной функции | Low плюс `codebase-memory-mcp` и `serena` | `codegraph` для второго чтения связей |
| High, общий код или данные | Medium плюс `codeprism` или `php-deps-mcp`, `mysql` при данных | `semgrep` при auth, деньгах, PII |
| Critical, деньги, auth, мутации | High плюс `semgrep`, `phpstan`, `playwright` для UI | второй независимый проход аудитора |

Каждый пропущенный уровень записывается как `n/a` с причиной. Красный инструмент
не дает `pass`: он компенсируется поиском и чтением целиком, в журнале пишется
`уровень N красный, компенсирован`.

## Чек-лист

### Патчи и исходники

- [ ] каждый файл патчей прочитан целиком, Before совпадает байт в байт;
- [ ] After мысленно применен до конца файла или класса;
- [ ] поздние чтения измененной переменной учтены;
- [ ] все вызывающие из графа, трассировки и ссылок прочитаны целиком;
- [ ] каждый новый путь из поиска прочитан целиком.

### Смежный код

- [ ] статусы, перечисления, слушатели, контракты, точки входа и схема прочитаны;
- [ ] расхождение документации и кода записано, as-is взят из кода;
- [ ] план не пересказывает документационный вымысел.

### Полнота пути

- [ ] для каждого сценария проверена цепочка вход, вызовы, After, исчезновение симптома;
- [ ] отмена, ошибка и недоступность не дают лишних изменений состояния;
- [ ] OUT-вызывающие общего кода не меняют шаги без явного согласия.

### Минимальность

- [ ] лишние файлы убраны;
- [ ] второй обработчик, вторая точка входа и второе чтение переменной не выброшены;
- [ ] общий помощник использован вместо копирования;
- [ ] декомпозиция соответствует независимым причинам, без ритуальных шагов.

### Проверки и доказательства

- [ ] Diff principle N равно числу файлов патчей;
- [ ] у каждого R есть S с литеральным результатом, `php -l` не считается результатом;
- [ ] все T-id из AC, R и S есть в таблице источников;
- [ ] AC-ID совпадают в Acceptance criteria, Coverage matrix и закрытии задачи;
- [ ] каждый связанный номер задачи имеет ссылку на `task.md` или `none: not exported`;
- [ ] риск P1.2 совпадает с тем, что показывают история и вызывающие;
- [ ] в плане нет ссылок на удаленные артефакты: JSON-модель, механический
      валидатор, research-ledger, plan-audit.md, plan_hash.

### Закрытие задачи

- [ ] бриф перечитан целиком, при устаревании экспортирован заново;
- [ ] из описания и комментариев извлечены все пункты, которые нужно закрыть;
- [ ] Coverage matrix связана с Acceptance criteria;
- [ ] статусы `closed`, `partial`, `open`, `out-of-scope` расставлены по правилам;
- [ ] closure посчитан как закрытые к in-scope, а не как прогресс реализации;
- [ ] PARTIAL или BLOCKED не выдаются за ready.

## Zero-ambiguity

План читается как исполнителем без контекста и без права задавать вопросы.

- [ ] каждый Before находим поиском ровно один раз;
- [ ] каждый After готов к вставке, без многоточий и описаний вместо кода;
- [ ] ожидаемый результат это строка, число, код HTTP, значение в БД или код выхода;
- [ ] ни один шаг не требует придумать имя, архитектуру или поведение края;
- [ ] два разных исполнителя не могут получить разный код.

## Находки и правки

Аудит не оставляет находку без действия. Для каждой находки одно из двух:

1. правка внесена в план и помечена меткой прохода;
2. находка помечена `blocked` в журнале с одной строкой причины и вопросом
   пользователю.

Находка содержит:

```text
id, criterion (C1-C6), severity (blocker | major | minor),
path, evidence, failure_scenario, action
```

Правила:

- блокирующая находка не дает `pass`;
- стилистическое пожелание без связи с риском не блокирует;
- находка без пути, контрпримера и ущерба не считается доказанной;
- правка без метки прохода считается дефектом аудита.

## Вердикт

| Вердикт | Условия |
|---|---|
| pass | C1-C6 pass, closure 100 процентов, открытых находок нет, все правки помечены |
| fail | остались открытые находки, но их можно закрыть правкой плана |
| blocked | нужен ответ пользователя, смена рамок или недоступен обязательный вход |

Закрытие:

- FULL, 100 процентов in-scope критериев закрыты патчами и сценариями;
- PARTIAL, есть partial или open критерий, перечислить пробелы;
- BLOCKED, требования извлечь нельзя, критерии не выдумывать.

PARTIAL не ставится только потому, что код еще не внедрен. Это покрытие плана,
а не прогресс реализации.
