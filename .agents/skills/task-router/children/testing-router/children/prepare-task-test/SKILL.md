# Prepare Task Test — конструктор теста задачи

Две фазы: сначала понять что проверять (A), потом собрать тест из готовых
частей (B). Скил создаёт файлы, но не запускает прогон — запуск и отчёт
делает [`browser-verify`](../browser-verify/SKILL.md).

Канон полноты и воспроизводимости: [`.doc/harnes/testaudit.md`](../../../.doc/harnes/testaudit.md).
Тест строится по требованиям, а не только по diff. Учитывай последние
комментарии задачи и дополнительные условия, которые пользователь явно передал
со слов тимлида или QA. У каждого требования должны быть источник и AC-ID.

Бизнес-аналитик снят с харнеса. Требования брать из `task.md`, комментариев и
diff задачи, не из `business_context`. Каждое требование получает свой AC-ID и
источник.

---

## Где лежат тесты

```
.doc/tasks/{N}/
├── task.md          из Jira
├── plan.md          от prepare-plan
├── test.md          сценарии и чек-лист   <- этот скил
├── tests/           сам тест              <- этот скил
│   └── {Slug}Cest.php
└── test-runs/       результаты прогонов   <- browser-verify
```

Тесты **не попадают в git**: `.doc/` исключён локально. Codeception
находит их через симлинк `tests/Acceptance/Task/{N}` -> `../../../../tasks/{N}/tests`,
его ставит генератор.

Неймспейс — `Tests\Acceptance\Task\T{N}`, чтобы одинаковые имена классов
в разных задачах не конфликтовали.

---

## Слои: что откуда берём

| Слой | Где | Что содержит | Пишем сюда? |
|---|---|---|---|
| Page | `.tools/codeception/tests/Support/Page/*.php` | селекторы и примитивы одного экрана | да, если экрана ещё нет |
| Step | `.tools/codeception/tests/Support/Step/*.php` | бизнес-сценарии из Page | да, если сценарий переиспользуемый |
| Actor | `.tools/codeception/tests/Support/AcceptanceTester.php` | вход, фикстуры БД, `checkpoint()` | да, если это общая инфраструктура |
| Cest задачи | `.doc/tasks/{N}/tests/` | только логика конкретной задачи | да, это цель скила |

**Правило: в Cest задачи не должно быть сырых селекторов.** Ни XPath,
ни `contains(@class`, ни `document.querySelector`. Всё это живёт в Page.
Проверяет `check-selectors.py`, гейт G10.

Причина не в эстетике: селектор в Cest не попадает под сверку с реестром
`data-test`, и когда шаблон переименует атрибут, `dontSeeElement()` станет
проходить всегда. Тест зелёный, регрессия не ловится.

## Фаза A — что проверять

1. `task.md` — что меняется с точки зрения пользователя. Выпиши **точные
   формулировки** из задачи и комментариев QA: они станут литералами в
   `$I->see(...)`. Пересказ своими словами не годится, гейт G7 про это.
   Последний комментарий с инцидентом читается как отдельный источник AC:
   элемент из инцидента (какой флаг/кнопка) фиксируется дословно и требует
   своей строки ветки, даже если Cest уже кликает соседний элемент.
2. `diff.files.md` — какие файлы реально менялись.
3. Сопоставь пути с таблицей «Флоу» в `qa/index.md`:
   - пересечение есть → строй тест по контракту флоу
   - пересечения нет → **Index Gate**: предложи создать flow-документ,
     не пиши тест без контракта
4. Если в task.md конкретный `clientId` — используй
   [`login-as-user`](../login-as-user/SKILL.md), а не абстрактного клиента.
5. Вывод перед Фазой B. Ветки не выдумывать заново: правило в [testaudit §9](../../../.doc/harnes/testaudit.md#9-когда-проверять-и-что-считать-веткой).

```
Подготовка теста задачи {N}
- Флоу: [из qa/index.md]
- Ветки из Decomposition: R1/S1 ... (каждый наблюдаемый исход отдельной строкой)
- Ветки диффа без S: [file:line | нет]
- Page есть: [список]
- Page нужно создать: [список]
- Step есть / нужно: [список]
- Фрагменты актора нужны: [список]
- Вход: devLoginAsClient(1) / loginAsClientById({id})
- Литералы из task.md: [точные строки]
- Дополнительные условия пользователя: [список с источником user-extra]
- Конфликты требований: [нет / список, при конфликте сборка блокируется]
- AC-матрица: [путь в test.md]
```

## Фаза B — сборка

### B1. Каркас

```bash
python3 .cursor/skills/task-router/children/prepare-task-test/scripts/new-task-test.py {N} {Slug} --title "краткое описание"
```

Создаёт Cest с уже проставленными `@group task-{N}`, входом,
`initConsoleCapture()`, `checkpoint()` и местами под проверки БД,
плюс `test.md` с каноническим чек-листом и симлинк для Codeception.

### B2. Page и Step

Нет Page нужного экрана — создай `Support/Page/{Screen}Page.php`:
- наследник `BasePage`
- селекторы в `private const`, обращение через `self::test(self::CONST)`
- методы: `open()`, действия, `see*` / `dontSee*`
- каждый `data-test` должен реально существовать в шаблонах,
  иначе `check-selectors.py` не пропустит

Сценарий переиспользуемый (логин, заполнение wizard, создание заказа) —
выноси в `Support/Step/{Domain}Steps.php`, а не копируй в Cest.

**Шаблоны не правим.** Нет `data-test` — бери id, стабильный BEM-класс,
текст или `executeJS` по Vue. Новый `data-test` — только отдельная
продуктовая задача по решению пользователя.

### B3. Сам Cest

Порядок методов в классе - по правилу [test-priority](../../../.cursor/rules/test-priority.mdc):
сначала методы R/S текущего этапа, затем ветки diff без S, затем regression соседних флоу.

- `@group task-{N}` на каждом методе
- Один логин (или один хелпер входа) на сценарий. Не копировать полный login в каждый метод, если исход тот же вход
- `$I->checkpoint('метка')` один раз на наблюдаемый исход ветки, не на каждый клик: скрин, консоль и DOM и так снимаются
- Если патч меняет видимый интерфейс (шаблон, JS/Vue поведение на экране),
  каждый метод на такую ветку обязан содержать `checkpoint`: изменение без скрина
  = тест не собран. UI-only ветка без скрина не закрывается
- happy path обязателен
- happy path цели задачи/стейджа обязателен отдельной строкой: формулировка цели
  из brief/stage-плана (что должна делать задача, а не соседний флаг) получает
  свой метод, даже если общий handler уже покрыт другим элементом
- негативный сценарий обязателен, если применим: без "чего быть не должно" тест зелёный на любой реализации
- минимум одна проверка эффекта в БД (`seeInDatabase`), иначе гейт G6. UI-only задача: отметь это явно в `test.md`
- литералы из `task.md` дословно
- `$I->seeNoConsoleErrors()` и `$I->dontSeeErrorModal()` в конце метода
- В Cest не читать `lib/` через `file_get_contents`. Раннер монтирует только `.doc`, файла там нет. Контракт кода (нет `setcookie`, флаги заголовка, вызов метода) пишется в PHPUnit
- `_before`: `grabEntryFromDatabase` бросает исключение на отсутствии строки. Сначала `$I->grabNumRecords(...)`, чтение только при count > 0
- seed текстовых колонок с не-ASCII: не писать кириллицу через Db-модуль без HEX-проверки (latin1-соединение портит UTF-8). Пиши только флаги/ID, имя проверяет UI. После первой записи сверь `HEX(col)` с ожидаемым началом (кириллица UTF-8: `D0`/`D1`)

### B3b. PHPUnit, если ветка не видна в браузере

Слой из плана или из таблицы веток = `phpunit` (флаги `Set-Cookie`, срок из env, формула, ветка без экрана, второй вход вроде `loginByClientID` / `ChangeEmailEnd`):

- Файл: `tests/lib/.../{Class}Test.php` рядом с классом. Он в git. `run-phpunit.py` подхватит его по имени `{Class}Test.php`
- Один метод на одну строку ветки, assert на ожидаемый результат
- Не дублировать тот же исход ещё и в Cest, и в Playwright
- В `ac-matrix.json` поле `test` = `Class::method` этого PHPUnit-метода. Гейт ищет метод и в Cest, и в `tests/`
- Ошибка, уходящая в JS-переменную (`window.*`), а не в HTML: проверяй декодированный ответ (JSON.parse unicode-escape), а не сырой responseText

### B4. test.md

До записи "тест собран" таблица `## Ветки логики` обязана содержать:

- каждый S из `plan.md` ## Decomposition (разные исходы внутри одного S - разные строки)
- каждую развилку диффа, которой нет в S

Строка без метода (`Class::method`) и без статуса `N-A` с причиной = тест не собран, прогон не стартовать.

Каждый интерактивный элемент из incident/AC (кнопка, флаг, ссылка с точным
литералом) получает отдельную строку ветки со своим литералом и своим методом.
Проверка "соседнего похожего элемента через тот же handler" строку не закрывает:
общий handler не доказывает, что клик именно по этому элементу доходит до кода.

Одна строка ветки = один assert на её ожидание. `recordAcceptanceCriterion`, `checkpoint` и галочка §7 строку не закрывают. Чек-лист §7 заполняется отдельно.
Пустых `[ ]` остаться не должно: `[x]` покрыто, `[-]` неприменимо с причиной, `[~]` частично с пояснением. `[~]` и статус `open`/`partial` запрещают писать "готово".

Добавь матрицу требований: формулировка, источник, AC-ID, тест, ожидаемый результат. `covered` без метода запрещён.

### B5. Быстрая проверка без браузера

```bash
bash .agents/skills/task-router/children/testing-router/children/test-task/scripts/check-tests.sh
```

Ловит за секунды: битый симлинк задачи, синтаксис, коллизии классов,
мёртвые и сырые селекторы. Гонять до того, как звать browser-verify.

## Отчёт скила

```
prepare-task-test: задача {N}

test.md: .doc/tasks/{N}/test.md
```

## Hard rules

- Тесты задач — только в `.doc/tasks/{N}/tests/`. В
  `.tools/codeception/tests/Acceptance/Task/` лежат лишь симлинки.
- Не коммитить тесты задач в git.
- Сырых селекторов в Cest задачи быть не должно — всё в Page.
- Не править `templates/`, `admin/templates/` ради теста, включая
  добавление `data-test`.
- Новый Page/Step/фрагмент — сразу строка в `fragments.md` в том же проходе.
- Не оставлять пункт чек-листа без отметки.
- Не переписывать существующий `test.md` целиком — дополнять.
- Не запускать прогон и не писать `test-runs/*.md` — это `browser-verify`.
- Не считать заполненный чек-лист и вызов `recordAcceptanceCriterion` покрытием ветки.
- Не стартовать прогон, пока в `## Ветки логики` есть строка без метода (кроме `N-A` с причиной).
- Не читать `lib/` из Cest. Codeception монтирует только `.doc`.
- Не дублировать одну ветку в Cest и в PHPUnit.
- Серверную ветку (флаги куки, env, второй вход без экрана) класть в `tests/lib`, не в Playwright.
- Не терять user-extra условия при повторной подготовке теста.
- Не принимать противоречивые требования без явного уточнения.
- Не добавлять файлы в `.doc/qa/_map/selectors-legacy.txt`: этот список
  только сокращается.

## Машинная матрица AC

При подготовке задачи создать `.doc/tasks/{N}/ac-matrix.json`:

```json
{
  "task": 123,
  "db_isolation": "required",
  "required_neighbors": [{"task": 124, "group": "task-124", "reason": "общий серверный контракт"}],
  "requirements": [{
    "id": "AC-01",
    "text": "Проверяемое требование из task.md",
    "test": "TaskCest::methodName или PhpUnitClass::testMethod",
    "expected": "измеримый результат"
  }]
}
```

Каждый браузерный метод после assert вызывает `$I->recordAcceptanceCriterion('AC-01', true, 'evidence')`.
Формат ID строгий: `AC-` + две цифры (`AC-01`, не `AC1`). Один ID - один метод, дубликаты разных методов на один ID раннер отклоняет.
PHPUnit-метод в `tests/lib` в Cest не дублируется: гейт считает AC закрытым, если `phpunit.json` = passed.
Матрица не принимает только имя метода для Cest: нужен результат в `ac-results.json`.

Для DB-изменений runner использует только явно заданные `QA_DB_RESET_CMD` и `QA_DB_CLEANUP_CMD`; SQL для очистки нельзя угадывать.
