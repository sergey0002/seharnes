# Browser Verify — проверка UI-флоу и регрессии

Экономный по токенам скил проверки: сначала дешёвые детерминированные тесты,
потом агент закрывает только то, что тестами не покрыто. Браузер **всегда
видимый** — и в Codeception (WebDriver Chrome без `--headless`), и в Playwright
MCP (headed по умолчанию, флаг `--headless` не добавлять в `mcp.json`).

Канон полноты: [`.doc/harnes/testaudit.md`](../../../.doc/harnes/testaudit.md) §9.
Playwright не повторяет ветку, у которой уже есть метод PHPUnit или Cest.
Порядок прогона методов - по правилу [test-priority](../../../.cursor/rules/test-priority.mdc):
сначала методы свежих правок, затем полное покрытие, затем regression.

## Шаг 0 — Обязательное чтение перед работой

1. [`.doc/qa/index.md`](../../../.doc/qa/index.md) — реестр флоу, приоритет селекторов
   (существующий `data-test` → XPath/CSS/текст; **без правок шаблонов**),
   разделение слоёв проверки (Codeception / Playwright)
2. [`.doc/harnes/tests.md`](../../../.doc/harnes/tests.md) — план развития системы тестирования
   (библиотека фрагментов, тесты в папках задач, вход под пользователем через админку) —
   часть шагов этого скила может быть ещё не реализована, см. статус там
3. Если работа привязана к задаче — `.doc/harnes/doc_rules.md` порядок чтения задачи
    ([`.cursor/rules/bitbucket-tasks.mdc`](../../../.cursor/rules/bitbucket-tasks.mdc))
   — включая существующий `doc.md` и относящиеся к этапу фрагменты `diff.md`

Не сканировать `.doc/qa/flows/*.md` целиком — только пересечение с задачей
(шаг 1) или явно названный пользователем флоу.

## Шаг 1 — Определи область проверки (Impact mapping)

**Если есть TASK_ID:**
1. Прочитай `.doc/tasks/{TASK_ID}/diff.files.md` — список изменённых путей
2. Сопоставь пути с флоу в `.doc/qa/index.md`:
   - изменения в `templates/Item/*`, `scripts/module/item/*` → флоу `item-draft` и смежные
   - изменения в `templates/account/*`, auth-сервисы → флоу `account-signin`
   - если путь не пересекается ни с одним флоу — задача вне UI-регрессии,
     сообщи об этом и спроси, нужна ли проверка вообще
3. Если задача явно затрагивает флоу без документа в `.doc/qa/flows/` —
   **Index Gate**: предложи создать новый flow-документ (см. шаблон в
   `.doc/qa/index.md` → `flows/account-signin.md` как образец), спроси подтверждение,
   не создавай новый файл если похожий уже есть

**Если TASK_ID нет** (пользователь просто просит проверить флоу):
- Возьми флоу напрямую по названию из `.doc/qa/index.md`

Вывод перед выполнением:

```
🎯 Область проверки:
- Затронутые флоу: [список из .doc/qa/flows/*.md]
- Покрыты Codeception: [да/нет по флоу]
- Требуют Playwright MCP (нет покрытия): [список]
```

## Шаг 2 — Слой 1: регрессия через Codeception (по умолчанию первым)

Сначала дешёвая проверка без браузера — она ловит битые симлинки задач,
синтаксис, коллизии классов, мёртвые и сырые селекторы за пару секунд:

```bash
bash .agents/skills/task-router/children/testing-router/children/test-task/scripts/check-tests.sh
```

Затем прогон. Раннер сам разбирается с окружением (хостовый PHP или docker,
chromedriver на 9515 или Selenium на 4444, сеть, host-resolver-rules),
собирает артефакты в `test-runs/` и пишет `verdict.json`:

```bash
bash .agents/skills/task-router/children/testing-router/children/test-task/scripts/task-test.sh {N}                  # группа task-{N}
bash .agents/skills/task-router/children/testing-router/children/test-task/scripts/task-test.sh {N} --group item-draft  # соседний флоу
```

Для нескольких задач релиза используй `bash .agents/skills/task-router/children/testing-router/children/test-task/scripts/test-batch.sh N1
N2 ...` или `--file`. Прогон последовательный, результаты каждой задачи
сохраняются отдельно.

Где группа — тег `@group` из flow-документа (`item-draft`, `account-signin`).
Несколько флоу — несколько запусков, каждый даёт свой каталог прогона.

Вердикт не определять на глаз: `green: true` в `verdict.json` — единственный
критерий зелёного прогона. Там же счётчики, упавшие методы, ошибки консоли
и модалки, собранные через `checkpoint()`.

Раннер **не поднимает** стенд и chromedriver сам: если порт мёртв, он падает
с инструкцией. Агент обязан отличить "бинарник есть" от "процесс не слушает".

### Chromedriver перед слоем 1 (обязательно)

На WSL-стенде драйвер обычно **уже установлен**:
`~/.local/chrome-for-testing/chromedriver-linux64/chromedriver`.
Закрытый `:9515` ≠ "chromedriver нет".

Проверка только с `required_permissions: ["all"]`:

```bash
test -x "$HOME/.local/chrome-for-testing/chromedriver-linux64/chromedriver" && echo BINARY_OK
curl -fsS --max-time 3 http://127.0.0.1:9515/wd/hub/status   # ожидаем "ready":true
curl -fsS -o /dev/null -w '%{http_code}\n' --max-time 3 http://127.0.0.1:8030/
```

Старт видимого Chrome (headed, WSLg):

```bash
bash .agents/skills/task-router/children/testing-router/children/browser-verify/scripts/start-chromedriver-wsl.sh
```

| Ситуация | Что сказать / сделать |
|---|---|
| Бинарник есть, `:9515` не ready | "не запущен" + AskQuestion на старт скрипта |
| Пользователь: "есть chromedriver" / "подними" / да на AskQuestion | сразу `start-chromedriver-wsl.sh`, затем `task-test.sh` |
| Бинарника нет | ссылка на browser-setup, не выдумывать |
| Только sandbox `000` | перепроверить с `all`, не писать "нет драйвера" |

Стенд приложения (`:8030`) без спроса не поднимать. Chromedriver по таблице выше.
Не уходить в Playwright-only только из-за закрытого `:9515`, пока не предложили
старт headed-скрипта.

**Sandbox ≠ стенд лёг.** `curl` к `127.0.0.1:8030` / `:9515` из sandbox часто
даёт HTTP `000`, пока у пользователя UI на `localhost:8030` уже открыт.
Перед фразой "стенд/chromedriver недоступны" обязателен повтор проверки с
`required_permissions: ["all"]` (канон:
[browser-setup.md - AI/sandbox](../../../.doc/qa/browser-setup.md#ai--sandbox-ложный-стенд-недоступен-обязательно)).
Неверная диагностика: CT-2061 (стенд), CT-2607 (бинарник есть / процесс нет) - не повторять.

Предусловия и разбор типичных ошибок:
[`.doc/qa/browser-setup.md`](../../../.doc/qa/browser-setup.md).
Полный блок в оркестраторе: [test-task § Chromedriver](../test-task/SKILL.md#chromedriver-бинарник-vs-процесс).

**Падение теста = регрессия.** Разбирается первым, до перехода к Шагу 3:
прочитай конкретный failing-метод, сопоставь с `git diff`/`diff.md` задачи,
не переписывай тест только чтобы он прошёл. Сначала пойми, баг в коде или тест устарел.

Флак (таймаут, сеть, чужая запись в журнале при том же коде): один повтор `--filter` этого метода.
Не запускать весь `task-test.sh` заново. Второй одинаковый assert = дефект, не повод для третьего полного прогона.

Playwright не закрывает ветку, которую уже проверяет PHPUnit (`tests/lib`) или Cest.

## Шаг 3 — Слой 2: Playwright только для строк без метода

Брать строки `## Ветки логики` со статусом `open`, у которых слой ещё не
phpunit и не cest. Уже зелёный метод этого шага не повторять.

1. `browser_navigate` на маршрут флоу (из `## Маршрут и вход` flow-документа)
2. `browser_snapshot` — не скриншот, снапшот даёт ref для точных действий
3. Действия по селекторам из `## Селекторы` flow-документа (`browser_click`,
   `browser_type`, `browser_fill_form`). Если в flow указан `data-test` — только
   если атрибут **уже есть** в шаблоне на стенде; иначе XPath/CSS/текст из flow
   или стабильные признаки DOM (id, заголовок, BEM-класс, vue-тег компонента)
4. Сверка результата с `## Контракт поведения` flow-документа (бизнес-правила,
   ссылки на architecture — не выдумывать поведение, только то что описано
   или подтверждено в коде)
5. Если контракта для этой ветки логики в flow-документе нет — прочитай
    соответствующую секцию architecture-документа (по ссылке из flow), не весь файл

### Runtime-checkpoint для UI-правок

При исправлении вёрстки и ручной проверке сначала открой реальный URL под ролью из flow. Подтверди роль и наличие нужного элемента в rendered DOM. На dev/test-стенде используй документированный dev-вход только после подтверждения окружения; не подменяй вход искусственным DOM.

Если код и браузер расходятся, **до** вывода про Smarty-кеш, hard reload или пересборку сравни фактически загруженные `document.styleSheets[].href` / `script.src` с редактируемым файлом и `getComputedStyle` изменённого элемента. Если браузер использует bundle, определи его source/build путь. Сброс кеша или пересборку делай только при подтверждённой необходимости, не как первый диагностический шаг (см. [browser-setup.md](../../../.doc/qa/browser-setup.md#ассеты-и-кеш-перед-сбросом)).

Для layout/overflow зафиксируй `getBoundingClientRect().width` карточки и родителя до/после переключения, `scrollWidth > clientWidth` / `scrollHeight > clientHeight` у нужного контейнера и фактическое изменение `scrollLeft` / `scrollTop`. Для hover и кнопки проверь `getComputedStyle` и результат действия. Снимок после этих проверок делай на живой странице; mock/preview называй только mock/preview и не выдавай вместо скрина исправленного приложения. Если роль или стенд недоступны, сообщи об ограничении, а не объявляй UI проверенным.

Экономия токенов:
- Не листать весь Cest-файл, если нужен один метод — искать по имени
- Не делать `browser_take_screenshot` вместо snapshot для проверки состояния —
  только когда нужна визуальная проверка (вёрстка, а не логика)
- Не повторять вручную то, что уже прошло на Шаге 2

`seeInDatabase` для side-effects, не только UI).

## Шаг 6 — Отчёт

Краткая сводка в чат — только как анонс, полный отчёт обязателен как файл
по стандарту [`.doc/harnes/tests.md` §8](../../../.doc/harnes/tests.md):

```
.doc/tasks/{N}/test-runs/{YYYY-MM-DD}_{group}.md   ← если проверка привязана к задаче
.doc/qa/reports/{flow}_{YYYY-MM-DD}.md              ← если проверка без привязки к задаче
```

Файл обязан содержать все секции стандарта (окружение, чек-лист полноты по
13 категориям из `.doc/harnes/tests.md` §7 — без пропусков, пошаговый журнал,
найденные расхождения, «не проверено», вердикт). Молчание про категорию
чек-листа недопустимо — если категория не применима, писать явно причину.

`.doc/tasks/{N}/test.md` / `.doc/qa/flows/{flow}.md` получают только ссылку
на этот файл + строку в таблице истории прогонов, не копию текста.

Сводка в чат после сохранения файла:

```
✅ Browser-verify: [флоу/задача]
Отчёт: [ссылка на файл test-runs/... или qa/reports/...]

Слой 1 (Codeception):
  Прогнано групп: N | Пройдено: N | Упало: N
  [failing-методы, если есть]

Слой 2 (Playwright MCP):
  Проверено вручную: [список сценариев]
  Соответствует контракту: да/нет — [расхождения]

Чек-лист полноты: N/13 покрыто, M отмечено «не применимо» (см. отчёт)
Пробелы покрытия: [список, если предложено добавить тесты]
Обновлено flow-документов: N
```

## Шаг 7 — Гейты готовности (только если проверка привязана к задаче)

Отчёт сам по себе не означает, что задачу можно отдавать. Финальное слово —
за гейтами:

```bash
python3 .agents/skills/task-router/children/testing-router/children/test-task/scripts/gates.py {N}
```

12 проверок G0-G11 плюс G12 (машинный прогон) и G13 (таблица веток, [testaudit §9](../../../.doc/harnes/testaudit.md#9-когда-проверять-и-что-считать-веткой)).

Пока хоть один блокирующий гейт красный — задача **не** ready-for-qa.
Не обходить гейт правкой теста под зелёный результат: если гейт красный,
это либо дыра в проверке, либо реальная проблема.

Итог в чат одной строкой:

```
Гейты: ГОТОВО / НЕ ГОТОВО (красные: G3, G6)
```

## Hard rules

- **Запрещено** править `templates/`, `admin/templates/` (и любой продуктовый
  UI-код) ради тестов: не добавлять `data-test`, не менять разметку для
  селекторов. Селекторы — в тестах/фрагментах (`AcceptanceTester`, flow-док):
  существующий `data-test`, id, стабильный текст, BEM-класс, scoped XPath
  (mobile/desktop), `executeJS` для Vue. Новый `data-test` в шаблон — только
  отдельная продуктовая задача с явным решением пользователя.
- Codeception — первый выбор для покрытых флоу, не Playwright «по привычке»
- Браузер только headed (видимый) — не добавлять `--headless` ни в Codeception, ни в Playwright MCP
- Не гонять весь Acceptance suite, если задача трогает один флоу — только нужные `-g`
- Не выдумывать бизнес-правила — только из architecture-документа по ссылке или из кода
- Не создавать новый flow-документ без Index Gate (проверить `.doc/qa/index.md`)
- Не редактировать `.doc/architecture/*.md` в рамках этого скила без явного запроса
  пользователя (это не task-doc режим B, обратные ссылки сюда не входят по умолчанию)
- Не поднимать стенд (`:8030`) без запроса. Chromedriver: не говорить "нет",
  если бинарник на месте; поднимать через
  `bash .agents/skills/task-router/children/testing-router/children/browser-verify/scripts/start-chromedriver-wsl.sh` после AskQuestion
  или явной фразы пользователя ("есть chromedriver", "подними", "гоняй")
- **Не объявлять стенд/chromedriver мёртвыми** по `curl`/`ss` из sandbox
  (HTTP `000`). Сначала повтор с `required_permissions: ["all"]`; если
  пользователь видит UI на `:8030` - перепроверить, не спорить. Канон:
  [browser-setup.md § AI/sandbox](../../../.doc/qa/browser-setup.md#ai--sandbox-ложный-стенд-недоступен-обязательно)
- **Не писать "chromedriver нет / не установлен"**, если
  `~/.local/chrome-for-testing/chromedriver-linux64/chromedriver` executable:
  формулировка только "не запущен на :9515"
- Тесты задач живут в `.doc/tasks/{N}/tests/` и в git не идут. В
  `.tools/codeception/tests/Acceptance/Task/` только симлинки
- Сырых селекторов в Cest задачи быть не должно — всё в `Support/Page/`
- Вердикт прогона берётся из `verdict.json`, не из чтения лога глазами
- Не править тест ради зелёного гейта: сначала понять, баг в коде или
  тест устарел
- Не считать последний verdict достаточным без проверки его номера задачи,
  группы и актуальности кода и требований.
- Не повторять в Playwright ветку, у которой уже есть метод PHPUnit или Cest
  ([testaudit §9](../../../.doc/harnes/testaudit.md#9-когда-проверять-и-что-считать-веткой)).
- Не пропускать AC-ID, который есть только в комментарии или user-extra.
- Не закрывать задачу после Playwright-only, если стабильный сценарий можно
  перенести в Cest.

## Обязательный lint правок

До запуска браузера этот skill обязан выполнить:

```bash
python3 .agents/skills/task-router/children/testing-router/children/test-task/scripts/qa-lint.py --task {N} --run-dir .doc/tasks/{N}/test-runs/{RUN}
```

Для PHP выполняется `php -l`, для JS/Vue - ESLint. Отсутствие соответствующего инструмента считается ошибкой, а не пропуском. Основной путь `task-test.sh {N}` запускает тот же lint автоматически.
