# task-spec

Скил ведет один черновик постановки задачи в свободной переписке. Пользователь
присылает замечания, баги, скриншоты и тексты отдельными сообщениями. Скил ничего
не переписывает и не планирует, пока пользователь не скажет "сформулируй задачу".
После этой команды черновик превращается в готовый документ задачи.

## Когда применять

- пользователь начинает ставить задачу словами, без номера Jira и без готового
  описания;
- пользователь присылает скриншоты и замечания несколькими сообщениями и просит
  просто фиксировать;
- пользователь говорит "постановка задачи", "собери требования", "новая задача",
  "сформулируй задачу";
- в проекте уже есть активный черновик, и очередное сообщение продолжает его.

Не применять:

- для перехода к существующей задаче Jira: `gototask`;
- для приведения в порядок уже существующей задачи: `task-intake`;
- для плана реализации: `prepare-plan`;
- для тестов и отчета: `test-task` и `task-report`.

## Вход

- корень проекта;
- свободный текст пользователя: замечания, описание бага, требования, решения;
- вложения: путь к файлу в рабочей среде или публичная ссылка Яндекс.Диска;
- активный черновик в `.doc/skil_data/task-spec/{id}/`.

## Шаги

### Шаг 1. Начало разговора

1. Проверить активный черновик:

```bash
python3 .agents/skills/task-router/children/task-spec/scripts/task_spec.py --root . current
```

2. Если черновика нет и пользователь начал описывать задачу, создать его. Новый
   черновик создается и тогда, когда активный черновик уже есть, но пользователь
   явно сказал "новая задача", "начни новую" или "постановка задачи":

```bash
python3 .agents/skills/task-router/children/task-spec/scripts/task_spec.py --root . start --title "<короткое название>"
```

3. Поздороваться и назвать порядок работы:

```text
Здравствуйте. Опишите задачу: присылайте замечания, скриншоты и тексты по одному сообщению. Я всё зафиксирую. Когда закончите, напишите: сформулируй задачу.
```

Если черновик уже активен, приветствие не повторять. Продолжить сбор с текущего
места и при необходимости показать, что уже записано:

```bash
python3 .agents/skills/task-router/children/task-spec/scripts/task_spec.py --root . show
```

### Шаг 2. Сбор требований

Для каждого сообщения пользователя выполнить ровно одно действие и вернуть
короткое подтверждение.

| Что прислал пользователь | Действие |
|---|---|
| текст с замечанием, багом, требованием или решением | `add --kind <тип> --text "<текст>"` |
| путь к скриншоту или файлу | `attach --path "<путь>" --caption "<подпись>"` |
| публичная ссылка Яндекс.Диска | скачать через скил `yadisk-screenshot`, затем `attach --path "<скачанный файл>"` |
| вопрос по ходу сбора | ответить коротко и записать ответ, если он меняет требование |
| несколько вложений в одном сообщении | вызвать `attach` для каждого файла по очереди |

Команды:

```bash
python3 .agents/skills/task-router/children/task-spec/scripts/task_spec.py --root . add --kind remark --text "<текст>"
python3 .agents/skills/task-router/children/task-spec/scripts/task_spec.py --root . attach --path "<файл>" --caption "<подпись>"
```

Правила сбора:

- Текст пользователя записывается дословно. Не сокращать, не переписывать и не
  добавлять свои выводы в `notes.md`.
- Тип выбирается по смыслу: `remark` для замечания, `bug` для ошибки,
  `requirement` для требования, `decision` для принятого решения, `question` для
  открытого вопроса.
- Если в сообщении есть и текст, и файл, сначала записать текст, затем вложение.
- Если пользователь прислал картинку без пути к файлу и без ссылки, один раз
  попросить путь или ссылку. Не выдумывать имя файла и не описывать картинку
  вместо сохранения.
- После каждого сообщения ответить ровно:

```text
Ок, запомнил. Ещё замечания или сформулировать задачу?
```

- Не задавать уточняющих вопросов, которые можно закрыть при формулировке.
- Не создавать `.doc/tasks/{N}`, не менять код и не запускать планирование.

### Шаг 3. Формулировка задачи

Команда запуска: пользователь написал "сформулируй задачу", "сформулируй" или
"готово, формулируй".

Если активного черновика нет, не выдумывать задачу. Попросить пользователя
описать ее и сначала выполнить шаг 1.

1. Загрузить черновик, если контекст мог быть потерян:

```bash
python3 .agents/skills/task-router/children/task-spec/scripts/task_spec.py --root . show
```

2. Исследовать материал:
   - прочитать `.doc/architecture/index.md` и только релевантные разделы;
   - документацию искать через `jdocmunch`, код через `codebase-memory-mcp`,
     `codegraph` и `serena`;
   - назвать точные файлы, классы, маршруты, таблицы и экраны, которых касается
     задача. Неподтвержденный факт пометить "не подтверждено источниками".
3. Декомпозировать задачу, если замечания относятся к разным экранам, ролям,
   сценариям или бизнес-процессам. Каждая часть получает свой номер, границы и
   критерии приемки.
4. Собрать документ по шаблону `references/task-template.md`. Писать как
   идеальный постановщик задач для программных продуктов: одно требование имеет
   одного актора, одно предусловие, одно действие и один наблюдаемый результат.
5. Пройти проверку однозначности:
   - каждое замечание пользователя закрыто требованием или явно вынесено в
     "Вне области";
   - каждое вложение связано относительной ссылкой `attachments/<файл>` и имеет
     объяснение роли;
   - нет слов "улучшить", "исправить", "как надо", "при необходимости" без
     конкретного определения;
   - каждый критерий приемки проверяем без догадок;
   - открытые вопросы, которые меняют реализацию, заданы пользователю одним
     блоком. Если вопрос не блокирует формулировку, он остается в разделе
     "Открытые вопросы" с выбранным значением по умолчанию.
6. Записать `task.md` в папку черновика и опубликовать его:

```bash
python3 .agents/skills/task-router/children/task-spec/scripts/task_spec.py --root . finalize --file ".doc/skil_data/task-spec/{id}/task.md"
```

Скрипт проверяет, что каждая ссылка `attachments/...` указывает на существующий
файл, и переводит черновик в статус `formulated`.

7. Ответить пользователю: путь к `task.md`, число замечаний, вложений и
   требований. Если остался блокирующий вопрос, задать его сразу. Иначе сообщить,
   что задача сформулирована.

## Выход

- `.doc/skil_data/task-spec/{id}/notes.md`: исходные замечания и вложения;
- `.doc/skil_data/task-spec/{id}/attachments/`: все скриншоты и файлы;
- `.doc/skil_data/task-spec/{id}/task.md`: готовый документ задачи;
- `.doc/skil_data/task-spec/{id}/meta.json`: статус, заголовок и даты;
- `.doc/skil_data/task-spec/index.json`: список черновиков.

## Ограничения

- Скил не создает задачу в Jira, не переключает ветку, не коммитит и не пушит.
- Скил не пишет `.doc/tasks/{N}` и не запускает `prepare-plan`.
- Без скила `yadisk-screenshot` ссылки Яндекс.Диска не скачиваются: скил просит
  пользователя прислать файл или локальный путь.
- Скил не восстанавливает картинку, у которой нет ни файла, ни ссылки.
- `notes.md` хранит слова пользователя, `task.md` хранит их структурированную
  формулировку. Смешивать эти роли нельзя.
- Данные лежат только в `.doc/skil_data/task-spec/`, не в папке скила.
