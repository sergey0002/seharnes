# План скила task-change-report

Статус: draft

## 1. Цель

Создать переносимый project skill `task-change-report`, который по материалам задачи
формирует автономный HTML-отчёт о выполненных изменениях.

Отчёт должен объяснять работу изменений простым языком и показывать связи между
затронутыми файлами, модулями, точками входа и сценариями. Основная аудитория -
программист, который знакомится с проектом и ещё не знает его архитектуру.

Результат сохраняется внутри каталога задачи:

```text
.doc/tasks/{N}/reports/change-report/
├── report.html
├── report-data.json
├── sources/
│   ├── task.md
│   ├── diff.files.md
│   └── diff.md
└── assets/                 # только если нужны внешние или отладочные материалы
```

Главный файл для чтения и передачи другому человеку - `report.html`.

## 2. Основа и повторное использование

Перед реализацией сверить существующие подходы:

1. `.codex/skills/task-router/children/reporting-router/children/task-report/` - источник правил для чтения `task.md`, версии,
   скриншотов и простого текста для отчёта.
2. `.agents/skills/harness-router/children/environment-sync/scripts/sync-agent-views.sh` - текущая схема представлений Cursor,
   Antigravity и других сред.
3. `.codex/skills/task-router/children/task-diff/` - источник правил получения diff задачи и списка
   затронутых файлов. Для Codex запускать wrapper `.codex/task-diff.ps1`, а не
   читать дублирующий skill через shell.

Нельзя копировать в новый skill бизнес-логику продукта или придумывать данные,
которых нет в task.md, diff и исходниках.

## 3. Рабочий контракт скила

### 3.1 Триггеры

Скил должен срабатывать на формулировки:

- `сформируй отчет по задаче N`;
- `сделай html отчет по задаче N`;
- `покажи логику изменений задачи N`;
- `task change report N`;
- `change report N`.

Номер задачи обязателен. Если номер не указан, скил должен попросить его и не
создавать отчёт в неопределённой папке.

### 3.2 Входные данные

Обязательные источники:

- `.doc/tasks/{N}/task.md`;
- `.doc/tasks/{N}/diff.files.md`;
- `.doc/tasks/{N}/diff.md`, если он существует;
- текущие исходные файлы из diff и их реальные вызовы.

Дополнительные источники:

- `.doc/tasks/{N}/doc.md` и stage-документы;
- архитектурные документы, выбранные через `.doc/architecture/index.md`;
- git history и blame для объяснения контекста;
- результаты тестов и скриншоты из `.doc/tasks/{N}/test-runs/`.

Документы используются как карта. Факты о поведении подтверждаются исходниками,
diff и результатами тестов. Если факт не подтверждён, в отчёте показывается
пометка `Не подтверждено в источниках`, а не догадка.

### 3.3 Выходные данные

Скил создаёт или обновляет только:

- `.doc/tasks/{N}/reports/change-report/report.html`;
- `.doc/tasks/{N}/reports/change-report/report-data.json`;
- `.doc/tasks/{N}/reports/change-report/sources/`.

Повторный запуск должен полностью пересобирать HTML из нормализованных данных,
не добавляя дубликаты блоков. Время генерации, commit и хеш входных материалов
записываются в `report-data.json`.

## 5. Пайплайн генерации

### Шаг 1. Разрешение задачи

1. Прочитать номер из команды.
2. Проверить существование `.doc/tasks/{N}`.
3. При отсутствии task.md сообщить, что сначала нужен экспорт задачи.
4. Не переключать ветку автоматически.
5. Определить текущую среду и выбрать её локальный entrypoint.

### Шаг 2. Сбор источников

`collect_task_sources.py` должен:

- скопировать task.md, diff.files.md и diff.md в `sources/`;
- собрать список файлов из diff.files.md;
- найти stage-планы, doc.md и test.md в каталоге задачи;
- собрать пути тестовых скриншотов без копирования больших лишних файлов;
- посчитать SHA-256 каждого входного файла;
- сформировать `source-manifest.json`;
- отбрасывать `.env`, секреты, дампы с персональными данными и бинарные файлы,
  если они не нужны для визуального подтверждения.

В отчёт не переносить пароли, токены, cookies, полные email, паспортные данные и
сырые пользовательские payloads. Для таких значений использовать маскирование.

### Шаг 3. Построение модели изменений

`build_change_model.py` формирует нормализованный JSON с сущностями:

```json
{
  "task": {},
  "summary": {},
  "files": [],
  "modules": [],
  "entrypoints": [],
  "flows": [],
  "diagrams": [],
  "tests": [],
  "risks": [],
  "evidence": []
}
```

Для каждого файла хранить:

- путь;
- тип файла;
- роль в изменении;
- добавленные, удалённые и изменённые строки;
- связанный модуль;
- подтверждённые символы;
- входящие и исходящие связи;
- ссылку на источник с номером строки.

Для каждого модуля хранить:

- назначение до изменения;
- что изменилось;
- кто вызывает модуль;
- какие данные входят и выходят;
- какой пользовательский или системный сценарий затронут.

### Шаг 4. Генерация объяснения

Текст строится по шаблону:

1. Что было проблемой.
2. Что изменили.
3. Как теперь проходит сценарий, от входа до результата.
4. Какие модули участвуют.
5. Что проверено.
6. Какие ограничения или риски остались.

Каждый технический термин должен иметь короткое пояснение при первом упоминании.
Например: `контроллер, входная точка HTTP-запроса`.

Нельзя описывать изменение фразами `магия`, `просто`, `очевидно`, `и так далее`.
Не использовать длинные абзацы без схемы или списка.

### Шаг 5. Генерация HTML

`generate_report.py` должен:

- проверить JSON по схеме;
- встроить CSS и JavaScript в один HTML;
- встроить версии Mermaid и Chart.js из `assets/`;
- не требовать интернета для открытия отчёта;
- добавить печатную версию через `@media print`;
- добавить якоря разделов и оглавление;
- сохранить стабильный порядок блоков;
- экранировать все значения, пришедшие из исходников и task.md.

## 6. Структура HTML-отчёта

### 6.1 Верхняя карточка

Показывает:

- номер и название задачи;
- статус отчёта;
- дату и commit генерации;
- краткий вывод в 2-4 предложениях;
- предупреждения о неполных источниках.

### 6.2 Сводка изменений

Карточки с числами:

- изменённые файлы;
- затронутые модули;
- добавленные и удалённые строки;
- найденные entrypoints;
- сценарии тестирования.

Числа должны иметь подпись и ссылку на расшифровку. Нельзя показывать число без
объяснения, откуда оно взялось.

### 6.3 Как работает сценарий

Основной раздел для начинающего разработчика:

1. вход пользователя, HTTP или cron;
2. первый обработчик;
3. проверка данных;
4. вызов бизнес-сервиса;
5. запись или изменение состояния;
6. ответ, событие, письмо или следующий шаг.

Каждый шаг содержит название, простое описание, файл и ссылку на источник.

### 6.4 Диаграммы

Минимальный набор:

- flowchart текущего основного сценария;
- sequence diagram для HTTP или межмодульного вызова;
- component diagram затронутых модулей;
- state diagram, если меняется жизненный цикл сущности;
- diff impact diagram, если изменения распределены по нескольким слоям.

Диаграмма создаётся только когда есть подтверждённые узлы и связи. Если данных
недостаточно, показывается компактная текстовая схема с пояснением.

Правила диаграмм:

- не более 12-15 узлов на одну схему;
- один узел отвечает за одну понятную роль;
- подписи без названий только внутренних классов;
- направление стрелки должно быть однозначным;
- ошибки и альтернативные ветки выделяются отдельно;
- легенда обязательна для цвета и типа стрелок;
- каждая схема имеет подпись `Источник`.

### 6.5 Модули и файлы

Таблица или карточки для каждого модуля:

- зачем он нужен;
- что изменилось;
- какие файлы входят;
- входы и выходы;
- связи с соседними модулями;
- ссылка на строки исходника.

Отдельно показать файлы, которые были просмотрены, но не изменены и намеренно
остались без правок. Это снижает риск неправильного понимания blast radius.

### 6.6 Изменение до и после

Для каждого ключевого правила показывать компактный блок:

```text
Было: условие или путь выполнения.
Стало: новое условие или путь выполнения.
Зачем: какой результат это даёт.
```

Сырые diff-блоки использовать только в раскрываемом разделе, а не как основной
текст отчёта.

### 6.7 Тесты и доказательства

Показывать:

- какие тесты были запущены;
- результат каждого теста;
- покрытый сценарий;
- ссылки на скриншоты;
- непроверенные ветки;
- ограничения окружения.

Статус `не запускалось` не заменять на `проверено`.

### 6.8 Риски и продолжение

В конце отчёта выводить:

- найденные риски;
- места, зависящие от legacy-поведения;
- неохваченные callers;
- вопросы, которые требуют ручной проверки;
- короткий список следующих действий.

## 7. Единый дизайн

`assets/report.css` должен быть единственным источником визуальных правил.

Требования:

- светлый фон и высокий контраст;
- ограниченная ширина текста для чтения;
- нейтральная базовая палитра;
- отдельные цвета только для статусов, ошибок и типов связей;
- единые карточки, таблицы, отступы и заголовки;
- адаптивность для ширины 1280, 1024 и 375 пикселей;
- печать на A4 без обрезания схем;
- отсутствие анимации, мешающей чтению;
- заметный focus state для клавиатуры;
- не полагаться только на цвет.

Цветовая семантика:

- синий: вход или связь;
- фиолетовый: бизнес-логика;
- зелёный: подтверждённый успешный путь;
- оранжевый: предупреждение;
- красный: ошибка или риск;
- серый: контекст без изменения.

## 8. Библиотеки и лицензии

Основной вариант:

- Mermaid, MIT, для flowchart, sequence, state и component схем;
- Chart.js, MIT, для столбчатых и линейных графиков статистики diff и тестов;
- без обязательного CDN, библиотеки поставляются локально и встраиваются в HTML;
- версия каждой библиотеки фиксируется в `THIRD_PARTY_NOTICES.md`;
- лицензии и copyright notices хранятся рядом с assets.

Графики применять только для данных, где сравнение действительно помогает:

- количество изменений по типам файлов;
- распределение изменений по модулям;
- покрытие сценариев тестами;
- количество входящих и исходящих связей.

Не использовать круговые графики при большом количестве категорий и не строить
график из оценочных чисел.

## 9. Валидация

`validate_report.py` проверяет:

- обязательные разделы HTML;
- корректность JSON-схемы;
- отсутствие внешних ссылок на CSS, JS и шрифты;
- отсутствие незакрытых или неэкранированных значений;
- наличие ссылок на источники у фактических утверждений;
- отсутствие секретов и запрещённых персональных данных;
- наличие alt-текста и aria-label;
- наличие печатной версии;
- работоспособность Mermaid и Chart.js в локальном HTML.

`inspect_report.py` выполняет быстрый smoke-check:

- открывает HTML локально через Playwright, если он доступен;
- проверяет, что заголовок и ключевые разделы видимы;
- проверяет отсутствие JavaScript errors;
- проверяет, что диаграммы и графики имеют ненулевые размеры;
- сохраняет скриншот превью в каталоге отчёта только по явному флагу.

Команда `generate-report.ps1` должна возвращать ненулевой код при ошибке
валидации и печатать итоговый путь к HTML.

## 10. Тестовые фикстуры

Подготовить минимум три фикстуры:

1. PHP + Vue задача с HTTP-входом и изменением backend/frontend.
2. Backend-задача с несколькими сервисами и состояниями.
3. Неполная задача без diff.md и без тестов.

Для каждой фикстуры проверить:

- корректное построение модели;
- отсутствие выдуманных связей;
- понятность текста без знания проекта;
- повторную генерацию без дубликатов;
- автономное открытие HTML;
- печать и мобильную ширину;
- безопасное маскирование данных.

## 11. Документация SKILL.md

В `SKILL.md` описать:

- назначение и триггеры;
- обязательный номер задачи;
- быстрый запуск для Cursor и Codex;
- порядок источников и правила доказательств;
- каталог результата;
- команды генерации, валидации и smoke-check;
- поведение при неполных исходниках;
- ограничения по секретам и персональным данным;
- правила повторного запуска;
- синхронизацию с представлениями Antigravity.

README должен быть коротким и содержать только установку, запуск и пример
результата. Подробные правила писать в SKILL.md и references.

## 12. Этапы реализации

### Этап 1. Каркас и контракт

- создать каталог скила;
- зафиксировать JSON-схему;
- создать шаблон HTML и базовый CSS;
- определить имена команд и параметры;
- создать минимальную фикстуру.

Результат: пустой, но валидный отчёт открывается локально.

### Этап 2. Сбор данных задачи

- реализовать поиск task.md, diff.files.md и diff.md;
- реализовать manifest и SHA-256;
- добавить маскирование секретов;
- добавить сообщения об отсутствующих источниках.

Результат: формируется стабильный `report-data.json`.

### Этап 3. Модель изменений и текст

- разобрать diff по файлам и строкам;
- сгруппировать файлы по модулям;
- добавить entrypoints и callers;
- построить before/after описание;
- добавить evidence links.

Результат: отчёт объясняет изменение без просмотра полного diff.

### Этап 4. Диаграммы и графики

- подключить Mermaid;
- подключить Chart.js;
- реализовать ограничение размера схем;
- добавить fallback на текстовую схему;
- встроить легенду и источники.

Результат: схемы показывают подтверждённую логику и не ломают HTML при
неполных данных.

### Этап 5. Тесты, доступность и печать

- реализовать validate_report.py;
- реализовать inspect_report.py;
- проверить клавиатурную навигацию;
- проверить мобильный режим и A4;
- добавить тесты на повторную генерацию.

Результат: отчёт готов для передачи другому разработчику.

### Этап 6. Адаптеры сред

- добавить одинаковые команды в Codex и Cursor;
- проверить Antigravity через существующий симлинк skills;
- не добавлять секреты в каталог скила;
- проверить, что локальные пути не завязаны на одну операционную систему;
- зафиксировать различия сред в README.

## 13. Критерии готовности

Скил считается готовым, когда:

- команда по номеру задачи создаёт HTML в каталоге задачи;
- HTML открывается без интернета;
- в отчёте есть summary, сценарий, модули, файлы, диаграммы, тесты и риски;
- все фактические утверждения имеют источник или пометку о неполных данных;
- используется общий CSS и одинаковая структура отчётов;
- диаграммы читаются начинающим разработчиком;
- нет секретов и незащищённых персональных данных;
- повторная генерация даёт тот же результат при тех же источниках;
- validate и smoke-check завершаются успешно на всех фикстурах;
- отчёт корректно печатается и читается на мобильной ширине;
- Codex, Cursor и Antigravity имеют документированный запуск;
- синхронизация не требует ручного копирования вспомогательных файлов.

| Риск | Решение |
|---|---|
| В diff нет полного контекста | Читать целые исходные файлы и явно показывать границы доказательств |
| AI придумывает связь модулей | Разделять подтверждённые и предполагаемые связи, предположения не рисовать как факт |
| HTML зависит от CDN | Встраивать зафиксированные локальные open source assets |
| Большой diff ломает диаграмму | Ограничивать узлы, группировать повторяющиеся вызовы, давать текстовый fallback |
| В отчёт попадают секреты | Маскирование до рендера и проверка по шаблонам в validator |
| Разные среды запускаются по-разному | Общий контракт данных и отдельные адаптеры команд |
| Симлинк не поддерживается средой | Хранить канонические файлы в разрешённом каталоге среды и проверять ссылки smoke-командой |
| Ошибки библиотеки ломают весь отчёт | Ошибка диаграммы не должна скрывать текстовое описание и таблицы |
