# Task Change Report

Скил строит компактный HTML-лендинг-презентацию из структурированной JSON-модели
и материалов задачи. Он не меняет продуктовый код и не отправляет отчёт в Jira.
Канонический артефакт - `report-model.json`, HTML является производным результатом
детерминированного renderer. Первый экран должен объяснять задачу за несколько секунд,
а подробности открываются ниже: стадии, полный task, было → изменение → стало → почему,
Mermaid-схемы, скриншоты, все файлы, проверки и готовый ответ для Jira.

## Главный принцип отчёта

Отчёт всегда разделяет два слоя:

1. **Общая логика**: как бизнес-процесс или технический фрагмент работал в целом,
   независимо от этой задачи.
2. **Правки задачи**: что именно изменилось, в каких файлах и как это повлияло на
   общий процесс.

Если факт нельзя подтвердить task.md, diff, исходником или результатом теста, он
помечается как `Не подтверждено источниками` и не рисуется как установленная связь.

## Обязательные требования к текстам отчёта и представлению

0. **Бизнес-изменения отдельно от технических**:
   - В `report-model.json` обязателен `business_changes[]`, если в `task.json` есть `business_logic.facts`.
   - Каждый элемент: `title`, `statement`, `type`, `code[]`, `tests[]`.
   - `statement` пишется по правилу `text-style`: самостоятельное правило, 2-4 предложения, без контекста задачи и кодов без расшифровки.
   - Таблица `changes[]` остаётся технической. В панели и HTML она называется "Технические изменения" и не заменяет бизнес-слой.
   - Если фактов нет, `business_changes` пустой, отчёт использует только технические изменения и явно это указывает.

1. **Человеческий язык и расшифровка терминов/кодов**:
   - Общее правило: `.cursor/rules/text-style.mdc`, раздел "Отчёты".
   - В отчёте дополнительно: любой код, статус, класс или метод в `business_changes[]`, `changes[]` и `statement` сопровождается расшифровкой для бизнеса в скобках.
   - Пример: `PaymentCommand (сервисный класс команды оплаты) применяет курс к кодам пополнения (135 - эл. кошельки, 150 - карты, 160 - системные переводы)`.

2. **Осмысленные функциональные роли файлов**:
   - В колонке "Роль" таблицы файлов ЗАПРЕЩЕНО выводить бессмысленную фразочку "Изменённый файл"!
   - В `report-model.json` через свойство `file_roles` (или массив `files` с полем `role`) агент ОБЯЗАН передать понятное объяснение: за что этот файл отвечает в системе и какую функцию выполняет в рамках задачи.
   - Пример: `lib/Objects/Payment/PaymentCommand.php` -> `Класс выполнения платежа: зачисление средств и применение курса конвертации`.

3. **Интерактивный Git Diff Viewer в таблице файлов**:
   - При клике на файл в таблице scope раскрывается спойлер с полным Git-диффом изменений задачи.
   - Дифф отформатирован в стиле Git Code Review: две колонки номеров строк (старая/новая), маркеры `+`/`-`, подсветка добавленных строк зеленым и удаленных красным цветом, и скроллбокс для длинных фрагментов.
   - Рядом с каждым файлом есть дата последнего редактирования/коммита и кнопка быстрого копирования пути.

4. **Интерактивный просмотр схем и картинок**:
   - Все Mermaid-диаграммы и скриншоты в отчёте являются кликабельными и открываются в полноэкранном модальном окне с размытием фона и увеличением для детального изучения.

5. **Инженерный контекст из `doc.md`**:
   - Автоматически извлекаются разделы «Подводные камни» (ПК-X: симптом, причина, решение) и «Принятые архитектурные решения» (Р-X: контекст, подход, альтернативы), а также ссылки на каноническую архитектуру `.doc/architecture/*`.

6. **Полная интеграция с Git и статусом релиза**:
   - Автоматическое определение факта слияния ветки задачи в релизы (`releases/*`), номера PR и даты слияния с выводом статусного бейджа в шапке.

7. **Результаты тестирования (`test-runs/` и `test.md`)**:
   - Вывод общего вердикта последнего запуска (`GREEN` / `RED`), счетчиков тестов, времени выполнения каждого тест-кейса, статуса качественных ворот (Gates: static, lint, phpunit, ac, db) и ошибок консоли браузера.
   - Таблица веток логики и интерактивный чек-лист из `test.md`.

8. **Интерактивные UX-инструменты**:
   - Сегментированная шкала (прогресс-бар) распределения правок по модулям (Backend, Database, Frontend, Tests).
   - Живой поиск по файлам и таб-фильтры по модулям.
   - Кнопка «📋 Скопировать ответ для Jira» с всплывающим тостом.
   - Кнопка «🖨️ Печать / PDF» для вывода отчёта на печать или сохранения в PDF.

9. **Правила оформления Mermaid-диаграмм в отчёте**:
   - **Рекомендуемый тип диаграмм**: всегда предпочитать `flowchart TD` или `flowchart LR`.
   - **Метки узлов**: любой текст узла с пробелами, двоеточиями, спецсимволами (`:`, `/`, `'`, `(`, `)`) **обязательно** заключать в двойные кавычки: `NodeID["Шаг 1: Ввод номера телефона"]`.
   - **Запрет опасных конструкций**: категорически избегать `stateDiagram` / `stateDiagram-v2` с двоеточиями в описании состояний (`State: Шаг 1: Описание` ломает Mermaid v10 с ошибкой `Syntax error in text`).
   - **Идентификаторы узлов**: только латинские буквы, цифры и знак подчёркивания (например `Step1_InputPhone`, `CheckStatus`), без кириллицы и пробелов в ID.
   - Валидатор `generate_report.py` блокирует сборку при обнаружении несбалансированных скобок, незакрытых кавычек или опасных двоеточий.

## Запуск

### Общий машинный контекст

Для составной цепочки обязателен `workflow-context.json` рядом с моделью отчёта,
по `assets/workflow-context.schema.json`. Самостоятельный HTML-запуск тоже
создаёт этот контекст; старые модели без него поддерживаются renderer только
как legacy-вход, не как доказательство выполненной цепочки.

Контекст создаёт внешний вызывающий skill после разрешения пользователя.
Содержит `version`, `task_id`, `scope`, `allowed_steps`, `refresh_authorized`,
`sources`, `facts`, `steps` и результат `jira`. В sources хранятся относительные
пути, SHA-256 и роли; facts ссылаются на эти источники. Не копируй полные исходники
или transcript. Секреты в контекст не включать. Схема, а не пример в чате, задаёт
точные поля и допустимые значения.

Перед следующим шагом запусти из skills текущей среды:

```bash
python3 .cursor/skills/task-router/children/task-change-report/scripts/workflow_contract.py \
  --context .doc/tasks/{N}/reports/change-report/workflow-context.json --project-root .
```

Используй компактный результат: `input_hash`, `needed_steps`, `reusable_steps`,
`errors`, `next_action`. Код 0 означает пригодный контекст, не доказательство
исполнения всех шагов; 1 - stale/blocked, 2 - некорректный вход.
Скрипт read-only, не выполняет skills и не получает согласие вместо пользователя.
JSON с allowed_steps не является новым разрешением: сверяй с явным запросом.

Каждый skill обновляет только свой результат и зарегистрированные изменённые
источники. `steps` содержит статус, input_hash и artifacts с hashes. Отмечай
passed только после фактической проверки артефактов. Не исправляй stale заменой
hash без перепроверки фактов. Hash подтверждает неизменность, не истинность вывода.
Смена scope или evidence требует проверки зависимых выводов. Повторное чтение
неизменённых проверенных данных не нужно; новые gates и вопросы не пропускаются.

После записи `doc.md` используй `checkpoint(context, project_root, facts,
generated_sources=...)` из `workflow_contract.py`. Он принимает изменение только
если оно совпадает с проверенным artifact шага documentation, обновляет источник
документации и переаттестует upstream steps. Произвольное изменение блокируется.
Checkpoint ничего не пишет: вызывающий skill атомарно сохраняет возвращённый
контекст после проверки. Не добавляй артефакты в `sources` без checkpoint.

`needed_steps` не означает порядок вызовов: HTML-skill сначала получает Jira,
затем рендерит HTML. Повторный вход не создаёт цикл. Сохраняй счётчики выполненных
и переиспользованных шагов в результатах запуска; не заявляй экономию токенов
без телеметрии. Полное исследование разрешено, если контекста недостаточно.

### Взаимодействие skills

Цепочка: `task-doc -> task-change-report -> task-report`. Этот skill владеет только
моделью и HTML; task-doc владеет документацией и индексом, task-report - текстом
Jira и подбором вложений. Это вызовы агентом skills, не автоматические вызовы LLM
из Python renderer. Машинный контекст передаётся renderer через `--context`.

1. Прими task ID, scope/стадию, commit, решения пользователя, пути и проверенные
   факты из task-doc. Используй свежий `doc.md`: решения, подводные камни, связи,
   результаты gates и документирования. Не повторяй выполненный анализ неизменённых
   источников, но допроверь непокрытые факты. Не вызывай task-doc обратно.
2. При самостоятельном запросе HTML прочитай имеющийся `doc.md` и актуальные
   источники. Если документации нет или она устарела, отметь это в `risks`, исследуй
   необходимые факты по коду; не запускай документирование без команды пользователя.
3. До рендеринга вызови `task-report` во вложенном режиме, если пользователь явно
   не исключил Jira. При "без Jira" не вызывай его, не добавляй старый `jira_reply`,
   укажи в `risks`, что блок исключён пользователем (это не ошибка).
   Передай проверенные факты
   реализации и тестов, task ID/scope, релиз с источником и решения пользователя.
   Внеси возвращённый текст без перефразирования в `jira_reply`, все отобранные
   вложения в `screenshots`, их подписи и пояснение о приложении отдельно от текста.
   `shots: 0`, `more` и ограничения отрази в `risks`; прочие проверенные скриншоты
   отчёта сохрани, объедини по пути без дубликатов. Источники включи в `evidence`.
   Не сочиняй Jira-текст вместо этого skill. При неизвестном релизе запроси только
   недостающее; при отказе пометь Jira-блок как заблокированный, не как готовый.
4. Сформируй/актуализируй `report-model.json` по схеме. Заполни `business_changes[]`
   из verified `business_logic.facts` задачи. Неподтвержденные правила отдельно
   в модель не дублируй: renderer читает `business_logic.unconfirmed[]` из
   `task.json` и выводит их с пометкой, score и всеми checks карантина. Не удаляй разделы, стадии,
   evidence, вопросы тимлида, файлы, диаграммы и тесты ради краткости чата.
   Устаревшие факты исправляй по источникам, а не копируй из старой модели.
5. Сверь доступные параметры через `generate_report.py --help`; проверь модель,
   task ID, свежий task-owned diff и существование evidence. Renderer не делает
   исследования и не заменяет Jira-skill. Запусти его один раз после preflight.
6. Проверь четыре артефакта report-model/data/manifest.json и report.html, наличие
   всех разделов и Jira-текста (кроме явно исключённого), ссылок на скриншоты. Успех процесса или SKIP сам
   по себе не доказывает актуальность. При вложенном запуске верни результат
   task-doc без отдельного сообщения, родитель выводит одну итоговую ссылку.

### Повторный запуск

Сравни `report-manifest.json` (model_sha256, git_head, source_hashes) с текущими
источниками. Дополнительно проверь scope, evidence, test-runs, скриншоты и стадии:
не все они покрыты manifest. Неизменённый полный отчёт с Jira-блоком используй
повторно без нового анализа/рендеринга. Отсутствующий Jira-блок, новые источники
или неизвестная свежесть требуют обновления. Явно исключённый пользователем
Jira-блок не является отсутствующим обязательным входом. Повторное использование
должно учитывать и ограничения текущего запроса, не только hashes.

При отсутствии HTML используй `--if-missing`. При существующем HTML обновление
модели и запуск `--force` разрешены только явным запросом обновить отчёт или
согласием на post-push цепочку, где обновление названо явно. Иначе предложи
обновление с фразой "Напишите да, если сделать". Сам флаг --force не является
согласием. Не используй запуск без --if-missing для обхода защиты: текущий
renderer без этого флага может перезаписать HTML. При blocker не выдавай старый
отчёт за новый и не делай повторных запусков на тех же некорректных входах.

Из корня любого проекта:

```bash
python3 .codex/skills/task-router/children/reporting-router/children/task-change-report/scripts/generate_report.py \
  --task 2606 --project-root . --if-missing
```

Для Cursor используется тот же файл через `.cursor/skills/task-router/children/task-change-report/`.

Основные параметры:

- `--task N` - номер задачи, обязательно;
- `--project-root PATH` - корень проекта, по умолчанию текущий каталог;
- `--output PATH` - отдельный каталог отчёта;
- `--open` - принят CLI, но renderer сам браузер не открывает; открытие по запросу выполняет агент;
- `--offline` - собрать отчёт без внешних ссылок, диаграммы остаются в виде Mermaid-кода.
- `--model PATH` - использовать подготовленную JSON-модель по строгой схеме;
- `--if-missing` - завершить без перезаписи, если HTML уже существует;
- `--force` - разрешить явную пересборку существующего отчёта.

Результат по умолчанию:

```text
.doc/tasks/{N}/reports/change-report/report.html
.doc/tasks/{N}/reports/change-report/report-model.json
.doc/tasks/{N}/reports/change-report/report-data.json
.doc/tasks/{N}/reports/change-report/report-manifest.json
```

Для отдельной стадии используй отдельный output-каталог, например
`.doc/tasks/{N}/reports/stage2-change-report/`, и stage-specific `report-model.json`.
Текущий renderer всё равно собирает diff/файлы/doc/test-runs из корня всей задачи:
отдельный output и поле stage не фильтруют эти секции. Явно обозначь в модели
и рисках границу: объяснение стадии, общие секции всей задачи. Если запрошен строго
stage-only отчёт, это blocker текущего renderer, а не повод выдать общий за частный.

Без валидного `report-model.json` renderer завершается с ошибкой и не сочиняет
текст логики сам. В модели обязательны `before`, `after`, `delta`, `rationale`,
диаграммы, evidence и статусы тестов.

## Формат ссылки и вывод в чат

При генерации или упоминании отчёта агент **обязан** вывести в чат:
1. Отдельную кликабельную Markdown-ссылку на фактически созданный `report.html`:
   `[Открыть HTML-отчёт](file://wsl.localhost/{WSL_DISTRO_NAME}{path_to_report.html})`.
2. Отдельный блок кода для копирования в формате WSL:
   ```text
   file://wsl.localhost/{WSL_DISTRO_NAME}{path_to_report.html}
   ```
   (например: `file://wsl.localhost/Ubuntu/home/newuser/projects/copytrust/testdeploydocker/.doc/tasks/{N}/reports/change-report/report.html`).
3. В финальном ответе нельзя ограничиваться строкой `FILE:` или `WSL_URL:` из вывода скрипта. Полный `file://wsl.localhost/...` URL должен быть продублирован в сообщении чата.
4. Предложить пользователю скопировать ссылку и вставить в адресную строку браузера Chrome (или кликнуть по ссылке).
5. При запросе пользователя открыть в браузере или при флаге `--open` — сразу вызывать штатный Chrome на хосте Windows.

Это весь успешный итог: ссылка, URL для копирования и короткое "Открыть в Chrome".
Не печатай в чат Jira-текст, таблицы файлов, результаты gates и пересказ документации:
они остаются в HTML. Ошибка или существенное ограничение добавляется одной строкой.
Во вложенной цепочке финальный ответ публикует только родитель. Дистрибутив WSL
определи из среды, не угадывай Ubuntu; вне WSL используй корректный локальный file URI.

## Источники

Скил использует универсальные имена, но не требует конкретного трекера:

- `.doc/tasks/{N}/task.md`;
- `.doc/tasks/{N}/diff.files.md`;
- `.doc/tasks/{N}/diff.md`;
- `.doc/tasks/{N}/doc.md`, `plan.md`, `test.md` и stage-планы;
- task-owned git diff для исследования; до рендеринга требуется актуальный `diff.md`;
- исходные файлы из списка diff.

Отсутствующие файлы фиксируются как предупреждения. Отсутствие модели, diff или
обязательного evidence блокирует генерацию, а не маскируется общим текстом.

Поле `source` в модели - один существующий относительный путь, без перечислений
через `;` и без суффиксов (`§`, `lines`, `commit`). Рендерер проверяет каждый путь
на существование и отклоняет всю модель при первом missing.

## Разделы HTML

Генератор создаёт один и тот же порядок разделов:

1. Hero-выжимка: задача, результат, scope и число стадий.
2. Полный task с быстрым объяснением проблемы и решения.
3. Было → изменение → стало → почему.
4. Mermaid-схемы текущей и новой логики.
5. Скриншоты с подписями, если они прикреплены к модели.
6. Полный список файлов и их роль.
7. Все проверки со статусом и ссылкой на evidence.
8. Готовый ответ для Jira.
9. Ограничения и риски.

Текст рассчитан на автора задачи перед разговором с тимлидом: сначала краткая
карта и блок "Что сказать тимлиду", затем `Как было -> Что изменили -> Как
стало -> Почему`, схемы, файлы, строки, тесты и риски.

## Универсальность

Скил не знает названия классов, таблиц, роутов или фреймворков заранее. Он работает
с любым языком и проектом, а анализ строит по task.md, diff и тексту исходников.
Проектные адаптеры можно добавить рядом со скилом, но нельзя зашивать их в общий
генератор.

## Безопасность

Перед рендерингом маскируются токены, пароли, cookies, ключи и похожие секреты.
Значения из исходников HTML-экранируются. Не переносите в отчёт production dump,
полные персональные данные или `.env`.

## Синхронизация сред

Канон находится в `.cursor/skills/`. Представления Codex, Kilo, Antigravity,
Gemini и Agents синхронизируются штатным adapter-скриптом, независимо не правятся.
Во время работы загружай skills из каталога текущей среды.
