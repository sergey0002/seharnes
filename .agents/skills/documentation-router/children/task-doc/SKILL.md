Скил активируется по команде:
- "задокументируй задачу"
- "document task"
- "обнови документацию задачи"
- "зафикси прогресс"

## Шаг B0 — Обязательное чтение перед работой

Бизнес-аналитик снят с харнеса. `analysis-context`, rule IDs и версии правил
больше не используются: требования берутся из `task.md`, комментариев и диффа.

**Перед любой записью в `.doc/`** прочитай [`.doc/harnes/doc_rules.md`](../../../.doc/harnes/doc_rules.md).

Там собран единый стандарт документации проекта:
- структура и формат файлов: `# H1`, потом `<!-- meta ... -->`,
  потом `## Суть`, тематические секции, `## Связи`,
  `## Известные проблемы и ограничения`, `## История изменений`
- блок `<!-- meta ... -->`: `type`, `status`, `updated`, `related`, `tags`
- `type` строго из списка `doc_rules`: `architecture | rules | api | model | flow | config | index`.
  Для `doc.md` задачи использовать `flow`; `task` и `task-doc` валидатор считает неизвестными
- заголовки обязательных секций без эмодзи и без изменения текста:
  `## Суть`, `## Связи`, `## Известные проблемы и ограничения`, `## История изменений`
- правила ссылок и якорей
- маркеры статуса в тексте, не в заголовках
- callouts, теги
- **правило обратных ссылок** (документ A → B обязывает B → A)
- **правило ссылок из задач** (см. ниже Шаг B3.3)
- чеклист перед коммитом

Этот скил применяет правила из `doc_rules.md` к конкретной задаче.
Если что-то не описано здесь — ответ ищи в `doc_rules.md`, не угадывай.

## Шаг B1 — Определи задачу и файлы

1. Используй task ID и `TASK_DIR` из явного запроса или вызывающего workflow.
   Только если их нет, найди `TASK_DIR` по паттерну `.doc/tasks/*/task.md` (glob).
2. Если задача остаётся неоднозначной, спроси пользователя какую документировать.
3. Определи `TASK_ID` из имени папки (только цифры).
4. Проверь существует ли `{TASK_DIR}/doc.md`:
    - НЕТ → создай по шаблону из раздела «ШАБЛОН doc.md» ниже
    - ДА → прочитай полностью перед любой записью

До создания/изменения документов и B3 проверь актуальность task/diff/doc по текущему
коду и task-коммитам. Устаревший или непроверенный diff сначала обновляется через
task-diff с разрешением (post-push согласие это покрывает). При отказе не фиксируй
непроверенные выводы, сообщи blocker. Не откладывай эту проверку до post-step.
Зафиксируй разрешённые шаги: явное "только документацию", "без HTML" или "без Jira"
ограничивает всю вложенную цепочку. Передавай ограничения дочерним skills.
Используй `workflow-context.json` и preflight по разделу "Общий машинный контекст"
skill `task-change-report`. При самостоятельном вызове создай его для разрешённых
шагов. До записи выполни preflight; передай HTML-skill тот же путь, не новый пересказ.
После B4.5 зарегистрируй hashes doc.md, изменённой архитектуры и индекса,
проверенные факты/evidence и результат documentation. При изменении входов
перепроверь зависимые результаты; не объявляй предыдущие steps актуальными автоматически.

## Шаг B1.5 - JSONdoc batch доступ (чтение и запись)

Канон движка: `python3 .agents/skills/documentation-router/children/task-doc/scripts/jsondoc.py --root .`.
Полный контракт: `.doc/harnes/jsondoc.md` 6.1 (чтение), 6.5 (batch), 9.4 (типовые пачки).
Реализация: пакет `.agents/skills/documentation-router/children/task-doc/scripts/jsondoc/` (модули batch, search, лимит `MAX_CALLS` 20 на batch).

Входной файл только под work-зоной:
- операция задачи: `.doc/tasks/{ID}/_jsondoc/work/batch.json`;
- глобальная операция: `.doc/skil_data/task-doc/work/batch.json`.

Допустимые calls: `get`, `search`, `related`, `stages`, `tags_search`. Лимит 20 calls
на batch (константа `MAX_CALLS` пакетного модуля). Ответ один envelope:
`{status, batch_id, snapshot_revision, results:[{id, status, data, counts, errors}], apply_summary}`.

Пример read-пачки (keys + findings + related):

```json
{
  "batch_id": "task-{ID}-preflight-01",
  "calls": [
    {"id": "keys", "command": "get", "args": {"task": "{ID}", "keys": true}},
    {"id": "pitfalls", "command": "get", "args": {"task": "{ID}", "select": ["/findings"], "limit": 3}},
    {"id": "rel", "command": "related", "args": {"task": "{ID}", "profile": "discovery-v1", "limit": 5}}
  ]
}
```

```bash
python3 .agents/skills/documentation-router/children/task-doc/scripts/jsondoc.py --root . batch --input .doc/tasks/{ID}/_jsondoc/work/batch.json
```

Фильтры `search`: `--text`, `--tag` + `--tag-mode all|any`, `--file`, `--release`,
`--branch`, `--tasks`, `--limit`. Поиск тегов по словарю: команда `tags_search`
по `.doc/skil_data/task-doc/state/tags.json`. Связанные задачи: `related`
с профилем `discovery-v1` (по задаче) или `legacy-v1` (по arch-документу).

Запись: ровно один `apply` после всех calls (update envelope 6.3, `actor=task-doc`,
`expected_revision`, `operation_id`), затем отдельная команда `render`.
Reads видят состояние до apply. Чтение после записи - отдельным следующим batch.

Когда использовать:
- 3 и более чтений одной задачи - один batch вместо отдельных get;
- search + точечные get по известным ID - один batch;
- серия правок - один apply envelope.

Когда не использовать:
- одиночный вопрос - одиночная команда `get`/`search`/`related`;
- цепочка, где следующий запрос зависит от результата предыдущего;
- чтение + запись, если write должен увидеть результат read из этой же пачки.

Валидность JSONdoc для задачи: есть `.doc/tasks/{ID}/task.json` и receipt
`.doc/tasks/{ID}/_jsondoc/receipt.json`. Нет receipts или CLI недоступен -
прежний путь по `doc.md` (legacy fallback). Ручная правка generated `doc.md`
запрещена (`VIEW_CONFLICT`).

Не дублирует другие скрипты:
- `find-related-tasks.ps1` остается точкой входа для P0.5a/V6 (скоринг score>=20,
внутри fast path через `related --profile legacy-v1`);
- `build-tasks-index.ps1 -AlsoTsv` остается владельцем `.doc/tasks/index.md`
и `_map/file-to-tasks.tsv`;
- batch не заменяет TSV-индекс и не меняет скоринг PS1.

**Статус:**
- Что завершено
- Что в процессе
- Что заблокировано

## Шаг B2.5 — MCP Reuse Gate (ОБЯЗАТЕЛЬНО при доступном MCP)

Перед фиксацией решения в `doc.md` проверь, не дублирует ли задача существующую реализацию.

Порядок:

1. `codebase-memory-mcp`:
   - `list_projects` -> `search_graph` по ключевым словам задачи (например, popup/order/payment)
   - `trace_path` для 1-3 ключевых символов, если нужен контекст вызовов
2. `codegraph` (если MCP зелёный):
   - `codegraph_explore` по терминам шага 1, `maxFiles` 5-6
   - `codegraph_callers` / `codegraph_impact` для связей и blast radius
   - литералы и regex по `.js`/`.tpl` — `multi-search.sh` / `rg`, не codegraph
   - для другого проекта каждый вызов с `projectPath=<корень проекта>`
   - сообщества, god nodes и shortest path не заменяются; для них CBM `trace_path`
3. `serena`:
   - `find_symbol` / `find_referencing_symbols` для подтверждения реального reuse
3. Если домен связан с БД — `mysql describe_table` для валидации модели данных

3+ независимых поисков идут пачкой, не по одному (см. правило `batch-calls`): `.doc/` через `multi-search.sh`, код через `execute` + `Promise.all`.

Сохрани в контексте и документации для HTML (перед B3/B4), не печатай отдельный
успешный блок в чат:

```
♻️ Reuse Gate:
- Найдено готовых реализаций: N
- Рекомендация: reuse | расширить | создать новое
- Почему: [кратко]
```

Если найдено подходящее решение, по умолчанию фиксируй reuse, а не создание новой сущности.

## Шаг B2.6 — MCP Impact Gate (ОБЯЗАТЕЛЬНО при доступном MCP)

Перед финальной записью в `doc.md` проверь риск поломки соседних модулей.

Порядок:

1. `codebase-memory-mcp`:
   - `trace_path` (`direction=both`, `mode=calls`; для UI/API модулей также `mode=cross_service`)
   - оцени inbound/outbound связи
2. `codegraph`:
   - `codegraph_impact` по затронутым символам
   - литералы, шаблоны, строковые ключи API — `multi-search.sh` / `rg`
3. `serena`:
   - уточни references в файлах, которые могут сломаться
4. При существенных PHP/security изменениях — предложи пользователю верификацию:
   - `phpstan-mcp` (`phpstan_analyze`)
   - `semgrep` (security checks)
5. Для UI-flow по запросу/необходимости — `playwright` smoke

3+ независимых поисков идут пачкой, не по одному (см. правило `batch-calls`).

Сохрани в контексте и документации для HTML, в чат только существенный blocker:

```
⚠️ Impact Gate:
- Рискованные зависимости: [список]
- Что может сломаться: [кратко]
- Что проверить: [phpstan/semgrep/playwright или ручной сценарий]
```

## Шаг B3 — Обработка архитектурной документации

**B3.1 — Сбор ссылок**

1. Открой `.doc/architecture/index.md`
2. Найди все разделы релевантные задаче
3. Для каждого релевантного документа определи:
   - Конкретные секции/абзацы связанные с задачей
   - Конкретные строки если возможно (формат: `файл.md#заголовок`)

**B3.2 — Аудит актуальности (Шаг D)**

Для каждого документа на который ссылается doc.md:
1. Прочитай только связанные секции
2. Сравни с тем что нашли в ходе работы над задачей
3. Если есть расхождения — зафикси их

Зафиксируй результат сверки в документации задачи (в чат только blocker):

```
📋 Аудит документации по задаче {TASK_ID}

Проверено документов: {N}
Найдены расхождения:

  ⚠️ `.doc/architecture/payments.md#limits`
     Документация говорит: "..."
     По факту в коде: "..." (найдено в File.php:234)
      → Исправить связанную секцию и оставить evidence.

  ✓ `.doc/architecture/models.md#user` — актуально
```

В режиме B исправь подтверждённые расхождения существующих связанных документов
без повторного согласования, как требует `doc_rules.md`. Новый architecture-файл
по-прежнему требует Index Gate и согласия; не расширяй scope на чужие разделы.
При обновлении:
- Не переписывай весь документ
- Меняй только конкретную секцию
- Добавляй комментарий `<!-- updated: YYYY-MM-DD, task: {TASK_ID} -->`
- Обнови поле `updated:` в блоке `<!-- meta ... -->`
- Добавь запись в секцию `## История изменений` документа:
  `- YYYY-MM-DD: что изменилось и почему, задача #{TASK_ID}`
- **Обязательно** выполни Шаг B3.3 — проставь обратную ссылку.

**B3.3 — Обратная ссылка arch ← task (ОБЯЗАТЕЛЬНО при любой правке архитектуры)**

Цель — связать архитектурный документ с конкретными правками по задаче,
чтобы потом из `payments.md` сразу было видно «эту секцию правила задача #1612».

Для каждого архитектурного документа, который правился или к которому из
`doc.md` задачи появилась ссылка:

1. Открой архитектурный документ, перейди в секцию `## Известные проблемы и ограничения`.
   Если секции нет — создай (она обязательная по `doc_rules.md`).
2. Добавь или дополни запись в формате:

   ```markdown
   ### П-N: {Короткое название проблемы/изменения}
   <!-- updated: YYYY-MM-DD, task: {TASK_ID} -->
   - **Симптом / контекст:** что наблюдали или что меняли
   - **Причина:** почему так в коде
   - **Ограничение или решение:** к чему пришли
   - **Файлы:** `path/to/file.php:строка`
   - **Задача:** [#{TASK_ID} — task.md](../tasks/{TASK_ID}/task.md){ALSO_DOC_MD}
   ```

   Где `{ALSO_DOC_MD}` — добавляй ` | [doc.md](../tasks/{TASK_ID}/doc.md)`
   только если файл `.doc/tasks/{TASK_ID}/doc.md` существует.
   Если `doc.md` нет — оставляй ссылку только на `task.md`.

3. Проверь, есть ли в архитектурном документе блок `## Связи` —
   если эта задача добавила связь с другим архитектурным документом,
   обнови `## Связи` (по правилу обратных ссылок из `doc_rules.md`).

4. В `doc.md` задачи в соответствующем пункте `## ⚠️ Подводные камни`
   проставь зеркальную ссылку:
   `**Связанная документация:** файл.md#раздел`

5. Проставь обратные ссылки в существующих связанных документах без повторного
   согласования в режиме B. Список правок сохрани в `doc.md` для HTML-отчёта.

## Шаг B3.6 — Покрытие условий

Если в `doc.md` есть таблица покрытия условий, она пишется по единому формату:

| Колонка | Требование |
|---|---|
| `Условие` | самостоятельное утверждение: кто, когда и что происходит. Без кода, стрелок и контекста задачи. |
| `Где проверено` | код, тест, задача или ручная проверка. Код только здесь. |
| `Статус` | `закрыто тестом`, `закрыто проверкой`, `закрыто после #N`, `вне задачи` |

Правила:

- одна строка = одно условие;
- без `Оплачен → в работе`, писать `заказ переходит из статуса Оплачен в статус В работе`;
- без названий методов в колонке `Условие`;
- без сырых логов, HTML-комментариев и `Array`;
- если условие относится к другой задаче, писать `вне задачи` и номер задачи;
- связанные задачи оформлять ссылками.

## Шаг B3.7 — Требования к описаниям

Каждая секция `doc.md` пишется для человека, который видит задачу впервые.
Общие требования к тезису, языку и секциям `doc.md`: `.cursor/rules/text-style.mdc`,
раздел "Документация `.doc/**`". Не дублируй их в этом скиле.

Проверка перед B4.5:

```bash
python3 .agents/skills/documentation-router/children/project-doc/scripts/check-doc-text.py --task {TASK_ID} --baseline .doc/tasks/{TASK_ID}/_jsondoc/text-baseline.json
```

Скрипт не переписывает файл. Он возвращает JSON с `errors`, `warnings`, номером
строки и секцией. Проверяются только секции, изменившиеся с момента baseline.
Служебные комментарии `<!-- meta -->`, `<!-- generated ... -->`, `<!-- updated: ... -->`,
`<!-- task-dir ... -->` и `<!-- project-root ... -->` ошибкой не считаются; inline-код
и цитаты в кавычках исключены из проверки символов.

Первый прогон для старой задачи, у которой baseline ещё нет:

```bash
python3 .agents/skills/documentation-router/children/project-doc/scripts/check-doc-text.py --task {TASK_ID} --write-baseline .doc/tasks/{TASK_ID}/_jsondoc/text-baseline.json
```

`--write-baseline` фиксирует принятый текст и возвращает exit 0. После него обычный
прогон с `--baseline` проверяет только новые правки. Ошибки исправляются в
JSON-модели через `jsondoc.py apply`, затем `render`.

После render выполни read-only проверку схемы и ссылок:

```bash
python3 .agents/skills/documentation-router/children/task-doc/scripts/jsondoc.py --root . validate --task {TASK_ID} --links
```

Exit 1 означает ошибку схемы или битую локальную ссылку; вывод содержит `errors`
и `broken_links`.

## Шаг B4 — Запись в doc.md

Mixed-режим JSONdoc: если у задачи есть валидный `task.json` (receipt на месте),
знания (findings/decisions/relations/files/notes) пишутся одним batch:
`jsondoc.py batch` с apply envelope (actor=task-doc) + авторендер view; менять
generated doc.md руками нельзя. Если task.json нет - прежняя запись в doc.md.
Полный контракт: `.doc/harnes/jsondoc.md` §6.4-6.5, §9.4.

**Правила:**
- НИКОГДА не удаляй существующий контент без явной команды
- Дополняй существующие секции
- Устаревшее помечай: `~~устарело~~` → новая информация
- Дубли не добавляй
- Пиши для человека который видит задачу впервые
- Код только если без него не понять суть
- Все пути файлов — полные, относительно корня проекта
