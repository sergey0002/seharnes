# Ревью изменения

Проверить изменение как старший разработчик, которого разбудят, если оно сломается.
Порядок важности: правильно, безопасно, держит нагрузку, покрыто тестом, быстро,
без лишнего кода. Лишний код тоже важен: каждую строку потом читают, тестируют и
чинят. Это отчёт, который попросили, поэтому он даётся полностью.

Правила проекта важнее этого документа. Для задачи сначала работает
`task-code-review`: он проверяет, что hunk принадлежит коммитам задачи. Этот
документ добавляет качество, но не расширяет область задачи.

## 1. Сначала понять

- Проверять то, что назвал пользователь: незакоммиченные или staged изменения,
  ветку, ссылку на PR или файлы. Если ничего не названо, брать незакоммиченные
  изменения, а если их нет, последний коммит.
- Прочитать диф, затем код, который он затронул: вызывающие места каждой
  изменённой функции, функции, которые она вызывает, тесты, README.
- Проследить реальный поток: откуда приходят данные, что сохраняется, что уходит
  наружу.
- Изменение может сломать код, который оно не трогало. Если меняется сигнатура,
  возвращаемое значение или поведение, проверить всех вызывающих.
- Найти ожидаемую нагрузку в репозитории по README и конфигу деплоя: один человек
  запускает скрипт или много пользователей и процессов одновременно. Судить о
  масштабе по этой нагрузке и назвать её в отчёте.

## 2. Что искать

1. **Ошибка:** неверный результат, падение, пропущенный крайний случай (пусто,
   ноль, последний элемент, округление, часовые пояса), сломанный вызывающий код,
   исправление в одном месте при сломанной общей функции.
2. **Риск:** уязвимость (инъекция, слабая случайность, секреты в коде, нет
   проверки входных данных), потеря данных (ошибка проглочена, запись в неверном
   порядке, нет транзакции).
3. **Нагрузка:** нормально для одного пользователя, плохо для многих: гонка между
   проверкой и записью, одна и та же работа в каждом процессе, списки, которые
   только растут, запрос на каждый элемент, O(n^2) на большом входе, состояние
   процесса, которое должно быть общим.
4. **Нет теста:** рискованная новая логика (ветка, парсер, деньги, безопасность,
   запись данных, исправление ошибки) без теста, который падает при поломке. Один
   хороший тест, а не покрытие ради процента.
5. **Скорость:** большое замедление это проблема. Маленький выигрыш (работа,
   повторяемая в горячем цикле) это предложение; некоторый код считает каждую
   миллисекунду.
6. **Лишний код:** код, которого не должно быть или который должен быть меньше.
   - удалить: мёртвый код, неиспользуемые опции, спекулятивные функции;
   - переиспользовать: в репозитории уже есть этот помощник (назвать путь);
   - stdlib или платформа: стандартная библиотека или платформа уже это умеет;
     новая зависимость ради нескольких строк;
   - yagni: абстракция с одной реализацией, конфиг, который никто не задаёт;
   - объединить: почти копии, которые должны меняться вместе;
   - разделить: одна функция делает несколько несвязанных работ, её трудно
     читать или тестировать. Делить по работе, а не по количеству строк, и не
     создавать помощников только ради сокращения функции.

## 3. Проверить до отчёта

- У каждой находки есть конкретный случай: "такой вход или такая ситуация даёт
  такой неверный результат". Нет случая, нет находки.
- Перечитать строки и подтвердить: вызывающий правда существует, значение правда
  может быть пустым, код правда не используется.
- Комментарий `shortcut:` (или старый `ponytail:`) с названным пределом это
  решение, а не находка, пока ожидаемая нагрузка не перешла предел.
- Предлагать самое маленькое исправление, которое работает. Предпочитать
  исправления, которые удаляют код. Не добавлять слои, фреймворки и конфиг,
  которые задаче не нужны.
- Без вкусовщины, без "можно рассмотреть", без расплывчатых опасений.

## 4. Выход

Простой и короткий текст. Технический термин объяснять при первом использовании.
Читатель мог никогда не видеть этот код.

Начать с `Что делает изменение:` в двух или трёх предложениях.

Затем находки тремя группами, самые важные первыми, пустые группы пропустить:
- **Исправить обязательно:** ошибка, безопасность, потеря данных, поломка при
  ожидаемой нагрузке.
- **Исправить желательно:** рискованный код без теста, реальное замедление,
  дублирование, функция смешивает работы, код, которого не должно быть.
- **Можно улучшить:** небольшое ускорение, более короткая форма.

Нумеровать находки сквозь все группы, чтобы можно было сказать "исправь 2 и 5".
У каждой находки четыре части, по одной или две короткие фразы:

2. **Заказы попадают не в тот день** (`billing/close_day.py:L40-52`)
   - **Что это:** В полночь задача закрывает день и выставляет счета за все заказы дня.
   - **Проблема:** Она берёт "сегодня" из часов сервера, а сервер работает в UTC. Заказ,
     сделанный в 00:30 по Берлину, попадает в предыдущий день.
   - **Исправление:** Считать день один раз в часовом поясе магазина:
     `datetime.now(ZoneInfo("Europe/Berlin")).date()`. Одна строка, больше ничего не меняется.
   - **Если не исправить:** Поздние заказы показывают неверную дату, бухгалтерия правит их руками.

Закончить:
- `Вердикт: выпускать.` или `Вердикт: сначала исправить 1 и 3.`
- `Меньше кода: можно убрать N строк.` если есть находки про лишний код.
- `Не проверено:` одна строка, если что-то важное не удалось проверить.

Если находок нет: `Что делает изменение:`, затем `Выглядит хорошо. Выпускать.` и
одна строка о том, что проверено.

Документ только перечисляет находки и не меняет код.
