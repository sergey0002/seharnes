# bug-cause

Расследование причины бага с доказательствами. Скил не чинит код, а находит
минимальное условие, которое объясняет все наблюдаемые факты. Каждый вывод
подкрепляется файлом, строкой, дифом, логом, запросом или бизнес-правилом.

## Когда применять

- баг воспроизводится, но причина не очевидна;
- нужно понять, какой диф, релиз или задача изменили поведение;
- нужно пройти путь от действия пользователя до места ошибки;
- нужно отличить причину от симптома и сопутствующих факторов;
- нужно оценить blast radius перед исправлением.

## Условия запуска

Запускать, если пользователь говорит "найди причину бага", "почему так
работает", "root cause", "разбери баг по коду", "исследуй диф", "восстанови
путь вызовов", "граф вызовов", "бизнес-путь бага", "что сломало поведение".

Не запускать, если причина уже подтверждена тестом или логом и нужен только
план исправления: тогда сразу `prepare-plan`. Не запускать для проверки UI без
симптома: тогда `platform-browser-test`.

## Вход

| Параметр | Обязателен | Значение |
|---|---|---|
| Симптом | да | текст ошибки, статус, скриншот, жалоба QA |
| Ожидание | да | как должно работать по задаче или бизнес-правилу |
| Номер задачи | нет | Jira `2077`, если баг связан с задачей |
| Окружение | нет | стенд, версия, роль, clientId, заказ, UIN, время |
| Шаги | нет | как воспроизвести; без них причина ищется по коду и логам |

Если не хватает факта, без которого нельзя отличить гипотезы, задать один
точный вопрос. Не собирать анкету.

## Источники правды

| Источник | Что даёт | Как читать |
|---|---|---|
| `.doc/tasks/{N}/task.md` | требования, комментарии QA, заказы, клиенты | Read или `multi-exec.sh` |
| `.doc/tasks/{N}/doc.md`, `plan.md` | решения, этапы, ожидаемое поведение | Read или `jsondoc.py get` |
| `.doc/tasks/{N}/diff.md`, `diff.files.md` | изменённые строки и коммиты | `task-diff` |
| `.doc/architecture/index.md` | карта домена и документов | Read, только релевантные |
| `.doc/qa/index.md`, `.doc/qa/flows/*` | UI-флоу и покрытие | Read |
| `.doc/harnes/testaudit.md` | ветки логики и критерии тестов | Read |
| Код и тесты | фактическое поведение | CBM, codegraph, serena, Read |
| Git-история | кто и когда изменил поведение | `git log`, `git blame`, `git-task-blame` |
| `.env` и конфиги | флаги и режимы | Read, секреты не печатать |

Бизнес-правило важнее комментария в задаче. Если правило и код расходятся,
это и есть контракт бага, а не повод подогнать правило под код.

## Шаги

### 1. Зафиксировать контракт поведения

Записать:

- предусловие: данные, роль, статус, окружение;
- действие: что делает пользователь или крон;
- ожидаемый результат;
- фактический результат;
- частота: всегда, при части объектов, после определённого события.

Контракт это опора расследования. Без него любое наблюдение можно объяснить
несколькими причинами.

### 2. Прочитать пакет задачи

Одной пачкой через `.tools/scripts/multi-exec.sh --read`:

| Файл | Что искать |
|---|---|
| `.doc/tasks/{N}/task.md` | требования, комментарии QA, ошибки, заказы, клиенты |
| `.doc/tasks/{N}/doc.md` | принятые решения, известные ограничения |
| `.doc/tasks/{N}/plan.md` | этапы, ожидаемое поведение, проверки |
| `.doc/tasks/{N}/diff.md` | какие строки менялись и в каких коммитах |
| `.doc/tasks/{N}/diff.files.md` | список затронутых файлов |
| `.doc/tasks/{N}/test.md` | ветки логики и покрытие |
| `.doc/tasks/{N}/ac-matrix.json` | условия приёмки |

Если папки задачи нет или документы устарели, сначала выполнить `task-intake`
по номеру задачи. Не строить причину на неполном пакете.

### 3. Поднять документацию домена

1. Документацию домена искать через jdocmunch (`repo` `local/testdeploy-arch`) с
   `path_glob` по корпусу: `architecture/*`, `qa/*`, `harnes/*`, `tasks/{N}/*`.
   Перед большим документом брать `get_document_outline`.
2. Открыть найденный доменный раздел по симптому: заказы, платежи, реестр,
   тарифы, объекты, доступ.
3. Сравнить ожидаемое поведение из задачи и документации с фактическим кодом.
   Расхождение записать как кандидат в причину.

Не читать `.doc` обходом и не править сгенерированные документы руками.

### 4. Найти связанные задачи, дифы и историю строк

- `powershell .agents/skills/documentation-router/children/doc-verify/scripts/find-related-tasks.ps1 -Json` по изменённым файлам и доменным документам.
- `git log --oneline --all --grep "#{N}"`, `git log --merges --oneline --since=<дата>` и `git log -L <start>,<end>:<file>` по подозрительному диапазону.
- `git blame` по строкам, которые формируют ошибочное поведение.
- Скил `git-task-blame` для полной эволюции диапазона и риска конфликта.
- Скил `task-diff`, если нужно пересобрать диф задачи.

Отдельно проверить слияния релизов и соседних задач: регрессия часто появляется
после сведения двух веток, которые меняли один сервис или один статус.

### 5. Построить путь по бизнес-логике

Пройти цепочку и на каждом шаге записать доказательство:

```
действие пользователя или крон
-> маршрут или точка входа
-> контроллер или обработчик
-> сервис
-> доменная модель и правила
-> репозиторий или таблица
-> внешний сервис
-> ответ, письмо, статус или UI
```

Для каждого шага указать `file:line` и что именно там происходит. Если шаг
пропущен или обойдён, это отдельный факт. Сверить каждый переход с бизнес-правилом
из шага 3.

### 6. Построить путь по коду и граф вызовов

Порядок инструментов:

1. `codebase-memory-mcp`: `list_projects`, затем `index_status`. Имя проекта
   брать из вывода, не угадывать. Если `indexed_at` старше последнего коммита,
   отметить это и проверять спорные места чтением файлов.
2. `get_graph_schema`, `search_graph` по классу, методу, маршруту или таблице.
3. `query_graph` для многошагового вопроса, `trace_path` в режимах `calls` и
   `data_flow`, глубина 2-4.
4. `get_code_snippet`, `get_file_outline` для исходника и структуры файла.
5. `detect_changes` для текущего diff, `check_index_coverage` если файл или
   символ не находится.
6. `codegraph_explore` с `projectPath` равным абсолютному корню проекта, когда
   нужен один ответ с исходником, путём вызовов и blast radius. CLI:
   `codegraph callers`, `codegraph impact`, `codegraph affected`.
7. `serena` для точного символа, ссылок и диагностики PHP
   (`find_symbol`, `find_referencing_symbols`, `get_diagnostics_for_file`).
8. `codeprism` для структуры JS, TS и Vue, если CBM и codegraph не дают ответ.
9. `.tools/scripts/multi-search.sh` или `rg` для литералов, `.tpl`, `.js` и
   того, что не попало в граф.
10. `mysql describe_table` только если в цепочке есть данные; колонки не
    придумывать, `query` только на чтение, `execute` без разрешения не вызывать.
11. `context7` только если причина зависит от внешней библиотеки или API.

Для каждой ветви проверить: условие входа, состояние данных, побочный эффект,
обработку ошибки, асинхронность, повторный вызов. Отдельно проверить границы:
пустой список, один объект, несколько объектов, частичная ошибка, повторная
операция, потерянный обратный вызов.

### 7. Сформировать гипотезы

Минимум три гипотезы, каждая с проверяемым условием. Классы гипотез для этого
проекта:

| Класс | Что проверять |
|---|---|
| Статус и жизненный цикл | переходы статусов, условия финализации, порядок вызовов |
| Частичный успех | один объект против нескольких, пустой список, частичная ошибка |
| Внешний сервис | SOAP, таймаут, 503, текст и код ошибки, повтор |
| Асинхронность | крон, очередь, webhook, потерянный обратный вызов, повторная доставка |
| Платежи и возвраты | commit, полный и частичный возврат, двойное списание |
| Данные | null, пустая строка, форма ключа, несовпадение идентификаторов |
| Конфигурация | `.env`, флаги, режимы, различия стендов |
| Доступ | роль, clientId, чужой объект, имперсонейт |
| Кеш и сборка | Smarty, `frontend/dist`, basepack, stale response |
| Регрессия слияния | merge релиза, соседняя задача, изменённый общий сервис |
| Гонка | параллельные вызовы, транзакции, идемпотентность |

Формат таблицы:

| Гипотеза | Проверка | Результат | Вывод |
|---|---|---|---|
| неверный ключ или форма данных | прочитать преобразование и сравнить с потребителем | совпало или нет | подтверждена или отклонена |
| неверный переход статуса | пройти ветви смены статуса | | |
| потерянный обратный вызов или таймаут | найти обработчик и записи в логах | | |
| гонка или повторный вызов | проверить транзакции и идемпотентность | | |
| устаревший кеш или конфиг | проверить источник значения | | |

Гипотеза без проверки не считается результатом. Первая правдоподобная причина не
принимается без попытки её опровергнуть.

### 8. Проверить и сузить причину

Проверки по убыванию стоимости:

1. чтение кода и сравнение с предыдущей версией (`git show <sha>^:<file>`);
2. `git log -L` и `git blame` по диапазону;
3. чтение логов стенда через `platform-logs`;
5. чтение данных через mysql `query` только на чтение;
6. воспроизведение через `platform-browser-test` или Codeception `test-task`;
7. минимальный репро: один объект против нескольких, повтор, другая роль, другой
   статус;
8. `phpstan` или `semgrep`, если гипотеза про типы или безопасность.

После каждой проверки обновлять таблицу гипотез. Отклонённые гипотезы
сохраняются в отчёте: они показывают, что причина не первая найденная.

### 9. Зафиксировать истинную причину

Истинная причина должна:

- объяснять все наблюдаемые факты, а не часть;
- совпадать с местом в коде или данными;
- объяснять, почему баг не проявлялся раньше или проявляется не всегда;
- указывать минимальное условие воспроизведения;
- отличаться от симптома, триггера и сопутствующего фактора;
- соотноситься с бизнес-правилом и изменением из задачи.

Классифицировать причину: дефект кода, неверные данные, конфигурация, внешний
сервис, гонка, нарушенный контракт, регрессия слияния. Отдельно перечислить
триггер, сопутствующие факторы, blast radius, общие символы и тесты.

### 10. Подготовить отчёт

Шаблон отчёта:

```
## Симптом и контракт
предусловие, действие, ожидание, факт, частота

## Бизнес-правило
ID, statement, code_anchors, test_refs

## Путь по бизнес-логике
шаги с file:line и доказательствами

## Путь по коду
точки входа, цепочка вызовов, ветви, данные, побочные эффекты

## Изменения и связанные задачи
коммиты, дифы, задачи, слияния, зачем менялось

## Гипотезы
таблица: гипотеза, проверка, результат, вывод

## Истинная причина
минимальное условие и место в коде

## Классификация причины
дефект кода, данные, конфигурация, внешний сервис, гонка, контракт, регрессия

## Уровень доказанности
E1, E2 или E3 с объяснением

## Минимальный репро
данные, роль, шаги, ожидаемый и фактический результат

## Сопутствующие факторы
что усиливает или маскирует баг

## Blast radius
общие символы, вызывающие, тесты, соседние флоу

## Как проверить исправление
сценарий, данные, ожидаемый результат

## Регрессионный тест
какой Cest или PHPUnit метод закрывает причину

## Неподтверждённое
что осталось без доказательства и почему
```

## Уровни доказанности

| Уровень | Что есть | Можно ли называть причиной |
|---|---|---|
| E0 | гипотеза без проверки | нет |
| E1 | полный путь по коду с файлами и строками | только для чистого дефекта кода без runtime-зависимости |
| E2 | E1 плюс лог, данные или ответ внешнего сервиса | да, с оговоркой о среде |
| E3 | воспроизведение на стенде или тестом | да |

Если две гипотезы остаются равными и runtime-доступа нет, зафиксировать это в
разделе "Неподтверждённое" и указать, какой факт нужен. Не выбирать причину по
вероятности.

## Инструменты и границы

| Инструмент | Когда | Ограничение |
|---|---|---|
| jdocmunch | архитектура, задачи, QA-флоу | `.doc` не входит в граф кода |
| codebase-memory-mcp | структура, вызовы, данные, diff | проект только из `list_projects` |
| codegraph | исходник, путь вызовов, blast radius | `projectPath` только текущий проект |
| codeprism | структура JS, TS, Vue | не тела функций |
| serena | символы и ссылки PHP | JS, Vue, TPL не обслуживает |
| multi-search.sh / rg | литералы, шаблоны, минифицированный код | не заменяет чтение файла |
| mysql | схема и данные | только чтение без разрешения на запись |
| git, task-diff, git-task-blame | история и дифы | push и commit не делать |
| platform-logs | логи стенда | только чтение |
| platform-browser-test | воспроизведение в браузере | только тестовые стенды |

## Выход

- отчёт по шаблону;
- таблица гипотез с отклонёнными вариантами;
- точное место причины и условие воспроизведения;
- список доказательств: файлы, строки, коммиты, правила, логи, запросы;
- план проверки исправления и регрессионный тест без самого исправления.

## Ограничения

- Не исправлять код, пока пользователь не попросил отдельно.
- Не считать свежий диф единственным подозреваемым: баг может быть старым.
- Не доверять сниппету графа как доказательству: спорный файл читать целиком.
- Не строить вывод на одном источнике, если есть код, данные и логи.
- Не выдавать гипотезу за причину без проверки.
- Не использовать прод и не менять данные стенда.
- Не править сгенерированные бизнес-правила и `doc.md` руками.
