## Step P5 — Write plan.md

**Authored Markdown only.** План пишется прямо в `plan.md` по шаблону
[plan.template.md](../assets/plan.template.md). JSON-модели, генерируемого view,
plan writer и research-ledger в харнесе нет. План меняется правкой Markdown.

### Evidence and phase gate

Перед первым подразделом `## Правки по файлам` для плана medium/large или
High/Critical исследование должно быть закончено, а источники записаны в
`## Sources of truth` и `## Research audit (MCP)`. Наблюдения и digest чтения
файлов целиком остаются в секции Research audit. Хеш файла не доказывает, что
агент его прочитал и понял.

Для medium/large или High/Critical до патчей обязательны: доменные документы,
инвентарь точек входа P2.7, таблица связанных задач, git-task-blame, матрица
повторного использования, IN/OUT вызывающих, список намеренно не тронутых файлов
и таблица внешнего контракта, если затронуты SDK, деньги или авторизация. План с
патчами раньше этого этапа считается черновиком.

### Required sections

Всегда, при любом `scope_size`:

1. `## Sources of truth` — таблица T-id.
2. `## Acceptance criteria` — таблица AC-ID, у каждой строки источник T и тест S.
3. `## Related tasks` — ссылка на `task.md` у каждого упомянутого номера.
4. `## Decomposition` — один подраздел на независимую причину R со сценарием S.
5. `## Правки по файлам` — Before/After, у каждого файла `R` и `Verified by`.
6. Coverage matrix — те же AC-ID в связке AC, R, S.
7. Verification checklist — воспроизводимые шаги, включая OUT-вызывающих.
8. `## Самопроверка (P5)` — результат чек-листа `self-check.md`;
   `## Аудит плана` — журнал проходов, появляется после первого аудита.
9. `scope_size` в meta и Diff principle N.
10. Соседний `test.md` с `## Требования` и `## Ветки логики`, покрывающий все AC.
11. `## Research audit (MCP)` с таблицей уровней 0-8: `passed`, `n/a` или `red`
    с доказательством и компенсацией.

Когда применимо, иначе одна строка `N/A`:

12. `## Shared keys / callers (in/out)` для общего кода в патчах.
13. `## Invariants`, если найдены прошлые или общие контракты.
14. Строка `docs != code`, если P0.6 нашел расхождение.
15. `## Git-история правок (git-task-blame)` для каждого файла с историей.
    Задача из этой таблицы обязана быть и в `## Related tasks`.
16. `## Architecture check (P4.1)` — SOLID, DRY, повторное использование и слои.

**Trivial/Small:** не добавлять пустой вариант B, фальшивые стадии и
микро-патчи, которые пересказывают действия редактора. Одна причина R дает один
подраздел патчей.

### Truth table (required)

| ID | Kind | Where | Decides |
|----|------|-------|---------|
| T1 | brief | `{TASK_DIR}/task.md` Description | формулировка AC |
| T2 | comment | тот же файл, дата комментария | дополнительный AC |
| T3 | user | дата в чате или `user-extra` | решение вне трекера |
| T4 | arch | относительная ссылка на раздел архитектуры | документированный контракт |
| T5 | schema | относительный путь к вложению, DDL или схеме | поток или колонки |
| T6 | code | `path/File.php:120-180` | as-is из чтения этой сессии |
| T7 | db | `table.column` из инструмента схемы, не из памяти | форма хранения |
| T8 | test-canon | относительная ссылка на правила тестов | как запускается слой |

Виды только такие: `brief | comment | user | arch | schema | code | db | test-canon`.

```
□ Where это путь от корня репозитория, file:line или относительная ссылка
□ Абсолютных путей и wikilinks нет
□ Каждая строка arch и schema открывается читателем
□ У каждой строки code есть file:line из чтения этой сессии
□ Если документация и код расходятся, остаются обе строки
□ Каждый AC, R и S ссылается на существующий T-id
```

### Acceptance criteria table (required)

```
| AC-ID | Criterion | Source | Closed by | Test |
| AC1 | цитата или близкий пересказ источника | T1 | R1 | S1 |
```

- одна строка на каждый пункт брифа, комментариев и решений пользователя;
- out-of-scope тоже строка: `Closed by = out`, `Test = n/a` и причина со ссылкой
  на T-id или ответ пользователя;
- AC-ID в Coverage matrix и в аудите те же;
- AC без R или R без AC (и без явного риска общего кода) не допускаются;
- AC, который обещает поведение существующего непропатченного кода, обязан иметь
  `file:line` из чтения этой сессии.

### Decomposition scenarios (required)

Одна причина R дает один основной сценарий S. Сценарий может быть отдельным
Markdown-файлом, если он длиннее 40 строк.

```
### R1. Короткое имя
- **Closes:** AC1
- **Truth:** T4, T6
- **Docs:** ссылка на раздел или `none: нет документа для этого потока`
- **Independent because:** одно предложение
- **Files:** `a.php`, `b.php`
- **Verified by:** S1

#### S1
- **Layer:** sql | phpunit | http | browser | manual
- **Method doc:** ссылка на правила теста слоя или `none:` с командой
- **Precondition:** фикстура, строка, вход, URL
- **Action:** точная команда или последовательность кликов
- **Expected result:** литеральная строка, код HTTP, значение в БД, код выхода
- **State after:** что сохраняется
- **Must not change:** явный список
- **If it fails:** одна проверка устаревшего теста, одна проверка патча
```

**Поведение, не синтаксис.** Для изменения поведения, схемы, данных,
авторизации, денег, HTTP и UI не считаются результатом: `php -l`, чистый линтер,
`no errors`, `should work`, `file saves`. Синтаксис допустим только отдельной
строкой `compile only`.

Несколько файлов одной причины R ссылаются на один S. Каждому файлу не нужен
свой сценарий с `php -l`.

### Meta consistency (required)

- Diff principle N равно числу подразделов файлов в патчах;
- `~M lines` это оценка, но N не должен врать;
- `status: ready` только после прохода `audit-plan` с вердиктом `pass`;
- автор поднимает `plan_rev` при любой содержательной правке, аудит версию не меняет;
- `audit_passes` равно числу строк журнала `## Аудит плана`, `last_audit` равно дате
  последнего прохода;
- meta следует стандарту документации проекта (`DOCS_RULES` из `ADAPTERS.local.md`):
  `type`, `status`, `updated`, `related`, `tags`; ключи плана добавляются к ним;
- обязательные ключи meta и enum берутся из [plan.meta.schema.json](../assets/plan.meta.schema.json);
- `updated` равно дате последней правки плана;
- `task_closure` это процент покрытия плана, не прогресс реализации;
- отдельного `plan-audit.md`, `plan_hash` и таблицы хешей источников нет.

### Where

| Случай | Путь |
|---|---|
| Первый план | `{TASK_DIR}/plan.md` |
| После merge или новый инцидент | `{TASK_DIR}/stage2/plan.md` или `stage{N}/plan.md` |
| Уточнение существующего | правка секций, обновление `updated` в meta |

Неясно, новый план или stage2: спросить пользователя.

Создавать stageN только ради деления маленького плана на фазы запрещено.

### Template

Единый скелет: [plan.template.md](../assets/plan.template.md). Точные машинные
заголовки: `## Правки по файлам`, `## Research audit (MCP)`,
`## Git-история правок (git-task-blame)`. Заголовки патчей принимают
`### \`path\`` и `### 1. \`path\``. `**Diff principle:** N files` считает
уникальные заголовки файлов, не причины R.

Таблица git: File:range, Task, Status, Change, Invariant, Risk, Scope,
Resolution. Scope это `IN | OUT | n/a`. `Status: open` требует IN/OUT и
конкретное решение.

Критерии готовности, порядок повторного прохода и формат меток принадлежат
`audit-plan`: `../../task-router/children/audit-plan/references/criteria.md`.
Этот файл задает только то, что автор обязан записать до аудита.

Стиль текста: правило проекта `TEXT_STYLE` из `ADAPTERS.local.md`. Без длинных
тире, французских кавычек и эмодзи.
