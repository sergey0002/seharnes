# Методика и маршрут инструментов

Канонический порядок: `SKILL.md` и `blast-radius.md`. Конкретные привязки этого
репозитория: `ADAPTERS.local.md` (`BLAST_RADIUS_LADDER`). При расхождении
побеждает `SKILL.md`.

## Методика по фазам

Правило: сначала доказательство, потом текст плана. Каждая строка плана опирается
на конкретный вызов и чтение файла, а не на память и не на пересказ документации.

| Фаза | Вопрос | Инструмент и вызов | Доказательство в плане | Fallback |
|---|---|---|---|---|
| P0 документация | что говорит домен | `jdocmunch` `search_sections` с `repo=local/testdeploy-arch` и `path_glob`, затем `get_section_context` или `get_section` | строка T4, список доменных документов | прямой Read известного пути, затем `rg` |
| P0 бриф | что требует задача | `gototask -Action export-task` без смены ветки | цитата T1 или T2 в Acceptance criteria | существующий `task.md` с пометкой о свежести |
| P0.5 связанные задачи | кто уже трогал домен | `find-related-tasks.ps1 -Json -Limit 12`, score 20 и выше; TSV `file-to-tasks` | таблица Related tasks со ссылками на `task.md` | `rg` по `#N` и `../tasks/` только в уже прочитанных документах |
| P0.5b история строк | кто менял этот диапазон | скил `git-task-blame`: `git log -L`, `git blame`, экспорт задачи | таблица Git-история правок и Invariants | нет, шаг обязателен для файла с историей |
| P0.6 документация против кода | совпадает ли описанное с кодом | `serena` `find_symbol` с телом, затем чтение файла целиком; `codebase-memory-mcp` для навигации | строка `docs != code`, T6 с `file:line` | чтение файла целиком обязательно |
| P1 радиус | кто сломается | `codebase-memory-mcp` `search_graph`, `trace_path`; `codegraph`; `codeprism` `get_context`, `get_impact`; `php-deps-mcp`; `serena` ссылки; `multi-search`; `mysql`; `semgrep`; `phpstan` | риск по файлу, таблица IN/OUT, кто найден каким уровнем | `rg` по тем же расширениям и чтение целиком |
| P2 исследование | как устроен поток | чтение файлов целиком; `codegraph` и `codeprism` только для ориентации | as-is с `file:line`, инвентарь точек входа | `rg` и чтение целиком |
| P2.5 внешний SDK | что умеет версия | `context7` `resolve-library-id`, затем `query-docs`; runtime `class_exists` или `method_exists` | строка внешнего контракта с версией | чтение vendor-исходника последним средством |
| P3 синтез | почему так происходит | инструментов нет, только прочитанный код | причина одним предложением с `file:line` | нет |
| P4 варианты | какая правка минимальна | `ponytail`; `jdocmunch` для архитектурного раздела; чтение соседнего файла | Architecture check с цитатой файла или документа | `rg` по похожему решению |
| P5 запись и сценарии | чем проверить | шаблон и схема плана; инструмент слоя из TEST_CANON: PHPUnit, Codeception, Playwright | S с предусловием, действием и литеральным результатом | ручной шаг с явной пометкой |

Запрещено: писать as-is по документации, брать Before из сниппета, считать
пустой результат поиска доказательством отсутствия вызовов.

## Fixed ladder order (do not skip a green tier)

| Tier | Возможность | Когда обязательна |
|---|---|---|
| 0 | Граф и структурная карта | всегда для общего кода и изменения символа |
| 0b | Контекст модуля и влияние правки | PHP, JS, TS; структурный вопрос без чтения файла |
| 1 | Реальный граф вызовов PHP | смена сигнатуры, класса или контракта |
| 2 | Символ и ссылки LSP | перед переименованием и изменением публичного символа |
| 3 | Полный текст и семантика | шаблоны, строковые вызовы, клоны, `.tpl` |
| 4 | История git | каждый файл патчей с историей, повторно на аудите |
| 5 | Схема БД | затронуты колонки или таблицы |
| 6 | Паттерн и безопасность | авторизация, SQL, деньги, персональные данные |
| 7 | Типы и статический анализ | смена сигнатуры или типа |
| 8 | Runtime и браузер | последнее средство, когда чтение не объясняет симптом |

Красный уровень компенсируется поиском и чтением целиком. В плане пишется
`уровень N красный, компенсирован`.

## Project binding (this repo)

| Tier | Инструмент | Вызов |
|---|---|---|
| 0 | codebase-memory-mcp | `search_graph`, `trace_path`, `query_graph`, `detect_changes` |
| 0b | codegraph | `codegraph_explore` с `projectPath` |
| 0b | codeprism | `get_graph_stats`, `get_context`, `get_callers`, `get_impact`, `get_module_summary` |
| 1 | php-deps-mcp | `phpda_analyze`, `phpcallgraph_generate` |
| 2 | serena | `find_symbol`, `find_referencing_symbols`, `find_declaration`, `get_diagnostics_for_file` |
| 3 | multi-search | `rg` по glob, литералы и шаблоны |
| 4 | git-task-blame | скил, `git log -L` и `git blame` по диапазону |
| 5 | mysql | `describe_table` |
| 6 | semgrep | `semgrep_scan`, `semgrep_findings` |
| 7 | phpstan-mcp | `phpstan_analyze` с `paths` или `task` |
| 8 | playwright, Codeception | `browser_navigate`, `browser_snapshot`; сначала Cest |

Ограничения:

- codeprism и codegraph не индексируют Markdown, `.doc` и Smarty, для них только
  поиск по тексту;
- serena работает по PHP; для JS, Vue и TPL символьные операции не применять;
- свежесть графа проверяется по `indexed_at`, а не по факту ответа;
- перед незнакомым MCP-вызовом прочитать схему инструмента и записать точные
  имена аргументов. Ошибка валидации это дефект процесса, а не доказательство.

## Related tasks

| Источник | Как |
|---|---|
| Домен или симптом | индекс документации, дерево решений, затем чтение |
| Ссылки в брифе | `TASK_EXPORT` или `gototask -Action export-task` без смены ветки |
| Доменный документ в задачи | `find-related-tasks.ps1 -Json -Limit 12`, score 20 и выше |
| Путь файла в задачи | TSV `file-to-tasks` |
| Тот же диапазон в git | скил `git-task-blame` |

Не искать архитектурные документы только по номеру задачи. Не пересказывать
содержимое связанной задачи по одной цитате.

## Rules

- предпочитать возможности, а не имена классов продукта;
- сниппет инструмента не равен Before, доказательство это чтение целиком;
- не угадывать схему и поведение API;
- писать точные таймауты и факты проверки, не выдумывать дату проверки.
